### 本次核实的关键事实（来自「发布为应用」官方规则 + 本地实查）

1. **WorkBuddy 确实支持发布小程序**（此前仅从摘要判断，现已确认），但产出形态是「应用」不是 URL，且分两步：
   - 第一步（我调工具）：目录含 `project.config.json` / `app.wxss` / `app.json`+pages 时，自动创建小程序应用并注册项目，返回 `sites_miniprogram_app_created`（`deployed: false` 表示第二步未发生，不是失败）
   - 第二步（用户）：打开该小程序应用的预览面板 → 右上角「分享」→ 扫码绑账号（**试用小程序无需 AppID**）→ 上传/体检/发布全在 WorkBuddy 内完成
   - 明令禁止：不得用 H5/静态页顶替小程序；不得让用户去微信开发者工具或 mp 后台手动上传
2. **部署目标按目录决定**：根目录（有 `project.config.json`，appid 现为 `touristappid`）→ 走小程序路径；`server/` 目录 → 走 Node HTTP 服务路径，拿 shareLink。两者天然分离，正好对应「前端小程序独立预览 + 后端独立托管」。
3. **后端托管卡点已找到解法**：预检会拒绝依赖清单里含 `pg`/`mysql2`/`mongoose`/`ioredis` 等驱动的项目（沙箱只有一个 HTTP 端口，不提供数据库），但**公网托管数据库连接串（如 Supabase）明确允许**。实查：`server/package.json` 有 `pg@^8.16.3`，**但源码全程未引用**（DB 走 `@supabase/supabase-js` 的 HTTP 通道，且 dist 运行时 require 清单里也没有）。→ 开发阶段从依赖清单移除 `pg` 即可通过预检；将来真迁 TencentDB 再加回。
4. **数据独立性是当前最大隐患**：现有 Supabase 是扣子平台账号在火山引擎托管的（不是用户自己的 supabase.com 项目），10-17 的测试已往里写入匿名用户。若 preview 继续连它 = 与扣子线上共用同一库。建议另起用户自己账号下的免费 Supabase 项目跑同一个 `migrations/0002_fresh_schema.sql`。
5. **试用小程序的边界（要如实告知）**：试用小程序的 AppID 是平台分配的，不是用户手里的 `wx48bf5ba9bae0bf39`，故真实 `wx.login` → AppSecret 换 openid 链路大概率测不了（需实测确认），要等绑定真实小程序账号后才有意义；其余功能不受影响。
6. **切换机理**：同一真实 AppID 下，线上正式版只有一个（现在线上是扣子传的版本）；开发版/体验版与正式版平行存在互不干扰；我们发布正式版即覆盖扣子版本 = 「停掉扣子渠道」的动作。回滚 = 重传旧版本。正式版/体验版需备案域名（7-20 工作日，越早提交越好），开发版+调试模式可免。
