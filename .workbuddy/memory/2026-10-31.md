### 🔴 六条硬坑（照旧写法必卡）
1. **`--disable-triggers` 导出后用普通角色导入会失败**：`permission denied: "RI_ConstraintTrigger_a_…" is a system trigger`。pg_dump 写的是 `DISABLE TRIGGER ALL`（含系统 FK 触发器），只有 superuser 能关 ⇒ 导入要 `sudo -u postgres psql`
2. **迁移校验别用「行转文本 md5」**：时间戳按会话时区渲染（+00 vs +08），18 张表会全部假 MISMATCH。必须 `export PGTZ=UTC`；更稳的是两侧各自 pg_dump 后排序比字节（2268 行只剩 2 行 psql 随机 `\restrict` token）
3. **`OCR_VENV_DIR` 在 Linux 上根本不生效**：`resolvePython()` 只有 Windows 分支读它；Linux 候选表写死 `/workspace/projects/.venv-py` → `/opt/pocr3-venv` → 系统 `python3`。本机一个都不在 ⇒ 静默用无 fastapi 的系统 python ⇒ `app = FastAPI(...) if _WEB_DEPS_OK else None` 得 None ⇒ `@app.get("/healthz")` AttributeError，常驻进程 exit 1。**必须显式设 `OCR_PYTHON` + `PPSV3_PYTHON`**
4. **OCR 子进程 CWD 必须 gk 可遍历**：`paddlex/utils/fonts.py` 有 `Path(str(LOCAL_FONT_FILE_PATH)).is_file()`，变量默认 None ⇒ 实际 `os.stat("None")`，CWD 不可遍历时报 `PermissionError: 'None'`。我自己就因为在 `/home/ubuntu`(700) 下测误判过一次
5. **`paddleocr` 不再自动拉 `paddlepaddle`**：3.x 起要单独装（已补 3.3.1），否则 env-recovery 一直判缺失、反复触发恢复
6. **`paddlepaddle 3.3.1` 在这颗 CPU 上不可用**：必报 `(Unimplemented) ConvertPirAttribute2RuntimeAttribute not support [pir::ArrayAttribute<pir::DoubleAttribute>]`（`onednn_instruction.cc:116`）。已证伪三个开关：`FLAGS_use_mkldnn=0` / `FLAGS_enable_pir_in_executor=0` / `FLAGS_enable_pir_api=0`。**别再重复排查**
   - 好消息：生产默认 `--mode both` 融合实测**优雅降级** ⇒ `engine_used:['rapidocr']`、置信度 0.923、`low_confidence:false`、全文正常

### 🔴 paddlepaddle 3.3.1 崩溃**已解决**（此前判定"不可用"是错的）
- 根因：Paddle/Paddle#77340 —— 3.3.0 起 PIR 执行器默认启用 oneDNN(MKLDNN)，
  属性转换在 CPU 路径有回归；官方修复 #77430 **只合到 develop、从未回植 3.3.x**。
- ⚠️ 我之前试的三个开关**全都不对**：`FLAGS_use_mkldnn=0` / `FLAGS_enable_pir_in_executor=0` /
  `FLAGS_enable_pir_api=0` —— 它们是 **paddle 层** FLAGS，管不到 **PaddleX 层**自己默认打开的 oneDNN。
- ✅ **有效开关：`PADDLE_PDX_ENABLE_MKLDNN_BYDEFAULT=0`**，必须在 `import paddleocr` 之前设置。
  已写进 `ocr-engine/main.py` 顶部（`os.environ.setdefault`，位于惰性导入之前，与进程怎么被拉起无关）。
  ⇒ **不必降级到 3.2.x**，3.3.1 才有的模型/能力全部保住。代价：关 oneDNN 后慢 3~6 倍（换来"能用"）。
- 手测陷阱：不带 `PADDLE_PDX_CACHE_HOME` 时 gk 会去建 `/workspace` ⇒ `[Errno 13]` 且 paddle 返空。
  生产由 gk-api 的 EnvironmentFile 注入，不受影响。

## 24:3x 第五轮反馈（思傅：只剩「英文打标点/空格后光标跳结尾」，其余全正常）

- 真因：`decideInputCursor` 里 `if (composing) return null` 这个一刀切跳过。
  英文输入法里**空格/标点是「提交当前英文词」的动作**，会带出 composition 事件；
  而 `compositionstart/end` 与 `input` 的先后顺序各家不一致，input 到达时
  `composing` 往往还是 true ⇒ 这一次不写 cursor ⇒ value 把光标甩到末尾。

  **恰好正确**）；英文上屏选词 composition 已结束；删除不触发 composition；
  **只有"英文打标点/空格"会在中间位置被跳过**。
- 改法：**按位置分流，不看标志** —— 算出位置 `≥ 文本长度`（末尾追加）不写、
  `< 文本长度`（中间编辑）**必写**。对 composition 的时序完全免疫。
- 组词中的写入走**安静模式** `applyShot(pos, len, quiet)`：值没变就什么都不做，

- `blur` 去掉 `if (composingRef.current) return`，改为**强制清标志**：
  有些英文键盘只发 start 不发 end，标志一卡死，之后所有输入都被跳过。

## 第八轮：回声吸收真机失败 → Taro 源码级根因 → 阻断渲染（终版）

**用户反馈**：「又一次输不进去任何内容了，而且一输入光标就直接跳到结尾」——
第七版的回声吸收把输入彻底搞坏了（比之前更糟）。

**真根因（Taro 源码，不是推测）**：
`node_modules/@tarojs/react/dist/react.esm.js:366`
```js
const isFormElement = dom instanceof FormElement
for (i in newProps) {
  if (oldProps[i] !== newProps[i] || (isFormElement && i === 'value')) { ... }
}
```
**表单元素的 `value` 无条件进 setData**，与值变没变无关。于是：
- 受控（每帧下发最新值）⇒ 每帧重建文本 ⇒ 光标每帧落末尾；
- 第七版回声吸收（每帧下发同一个**旧值**）⇒ 每帧把刚打的字覆盖回旧值 ⇒ 打不进字。
两版同源：都以为"属性没变就不会发"。

**治法（结构层，不是参数层）**：让这一帧渲染根本不发生。
- `ui/textarea.tsx` 用 `useMemo` 缓存元素，**依赖里故意不含 `value`**（机关，注释写死别补）；
- 只在「外部写入 pushToken / 程序化定位 cursor / 聚焦边沿 focus / 样式属性变化」时重建；
- 重建时下发的永远是**当下最新** `props.value` ⇒ 最坏只退化成光标落末尾，**绝不丢字**；
- 回调统一走 `cb` ref（元素被缓存后内部闭包是旧的）；
- `value` / `cursor` 用条件展开（`value={undefined}` 会留下键 ⇒ 每帧下发空值；`cursor: -1` = 置于末尾）。

**`textarea-echo.ts` 重写**：`resolveEchoValue`/`recordNativeInput` → `reduceEcho`/`initEcho`，
判定语义从"下发什么值"变成"要不要重建元素"。

**复现器纠正**（`server/scripts/repro-caret.mjs`，在 server 目录跑）：模型 R1 改为"键存在就下发"后：

| 方案 | 结果 |
| --- | --- |
| 受控 + 钉 cursor | 光标失败 7 处 |
| 回声吸收（第七版） | **丢字 9 处** ← 精确复现"输不进任何内容" |
| 阻断渲染（现行） | 失败 0 处 |

**验证**：M12 断言重写（输入每步零放行、外部写入恰一次且幂等），门禁 35/35；tsc / lint / build:weapp 全过；
产物核实 `useMemo` deps 为 `[pushToken,focus,cursor,className,styleKey,restKey,ref,...]` **无 value**。

**提交**：`04d2d5a`（修复）`5eaa8fa`（教训录 L28）`457ac15`（复现器纠正）。**未 push。**
