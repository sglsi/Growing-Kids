# 第十六轮·「资料库搜题」接入百度网盘（13:00–14:00）

## 需求与澄清

思傅：「本项目之前有 ima 和百度网盘搜答案，可检索以前内容，之前是先 ima 再百度，现在可换为先百度再 ima。」

⚠️ **前半句与代码不符**：`git log -S"netdisk" -- server/src/answer-search/` 查无实现，网盘一直只有 `upload/list/download/remove`。所以这不是调顺序，是**新增读通道**。两轮 `AskUserQuestion` 后定下：检索范围 = 网盘 `/学生` 目录（他自己攒的教辅真题），粒度 = 要能搜正文。

## 摸底（先探针再动手）

- `method=search` 开放平台**可用**（errno=0，秒级返回 path/fs_id），不用自己递归遍历。
- `/学生` 采样 120 次列举（深度≤4，尚有 440 目录未穷尽）即见 **1318 文件 / 252GB**：PDF 623、MP4 540、DOC 65、DOCX 44、压缩包 24、图片 18。
- ⇒ **全量正文索引直接否掉**：大量扫描版 PDF，26s/页 OCR + 网盘限速，251GB 起步不现实。
- 复用现成件：`ocr-engine/pdf_tool.py`（pypdfium2 取文字层）+ `src/ocr/pdf-tool.ts` 封装。

## 实现（两级检索）

| 级 | 做法 | 实测 |
|---|---|---|
| L1 文件名/路径 | 网盘原生 `method=search`（`recursion=1`），题干 bigram 提词，每 key 30 条 | 3.3s |
| L2 正文 | 只对 L1 前若干候选下载 + `pdf_tool.py --text-only` 抽文字层比对，结果落 `netdisk_files.text_content` | 6.5s |

- 新表 `netdisk_files`(0022)：`(user_id, fs_id)` 唯一键；`text_status` = pending/ok/none/skipped/too_big。**是缓存不是镜像**。
- `pdf_tool.py` 加 `--text-only` / `--max-pages`：不渲染扫描页（否则 base64 图撑爆内存）。
- `answer-search` 的 `mode=kb` 分支：先 `NetdiskSearchService.search()`，未命中/异常原样落 ima。
- 前端 `source` 新增 `'netdisk'`，标题「网盘资料检索结果（N 份）」、来源小标题「相关资料文件（网盘路径见上方）」；采纳时记 `library` 不记 `mixed`。

## 🔴 4) 本轮最贵的教训：失败不该把好数据判死

新写的回填脚本没带 `OCR_PYTHON` 就跑 `--apply`，7 条全部 `no-python` 失败，
而 `indexText` 把**所有**失败一律记 `text_status=none` ——
`none` 的语义是「确认这份文档没有文字层，不再重试」，
于是 6 条本来抽得到正文的 docx/pdf 被洗成永久搜不到。靠 `--force` 重抽才救回。

修法（两类失败必须分开）：
- 环境类（`no-python` / `no-script` / `timeout`）⇒ 保持 `pending`，下次重试
- 内容类（解析不了 / 扫描版真没字）⇒ 才记 `none`
- `netdisk.ensureText` 同样：环境类失败**不写缓存**（写了就永久判死）

### 3. 增量机制（思傅问「有没有只在变化后才同步变化部分」的机制）
- `multimedia?method=listall`（一次拿全量清单）**不可用**：实测 `errno 20020`，该接口要单独申请权限。

- **实测**：生产全量 1445s → 增量 **0.8s**（1 次请求、跳过 11 棵、删 0 行）；本地 3.1s。

- 盲区：只看目录 mtime，**文件内容替换（名字/大小不变）发现不了**；对检索无影响，换教材版本用 `--full`。

### 4. 🔴 一次真实的误删事故（最贵的教训）
`node scripts/netdisk-index.mjs --root /学生/最新 --apply --full-clean` 在 Git Bash 里执行：
**MSYS 把 `/学生/最新` 转成了 `D:/Program Files/AI/WorkBuddy/resources/vendor/PortableGit/学生/最新`** ⇒ list 一个不存在的目录返回 0 条 ⇒ 脚本判定「完整遍历」⇒ `--full-clean` **把本地 netdisk_files 65890 行全删了**。
- 生产库未受影响（Linux 无路径转换）。
- 本地数据已重跑全量恢复（2099s / 78400 行，含 12510 个目录快照）。
- **加了三条护栏**：① root 必须以 `/` 开头且不含 `:`/`\`，否则退出；② 本轮零文件拒绝清理；③ 待删超库内一半要 `--force-clean`。
- 教训：**凡是「遍历完整才执行破坏性操作」的判定，必须同时校验「遍历真的走过了」**，不能只看计数器等于 0。

### 5. 回答「为什么 25~36 分钟」「检索要不要这么久」
- 25~36 分钟 = **全量遍历 12511 个目录**的时间：每目录一次 list 请求，串行 0.43s/目录，4 并发≈8~9 目录/秒 ⇒ 12511/8.5 ≈ 1470s（生产 1445s、本地 2099s）。
- **检索不要这么久**：检索是纯 SQL，0.5 秒，完全不碰网盘。这两件事互不相关，日常增量后连遍历也只要 1 秒。
