## 视觉美学设计方案 + 界面美化（2026-10-24 07:00，3 个 commit：`efdf761` + `d48dc48` + `ebfc51f`，本地领先 origin 16，未 push）

思傅要求「研究小程序/软件的美学结构、布局、色彩搭配 → 形成设计方案 → 美化项目界面」。

### 一、调研依据（写进方案第 1 章，非凭直觉）
- **微信小程序设计规范**：对比度 ≥4.5:1、TabBar ≤4（点击区域）、包体限制禁引字体
  ⇒ 结论：**只能靠字阶与字重建立层级，不能靠字体**。
- **通用原则**：视觉层级效力排序 **尺寸 > 颜色 > 字重 > 邻近(留白) > 位置 > 深度(阴影)**；
  8pt 栅格；相关性原则（越相关越近）+ 眯眼测试。
- **EdUX（教育类认知研究）**：低饱和暖色降焦虑、纸张材质、大量留白、**One Voice Rule**
  （单一强调色，稀缺性即效力）。参考案例 iTutor「Paper and Emerald」与本项目纸感定位
  高度同构（暖纸底 + 墨黑 + 单一强调色），说明本项目方向对，**缺的是把意象变成硬约束**。

### 二、量化诊断（扫描 src/ 得出，是改造靶子）
1. **P0 配色语义冲突**：`--correct #BE3E2D` 与 `--destructive #C04A3A` **同为红色相**，
   用户分不清「强调」和「要删我东西」；且 `var(--correct)` 实际使用 **0 处**，
   朱砂红全靠硬编码（`'#BE3E2D'` 111 处 + rgba 39 处）。
2. **P0 对比度不达标**：`#8A8275` 于 `#FAF8F3` 纸底仅 **3.55:1**（WCAG AA 要求 4.5:1）。
   ⇒ 这是思傅反复反馈「字符太小看不清楚」的**另一半根因**：小字号叠加低对比度。
3. **P1 字阶塌陷（本次最严重）**：text-xs(12px) **255 处** vs text-base(16px) **仅 13 处**
   ——整站基准字号下沉到 12px，层级是平的甚至倒挂。

   治本是正文上提 14px，不是改按钮。

## 九、RLS 重新评估 + 数据隔离加固（思傅要求「同步改造并重新评估 RLS」）

### 1. RLS 重新评估结论：**不启用**（已写进 ADD-07 第 3.1 节，四条可验证理由）
1. **生效前提不成立**：RLS 只对「anon key + 用户 JWT 走 PostgREST」自动生效；本项目所有查询走后端 NestJS + service_role，而 **service_role 一律绕过 RLS** ⇒ 启用纯装饰。
2. **策略写不出来**：谓词依赖 `auth.uid()`，但登录体系是自定义的（微信 code2session + 内存 login_tickets），**没有 Supabase Auth JWT** ⇒ `auth.uid()` 恒空，只能写 using(false) 或全放。
3. **覆盖面不增**：0002 预留的 4 条策略只覆盖 4/15 张表，补全负担与代码层 `.eq('user_id')` 相同，还多一层"看起来安全"的错觉。
4. **与共享模型冲突**：共享后可见性 =「本人空间 ∪ 被授权空间」，策略要 join 授权表，放应用层一个收口函数更可控可测。

### 2. 落地替代：静态门禁 `server/scripts/check-isolation.mjs`
- `pnpm --filter server check:isolation`；扫描所有 `.from()` 查 user_id；豁免四类：表级白名单（knowledge_articles/blob_objects/health_check/users）、文件级白名单（maintenance/tier-stats/provider）、insert 链（隔离靠 payload）、源码级 `// check-isolation-ignore: 理由`。

## 十二、真机全站加载失败排查：后端进程被回收（2026-10-24 15:31 修复）

## 深夜（再续）：后台弹窗再排查 —— 抓到真凶

### 手法
写了 `server/scripts/flash-probe.ps1`：200ms 轮训抓短命进程（新进程立刻补 CommandLine
+ 父进程，消失时记存活时长）。⚠️ 脚本必须纯 ASCII——PS 5.1 按 ANSI 读 UTF-8 中文会
把脚本结构搞坏（第一次就栽在这，日志里中文全乱码 + Hashtable 变 Null）。

### 三个弹窗源（按危害排序）
1. **唤醒服务每次查询都派生 powershell**（主因）
   查「3001 pid / dist/main 进程 / 启动时间」三处都用 execFileSync('powershell.exe')，
   而 daemon 每 60s 定时刷新也调 ⇒ **后台每分钟闪一次窗口**。
   探针实锤：powershell pid=29688 parent=node(46252)，life≈2s。
   改：process.kill(pid,0) 探活 + TCP 探测端口 + 自写 logs/.backend.pid（{pid,startedAt}）。
2. **env-recovery 用 cmd.exe 跑 ps1 参数**：ComSpec=cmd.exe，参数喂错 ⇒ 进交互模式
   （日志 banner "Microsoft Windows [版本…]" 就是证据）⇒ 脚本没跑还弹 cmd 窗。
   改：直接 spawn powershell（-NoProfile -NonInteractive -ExecutionPolicy Bypass -File）。
3. Windows 上 `execSync('command -v python')` 必失败还派生 cmd ⇒ 改纯 PATH 扫描。

### 顺带挖出的 latent 致命 bug
wake-server 的 `server.listen(3002)` 在模块顶层 ⇒ **启动器自己也占用 3002** ⇒
第一步 portListening(3002) 永远探测到自己 → exit(0)，既不拉 daemon 也不写日志。
表现就是「计划任务/启动项都跑了，唤醒服务就是没起来」。改：只有 --daemon 才 listen。

### 还修了 OCR 自检误判
启动瞬间与 persistent-ocr 预热并发 ⇒ 一次性 import 8 个大件被内存峰值杀（exit≠0），
拆开逐个 import 又全过 ⇒ 包是齐的。旧逻辑判成 venv 损坏 → 每次启动都触发 3~6 分钟
重装（还要拉安装脚本）。改：probeAll 加 modulesOk 标记，超时或「逐包全过」都不重装。

### 验证
- 后端重启：日志不再出现「开始自动恢复」，persistent-ocr 正常就绪
- status→wake→wait-ready(2ms)→health 200→重复 status/wake 幂等
- 探针 90s + 140s：本项目**零 powershell 派生**（日志里剩下的都是 WorkBuddy 自己的监控）
