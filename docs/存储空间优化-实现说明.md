## 一、先说结论

上线前核查发现，设计文档 §11 的存储治理思想**一条都没落地**——这是本次最大的发现：

| 设计说要做的 | 上线前的实际状态 | 证据 |
|---|---|---|
| 压缩 + 转 WebP | **无任何压缩**。sharp 只用于「去手写」，输出一律 `.png()` | `image/image.service.ts` 全部 `uploadBuffer(..., 'image/png')` |
| 列表用缩略图 | **缩略图字段恒空**，列表直接拉原图 | `timeline_items.thumb_key` 存在但全链路无写入点 |
| 内容去重 | **去重索引闲置**，建了没用 | `timeline_hash_idx`（schema.ts:77）无人查询 |
| 清理孤儿文件 | 仅按用户维度删，**无孤儿扫描** | `maintenance.service.ts` 只处理过期匿名用户 |

**结果**：手机直出照片（3–6MB）原样入库、列表再原样拉回 —— 存储与流量双重浪费。

### 实测收益（本机 sharp 0.35.4 真跑，非估算）

用熵接近真实照片的噪声图（3024×4032，模拟手机拍照）实测：

| 处理 | 体积 | 相对原图 |
|---|---|---|
| 原图 JPEG q92 | **10.16 MB** | 100% |
| **展示图** WebP q80 / 长边 1600 | **749 KB** | **省 92.8%** |
| **缩略图** WebP q72 / 宽 400 | **18 KB** | 省 99.8% |
| （对照）AVIF q60 | 656 KB | 省 93.5% |

> **为什么选 WebP 不选 AVIF**：AVIF 仅再小约 12%，但编码慢数倍、小程序兼容面窄。
> 这 12% 不值得多付的编码耗时与兼容风险 —— 这是权衡后的主动选择，不是遗漏。

## 二、核心设计

### 2.1 三档派生图（同一份原图，三种用途）

```
原图 10MB ─┬─► original.webp   （原图留档，详情页可调阅高清）
           ├─► display.webp    （日常展示，长边≤1600 / q80）
           └─► thumb.webp      （列表卡片，宽≤400 / q72）
```

存储 key 按内容哈希分层，避免单目录对象过多：

```
blobs/{hash前2位}/{hash}/{original|display|thumb}.{ext}
```

**内容寻址的红利**：同一份内容天然落在同一个 key 上，上传天然幂等。

### 2.2 全局去重 + 引用计数（策略 4）

新增 `blob_objects` 表（`migrations/0003_blob_dedup.sql`），以 **sha256 为主键**：

```sql
content_hash  varchar(64) primary key,  -- 物理内容唯一标识
storage_key   text not null,
ref_count     integer not null default 0,  -- 引用计数：归零才删
variants      jsonb,                    -- { original, display, thumb }
last_ref_at   timestamptz               -- 冷热判断
```

流程：

```
上传 → 算 sha256 → 命中已有行? ─是─► ref_count++ 且【复用 storage_key，不再上传】
                              └─否─► 上传三档产物 → 登记 ref_count=1
删除 → ref_count-- → 归零? ─是─► 进入待回收队列（GC 真删文件）
                           └─否─► 【禁止删文件】，别的用户还在用
```

> **踩过的坑**：最初的清理逻辑是「删用户 → 直接用 key 删文件」。在全局去重下这**会误删**
> 其他用户仍在引用的共享文件。已改为走 `BlobService.release()`，归零才删。

### 2.3 压缩管线（前端粗压 + 服务端精压）

| 端 | 作用 | 参数 |
|---|---|---|
| 前端 | 省**上传流量** | `Taro.compressImage`，长边≤1600 / q80 |
| 服务端 | **权威**压缩点 + 转 WebP + 缩略图 + 去重 | sharp |

**为什么两端都做**：前端是「优化」不是「依赖」——老客户端、绕过 UI 的调用都不会让存储失控，
因为服务端才是最终把关的那一环。

管线三条硬约束：

1. **幂等** —— 已是 WebP 且尺寸达标且 <40KB ⇒ 不重编码（避免多次压缩累积画质损失）
2. **降级** —— 任何异常（坏图/不支持编码）都回退为「原样透传」，**绝不阻断上传**
3. **EXIF 纠正** —— 手机竖拍照片必须 `.rotate()`，否则展示时躺倒

### 2.4 临时对象通道（策略 5② + 策略 7）：中间上传不再占引用计数

**发现的缺陷**：`purpose != save` 的上传（AI 识别前的中间图）也走正式 `ingest()`——
生成三档派生图、并 `acquire()` 一次引用。但它**不落库**（没有 timeline/library 条目），
意味着**永远不会有人 `release()`** ⇒ `ref_count` 恒为 1 ⇒ GC 只扫 `ref=0` ⇒
**这些图永久泄漏**，且每张白占 3 个对象（含一份根本用不上的高清留档）。

**修法**：新增 `ingestTemp()`，与正式路径有三点差别：

| | 正式 `ingest()` | 临时 `ingestTemp()` |
|---|---|---|
| 派生档数 | 3 档（original + display + thumb） | **1 档**（display） |
| 引用计数 | `acquire()` ⇒ ref_count ≥ 1 | **不 acquire**，登记为 `ref_count = 0` |
| 回收 | 归零后才回收 | `ref_count=0` + 过宽限期 ⇒ **已有孤儿 GC 直接回收**，无需新增定时任务 |
| key 前缀 | `blobs/{hash前2}/{hash}/{variant}.{ext}` | `tmp/{hash前2}/{hash}.{ext}` |

内容寻址 ⇒ 同一张图重复中间上传落在**同一个 key**，天然幂等、不重复占空间。

> ⚠️ **两个安全红线（比省空间更重要）**：
> 1. **分流判据必须是显式 `purpose === 'temp'`，不能按「是否落库」推断。**
>    识别链路（整卷识别 / 题答分传 / 文档识别）上传时不带 purpose，看似"中间态"，
>    但它们的 key 会写进识别结果的 `question_image_keys` 被题目**正式引用**——
>    若按"不落库 ⇒ temp"回收，24 小时后**已保存的题目图片会裂**。
>    所以只有调用方明确声明「用完即弃」才走 temp；其余一律走正式路径。
> 2. **`registerTemp()` 遇到已存在的记录必须直接复用、绝不覆盖。**
>    否则一次 temp 上传会把同内容的**正式资产降格成 temp**，24 小时后被删 → 图片裂。
>    反向也做了兜底：正式上传命中 temp 记录时 `acquire()` 会把它**转正**为 image。

## 三、踩坑记录（重要）

### 坑 1：`sharp().rotate().metadata()` 不反映旋转结果 ⚠️

本机实测：一张 400×200、`orientation=6` 的 JPEG，

```js
await sharp(buf).rotate().metadata()   // → 仍报 400x200，orientation=6（未变！）
await sharp(buf).rotate().jpeg().toBuffer()  // → 真实输出确实是 200x400
```

**`metadata()` 对 pipeline 是透传的**，不会体现 `.rotate()` 的效果。
若照抄 metadata 就会把竖拍照片的宽高写反 → 前端按错误比例预留位置 → **图片变形**。

**修复**：按 EXIF orientation 自行换算，`orientation ∈ [5,8]` 表示需旋转 90°，宽高对调。

> 这个坑很隐蔽：只跑「压缩比」测试永远发现不了，必须单独测 **方向** 才能暴露。
> 教训同 L2（测试要能反向证伪）——「尺寸没报错」不等于「尺寸是对的」。

### 坑 2：去重表的并发自增

PostgREST **没有原子自增**。`ref_count++` 只能「读-改-写」，并发下会少计。

**对策**：用 CAS（`update ... .eq('ref_count', 旧值)`），未命中则重读重试。
且**安全方向是明确的**：极端并发下只会「少计」→ blob 提前进入待回收队列 →
而 GC 前还有宽限期二次核对 → **不会误删在用文件**。

### 坑 3：软删时释放引用的顺序

必须 **①先查 hash → ②再软删 → ③最后释放引用**。
若顺序反了（先置 `deleted_at` 再查），查询会因 `deleted_at is null` 过滤而查不到，
引用永远释放不掉 → 文件永远回收不了。

并且软删 update 必须带 `.is('deleted_at', null)` 过滤，保证**同一条目重复删只释放一次**。

### 坑 4：SDK `deleteFile` 是**对象参数**，传字符串会静默失败 ⚠️

`S3Storage` 的签名是 `deleteFile(options: { fileKey })`。此前代码写的是 `deleteFile(key)`：

```ts
await anyStorage.deleteFile(key)               // ❌ options.fileKey === undefined
await anyStorage.deleteFile({ fileKey: key })  // ✅
```

**最危险的地方不是报错，而是不报错**：该调用包在 try/catch 里，失败被吞掉 ⇒
GC 与清理任务日志一切正常，**实际一个对象都没删掉**。这类 bug 会以"功能静默失效"
的形态潜伏很久——存储空间只增不减，而所有人都以为清理在跑。

> 对策（已做）：按对象参数调用并保留字符串签名兜底；同时给测试用例加了一条
> **源码一致性断言**（`run-quota.mjs` 组十一），防止日后被改回去。

| 十、中间上传 temp | 只新增 1 个对象（**反向：正式路径仍 3 个**）；key 走 `tmp/`；`ref_count=0`；`kind=temp`；重复上传复用且**对象数未增加**；过期后进入回收队列（**不再永久泄漏**） |
| 十（安全） | **正式资产不被 temp 上传降格**；先 temp 后正式 ⇒ **转正为 image** 且计数 +1；转正后不再被回收命中 |

## 九、已知缺口（诚实记录，不装作完成）

### 缺口 1：题目条目删除时，未释放其引用的图片

题目存在 `timeline_items` 表（`kind='question'`），图片 key 放在 **`content.images` 的 JSON 数组里**，
而不是 `file_hash` 字段。后果：

- 删除题目 ⇒ `release()` 拿不到 hash ⇒ **引用不释放** ⇒ 图片直到 GC 也回收不了；
- 识别链路（整卷识别等）上传的图 likewise：acquire 之后若用户没保存题目，也无人释放。

**为什么不顺手改**：正确做法是「条目创建时 acquire、删除时 release」逐条配对，
但一次识别可产生 **N 道题共享同一张试卷原图**——若只 release 不按引用数 acquire，
第一道题被删就会让 ref 归零 ⇒ **其他 N-1 道题的图片被误删**。
**误删用户照片的代价远大于多占一份存储**，所以本轮不动引用模型。

**后续方案（按此顺序做才安全）**：
1. 先让条目创建路径（含 `content.images`）能 acquire —— 需要按 key 反查 hash（新增 `findByKeys`）；
2. 再让删除路径 release；
3. 最后才开启「按引用核对」的回收（目前 GC 只看 `ref_count`，属保守策略）。

### ~~缺口 2：存储层不支持列举~~ —— ✅ 已澄清并解决（2026-09-27）

此前写"SDK 不支持列举"是**错的**：实测 `S3Storage` SDK **支持** `listFiles({ prefix })`。
已新增 `StorageService.listKeys(prefix, maxKeys)`（分页，20 页上限），
现在可以「扫 `tmp/` 前缀批量删」，不再只依赖数据库登记。

顺带在这次排查中**发现并修掉一个真实 bug**：SDK 的签名是 `deleteFile(options: { fileKey })`
——**对象参数**，而此前代码传的是裸字符串 key ⇒ `options.fileKey` 为 undefined ⇒
删除**静默失败**（异常被 catch 吞掉）。也就是说，此前的 GC / 清理任务"看起来在跑"，
**实际一个对象都没删掉**。现已按对象参数调用，并保留字符串签名兜底防 SDK 版本差异。

> 教训：SDK 的方法签名要从**实测**确认，不能靠猜；失败路径若被 catch 吞掉，
> 错误会以"功能静默失效"的形式长期潜伏。
