> 编号：调研纪要（决策凭据类，非 GK 规范性文档） ｜ 版本：**v4.3** ｜ 日期：2026-10-30 ｜ 状态：**验证优先版**
>
> **v4.3 变更（第四轮：L3 能不能走 6 个月免费）**：新增 **§2.8**。查到四条官方原文，结论是**不能**——① 轻量备案要求「**包年包月**、购买时长 **≥3 个月**、备案期间剩余有效期 ≥1 个月」（且不支持 EIP、带宽不能为 0）；② 「**按量计费、试用期的云服务器…均不支持备案**」；③ 云开发备案要求「剩余有效期**大于 6 个月**」+ 开启固定公网 IP ⇒ 刚开的 6 个月体验环境天然不满足，且「微信开发者 IDE 注册的体验环境**不支持直接续费**」；④ 「**自 2021 年 8 月 5 日起，云托管不再支持新增域名备案功能**」。⇒ 免费政策解决的是"数据库/函数要不要花钱"，**与"备案凭据"正交**。正确用法是**分段用**（P1 免费用 PG 试跑、P2 买轻量备案上线），且**L3 反而不该用免费 PG**（到期 19.9 元/月，同机自建 ¥0 且走内网）。
>
> **v4.2 变更（第三轮：控制台「新建环境」两个选项怎么选）**：新增 **§2.7**。核实出一条决定性的产品事实——**微信云托管自带的数据库只有 MySQL 5.7/8.0，没有 PostgreSQL**（官方 MySQL 页原文「当前支持 5.7/8.0 版本的 MySQL」），故 19 个 PG migration 与 218 处 PostgREST 查询在云托管里**一条都用不上**；反之**云函数返回即冻结/回收**，撑不住本项目 `async_jobs`（精准 OCR 实测 86.8s，任务在进程内存里）与 Python OCR 侧车 ⇒ **必须容器或服务器**。结论：两者不是二选一而是两块拼图；**若现在只能建一个，建「云开发环境」（PG），云托管押后**——云开发免费期自"小程序发布上线"起算，云托管免费额度自"创建/开通"起算，早建即白烧。
>
> **v4.1 变更（同日第二轮：思傅实操进控制台后产生的三个新事实）**：① **CloudBase PostgreSQL 与 Supabase 有意对齐**（PostgREST 同源、三角色同名、JWT claims 对齐、RLS 写法一致），迁库从"自建 PG + 自建 PostgREST"变为"建个环境 + 补一层路径重写" ⇒ **新增 §2.6**；② **微信云托管 ≠ 微信云开发**（官方 FAQ：两套独立体系，环境互不可见）⇒「云托管 + 云开发 PG」只能走公网 HTTPS，**不能内网直连**；③ **云开发环境可作备案云资源**（个人版及以上 + 剩余有效期 ≥6 个月 + 开启云托管固定 IP）⇒ 备案不必另买服务器。据此把 §3.2 的路线结论从"L1 一刀切否定"改为"**按时间压力分岔**"。穿刺 2/3 由 D 级升为「A（界面）+ D（创建）」——能进不等于建成，仍需提交后确认。

### 1.3 逐项交代

#### 穿刺 1｜`callContainer` 的传输能力（B 级）

官方两页原文（均"最后一次编辑于 2026-08-24"）：

- 《调用云托管服务》：「请求大小限制 **100KiB（文本 100KiB，二进制 20MiB）**；返回包大小限制 **1000KiB**；请求最大超时时间为 60 秒」
- 《微信小程序-访问云托管服务》参数表：`data` 类型为 `string/object/ArrayBuffer`；`timeout` **「最大值不能超过 15 秒，否则无效」**；使用限制处另加一句：「对象类型限制 20 MiB，**请求中不建议包含图片，可通过对象存储处理**」

两页那句"60 秒"与参数表"15 秒"并不矛盾：**60s 是平台侧收单上限，客户端根本等不到**。你实测的精准 OCR **86.8s** 在这条线上必然失败——这与"长任务必须走 `POST /api/jobs` 202 + 轮询"的既有实现完全吻合，无需改判。

另有一条容易漏的前置（B 级）：需在小程序管理后台「设置 → 功能设置 → **基础库最低版本设置**」把值设为 **2.23.0 及以上**，否则 `callContainer` 不可用。

**判定**：传输能力本身没问题，但"官方不建议用它传图片"+"返回包 1MB"+"超时 15s"这三条叠加，意味着走 L1/L2 就得把**图片上传、文件下载、长任务**三条链路全部改造成另一套形态。这是 L1 不作主线的核心理由——**不是它不能用，是它逼你重写三条链，换来的只是一个"免备案"，而备案本身是免费的，只花时间。**

#### 穿刺 4｜PostgREST 兼容性（A 级：协议层实测）

本机没有 Docker、没有 PostgreSQL、`.co` 域名在本机 shell 也不可达（见 §2.5），因此**无法起真库跑端到端**。改用更强的做法——**抓真实请求**：

把仓库里真实使用的 `@supabase/supabase-js@2.95.3` 指向本地回声服务，逐条执行本项目实际在用的调用模式，录下它落到 HTTP 上的方法/路径/查询串/请求头（脚本：`server/scripts/probe-pgrst-contract.mjs`，复现步骤见附录 C）。

| 真实业务形态 | 实测发出的请求 | PostgREST 官方支持 | 依据 |
|---|---|---|---|
| 列表分页 + 总数 | `GET /rest/v1/timeline_items` `select=*&user_id=eq.…&order=created_at.desc&offset=0&limit=10`，`Prefer: count=exact` | ✅ 全文支持 | Pagination and Count（`limit/offset` + `count=exact` + `Content-Range`） |
| 取单条（40 处 `maybeSingle`） | `Accept: application/json`，客户端自行取首行 | ✅ 不依赖服务端单数模式 | — |
| 取单条（17 处 `single`） | `Accept: application/vnd.pgrst.object+json` | ✅ 支持；**0 行时返回 406 `PGRST116`** | Resource Representation |
| 新增并回行（22 处） | `POST` + `Prefer: return=representation` | ✅ | Prefer Header |
| Upsert（3 处） | `POST` + `on_conflict=…` + `Prefer: resolution=merge-duplicates` | ✅ | Tables and Views |
| 更新/删除回行数（56/26 处） | `PATCH`/`DELETE` + `.select('id')` | ✅ | Tables and Views |
| 算子 `eq/neq/gte/lte/in/is/ilike/not` | `?col=eq.v`、`?col=not.is.null`、同列 `gte`+`lte` 并存 | ✅ 全部在官方算子表 | Tables and Views |
| 数组包含（2 处 `contains`） | `?tags=cs.{错题}` | ✅ | Tables and Views |
| 模糊搜索 + JSON 路径（4 处 `or`） | `?or=(title.ilike.%分式%,content->>question.ilike.%分式%)` | ✅ 逻辑树与 `->>` 过滤分别有原文示例 | Tables and Views |
| RPC（1 处，未接线） | `POST /rest/v1/rpc/exec_sql` | ✅ 机制支持，**但该函数在库里不存在** | Functions as RPC |

**结论**：`supabase-js` 没有走任何"Supabase 私有扩展"，它就是 PostgREST 的标准客户端。**换成自建 PostgREST，218 处查询不需要改一行。**

顺手证实了一个采集陷阱（记录在此以免后人重踩）：抓请求时若用 `Object.fromEntries(URLSearchParams)`，同名列的多值过滤（`gte`+`lte`）会被折叠成最后一个，看起来像"丢了一个条件"。改用 `getAll` 后证实客户端行为正确——**这是我的采集缺陷，不是项目 bug**。

#### 穿刺 5｜AnyService（B 级存在性 + D 级细节）

- 官方（docs.cloudbase.net）确认：AnyService 把**轻量应用服务器 / CVM / CLB** 上的既有服务接入小程序，**仅需 IP、无需域名、无需配域名白名单**，支持 SSE/WebSocket。这确实是一条 2026 年才有的新通道。
- **但该文档全篇没有写**：请求体/响应体上限、超时上限、是否需付费套餐、是否支持文件上传。这类"没写"的参数在真实项目里往往就是死因，**必须去控制台看实际提示**（§1.4 第 3 项）。
- 另一条硬事实（三个官方来源表述一致，B 级）：**云开发免费环境在小程序发布后，到期时间变更为上线后第 15 天，未转付费即停服销毁**；个人版 **19.9 元/月**；免费体验活动**截止 2026-12-31**。

**判定**：L2 可以跑通，但它的地基是"云开发环境"这一层。把它当主线 = 把上线押在一个 15 天免费期与一个 12-31 截止的活动上，这正是思傅要求①里"最后发现此路不通"的典型形态。**降级为过渡通道。**

## 2. 已验证的硬事实

### 2.1 客户端四条上限（B 级原文 × A 级项目对照）

| 上限 | 官方原文 | 本项目实测对照 | 影响与处置 |
|---|---|---|---|
| 文本请求 **100KiB** | 「请求大小限制 100KiB（文本 100KiB…）」 | `createBatch` **无条数上限**（`timeline.service.ts` 实测只校验非空）；单题含题干+答案+解题约 1–3KB ⇒ 约 30 题即逼近上限 | 无论走哪条路线，都该给 `batch` 加 **≤20 条**上限：L1/L2 下是硬错，L3 下是防呆 |
| 二进制请求 **20MiB** | 「二进制 20MiB」 | 前端压缩：长边 ≤1600、`quality=80`（`api.ts:164-165`）；后端 multer `fileSize: 20MB` | 体积够用；但官方「不建议请求中带图片」⇒ L1/L2 应改走对象存储直传 |
| 返回包 **1000KiB** | 「返回包大小限制 1000KiB」 | 导出 docx 实测 **10–22KB**（`[document/export]` 日志 `bytes:` 取值）；列表 20 条为几十 KB 量级 | 当前不撞线；但**大导出/批量下载**在 L1/L2 必须分片或走对象存储 |
| 超时 **15s** | `timeout`「最大值不能超过 15 秒，否则无效」 | 精准 OCR 实测 **86.8s** | 长任务只能异步——`POST /api/jobs` 已实现，**这条不变** |

### 2.2 政策两条死线（B 级，决定 L3 可行性）

**死线一：个人主体不能碰"前置审批"内容。**

| 官方原文 | 出处 |
|---|---|

### 2.3 现网链路已经不健康（A 级实测）

本机直接请求现网 `…supabase.co/rest/v1/`：**HTTP 000，耗时 16.8s**（连接失败，非 4xx/5xx）。这与仓库里 `supabase-dns-pin.ts` 记录的现象一致——2026-10-22 实测 GFW **间歇黑洞** supabase 的 Cloudflare IP，表现为「TCP 可连、TLS 握手挂死」，封锁面每几分钟漂移，为此写了 24 个候选 IP + TLS 探针 + 5 分钟重探。

⇒ **迁库不是"优化项"，是"已有故障的根治"**。一个家庭应用要自己维护 IP 池对抗黑洞，本身说明这条链路不该留在生产里。

### 2.4 迁库的三个真前置（含我上一轮的错）

| # | 前置 | 事实（A 级） | 不处理的后果 |
|---|---|---|---|
| 1 | **密钥不是 JWT** | 现网 anon key 长 46 字符、前缀 `sb_publishable`；service key 长 41、前缀 `sb_secret`；**均非三段式 JWT**。而 `supabase-js` 会把 key 同时放进 `apikey` 与 `Authorization: Bearer` | 自建 PostgREST 配了 `jwt-secret` 后**全站 401**。正确做法：自签一对 HS256 JWT（claim 带 `role`），填进 `.env` |
| 2 | **Storage 实际在用**（我上一轮写错） | `.env` 为 `STORAGE_DRIVER=supabase`；`storage.service.ts` 有 4 处真实 `supabase.storage.from(bucket)` 调用（upload / getPublicUrl / download / remove），bucket=`media` | 只迁库不迁文件 ⇒ 历史图片全部 404。必须同批迁对象存储（COS 或 MinIO），并新增一个 `s3` 驱动（只需实现这 4 个方法） |
| 3 | **`ocr_results` 启用了 RLS 且无 policy** | `migrations/0016_ocr_result_cache.sql:51` 有 `enable row level security`，全仓无对应 `create policy` | 自建 PG 里若用普通角色，该表**永远查不到行**（Supabase 侧是靠 service_role 的 BYPASSRLS 规避的）。自建角色需 `bypassrls`，或补一条 policy |

另有一条**不要顺手做的事**：仓库已有 `DB_PROVIDER=tencent-pg|dual` 开关与 `tencent-pg.provider.ts`，但它的 `query()` 依赖 `rpc('exec_sql')`，**该函数在库里并不存在**（provider 注释自己写着"若未创建…请改用 raw() builder"）。⇒ **迁库别开这个开关**，它只会带来一个必失败的路径。

### 2.6 CloudBase PostgreSQL：与 Supabase 的对齐度（B 级，2026-10 官方原文）

> **本节为 2026-10-30 第二轮核实新增**，起因是思傅进入控制台后发现「PostgreSQL 数据库」选项上标着"兼容 Supabase SDK"。上一轮建议的「自建 PG + 自建 PostgREST（0.5–1 天 + 自签 JWT）」**不是唯一路径**，腾讯云已有更短的。

官方《从 Supabase 迁移》原文（`docs.cloudbase.net/quick-start/migration/supabase`）：

> CloudBase PG 的设计在很多关键点上**有意对齐 Supabase**：相同的 `auth`/`storage` schema 划分、对齐的 JWT claims（`sub`/`role`/`aud`）、相同的 `anon`/`authenticated`/`service_role` 三角色模型、相同的「GRANT + RLS」双层权限范式。**绝大多数 Supabase 项目可以以最小改动迁移过来**。

**对齐项（本项目的 218 处查询全部命中）**：

| 概念 | Supabase | CloudBase PG | 对本项目 |
|---|---|---|---|
| 自动 REST API | PostgREST | PostgREST（**同一开源项目**） | 查询语法一致 |
| `.rpc()` | ✅ | ✅ 直接兼容 | 仅 1 处占位，无影响 |
| 三角色 | anon / authenticated / service_role | 同名同义 | 后端用 service_role（BYPASSRLS） |
| JWT `sub` | uuid 字符串 | `varchar(64)`（兼容 uuid 字符串） | `users.id` 是 `varchar(36)` ⇒ **兼容** |
| RLS Policy | 标准 PG | 标准 PG，写法完全一致 | `migrations/` 里的 policy 可原样复用 |

**差异项（只有两条会影响本项目，其余都是未使用的能力）**：

| 差异 | Supabase | CloudBase PG | 本项目动作 |
|---|---|---|---|
| REST 端点 | `/rest/v1/<table>` | **`/v1/rdb/rest/<table>`** | 加一层路径重写（见下） |
| 域名 | `<project>.supabase.co` | `<envId>.api.tcloudbasegateway.com` | 改 `.env` |
| Realtime 实时订阅 | ✅ 内置 | ❌ 不支持 | **未使用**，无影响 |
| GraphQL | ✅ pg_graphql | ❌ 不支持 | **未使用**，无影响 |
| 数据库 branching | ✅ | ❌ | **未使用**，无影响 |
| 存储 API | `supabase.storage.from().upload()` | `app.uploadFile()`；Supabase Storage 兼容 HTTP API「第二阶段」提供 | 见 §2.4-2，**仍需改写** |

**路径落差怎么补（三种做法，按改动量排序）**：

1. **同容器内反向代理（推荐）**：`supabase-js` 完全不动，`SUPABASE_URL` 指向 `http://127.0.0.1:<port>`，由一段中间件把 `/rest/v1/*` 重写为 `/v1/rdb/rest/*` 并注入 `Authorization: Bearer <API Key>`。**218 处查询零改动**，改动量集中在 1 个文件约 30 行。
2. 换 `@cloudbase/js-sdk` 的 `app.rdb()`：链式 API 基本对齐（`from/select/eq/order/limit/insert/update/upsert/rpc` 都在），只需改 `getSupabaseClient()` 这一个收口点（110 处调用方不受影响）。
3. 直接把 `SUPABASE_URL` 改成 `…/v1/rdb`：**行不通**——`supabase-js` 硬编码拼接 `/rest/v1`，最终会变成 `/v1/rdb/rest/v1/xxx`（多一层）。这条写在这里是为了防止有人"顺手一试"后误判为不兼容。

**三条必须提前知道的硬约束**：

- **免费 6 个月 ≠ 长期可依赖**：环境到期与「小程序发布后第 15 天」是两条**独立**计时（后者三处官方源一致，见 §1.2-5）。正式上线前必须转个人版（**¥19.9/月**），否则环境被限流而非"还能凑合用"。
- **公网访问即可，不必买内网互联**：`<envId>.api.tcloudbasegateway.com` 是**公网域名**，微信云托管容器走公网 HTTPS 调它就行（同城延迟低），**不需要**「云托管服务资源包」（那是连 TDSQL-C 内网才要的）。云托管侧公网流量 0.8 元/GB，小体量可忽略。
- **"直连 PG 跑迁移"不可靠**：外网 `postgresql://` 需控制台开启「外网 IPv4 地址」+ 关联安全组，且**仅部分地域支持**（C 级，社区答复自认为经验推断）。⇒ 迁移走云 API `ExecutePGSql`（官方原文：**每次只能执行一条 SQL**；部分 DDL 需用 `DO LANGUAGE plpgsql $$ BEGIN EXECUTE '...'; END $$` 包装后重试）。

**落地前的静态预检（A− 级：静态扫描全部 19 个 `migrations/*.sql`，未实跑）**：

| 检查项 | 结果 | 对 CloudBase PG 的影响 |
|---|---|---|
| `create extension` | **0 处** | 无扩展依赖，不存在"扩展未安装"风险 |
| `gen_random_uuid()` | 12 处 | PG 13+ 已并入核心；CloudBase 是 **PostgreSQL 17**，原生可用，**不需要 `pgcrypto`** |
| `auth.uid()` | **全在注释里**（`0002:147-153`） | 不依赖 CloudBase 的 `auth` schema，无需迁移账号体系 |
| `storage.` schema | **0 处** | 存储是自有实现（`STORAGE_DRIVER=supabase` ⇒ 要换 S3/COS），**不碰 PG 的 storage schema** |
| RLS | 仅 `ocr_results` 启用且**无 policy**（`0016:51`） | 与现状一致；后端用 service_role（BYPASSRLS），行为不变 |

⇒ 预期 **19 个 migration 可原样执行**，不需要改 SQL。真正的 A 级确认需在环境建好后实跑一次（走 `ExecutePGSql`，单条执行）。

**一条容易踩错的架构事实（B 级，官方 FAQ 原文）**：

> 微信云托管和微信云开发是**两套独立体系**，微信云托管的环境**只能在微信云托管控制台看到**，在微信开发者工具的云开发控制台中不能看到。……微信云托管的环境只能在微信云托管控制台看到，**在腾讯云控制台中不能看到**。

⇒「微信云托管 + 云开发 PG」**不能内网直连**，只能走公网 HTTPS。这条同时纠正了网上大量"云托管与云开发内网互通"的教程——那说的是**已停止更新**的云开发内置云托管，官方原文：「云开发中的云托管能力**已停止功能更新**，仅支持存量业务继续运行」。

**附带发现（影响备案策略）**：官方《ICP 备案问题》（`cloud.tencent.com/document/product/876/128405`，2026-07-02 更新）原文——

> 云开发（CloudBase）环境可作为备案云资源，**无需额外购买云服务**。需满足下列**所有**条件：① 套餐版本：**个人版及以上**套餐的环境（**免费体验环境不支持**）② 剩余有效期在 **6 个月** 以上 ③ 对应云环境**开启了云托管固定 IP**。

⇒ 若走自有域名路线，备案云资源可用云开发环境（需先升个人版），不必另买轻量；但**免费体验版环境不能用于备案**。

### 2.7 「云开发环境」与「云托管环境」：两个选项的真实差别（B 级官方原文 + A 级项目对照）

微信侧控制台「新建环境」并列的这两项，**不是同一个产品的两种规格，是两套独立产品**（官方 FAQ：两套独立体系、控制台互不可见，云托管环境在腾讯云控制台也看不到）。

| 维度 | **云开发环境**（CloudBase） | **云托管环境**（微信云托管） |
|---|---|---|
| 定位 | 一站式后端**能力包**（数据库/存储/函数） | 容器**托管**（跑任意 Docker 镜像） |
| 计算形态 | 云函数，事件或 HTTP 触发，**短生命周期** | **常驻容器**，支持长连接、常驻进程 |
| 数据库 | 云数据库（文档型，类 MongoDB）+ **PostgreSQL**（官方明示兼容 Supabase SDK） | **只有 MySQL 5.7 / 8.0**（Serverless TDSQL-C）；官方 MySQL 页原文：「当前支持 5.7/8.0 版本的 MySQL」，**无 PostgreSQL** |
| 对象存储 | 云存储 | COS（自带安全域名校验与 CDN） |
| 小程序调用 | `wx.cloud.callFunction`（微信专线）或 HTTP 访问服务 | `callContainer`（**免域名免备案**）或公网域名 |
| 计费与免费期 | 免费体验环境**在小程序发布上线后第 15 天到期**；个人版 19.9 元/月 | 按量计费，首个环境有免费额度，**按创建/开通起算** |
| 适用 | 前端为主的轻后端、CRUD、免运维 | 已有后端代码、任意语言、长任务、WebSocket |

**对「成长学童」的三条判定**：

① **数据库这一票，云托管直接出局**。19 个 `migrations/*.sql` 是 PG 方言、218 处查询走 PostgREST，云托管自带的 MySQL **一条都用不上**。"数据层回国"这件事，只能在云开发 PostgreSQL（或自建 PG）里做。

② **计算这一票，云开发直接出局**。项目现状是 `async_jobs` 任务在**同一个进程内存里**跑（精准 OCR 实测 86.8s，进程一重启即 `failed`）。云函数**返回即冻结/回收**，后台任务会被掐断；而 OCR 还有 Python 侧车（`D:/AI/gk-ocr-env`）⇒ 必须跑在**容器或服务器**上。

③ ⇒ **不是二选一，是两块拼图**：PG 只能来自云开发环境，长驻进程只能来自云托管（或轻量）。三种组合的真实代价：

| 组合 | 后端跑在哪 | 数据库 | 需域名备案 | 主要风险 | 判断 |
|---|---|---|---|---|---|
| 只建云开发 | 云函数 | 云开发 PG | 否（`callFunction`） | 云函数撑不住 `async_jobs` 与 Python 侧车 | ❌ 不成立 |
| **云开发 + 云托管** | 云托管容器 | 云开发 PG（公网 HTTPS） | **否** | 两个免费额度同时倒数；容器无持久盘 | ✅ **唯一"零备案"可行解（L1′）** |
| 云开发 + 轻量 | 轻量容器 | 云开发 PG 或轻量自建 PG | **是**（7–20 工作日） | 云开发环境 15 天到期（若仍依赖它） | ✅ **长期最优（L3）** |

**若现在只能建一个：建「云开发环境」，把「云托管环境」押后。** 两条理由都是硬的：

- **时钟起算点不同**：云开发的免费体验期从「小程序**发布上线**」起算，开发期建不吃亏；云托管的免费额度从「**创建/开通**」起算，早建一个月就是白烧一个月。
- **不可替代的那块在云开发**：PG（且兼容 Supabase）只在这里有；容器则是"哪儿都能跑"（云托管 / 轻量 / 自己的机器），随时可补。

**两个必踩的坑（提前记）**：两套系统**不能内网直连**，云托管容器连云开发 PG 只能走公网 HTTPS（要把出网流量算进成本）；云开发**免费体验环境不能作备案云资源**（需个人版及以上 + 剩余有效期 ≥6 个月 + 开启云托管固定 IP）。

### 2.8 「6 个月免费」覆盖什么、不覆盖什么（B 级官方原文，备案页 2026-10-16 更新）

**结论先给**：这套免费政策解决的是"**数据库和函数要不要花钱**"，解决不了"**备案凭据**"。**L3 的门票不是它，也顶不了它。**

**① 备案凭据的硬条件（与免费政策正交）**

腾讯云《备案云资源》原文（`cloud.tencent.com/document/product/243/18908`，2026-10-16 更新）：

- **轻量应用服务器（Lighthouse）**：「计费模式需为**包年包月**，购买包月 **3 个月及以上**（包含续费）且备案期间**剩余有效期需大于（含）1 个月**」，并需绑定中国境内公网 IP（**不支持绑定 EIP 进行备案**）、**带宽不能为 0**。
- **云服务器（CVM）**：同上口径。
- **云开发（TCB）**：「备案期间，云开发（TCB）资源的**剩余有效期须大于 6 个月**，且需在云开发中**开启固定公网 IP**」；每个资源可备案 2 个服务，**不支持生成备案授权码**。
- **云托管**：「**自 2021 年 8 月 5 日起，云托管不再支持新增域名备案功能**。存量已备案成功的用户可继续使用。」
- 《其他问题》页原文：「**按量计费、试用期的云服务器**，以及高性能应用服务（HAI）等**均不支持备案**。」

⇒ **三条推论，条条对 L3 不利**：

1. **免费试用的服务器不能备案** ⇒ L3 的第一笔钱（轻量**包年包月 ≥3 个月**）是**门票**，不是可选项，省不掉。
2. **刚开的 6 个月云开发环境也不能当备案资源**：要求是"剩余有效期**大于** 6 个月"，6 个月本身不满足；且另处要求**个人版及以上**；再加「微信开发者 IDE 注册的体验环境**不支持直接续费**，只能原价升级或注销重建」——从微信侧建的正是这一类。
3. **云托管压根不能备案**（2021-08-05 起停止新增）——它靠 `callContainer` 免域名，本就不需要备案，这也解释了它的定位。

**② 免费政策真正覆盖的范围（官方套餐页 `cloud.tencent.com/product/tcbs`）**

| 项目 | 免费体验版 | 说明 |
|---|---|---|
| 价格 | ¥0 | 单账号限 **1 个**免费环境 |
| 资源点 | **3,000 点/月**（官方口径 1,000 点 ≈ ¥1） | 数据库/函数/存储/CDN **共用同一个池** |
| 有效期 | **6 个月** | 到期前 1 个月可参与"分享 0 元续 6 个月"（活动至 2026-12-30） |
| 资源包 / 按量 | **不支持** | ⇒ 超额只能升级套餐，不能加买 |
| PostgreSQL | 套餐页把 PG 列在**个人版**（¥19.9/月，40,000 点）的"增加"项 | 与你在控制台看到的"PG 免费 6 个月"口径不一致 ⇒ **以下单页为准（D 级）** |

**③ 正确用法是"分段用"，不是"拿它顶 L3"**

| 阶段 | 数据库放哪 | 花多少 | 换阶段会作废吗 |
|---|---|---|---|
| **P1 开发/试跑（现在）** | CloudBase 免费 PG（6 个月） | ¥0 | 建表脚本 + 路径重写层 **不作废** |
| **P2 要上线** | 轻量**同机自建 PG**（或继续用 CloudBase PG，升个人版） | 轻量 ¥38–109/年 + 域名 ¥30–70/年 | — |

**④ 一个反直觉的结论：L3 其实不该用那 6 个月免费 PG**

- 免费 PG 到期后 ⇒ 个人版 **19.9 元/月 = ¥239/年**；而 L3 在轻量**同机自建 PG，¥0 额外**。
- 云开发 PG 只能从云托管容器**走公网 HTTPS** 访问（两套体系不互通），**出网流量另计**；同机自建是 `127.0.0.1`，零延迟、零流量费。
- ⇒ 拿免费 PG 顶 L3 是"省半年小钱、添两个长期成本"。

**⑤ 两条别忘的锁**

- **L3 是年费，不是一次性**：备案绑定资源，**服务器到期不续费会导致备案失效**；域名也要年年续。真实年成本 ≈ **¥150–200**。
- **个人账号不能生成备案授权码**（官方：个人账号不支持），所以**不能借别人的服务器备案**，必须自己有一台符合条件的。

## 3. 方案（按验证结果重排）

### 3.1 三条路线

| 维度 | **L1 微信云托管** | **L2 AnyService + 轻量** | **L3 域名备案 + 轻量自建** |
|---|---|---|---|
| 免域名/免备案 | ✅（仅 `callContainer`） | ✅（IP 直连，官方明示免备案） | ❌ 需域名备案 |
| 客户端超时 | **15s**（硬） | 文档未写明（**D 级**） | 无此限制（`wx.request` 60s） |
| 返回包上限 | **1000KiB**（硬） | 文档未写明（**D 级**） | 无 |
| 持久盘 | ❌ 无（库与文件都须外置） | ✅ 轻量自带 | ✅ |
| 数据库能否回国 | **✅ 可**：CloudBase PG 走公网 HTTPS，**不必买服务资源包**（那只为连 TDSQL-C 内网） | ✅ 同机自建 | ✅ 同机自建（零延迟） |
| 存储 | 须用云托管自带对象存储（COS，5GB 免费额度） | 同 L3 | 同机/COS 均可 |
| 其他硬伤 | **OCR 是 Python 侧车 ⇒ 必须单独建服务或打多阶段镜像**（新增工程量） | **依赖云开发免费环境（发布后 15 天计时）** | 无 |
| 阻塞项 | 无（但改造量最大：文件链路 + OCR 拆分） | 需 B/C 两项人工验证 | **域名备案 7–20 工作日** + 个人主体命名口径 |
| 结论 | **能立刻上线，但改造最重** | **过渡通道** | **长期最优** |

### 3.2 怎么选：先答一个问题——「今天就要上线吗？」

**结论修正（2026-10-30 第二轮）**：上一轮写「L1 放弃作主线」，理由是"投入产出倒挂"。在 CloudBase PG 出现后，这个理由**有一半不成立了**——L1 最贵的分支（迁库需买服务资源包做内网互联）可以绕开，改走公网 HTTPS 即可。所以改为**按时间压力分岔**，不做一刀切否定。

| 你的约束 | 选 | 要付的代价 |
|---|---|---|
| 尽快让真机/体验版跑通完整链路 | **L1** | 15s（长任务只能走 jobs，**已实现**）+ 1000KiB 返回包 + 文件链路重写 + **OCR 单独建服务** |
| 可以等 7–20 个工作日 | **L3** | 等备案；但四条上限全无，PG/OCR/后端同机，最省心也最省钱 |
| 两者都要（先跑通、再迁） | **L2 过渡 → L3 落地** | 过渡期绑在云开发免费环境（发布后 15 天计时，见 §1.2-5） |

不变的三条判断：

- **L2 不能当地基**：改造成本最低，但寿命绑在云开发免费环境上（15 天计时 / 12-31 活动截止 / 限额未写入文档）。
- **L3 仍是长期最优**：唯一同时满足「无 15s 天花板、存储自持、无第三方政策开关、同机零延迟」的路线。
- **T1-α / T1-β（迁库 + 容器化）三条路线共用**，换路线不作废——这是为"不推倒重来"做的结构性设计。**迁库这件事无论走哪条路都要做，先做不亏。**

### 3.3 分阶段（标注哪些投入不作废）

| 阶段 | 内容 | 依赖 | 换路线是否作废 |
|---|---|---|---|
| **T0**（今天，15 分钟 + 0 元） | 跑 §1.4 三项人工验证（**A/B 已过一半：能进界面**）；**启动域名备案**（最长链路先跑） | 你扫码 | 不废 |
| **T1-α**（0.5 天，**建议先做这个**） | 建 **CloudBase PG** 环境 → 实跑 19 个 migration（`ExecutePGSql`，单条）→ 补 `/rest/v1` → `/v1/rdb/rest` 路径重写（§2.6 方案 1）→ 用现网数据跑通 `/api/timeline` | 环境已建（免费 6 个月） | **不废**（三条路线都要"路径处理层"；若 CloudBase PG 受阻，退回自装 PG + PostgREST，只换反代目标） |
| **T1-β**（1 天，与备案并行） | 存储迁 COS 并新增 `s3` 驱动；后端容器化；全量跑 `verify` 套件 | 视路线 | **不废**（L1/L2/L3 都要容器化与迁存储） |

| **T4** | 提审上线 | T3 | — |

> **T1-α 排在最前的理由**：先把"数据落地"做完，再动"流量入口"。这样即使备案被驳回、必须退回 L1/L2，T1 的工作 100% 保留。迁库是三条路线**唯一的公共前置**——做完它，"能不能上线"这个问题就从"数据库在国外"退化成"只剩入口选择"。

### 1. 扣子时代「没备案也能跑」的真实机制（2026-10-19 实证）

用户此前的印象是"自托管 NestJS 且未备案也能运行"。考证仓库证据后澄清——**当时并非自托管，也没有任何绕过手段**：

#### 1.1 后端跑在扣子平台基础设施上

仓库根目录 `.coze`（扣子项目清单文件）：

```toml
project_type = "miniprogram"
template = "taro"

[deploy]
build = [ "bash", ".cozeproj/scripts/deploy_build.sh" ]
run   = [ "bash", ".cozeproj/scripts/deploy_run.sh" ]
```

NestJS 由扣子平台构建、运行、提供对外域名（`COZE_PROJECT_DOMAIN_DEFAULT`，构建时注入前端 `PROJECT_DOMAIN`）。服务器与域名均为扣子所有，平台域名由平台方备案——**用户侧无需备案任何东西**。

#### 1.2 小程序全程只有开发版

旧 `project.config.json`（合并前基线）：

```json
{ "appid": "touristappid", "setting": { "urlCheck": false } }
```

微信官方规则：开发者工具关闭域名校验后，模拟器可请求任意 http/https 地址，**合法域名白名单与备案规则不生效**——这是开发阶段的正式豁免。用户已确认扣子侧仅到「开发版」，从未发布体验版/正式版。

#### 1.3 扣子预览通道不是微信客户端

扣子 IDE 预览为扣子自建 WebView 容器，不走微信域名策略；扣子作为第三方平台服务商（曾占"小程序开发与数据分析"授权）代管上传。

> **借鉴**：判断一个"当年怎么跑起来的"问题，先分清「平台托管 / 自托管」与「开发版 / 体验版 / 正式版」两个维度，多数"豁免"只是未进入受限场景。

### 2. WorkBuddy 域名为何不能当小程序 API 后端（2026-10-19 线上实证）

#### 2.1 现象

小程序（DevTools 与真机同）请求 `https://growing-kids.app.workbuddy.host/api/*` 一律 **403**；`curl` 同地址全部 **200**。

#### 2.2 定位过程（全部可复现）

| 测试 | 结果 |
|---|---|
| 无特殊头 curl | 200 |
| `Referer: https://servicewechat.com/...` | 200 |
| `User-Agent: Mozilla/5.0 wechat miniprogram` | 200 |
| **`User-Agent` 含 `MicroMessenger`** | **403**（3/3 确定性，非限流） |
| 空 UA | 200 |

403 响应体标题为「**请在浏览器中打开**」，带腾讯网关头 `Acp-Connection-Id`。后端源码 0 处 `ForbiddenException`、无全局 guard/限流（`app.module.ts` 仅中间件）。

#### 2.2b 2026-10-20 换新域名后复测（同一结论，排除偶发）

迁移到 `d02753307b5b4364b073bee6f42a4e70.app.workbuddy.host` 后重跑，四组对照：

| UA | http_code |
|---|---|
| iPhone 真机完整 UA（含 `MicroMessenger/8.0.49` + `MiniProgramEnv/iPhone`） | **403** |
| `GrowingKidsSmoke/1.0`（普通 UA） | 200 |
| 仅 `MicroMessenger/8.0.49` | **403** |
| 不带 UA | 200 |

⇒ 拦截判据就是 **UA 是否含 `MicroMessenger` 子串**，与域名、路径、Referer 无关。403 体为「请在浏览器中打开」HTML，非后端产生。

#### 2.3 结论

`app.workbuddy.host` 是 **WorkBuddy「应用发布」的浏览器分享链接通道**，边缘网关拦截微信 UA。微信 `wx.request` 固定携带 MicroMessenger UA 且基本不可覆盖 → **小程序无法连接部署在该域名的后端**。

叠加约束：即便无 UA 拦截，正式小程序后端域名必须进 MP 后台「request 合法域名」（要求 HTTPS + 域名所有者可验证 = 需 ICP 备案），平台子域无法验证所有权 → **本来就不能当生产小程序后端**。

> **借鉴**：小程序后端选型先过两关：① 目标域名是否拦截微信 UA；② 能否进入合法域名白名单（备案 or 腾讯官方域名 or callContainer）。

#### 3.5 WorkBuddy 云服务的小程序专用通道（2026-10-20 新发现）

读官方 `cloud-service` 技能 `references/mini-program/routing.md`（C2 节）得到两条此前未知的事实：

1. **小程序不用应用自己的域名，而是固定网关**
   `publicConfig.endpoint` = `mp-api.app.workbuddy.host`（生产）/ `mp-api.app-staging.workbuddy.host`（staging）。
   原因：微信 request 合法域名不支持通配、且有条数上限，按应用分配域名无法规模化，故所有小程序共用这一个已备案网关。
2. **发布流程自动注册白名单**（关键）
   原文：「The same host is registered **idempotently** in WeChat's request / upload / download allowlist **by the publish flow before the code is uploaded**, so a release needs no manual domain setup.」
   ⇒ 这解释了 MP 后台显示的「服务器域名已托管给第三方」——本项目的第三方平台正是 **WorkBuddy 小程序三方服务商**，域名管理权在它手里，用户无需、也无法在 MP 后台手动改。

**但能力边界没变**：云服务只有 Database / Auth / Storage / LLM 四模块，**没有容器、没有云函数、没有长驻运行时**。
本项目后端 63 个 ts / 21 模块（NestJS + `@nestjs/schedule` + multer + pdf-lib/docx + Python OCR 侧车）**无法部署上去**，
「迁过去」实质等于把后端业务重写成前端直连 BaaS，且文档型库要重设计 drizzle schema。

> 文档同时警告：不要直接 curl 探测该网关、不要据直连结果改写 `endpoint`——网关只转发带 `publishableKey` + `Referer: https://servicewechat.com/{appid}/...` 的签名请求，
> 裸请求回落到「链接已失效 / 该应用尚未发布」是**预期行为**，不是域名错误。

   **⚠️ 2026-10-25 复核补记——Supabase 跨境延迟的完整解法（按推荐序）**：

     可达 1.5s）降到 <1ms。代价 = 自己管备份（pg_dump 定时 + 异地副本）与故障恢复。

     schema 原样）。这就是《迁移到腾讯云-方案与步骤.md》里既定的第二步，云托管 + 云数据库同地域部署即可。
   - **③ 微信云托管自带 MySQL**：计价表里有，但 Postgres→MySQL 是伤筋动骨的迁移（JSONB/57 处查询），**不选**。

### 7. 多云适配度评估（2026-10-25，微信云 / 阿里云 / 百度云 / 运营商云）

本项目选型的约束按重要性排序：**① 微信小程序后端免备案通道（callContainer 只有微信云托管有）→ ② NestJS 长驻 + OCR 重 CPU + 定时任务（容器平台）→ ③ 国内延迟 → ④ Postgres 内网可达 → ⑤ 成本（¥0-50/月）**。

| | 微信云托管 | 阿里云 | 百度云 | 运营商云（天翼/移动/联通） |
|---|---|---|---|---|
| callContainer 免备案 | ✅ **独占** | ❌ | ❌ | ❌ |
| 微信生态协同（openid 透传/服务通知） | ✅ 原生 | 手动 | 手动 | 手动 |
| 容器产品成熟度 | 中（单端口/单镜像限制） | **高**（ACK/ASK 全家族） | 中（CCE 可用） | 中低 |
| 国内节点与延迟 | ✅ | ✅ | ✅ | ✅ |
| 数据库内网可达（PG） | ✅（VPC 配置，见 §5.4） | ✅（RDS PG） | ✅ | ✅ |
| 与混元生态协同 | ✅ 同生态 | 跨云调用 | 跨云 | 跨云 |
| 开发者生态（文档/SDK/社区） | 微信场景强 | **最强** | 弱 | 弱 |
| 结论 | **首选**（约束①只有它满足） | 愿意备案后的第二选择 | 无差异化优势 | 仅政企合规/特殊价格时考虑 |

**结论**：不是因为技术最强，而是**约束①（免备案 + 微信生态原生）只有微信云托管满足**；若未来愿意备案且要更强基础设施能力（多产品线、可观测性、编排），阿里云是合理的第二选择（届时 callContainer 优势消失，拼产品成熟度）。百度云与运营商云对本项目无差异化优势。
**计费拆细的逻辑**（答"为什么分这么多种计费项"）：每类资源成本结构不同——CPU/内存是时间资源（实例活着就烧钱，与忙闲无关）按核·小时；流量是带宽资源按 GB；构建是 CI 机器时间按分钟（防滥用 + 引导用户自管镜像）；存储是空间×时间按 GB·天；操作次数有固定机器开销（数据量为 0 也花钱）按万次。拆得越细，**用户越只为真实消耗付费、能逐项优化，平台越能精确覆盖成本、提高多租户资源周转**（也是敢送 3 个月免费额度的底气——多数试用者根本用不完）。代价是账单复杂度，需盯费用中心。

### 8. 2026-10-29 增补：小程序 ICP 备案通过后的状态更新与最新建议

#### 8.1 一条必须先分清的事：两条备案，两把不同的锁

2026-10-29 小程序 ICP 备案通过（**陕ICP备2026030931号-1X**），最容易误读成"备案搞定了，后端也能上了"。**不是。** 这是两条完全独立的链，锁的是两件不同的事：

| | 小程序 ICP 备案 | 域名 ICP 备案 |
|---|---|---|
| 备案对象 | 小程序本身（名称、服务内容、主体信息） | 域名 + 其接入的大陆服务器 |
| 提交入口 | mp 后台（备案专项入口） | 域名接入服务商（腾讯云/阿里云等）→ 管局终审 |
| **解锁什么** | **能否提交代码审核、能否发布上线**（平台侧前置） | **正式版 `wx.request` 能否访问该域名**（request 合法域名白名单前置） |
| 本项目状态 | ✅ **已通过**（2026-10-29） | ❌ **未办**（无域名、无大陆服务器；后端仍是 `http://192.168.3.242:3001`） |
| 用户侧可见 | 备案号自动展示在小程序「更多资料」页 | 无（网站侧才需展示） |
| 周期 | 已走完 | 7-20 工作日（个人主体，部分省份受限） |

> **⇒ 由此定一条用词规矩**：本文与 GK 文档此后凡提"备案"，必须带定语（小程序备案 / 域名备案）。
> 笼统的"备案已通过"会让下一个读文档的人直接踩坑——以为可以配白名单了。

#### 8.2 备案通过实际改变了什么、没改变什么

**真正改变了三件事（都写进发布清单）：**

1. **「提审」这条前置条件满足了。** 此前即便代码全好，没有备案号也提交不了审核；现在可以走「体验版 → 提审 → 发布」全流程，只剩后端可达性这一关。
2. **备案时填报的服务类目成为约束。** 备案信息与实际运营需一致——后续若扩类目（例如将来升企业主体、加 AI 类目），**备案要一起变更**，不是只改 mp 后台。
3. **隐私政策里"运营者与备案信息"从空承诺变成事实。** 该节此前写不出编号，现在可写；且备案号在「更多资料」页自动可见，前后一致。

**没改变的三件事（选型结论一个字都不用改）：**

1. 后端域名仍进不了正式版白名单 ⇒ 路线仍是 **A 局域网 / B 云托管 / C VPS** 三选一。
2. `app.workbuddy.host` 依旧不能当后端（UA 拦截 + 平台子域无备案）——§2 结论继续有效。
3. `wx.cloud.callContainer` 仍是唯一"完全绕开域名"的通道——它省的是**域名备案**，与小程序备案无关。

#### 8.3 最新建议（2026-10-29 二次校正：B2 已被官方否决）

**先纠一条自己写错的结论**：本文与 `GK-OPS-19` §3.1 都把 **B2（云托管默认公网域名 + `wx.request`）**当成"只需 10 分钟验证"的优选，理由是"关联小程序后域名可能自动进白名单"。

2026-10-29 复核官方文档，**该假设不成立**。《微信云托管 · 开发常识》（developers.weixin.qq.com）原文：

> 「默认公网域名性能有限制，仅能支持接口测试使用，请勿用于正式生产环境。**小程序后台也无法配置使用默认公网域名。**」

同一页另一句是唯一真正的豁免：

> 「小程序/公众号可使用 CallContainer，**无需域名，因此不需要在 mp 管理后台配置服务器域名，从而一开始就无需申请域名，也无需备案**。」

顺手把"云托管绑自定义域名"也排掉：官方要求「自定义域名**仅支持已备案的域名**进行绑定」——那等于把域名备案又请回来。

⇒ **B2 不是"待验证"，是不可行。** 云托管能免的只有一条：走 `callContainer`。

##### 于是只剩一个真二选一（B1 与 C 的取舍）

| | **B1 · `wx.cloud.callContainer`** | **C · 自有服务器 + 已备案域名** |
|---|---|---|
| 免域名备案 | ✅ 官方明示免（免域名、免配白名单、免备案） | ❌ 必须（个人 7-20 工作日） |
| 前端改造 | **大**：图片上传要从 `wx.uploadFile` 改 `wx.cloud.uploadFile` 换 fileID；`callContainer` **超时 ≤15s、请求体 ≤100KB**（不能带图） | **几乎为零**：`PROJECT_DOMAIN` 换一个常量 + 配 request/uploadFile/downloadFile 三类白名单 |
| 后端改造 | NestJS + Python OCR 打进**同一镜像**（1.5–2 GB）、单端口、不支持 Compose | 无（Compose 可把 OCR 侧车拆成独立容器） |
| 主要风险 | **动核心链路**（图片识别是本项目主功能），改坏要用真机回归 | **动运维**（证书、备份、安全更新、磁盘/带宽） |
| 首次可用耗时 | 3-5 个工作日（改造 + 联调） | **7-20 工作日（等备案）** + 1-2 天部署 |

**关键判断：两条路的"等待时间"同量级**（改代码 3-5 天 vs 等备案 7-20 天），差别是**风险落在代码还是落在运维**。

##### 推荐（按目标分，不再有"免备案且零改造"的第三条路）

1. **只想给家人朋友用（体验版）**：两条都不必现在做。体验版开「开发调试」可绕过域名校验（QA-16 4.5.13 末段），先把功能验完。
2. **要发正式版、且代码改动越少越好** ⇒ **走 C**。现有 `wx.uploadFile → multer` 一行不改、OCR 侧车可独立容器。代价是备案周期 + 自管运维。
3. **要发正式版、且绝不想碰域名备案** ⇒ **走 B1**。必须接受：① 图片链路重写；② OCR 与 NestJS 同镜像、单端口，0.25 核规格带不动、冷启动变慢。

> ⚠️ **不要走"云托管 + 自定义域名"**：它既要备案、又要改镜像，把两条路的成本都付了，只省了运维。除非将来已有备案域名在手、又确实想要免运维，否则不选。

##### ⚠️ 一条容易漏掉的前置约束：当前"开发权限托管"本身就会否掉路线 C

本项目 mp 后台显示「开发管理已禁用，开发权限已托管给第三方」——这**不只是隐私指引进不去**，它同时意味着：

> 官方规则：小程序授权托管后，**只能使用第三方平台在微信开放平台登记的服务器域名** ⇒ 自己配 `request / uploadFile / downloadFile` 白名单**做不到**（`GK-QA-16` 4.5.12 影响 #2）。

⇒ **路线 C 在"保持托管"的前提下走不通**（代码再好，域名也进不了白名单）。
而 **B1 不受影响**——`callContainer` 恰恰不需要配任何服务器域名。

于是真正的决策矩阵变成：

| 你的选择 | 后端路线 | 隐私指引怎么办 | 代价 |
|---|---|---|---|
| **保持托管**（现状，不动） | 只能 **B1** | 托管面板 / 托管方代配 | 改图片链路；改完也不能配域名 |
| **解除托管**（管理员扫码，1 分钟） | 可走 **C** | 后台入口恢复，自己配 | 版本管理只剩自己上传的版本；托管方登记过的域名要逐条复核；上传/提审改走开发者工具 |
| **只发体验版自用** | 都不必做（开「开发调试」） | 仍需配（否则相册/剪贴板报 `errno 112`） | 无 |

**⇒ 如果这是要给真实用户用的正式版，我的建议是「解除托管 + 走 C」**：一次操作同时解决"域名白名单配不了"和"隐私指引配不了"两件事，而 B1 要动的是本项目最核心的图片识别链路。解除的操作与后果清单见 `GK-QA-16` **4.5.12**（本项目授权列表里只有 WorkBuddy 一个第三方，只需解它一个）。

### 9. 2026-10-30 全面复核：规则现状、路线重估与可上线设计方案

> **触发**：思傅要求「按各服务商最新规则复核、别拿旧规定当结论、别白费力气最后发现此路不通、数据库能迁回国内就迁回」。
> **方法**：只采信三类证据——官方文档原文（标注最后编辑日期）、本仓库代码/日志实测、社区公开记录（标注为参考）。**凡无出处支撑的判断一律标 `【待穿刺】`，不进决策、不写进代码计划。**

#### 9.1 三句话结论

1. **原文档的大方向没错，但有 4 条关键参数过时或被误读**：`callContainer` 真实可用超时是 **15s 不是 60s**；云托管直连腾讯云数据库**要先买服务资源包**；出现了 2026 年才有的新通道 **AnyService**；云开发**免费体验环境在小程序上线后 15 天到期**。这四条里任意一条踩空，都会在"改造做完、准备上线"那一刻才发现要返工。
2. **"发正式版"的真正卡点不是后端选型，而是「开发管理托管给第三方」**。只要保持托管，`request/uploadFile/downloadFile` 白名单就配不了——这直接判了 C 路线死刑，跟后端代码写得多好无关。而解除托管是管理员扫一次码的操作，且**同时顺手解决隐私指引进不去**的老问题。
3. **数据库必须迁回国内，而且有一条几乎零改造的路**：后端只用了 Supabase 的 PostgREST 部分（`.from()` 218 处），**完全没用 Supabase Auth、也没用 Supabase Storage**。在国内自建 Postgres + PostgREST，`supabase-js` 只改 URL 与 KEY，218 处查询一行不改。理由不只是"延迟低"，而是**现网已经在偶发挂死**（见 §9.6.1）。

| | **L1 · 云托管 + callContainer** | **L2 · 轻量 + AnyService** | **L3 · 轻量 + 域名备案 + `wx.request`** |

#### 9.6 数据库迁回国内（思傅第三条要求，也是本方案的最高优先级）

##### 9.6.1 为什么不是"更好"，而是"已经出事"

这不是选型偏好，本仓库里已经留下了故障证据：

| 证据 | 内容 | 等级 |
|---|---|---|
| `server/src/storage/database/supabase-dns-pin.ts` 文件头 | 2026-10-22 实测：本机对 `supabase.co` 的官方 Cloudflare IP 及大量同网段 anycast IP **被网络层随机封锁——TCP 可连但 TLS/HTTP 挂死**（`Connect Timeout`），**封锁面以数分钟为周期漂移**：18:47 时 6 个备用 IP 全通，20:26 只剩 1 个能通。公共 DNS 返回的始终是同样两个被封 IP，**故不是 DNS 污染而是 IP 级封锁** | **B** |
| 该文件的对策 | 维护 ~24 个跨网段候选 IP + **TLS 层探针**（因为被封 IP 的 TCP 能连、握手挂死）+ 补丁 `dns.lookup` 按实测延迟排序 + **每 5 分钟重探** | **B** |
| 接口耗时 | `/api/timeline/overview` 实测 **5777 / 8107 / 6678 ms**（同期 `/api/timeline` 仅 1–3 s） | **B** |

> **判断**：一个家庭级应用为了连数据库要维护 IP 池、TLS 探针和 5 分钟重探，本身就说明这条链路不该出现在生产里。**把它迁回国内不是优化项，是止血项。**

##### 9.6.2 三条迁法（按成本从低到高）

| | **A · 自建 Postgres + PostgREST**（推荐） | **B · TencentDB for PostgreSQL + PostgREST** | **C · 全量改写 drizzle/pg** |
|---|---|---|---|
| 218 处 `.from()` | **一行不改** | **一行不改** | **全部重写** |
| 工作量 | 0.5–1 天（装 PG + 跑 PostgREST + 迁数据 + 验证） | 1–2 天（多了实例开通、白名单、SSL） | **2–3 周**，且上线前做等于自找回归 |
| 月成本 | **¥0**（与后端同机） | 百元量级 | ¥0 |
| 延迟 | **<1ms（同机回环）** | 1–3ms（同 VPC）/ 公网另计 | 同左 |
| 运维 | 自己管备份（**已有 `db-backup.mjs` / `db-restore.mjs`**） | 平台托管 | 同 A |
| 风险 | 多维护一个组件（PostgREST），版本兼容需穿刺 | 成本高；且云托管连它还要买服务资源包 | 工期不可接受 |

**为什么 A 可行——这是本节最关键的一条实测**：后端对 Supabase 的依赖面只有 PostgREST 那一层。

| 依赖面 | 实测量 | 结论 |
|---|---|---|
| `supabase-js` 查询（`.from()`） | **218 处**，分布在数十个 service | 都是标准 PostgREST 语义（`select`/`eq`/`order`/`limit`/`maybeSingle` 40 处/`single` 17 处/`upsert` 3 处/`or` 4 处） |
| Supabase **Auth** | **0 处** | 项目用自己的 `X-Auth-Token` + `users` 表，**不需要部署 GoTrue** |
| Supabase **Storage** | **0 处**（`storage.service` 是自有实现，`STORAGE_DRIVER` 可取值 `local` 或 `supabase`，**默认 local**） | 若生产用 `local`，文件就在磁盘上 ⇒ **迁库不涉及文件迁移** |
| `.rpc()` | **1 处**，在 `supabase-db.provider.ts` 调 `exec_sql` | 该 provider 属双写抽象层，PostgREST 不提供任意 SQL 执行 ⇒ **迁库时确认它未启用**，勿走此路 |

> 换句话说：**Supabase 在本项目里被当成"一个 Postgres 的 HTTP 壳"在用**。换掉壳，218 处查询不用动。这是 0.5 天和 3 周的区别。

##### 9.6.3 落地步骤（A 方案）

| 步 | 做什么 | 判据（做没做对） |
|---|---|---|
| 1 | 轻量（上海）装 PostgreSQL 16（Docker），建业务库与低权角色 | `psql` 能连；`migrations/` 可跑 |
| 2 | **从 Supabase 导出**：在服务器上跑 `server/scripts/db-backup.mjs`（NDJSON + gzip + AES-256-GCM，已有），连接串用 Supabase 的**直连 5432**（不用 pooler 6543） | 产出归档文件且**立即读回自检通过**（脚本自带） |
| 3 | `db-restore.mjs` 灌入国内库 | 逐表行数比对一致；`schema_migrations` 已建 |
| 4 | 起 PostgREST 容器，配置 `PGRST_DB_URI` / `PGRST_DB_SCHEMAS=public` / `PGRST_DB_ANON_ROLE` / `PGRST_JWT_SECRET` | 容器健康；直连端口能返回 JSON |
| 5 | **Caddy/Nginx 反代**：把 `/rest/v1/*` 剥前缀转发到 PostgREST（`supabase-js` 一定会拼 `/rest/v1`，PostgREST 自身不吃这个前缀） | `curl /rest/v1/users?limit=1` 返回 `[...]` |
| 6 | 自签 anon JWT（HS256，`role=anon`）与 service_role JWT | PostgREST 接受；无 JWT 时按 anon 处理 |
| 7 | 后端 `.env`：`SUPABASE_URL=http://127.0.0.1:<port>`、`SUPABASE_ANON_KEY=<自签>` | `/api/timeline/overview` 从 5–8s 降到 **<300ms** |

**为什么 URL 可以是 `http://127.0.0.1`**：后端是唯一调用方，与 PostgREST 同机，不需要公网 HTTPS、不需要域名、不需要证书。"自建 Supabase 要配一整套"的复杂度在这里被消掉了 90%。

##### 9.6.4 必须实测的兼容点（`【待穿刺】`）

| 点 | 为什么可能踩坑 | 怎么验 |
|---|---|---|
| `supabase-js@2.95.3` ↔ PostgREST 版本 | `maybeSingle()`/`single()` 依赖 `Accept: application/vnd.pgrst.object+json`，老版本 PostgREST 行为不同 | 起容器后跑一遍 `maybeSingle` 与 `upsert` 的等价 curl |
| 权限 | 本项目 **RLS 未启用**，现网靠 `.eq('user_id', …)` 过滤 | PostgREST 的 anon 角色需 `GRANT SELECT/INSERT/UPDATE/DELETE`；**RLS 仍未启用 ⇒ 安全边界不变，但也别因此以为更安全** |
| 数据类型 | `JSONB`、数组、`timestamptz` 的返回形态 | 抽 3 张表（`timeline_items`/`blob_objects`/`users`）做往返比对 |

##### 9.6.5 一条不想写但必须写的实话

迁库后会失去 Supabase 控制台的"可视化运维"（表浏览、SQL 编辑器、日志）。**换来的是 <1ms 延迟、不再被黑洞、账单归零。** 对本项目（单用户家庭级、数据量小、维护者只有一人）这笔交换是划算的；但如果将来要做多租户 SaaS，应该回到 B 方案（托管 PG），而不是继续自建。

#### 9.7 推荐方案：分三阶段，把"不可逆投入"压到最低

**推荐主线 = L3（解除托管 + 域名备案 + 轻量自建全栈）**，理由不是它最先进，而是**它唯一同时满足"数据库回国 + 无 15s 天花板 + 无政策地基风险 + 成本最低"**。代价是等备案 7–20 个工作日——而这恰好可以被其他工作填满。

| 阶段 | 时间 | 做什么 | 产出 / 为什么现在做 |
|---|---|---|---|
| **T0 · 穿刺** | **今天，1–2 小时** | 跑 §9.8 的 5 项验证 | 拿到"能不能走"的确定答案，**避免投入后才知此路不通** |
| **T1 · 并行启动（不阻塞）** | 今天起 | ① 买域名 + 提交**域名备案**（0 元，最长链路先跑）② 买上海轻量 4核4G ③ 后端 Docker 化 ④ 按 §9.6 迁库 | ①②只花等待；③④三条路线共用，**不因换路线作废** |
| **T2 · 上线** | 备案下来后 1–2 天 | 解除托管 → 配 4 类域名白名单 → 上传体验版 → 真机回归 → 提审 | 解除托管同时**恢复隐私指引入口**（4.5.12 清单），一并解决老问题 |
| **兜底** | 随时 | 若必须"本周就给真实用户用"：走 **L2**（轻量 + AnyService），付云开发个人版 ¥19.9/月 | 因 T1 已完成，L2 只需**加一层接入配置 + 改请求通道**，1–2 天可切；**这就是"不推倒重来"的保险** |

**关于"要不要解除托管"的判断标准，一句话**：

> 只想给家人朋友用体验版 ⇒ **不用解除、不用备案**，现状 + 开「开发调试」即可（QA-16 4.5.13 末段）。
> 要发**正式版给真实用户** ⇒ **必须解除**，因为托管状态下白名单只能填第三方平台的域名（§9.3-⑦，官方原文），这与代码质量无关。
