## 1. 最终形态

### 1.1 架构

```
微信小程序
   │  https://<域名>/api/*          ← ICP 已备案域名 + 受信 CA 证书
   ▼
┌──────────────────────── 轻量应用服务器（2核4G / 50G SSD，上海） ────────────────────────┐
│                                                                                      │
│  Caddy  监听 0.0.0.0:80,443          [自动 HTTPS，自动续期]                            │
│    ├─ /                → 静态说明页（/srv/www）  ← 备案要求"首页不能是空目录"           │
│    ├─ /api/*           → 127.0.0.1:3000   NestJS                                      │
│    └─ 127.0.0.1:8080 内部站点（不对外）                                                 │
│         └─ /rest/v1/*  → 127.0.0.1:3001   PostgREST（handle_path 自动剥前缀）           │
│                                                                                      │
│  NestJS  :3000（仅 127.0.0.1）                                                        │
│    ├─ supabase-js → http://127.0.0.1:8080/rest/v1/…   → Caddy → PostgREST             │
│    ├─ 文件落盘    → /var/lib/gk/storage（STORAGE_DRIVER=local）                        │
│    └─ spawn python → 127.0.0.1:9000  OCR 侧车（15 分钟空闲自动回收）                    │
│                                                                                      │
│  PostgreSQL 17  :5432（仅 unix socket / 127.0.0.1）                                    │
│  PostgREST       :3001（仅 127.0.0.1）                                                 │
└──────────────────────────────────────────────────────────────────────────────────────┘
```

### 1.2 为什么五个进程都要挤在一台机

| 组件 | 能不能省 | 理由 |
|---|---|---|
| PostgreSQL 17 | 不能 | 19 个 migration 是 PG 方言；CloudBase PG 只能公网 HTTPS 访问且到期 ¥19.9/月 |
| PostgREST | 不能 | 后端 218 处 `.from()` 全靠它；改 drizzle 要重写 218 处 `[A]` |
| NestJS | 不能 | 业务后端 |
| Caddy | 不能 | 证书自动化 + 静态首页 + 前缀剥离，三件事一个进程 |
| OCR 侧车 | **可降级** | 只跑 `rapid` 引擎时内存 ~400MB；跑 `paddle` 时 ~1.2GB |

### 1.4 为什么这个后端不能用云函数 / 云开发跑

这一节是为了回答"既然有云开发，为什么还要买机器"。**结论不是"配置不够"，而是"函数"和"进程"的范式冲突。**

先把两套东西分清楚，它们的限制差一个量级：

| 维度 | 微信侧云开发（`wx.cloud.callFunction` 事件型） | 腾讯云侧 CloudBase（HTTP 云函数） |
|---|---|---|
| 超时上限 | **60 秒**（默认 3s，可调至 60s 封顶） | 普通函数 900s / HTTP 函数 7200s |
| 内存上限 | **2048MB** | 3072MB |
| 单个函数代码包 | **50MB** | 同上 |
| 同步请求 / 响应 | **各 6MB** | — |
| 运行时 | 创建时只有 Node.js | Python 3.11 / NestJS 均支持 |

`[B]` 前两列出自腾讯云《云开发 CloudBase 产品简介》PDF 系统限制表；后两列出自 `docs.cloudbase.net/cloud-function/function-configuration/config` 与 `/runtime-support`。
**两个官方来源数字不一致**（60s vs 900s、2048MB vs 3072MB），因为前者是微信小程序封装的云开发、后者是腾讯云侧的 CloudBase。本项目从微信侧进，按 **60s 封顶**取值。

**但真正的阻塞不在这些数字上——就算给 900 秒，一样跑不了。**五条按严重度排列：

| # | 硬限制 | 对本项目的具体后果 |
|---|---|---|
| **1** | **实例短生命周期、函数返回即冻结/回收**（`[B]` 官方产品模型原文："任务完成后，资源立即释放"） | **致命**。本项目 `async_jobs` 的 job 表活在**进程内存**里（`jobs.service.ts`）。提交任务的实例与轮询 `GET /api/jobs/:id` 的实例**不是同一个进程** ⇒ 任务提交成功、轮询永远查不到，实例一回收任务就消失。加内存、加超时都改不了 |
| **2** | **没有"常驻进程"，因而没有"侧车"这个概念** | 云函数是被动触发的单进程，不能起一个监听 3001 的常驻服务，也不能跑常驻 worker 轮询任务表。要跑 OCR 只能另建一个 HTTP 云函数，**每次冷启动重新加载 det/rec/cls 三个模型**（1GB 量级，10–30 秒），PaddleOCR 首次推理还要预热 |
| **3** | **没有持久磁盘**（`/tmp` 随实例回收清空） | `STORAGE_DRIVER=local` + `STORAGE_LOCAL_DIR` 落盘方案直接失效，必须改对象存储（COS）并新增 s3 驱动。而 L3 下这段代码**零改动**，这正是 §8-2 那条修正的价值 |
| **4** | **单个函数代码包 50MB** | `server/` 构建产物 + `node_modules` 已接近该量级，`paddlepaddle` wheel 单包 100MB+ ⇒ 塞不进去。改走 COS 挂载能绕过体积，但冷启动更慢 |
| **5** | **超时上限** | 本项目 OCR 实测峰值 **86.8 秒** `[A]`（`async_jobs` 就是为它建的）> 微信侧 60s 封顶 ⇒ 直接失败 |

**一句话：这个项目要的是"一台常驻机器同时跑 PG / PostgREST / NestJS / Caddy / Python 五个进程，任务队列活在内存里"；云函数只能提供"一次性、无状态、用完即焚的函数"。**
第 1、2、3 条是形态问题，不是配额问题——**给多少钱都改不了**。

> ⚠️ 唯一例外：如果哪天把 `async_jobs` 改成**外部队列**（表驱动 + 独立轮询进程）+ **对象存储** + **OCR 换云 API**，
> 形态就与云函数兼容了。但那是**重写数据流**，不是"迁个后端"，与本文"不推倒重来"的前提冲突。

### 3.5 两条实施路线的取舍：先 L2 再 L3，还是直接 L3

> L2 的定义（沿用调研纪要 §3.2）：**后端仍跑在轻量上（与 L3 同机同构），差别只在接入层**——L2 用云开发 **AnyService** 免域名直连，
> L3 用自有域名 + 备案 + `wx.request`。两者后端形态一样，**所以 S1/S2 的工作两条路线共用**。

| 维度 | L2 先行 → 切 L3 | 直接 L3 |
|---|---|---|
| 备案下来前能否真机跑通 | ✅ 能（AnyService 免域名） | ✅ **也能**：开发者工具 + 真机开发版勾"不校验合法域名"，用 `IP:端口` 直连 |
| 前端传输层 | ❌ **要维护两套**（`callContainer` 一套、`wx.request` 一套），切换时全量回归 | 一套，不切 |
| 图片链路 | ❌ **必须改造**（`callContainer` 15s 超时、返回包 1000KiB、官方明写"不建议请求中带图"） | **不用改** |
| 文件存储 | ❌ 必须 COS，要给代码加 s3 驱动 | `STORAGE_DRIVER=local`，**零改动** |
| 验证有效性 | ⚠️ L2 跑通 ≠ L3 能用（存储、超时、图片三处行为都不同） | 开发环境即生产环境 |
| 备案等待期 | 被浪费（在等 L2 上线） | **并行**：S1/S2 正好填满 7–20 个工作日 |
| 额外成本 | 云开发个人版 ¥19.9/月 + 免费环境**发布后 15 天**到期 | ¥0 |
| 唯一独有优势 | 备案没下来也能发**正式版** | 正式版必须等备案 |

**结论：直接 L3。**理由不是省钱，是**L2 唯一的价值（绕开备案）在本项目不成立**：

1. **开发测试从来不需要备案。** 备案只在"发正式版"那一刻才卡；开发版/体验版用 IP 直连就能跑通全链路（本项目真机已这样跑过：`PROJECT_DOMAIN=http://192.168.3.242:3001`）。
2. **L2 期间额外做的两套传输层 + COS 改造，搬到 L3 全是废码或要回退**——这正是最该避免的"花大力气最后推倒"。
3. **活动机把 L3 的开发期成本压到 ¥109 起**，绕 L2 的经济理由也随之消失。

**L2 保留为退路，触发条件只有三条**：
- 备案因"教育类"被驳回、或管局超 20 工作日仍无结果（→ 短期用 L2 让真实用户先用上）
- §3.1.1 的 3Mbps 带宽实测证明不可接受（入方向实测见 §S0-2 验收项）
- 不想长期自己运维这台机器

切 L2 的代价可控：因为后端形态不变，只需加一层接入配置 + 保存一份原传输层，**1–2 天**可切（调研纪要 §4 D2 的口径）。

### S0 采购与备案启动（今天，1.5 小时）

#### S0-1 解除开发管理第三方托管【必须先做】

原因（`[B]` 官方原文）：授权第三方后，服务器域名**只能是第三方平台登记的域名**，通过第三方发布后**原有域名会被删除**。

验收：开发者后台 → 开发管理 → 开发设置 → 能看到「服务器域名」的**修改**按钮。

**2b) 登不进去时：用网页终端完成「首次装公钥」**

服务器只认密钥、而你的公钥还没写进去，这是新机最常见的第一步卡点。用控制台网页终端绕过 SSH 装入：

1. 实例页右上「**登录**」→ 打开 OrcaTerm 网页终端。
   若要求输入密码且你从没设过 ⇒ 先到实例详情点「**重置密码**」（用户选 `ubuntu` 或 `root`），等重启（1–2 分钟）后用新密码登录网页终端。
2. 在网页终端里执行（`KEY=` 后面换成你自己的公钥整行）：

```bash
KEY='ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI...你的公钥... 你的备注'

# ① 当前用户（ubuntu）：不需要任何特权，这一步必定成功
mkdir -p ~/.ssh && chmod 700 ~/.ssh
grep -qF "$KEY" ~/.ssh/authorized_keys 2>/dev/null || echo "$KEY" >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
ls -l ~/.ssh/authorized_keys            # 判据：存在、600、非 0 字节

# ② root（可选，走 sudo；不装也不影响登录）
echo "$KEY" | sudo tee -a /root/.ssh/authorized_keys >/dev/null && \
sudo chmod 700 /root/.ssh && sudo chmod 600 /root/.ssh/authorized_keys
```

> ⚠️ **不要用 `for u in ubuntu root` 的写法**（v1.8 曾这么写，实测报错）：以 `ubuntu` 身份运行时
> 对 `/root` 无写权限，会刷出四条 `Permission denied`。虽然 `ubuntu` 那轮其实已成功、错误无害，
> 但极易被误判成「整体失败」。`grep -qF` 是为了防止重复执行把同一把公钥写两遍。
> ② 若提示 `sudo: a terminal is required`，说明当前不是交互式 TTY，跳过即可——**root 登录本来就该关掉**
> （§S1-1 的 `PermitRootLogin no`），装它只是给自己留后路，非必需。日常提权用 `sudo` 就够。

3. 回到本机 PowerShell，`ssh ubuntu@42.192.36.120` 应当**直接进入、不再问密码**。

   仍报 `Permission denied (publickey)` 时，按序自查（见 §S1-0 的 2c）。
   若 ubuntu 用户不存在（个别镜像只有 root）⇒ 改试 `ssh root@42.192.36.120`。

**2c) 公钥装进去了仍 `Permission denied (publickey)` —— 按序自查**

在网页终端里逐条看，四条覆盖了绝大多数原因：

```bash
# ① 文件在不在、权限对不对（.ssh 必须 700，authorized_keys 必须 600，且属主是 ubuntu）
ls -ld ~/.ssh; ls -l ~/.ssh/authorized_keys; id -un

# ② 写进去的字符串，与本机 ~/.ssh/id_ed25519.pub 是否逐字一致（首尾不能有换行/空格差异）
cat ~/.ssh/authorized_keys

# ③ 服务端实际生效的认证方式（`sshd -T` 打的是生效值，不是文件里写的字）
sudo sshd -T | grep -E '^(pubkeyauthentication|passwordauthentication|authorizedkeysfile|permitrootlogin)'

# ④ 服务端到底怎么拒的（最近 20 行，看是 "key not found" 还是 "bad ownership"）
sudo tail -20 /var/log/auth.log
```

对照判据：

| `auth.log` 里的关键字 | 含义 | 处置 |
|---|---|---|
| `Authentication refused: bad ownership or modes` | `.ssh` 或 `authorized_keys` 权限/属主不对 | 回 ① 修正：`chmod 700 ~/.ssh && chmod 600 ~/.ssh/authorized_keys && chown -R ubuntu:ubuntu ~/.ssh` |
| `Failed publickey for ubuntu` + `key not found` | 公钥内容没对上 | 回 ② 比对，**整行**（含 `ssh-ed25519 ` 前缀与结尾备注）重写一次 |
| `Connection closed by authenticating user` | 家目录权限过宽（如 `/home/ubuntu` 是 777） | `chmod 755 /home/ubuntu` |
| 什么都没有 | 请求没到 sshd，或另有 ssh 实例 | `ss -tnlp \| grep :22` 看监听进程；`sudo systemctl status ssh` |

> 有一条最容易被忽略：**`.pub` 文件的最后一个换行/缺换行**。`echo "$KEY"` 会补一个 `\n`，
> 用 `nano` 手工粘贴时若末尾没回车，sshd 会认为最后一行不完整。② 的 `cat` 之后多按一次回车即可确认没被截断。

> 备路（网页终端也进不去时）：控制台「密钥对」→「创建密钥对」→ **导入已有公钥**（粘贴本机 `~/.ssh/id_ed25519.pub`）→
> 回实例「更多操作 → 绑定密钥对」（**需关机**）→ 开机后用本机私钥登录。比网页终端多一次重启，但不需要知道系统密码。

#### S1-1 系统加固

**先在你自己的电脑上准备密钥**（Windows PowerShell 自带 `ssh-keygen`，别再装 PuTTY）：

```powershell
ssh-keygen -t ed25519 -C "gk-l3"      # 一路回车即可；已有 ~/.ssh/id_ed25519 可跳过
type $env:USERPROFILE\.ssh\id_ed25519.pub    # 复制输出的整行（以 ssh-ed25519 开头）
```

**再在服务器上按序执行：**

```bash
# 1) 更新
apt update && apt -y upgrade

# 2) 建运行服务用的用户（systemd 里用它跑，不用它登录）
adduser --disabled-password --gecos "" gk && usermod -aG sudo gk

# 3) 装公钥：把上一步复制的那一整行粘进编辑器
mkdir -p ~/.ssh && chmod 700 ~/.ssh
nano -w ~/.ssh/authorized_keys        # 粘贴 → Ctrl+O 回车 → Ctrl+X
chmod 600 ~/.ssh/authorized_keys

# 4) 时区与 UTF-8（本项目 OCR 对编码敏感，见记忆 §1）
timedatectl set-timezone Asia/Shanghai
locale-gen en_US.UTF-8 zh_CN.UTF-8

# 5) swap：先查后建（⚠️ 云镜像通常已自带 /swap.img，重复建会白吃 2G 磁盘）
swapon --show                            # 有输出 ⇒ 已经有 swap，跳过 fallocate 那行
# 仅当上面为空时才执行：
#   fallocate -l 2G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
#   echo '/swapfile none swap sw 0 0' >> /etc/fstab
# 已有 swap 只调倾向性（4G 内存 + OCR，尽量别换出）：
sysctl -w vm.swappiness=10 && echo 'vm.swappiness=10' >> /etc/sysctl.conf
```

**关密码登录前，必须先在另开的窗口验证密钥能进**（这一步是防锁死的关键）：

```powershell
ssh -i $env:USERPROFILE\.ssh\id_ed25519 ubuntu@42.192.36.120
```

- 免密进去 ⇒ 继续下面的 sshd 加固；
- 仍要密码 / 报错 ⇒ **停下，别改 sshd**，先回去查 `authorized_keys` 的权限（700 目录 / 600 文件）与内容。

**验证通过后，再在服务器上关掉密码登录：**

```bash
# 🚨 Ubuntu 24.04 的 sshd_config 顶部有 Include /etc/ssh/sshd_config.d/*.conf，
#    同键以「首次出现」为准 ⇒ 子文件里的设置会覆盖主文件。
#    云镜像常在 50-cloud-init.conf 里写 PasswordAuthentication yes，
#    所以只 sed 主文件是无效的——加固会「看起来做了，其实没生效」。
grep -rn "^PasswordAuthentication\|^PermitRootLogin" /etc/ssh/sshd_config /etc/ssh/sshd_config.d/ 2>/dev/null

cat > /etc/ssh/sshd_config.d/00-hardening.conf <<'XEOF'
PasswordAuthentication no
PermitRootLogin no
XEOF

sshd -t                                  # 语法自检，必须先过
systemctl restart ssh
sshd -T | grep -E "passwordauthentication|permitrootlogin"
# 期望两行都是 no；若不是 no，说明还有更高优先级的文件在覆盖
```

> `00-` 前缀是为了让它在字典序上**先于** `50-cloud-init.conf` 被读取——同键首次出现者生效。
> `sshd -T` 打印的是**实际生效**的配置，比肉眼核对文件可靠。
> 🔴 万一真的把自己锁在外面：控制台实例页右上角「**登录**」（OrcaTerm 网页终端）照常能进，从那里改回来即可。


防火墙（轻量控制台的"防火墙"是云侧，系统内还要一层）：

```bash
ufw allow 22/tcp
ufw allow 80/tcp
```

#### S1-3 建库建角色

#### S1-4 装 PostgREST

> 🔴 **GitHub release 下载在腾讯云上被墙**（`curl` 返回 000、8 秒超时），但 **`api.github.com` 能通**。
> 实测可行路径：**在你自己电脑上下载 → `scp` 上去 → 比对 sha256**。2026-10-30 实测本机下载 3.59 MB / 1.25 MB/s，
> `scp` 后两端 `sha256sum` 逐字节一致（`9f71269e…5527c`）⇒ 不经第三方代理也能拿到干净二进制。

```bash

  "https://github.com/PostgREST/postgrest/releases/download/v12.2.3/postgrest-v12.2.3-linux-static-x64.tar.xz"
sha256sum postgrest.tar.xz          # Windows: certutil -hashfile postgrest.tar.xz SHA256

# 【上传到服务器】然后两端哈希必须一致
scp -i ~/.ssh/id_ed25519 postgrest.tar.xz ubuntu@42.192.36.120:/tmp/
ssh ubuntu@42.192.36.120 'sha256sum /tmp/postgrest.tar.xz'
```

```bash
# 【服务器上】
cd /tmp
tar -xJf postgrest.tar.xz && install -m 0755 postgrest /usr/local/bin/postgrest
postgrest --version          # 期望 PostgREST 12.2.3
```

> `[B]` 查最新版：`curl -s https://api.github.com/repos/PostgREST/postgrest/releases/latest | grep tag_name`
> （2026-10-30 为 **v16.5**）。本文固定用 **v12.2.3**，因为它与 `supabase-js` 2.x 的组合已有大量生产验证；
> 追新版本要重新验证 `Prefer: count=exact`、`on_conflict` 等契约（见调研纪要 §2.4）。
> 静态二进制无依赖，这是选 PostgREST 而不是"自己写一层 REST"的核心理由。

配置 `/etc/postgrest/gk.conf`：

```ini
# ⚠️ 必须走 TCP + 密码，不能用 unix socket 的 peer 认证（见下方说明）
db-uri = "postgres://authenticator:<密码>@127.0.0.1:5432/gk"
db-schemas = "public"
db-anon-role = "anon"
jwt-secret = "<64 字符 hex，用 openssl rand -hex 32 生成>"
server-host = "127.0.0.1"
server-port = 3001
db-max-rows = 2000
db-pool = 10
db-use-legacy-gucs = false
```

> 🔴 **不要照抄 `postgres://authenticator@/gk?host=/var/run/postgresql`**（本文 v1.10 及更早版本如此写，是错的）。
> 那是 **peer 认证**：PostgreSQL 会要求「**操作系统用户名 == 数据库角色名**」。而 systemd 里是
> `User=postgrest`、DB 角色叫 `authenticator`，两者不等 ⇒ 连接直接被拒。两个解法：
> ① 改 TCP + 密码（本文采用，`pg_hba` 对 `127.0.0.1` 默认就是 `scram-sha-256`）；
> ② 或者把 systemd 的 `User=` 改成 `authenticator`，同时建同名系统用户 —— 更绕，不推荐。
> 密码从 `/etc/gk/secrets.env` 取（600 root），不要写进命令行历史。

需要一个能登录的 `authenticator` 角色来做连接池（`[B]` PostgREST 标准做法）：

```bash
sudo -u postgres psql -c "CREATE ROLE authenticator NOINHERIT LOGIN PASSWORD 'REPLACE_ME';"
sudo -u postgres psql -c "GRANT anon, authenticated, service_role TO authenticator;"
```

systemd unit `/etc/systemd/system/postgrest.service`：

```ini
[Unit]
Description=PostgREST (Growing Kids)
After=postgresql.service
Requires=postgresql.service

[Service]
User=postgrest
ExecStart=/usr/local/bin/postgrest /etc/postgrest/gk.conf
Restart=always
RestartSec=3
NoNewPrivileges=true
ProtectSystem=strict
PrivateTmp=true

[Install]
WantedBy=multi-user.target
```

```bash
useradd --system --no-create-home --shell /usr/sbin/nologin postgrest
mkdir -p /etc/postgrest && chown root:postgrest /etc/postgrest && chmod 750 /etc/postgrest
chmod 640 /etc/postgrest/gk.conf   # 里面有 jwt-secret
systemctl daemon-reload && systemctl enable --now postgrest
systemctl status postgrest --no-pager
```

> Caddy 用站点地址里的 IP 做 **Host 匹配**，并不等于绑定该网卡。本次靠腾讯云防火墙恰好没放行 8080 才没暴露。

> ```bash
> ss -tln | awk '$4 ~ /8080/{print $4}'      # 期望 127.0.0.1:8080，出现 *:8080 就是没绑定
> ```

> **`handle_path` 而不是 `handle`**：`handle_path` 会**剥掉**匹配到的前缀，

> 这正是 `supabase-js` 硬编码拼 `/rest/v1` 所需要的反向适配。
> 直接改 `SUPABASE_URL` 指向 PostgREST 是不行的——它会拼成 `/rest/v1/timeline_items` 而 PostgREST 不认识这个前缀。

#### S2-1 生成 JWT secret 与两枚 token

```bash
SECRET=$(openssl rand -hex 32)   # 64 字符，写进 gk.conf 的 jwt-secret
echo "jwt-secret = \"$SECRET\""

# 用一个一次性 Node 脚本签两枚不过期 token（本项目不做 PG 层鉴权，用不到 exp）
node - "$SECRET" <<'JS'
const crypto = require('crypto')
const secret = process.argv[2]
const b64 = (o) => Buffer.from(JSON.stringify(o)).toString('base64url')
const sign = (payload) => {
  const head = b64({ alg: 'HS256', typ: 'JWT' })
  const body = b64(payload)
  const sig = crypto.createHmac('sha256', secret).update(`${head}.${body}`).digest('base64url')
  return `${head}.${body}.${sig}`
}
console.log('ANON=' + sign({ role: 'anon', iss: 'growing-kids' }))
console.log('SERVICE=' + sign({ role: 'service_role', iss: 'growing-kids' }))
JS
```

把 `ANON=` 写进 `SUPABASE_ANON_KEY`，`SERVICE=` 写进 `SUPABASE_SERVICE_ROLE_KEY`。

> **不是 JWT** `[A]`。PostgREST 只认 JWT，直接拿旧 key 会 401 `PGRST301`。

#### S2-4 迁文件（Storage → 本地磁盘）

`[A]` 现状：`.env` 是 `STORAGE_DRIVER=supabase`，`storage.service.ts` 有 4 处真实
`storage.from('media')` 调用（bucket=`media`）。

**好消息：不需要改代码，也不需要装 MinIO。** `[A]` `storage.service.ts` 的 `local` 分支是完整的生产实现：

| 能力 | local 驱动 | 依据 |
|---|---|---|
| 落盘目录 | `STORAGE_LOCAL_DIR`（默认 `./.local-storage`） | `[A]` 第 59 行 |
| 读取路由 | `GET /api/storage/files/*` | `[A]` `storage.controller.ts` 第 44 行 |
| 路径逃逸防护 | `resolveLocal()` 校验 key 不越出根目录 | `[A]` 第 65–75 行 |
| 前端兼容 | 前端本来就走 `storageFileUrl(key)` → `/api/storage/files/{key}` | `[A]` `services/net.ts` |

所以只需**下载 + 切驱动**：

```bash
# 用一个一次性脚本：按 storage.objects 表列出 key，逐个从 Supabase Storage 拉下来
# 落盘路径必须与 key 一致（内容是 blobs/ab/hash/original.webp 这种分层结构）
export DEST=/var/lib/gk/storage
mkdir -p "$DEST"

sudo -u postgres psql -d gk -At -F'|' -c \
  "SELECT bucket_id, name FROM storage.objects WHERE bucket_id='media'" 2>/dev/null \
| while IFS='|' read -r bucket name; do
    out="$DEST/$name"
    mkdir -p "$(dirname "$out")"
    curl -fsS -H "Authorization: Bearer $SERVICE_ROLE_KEY" \
      "$SUPABASE_URL/storage/v1/object/$bucket/$name" -o "$out" || echo "MISS $name"
  done

find "$DEST" -type f | wc -l
```

#### S2-11 生产备份链（2026-10-31 落地，属 S4-3 提前做）

> 为什么这一节不放在 S4：**数据已经在服务器上、Supabase 还是原样没动**，
> 但服务器本身一旦成为唯一真相源却没有任何备份，等于裸奔。
> 备份是"上线前就该有"的东西，不能等切流之后再补——切流量的那一瞬间风险最大。

**① 备份什么、多久一次**

| 对象 | 频率 | 产物 | 保留 | 落点 |
|---|---|---|---|---|
| 数据库（19 表） | 每日 03:17（±10min 随机） | `gk-db-YYYYMMDD-HHMMSS.gkbk` | 14 份 | 本地 `/var/lib/gk/backups` + 百度网盘 |
| 对象文件（`/var/lib/gk/storage`） | 每周日 03:47（±15min） | `gk-files-YYYYMMDD-HHMMSS.gkbk` | 6 份 | 同上 |

**② 备份专用角色（不要用业务角色，更不要用 owner）**

三条结论：

1. **3.3.1+oneDNN 的崩溃在 3.2.2 上不存在**（同图同模型直接跑通）⇒ 确认是 3.3.0 引入的回归，
   降小版本即可绕过，**不必降到 3.0.x**（陷阱 27 里"只剩降 3.0.x"的说法据此订正）。
2. **结果完全一致**：两版 9 个块的 `label` / `order` / `content` 逐行 `diff` **无任何差异**，
   字符数 96、`U+FFFD` = 0 ⇒ oneDNN 只影响速度，不影响 OCR 质量。
3. **截至 2026-10-31，PyPI 最新仍是 3.3.1**（`pip index versions` + PyPI simple index 双源核对），
   **没有 3.3.2 / 3.4.x**；Paddle#77340 仍 open，且有人在「3.3.1 + paddleocr 3.7.0 + Python 3.12
   + linux/amd64」（正是我们的组合）下复现 ⇒ **短期内不会有修复版可回迁**，双 venv 是当前最优解。

**已执行的切换**（`/opt/gk/server/.env`，备份 `.env.bak-pre322-*`）：

```bash
PPSV3_PYTHON=/opt/gk/.venv-py322/bin/python
PADDLE_PDX_ENABLE_MKLDNN_BYDEFAULT=1     # 显式覆盖 main3.py 里的 setdefault('0')
```

- 侧车 `environ`：`PADDLE_PDX_ENABLE_MKLDNN_BYDEFAULT=1`、`PPSV3_UNWARP=0`、`PPSV3_ORIENT_CLS=0`
- `/api/health` 200

> **⚠️ 环境变量透传的真相（差点误判）**：`sidecar.supervisor.ts` 的 `buildConfig()` 里有个
> `engineEnv` 白名单（`OCR_ENGINE_MODE`/`PPSV3_*` 等 10 项），看起来「不在名单里就传不进去」。
> 但 spawn 时用的是 `pythonEnv(cfg.engineEnv)`，而 `pythonEnv` = `{...process.env, ...extra}` ——
> **全量继承 process.env**，白名单只是「额外补充」，不是隔离。
> 所以 `PADDLE_PDX_ENABLE_MKLDNN_BYDEFAULT` 只写 `.env` 即可生效，**不需要改白名单**。

代价与风险：

- 磁盘 +1.6GB（现余 42G，无压力）
- **常驻 RSS 1054 → 1610 MB**（+556MB，比 `--once` 的峰值 1790 更贴近真实占用）。

  兜住 `--once` 回落路径上「两个重型 python 同时起」的场景；常驻侧车本身单进程串行（`_INFER_LOCK`）

| 40 | 以为口令只被换过一次，按"一把锁"去找 | 用桌面留存的 10-27 副本反查，**6 份备份对应三代口令**：10-27×3=A、10-28=B、10-29=C、10-30=D(当前)。A 因用户手动另存桌面副本才救回 3 份；**B/C 两代从未留副本 ⇒ 含 10-29 的 1614 行永久作废**。根因是 `KEY-ESCROW.txt` 只有一个槽位，每次换锁就地覆盖。⇒ 换锁前必须 `recover-export` 落一份明文归档 + 立刻更新密码管理器副本，否则旧代次必然无解 | `[A]` 2026-10-31 逐份试解 + payload sha256 比对 |

### 5.4 与三条路线的关系（为什么这些投入不作废）

| 工作 | L3 用得上 | L1（云托管）用得上 | L2（AnyService）用得上 |
