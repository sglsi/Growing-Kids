## 0. 一句话

**L3 = 一台 2核4G 轻量（年付 ¥663）+ 一个 .cn 域名（¥33）+ 免费 DV 证书，同机跑 PostgreSQL/PostgREST/NestJS/Caddy/OCR 五个进程；前置卡点是域名 ICP 备案 7–20 个工作日，其余工作都能在等待期内完成，且换路线不作废。**

首年现金支出 **¥696**，之后每年 **¥701**。没有按量计费的变量（选了不限流量套餐）。

> 💰 **首年可压到 ¥221**：腾讯云「同价续费」专区的 **2核4G5M · 60G · 500GB · 1年 = ¥188**（新老同享、随时可买），
> **可再以同价 ¥188 续费 1 次**（⇒ 前两年共 ¥376），之后免费升配为 4核4G5M 并享 **3.5 折续费 1 次 ¥273**
> ⇒ **三年合计 ¥649**（188 + 188 + 273），比直接买锐驰型（¥1,989）省 ¥1,340。
> ⚠️ **顺序不能反**（官方原文「选择升配后，不再享受同价续费专区活动价」）：**先付第 2 年的 188，再点免费升配**。
> 这一步不是"顺手薅个优惠"——**第 2 年那 ¥188 是拿 4 核的门票**，不付就升配，第 2 年要按 4核4G 刊例续费（约 ¥1,100+）。

**这不是最便宜的方案，但是唯一同时满足"数据回国 + 无 15s 天花板 + 无第三方政策开关 + 存储自持"的方案。** 代价是一次性等待 7–20 个工作日。

## 1. 最终形态

### 1.1 架构

```
微信小程序
   │  https://<域名>/api/*          ← ICP 已备案域名 + 受信 CA 证书
   ▼
┌──────────────────────── 轻量应用服务器（2核4G / 50G SSD，上海） ────────────────────────┐
│                                                                                      │
│  Caddy  监听 0.0.0.0:80,443          [自动 HTTPS，自动续期]                            │
│    ├─ /                → 静态说明页（/srv/www）  ← 备案要求"首页不能是空目录"           │
│    ├─ /api/*           → 127.0.0.1:3000   NestJS                                      │
│    └─ 127.0.0.1:8080 内部站点（不对外）                                                 │
│         └─ /rest/v1/*  → 127.0.0.1:3001   PostgREST（handle_path 自动剥前缀）           │
│                                                                                      │
│  NestJS  :3000（仅 127.0.0.1）                                                        │
│    ├─ supabase-js → http://127.0.0.1:8080/rest/v1/…   → Caddy → PostgREST             │
│    ├─ 文件落盘    → /var/lib/gk/storage（STORAGE_DRIVER=local）                        │
│    └─ spawn python → 127.0.0.1:9000  OCR 侧车（15 分钟空闲自动回收）                    │
│                                                                                      │
│  PostgreSQL 17  :5432（仅 unix socket / 127.0.0.1）                                    │
│  PostgREST       :3001（仅 127.0.0.1）                                                 │
└──────────────────────────────────────────────────────────────────────────────────────┘
```

### 1.2 为什么五个进程都要挤在一台机

| 组件 | 能不能省 | 理由 |
|---|---|---|
| PostgreSQL 17 | 不能 | 19 个 migration 是 PG 方言；CloudBase PG 只能公网 HTTPS 访问且到期 ¥19.9/月 |
| PostgREST | 不能 | 后端 218 处 `.from()` 全靠它；改 drizzle 要重写 218 处 `[A]` |
| NestJS | 不能 | 业务后端 |
| Caddy | 不能 | 证书自动化 + 静态首页 + 前缀剥离，三件事一个进程 |
| OCR 侧车 | **可降级** | 只跑 `rapid` 引擎时内存 ~400MB；跑 `paddle` 时 ~1.2GB |

### 1.4 为什么这个后端不能用云函数 / 云开发跑

这一节是为了回答"既然有云开发，为什么还要买机器"。**结论不是"配置不够"，而是"函数"和"进程"的范式冲突。**

先把两套东西分清楚，它们的限制差一个量级：

| 维度 | 微信侧云开发（`wx.cloud.callFunction` 事件型） | 腾讯云侧 CloudBase（HTTP 云函数） |
|---|---|---|
| 超时上限 | **60 秒**（默认 3s，可调至 60s 封顶） | 普通函数 900s / HTTP 函数 7200s |
| 内存上限 | **2048MB** | 3072MB |
| 单个函数代码包 | **50MB** | 同上 |
| 同步请求 / 响应 | **各 6MB** | — |
| 运行时 | 创建时只有 Node.js | Python 3.11 / NestJS 均支持 |

`[B]` 前两列出自腾讯云《云开发 CloudBase 产品简介》PDF 系统限制表；后两列出自 `docs.cloudbase.net/cloud-function/function-configuration/config` 与 `/runtime-support`。
**两个官方来源数字不一致**（60s vs 900s、2048MB vs 3072MB），因为前者是微信小程序封装的云开发、后者是腾讯云侧的 CloudBase。本项目从微信侧进，按 **60s 封顶**取值。

**但真正的阻塞不在这些数字上——就算给 900 秒，一样跑不了。**五条按严重度排列：

| # | 硬限制 | 对本项目的具体后果 |
|---|---|---|
| **1** | **实例短生命周期、函数返回即冻结/回收**（`[B]` 官方产品模型原文："任务完成后，资源立即释放"） | **致命**。本项目 `async_jobs` 的 job 表活在**进程内存**里（`jobs.service.ts`）。提交任务的实例与轮询 `GET /api/jobs/:id` 的实例**不是同一个进程** ⇒ 任务提交成功、轮询永远查不到，实例一回收任务就消失。加内存、加超时都改不了 |
| **2** | **没有"常驻进程"，因而没有"侧车"这个概念** | 云函数是被动触发的单进程，不能起一个监听 3001 的常驻服务，也不能跑常驻 worker 轮询任务表。要跑 OCR 只能另建一个 HTTP 云函数，**每次冷启动重新加载 det/rec/cls 三个模型**（1GB 量级，10–30 秒），PaddleOCR 首次推理还要预热 |
| **3** | **没有持久磁盘**（`/tmp` 随实例回收清空） | `STORAGE_DRIVER=local` + `STORAGE_LOCAL_DIR` 落盘方案直接失效，必须改对象存储（COS）并新增 s3 驱动。而 L3 下这段代码**零改动**，这正是 §8-2 那条修正的价值 |
| **4** | **单个函数代码包 50MB** | `server/` 构建产物 + `node_modules` 已接近该量级，`paddlepaddle` wheel 单包 100MB+ ⇒ 塞不进去。改走 COS 挂载能绕过体积，但冷启动更慢 |
| **5** | **超时上限** | 本项目 OCR 实测峰值 **86.8 秒** `[A]`（`async_jobs` 就是为它建的）> 微信侧 60s 封顶 ⇒ 直接失败 |

**一句话：这个项目要的是"一台常驻机器同时跑 PG / PostgREST / NestJS / Caddy / Python 五个进程，任务队列活在内存里"；云函数只能提供"一次性、无状态、用完即焚的函数"。**
第 1、2、3 条是形态问题，不是配额问题——**给多少钱都改不了**。

> ⚠️ 唯一例外：如果哪天把 `async_jobs` 改成**外部队列**（表驱动 + 独立轮询进程）+ **对象存储** + **OCR 换云 API**，
> 形态就与云函数兼容了。但那是**重写数据流**，不是"迁个后端"，与本文"不推倒重来"的前提冲突。

### 3.5 两条实施路线的取舍：先 L2 再 L3，还是直接 L3

> L2 的定义（沿用调研纪要 §3.2）：**后端仍跑在轻量上（与 L3 同机同构），差别只在接入层**——L2 用云开发 **AnyService** 免域名直连，
> L3 用自有域名 + 备案 + `wx.request`。两者后端形态一样，**所以 S1/S2 的工作两条路线共用**。

| 维度 | L2 先行 → 切 L3 | 直接 L3 |
|---|---|---|
| 备案下来前能否真机跑通 | ✅ 能（AnyService 免域名） | ✅ **也能**：开发者工具 + 真机开发版勾"不校验合法域名"，用 `IP:端口` 直连 |
| 前端传输层 | ❌ **要维护两套**（`callContainer` 一套、`wx.request` 一套），切换时全量回归 | 一套，不切 |
| 图片链路 | ❌ **必须改造**（`callContainer` 15s 超时、返回包 1000KiB、官方明写"不建议请求中带图"） | **不用改** |
| 文件存储 | ❌ 必须 COS，要给代码加 s3 驱动 | `STORAGE_DRIVER=local`，**零改动** |
| 验证有效性 | ⚠️ L2 跑通 ≠ L3 能用（存储、超时、图片三处行为都不同） | 开发环境即生产环境 |
| 备案等待期 | 被浪费（在等 L2 上线） | **并行**：S1/S2 正好填满 7–20 个工作日 |
| 额外成本 | 云开发个人版 ¥19.9/月 + 免费环境**发布后 15 天**到期 | ¥0 |
| 唯一独有优势 | 备案没下来也能发**正式版** | 正式版必须等备案 |

**结论：直接 L3。**理由不是省钱，是**L2 唯一的价值（绕开备案）在本项目不成立**：

1. **开发测试从来不需要备案。** 备案只在"发正式版"那一刻才卡；开发版/体验版用 IP 直连就能跑通全链路（本项目真机已这样跑过：`PROJECT_DOMAIN=http://192.168.3.242:3001`）。
2. **L2 期间额外做的两套传输层 + COS 改造，搬到 L3 全是废码或要回退**——这正是最该避免的"花大力气最后推倒"。
3. **活动机把 L3 的开发期成本压到 ¥109 起**，绕 L2 的经济理由也随之消失。

**L2 保留为退路，触发条件只有三条**：
- 备案因"教育类"被驳回、或管局超 20 工作日仍无结果（→ 短期用 L2 让真实用户先用上）
- §3.1.1 的 3Mbps 带宽实测证明不可接受（入方向实测见 §S0-2 验收项）
- 不想长期自己运维这台机器

切 L2 的代价可控：因为后端形态不变，只需加一层接入配置 + 保存一份原传输层，**1–2 天**可切（调研纪要 §4 D2 的口径）。

### S1 服务器初始化（3–4 小时，不等备案）

> 全部命令在 root 下执行。**顺序不能乱**：先加固，再装服务。

#### S1-1 系统加固

```bash
# 1) 更新
apt update && apt -y upgrade

# 2) 建日常用户（后续都别用 root 跑业务）
adduser --disabled-password --gecos "" gk && usermod -aG sudo gk

# 3) SSH 加固：先确认自己的公钥已写入，再关密码登录（顺序反了会锁死自己）
mkdir -p /home/gk/.ssh && chmod 700 /home/gk/.ssh
# ...把公钥写入 /home/gk/.ssh/authorized_keys，chmod 600...
sed -i 's/^#\?PasswordAuthentication.*/PasswordAuthentication no/' /etc/ssh/sshd_config
sed -i 's/^#\?PermitRootLogin.*/PermitRootLogin no/' /etc/ssh/sshd_config
systemctl restart ssh

# 4) 时区与 UTF-8（本项目 OCR 对编码敏感，见记忆 §1）
timedatectl set-timezone Asia/Shanghai
locale-gen en_US.UTF-8 zh_CN.UTF-8

# 5) swap：2G（OCR 跑 paddle 模式时的兜底，见 §5.3）
fallocate -l 2G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab
sysctl -w vm.swappiness=10 && echo 'vm.swappiness=10' >> /etc/sysctl.conf
```

防火墙（轻量控制台的"防火墙"是云侧，系统内还要一层）：

```bash
apt -y install ufw
ufw default deny incoming
ufw allow 22/tcp
ufw allow 80/tcp
ufw allow 443/tcp
ufw --force enable
```

⚠️ 轻量控制台的防火墙也要放行 80/443（默认模板通常只开 22/80/443，需确认）。

#### S1-2 装 PostgreSQL 17

```bash
apt -y install curl ca-certificates gnupg
install -d /usr/share/postgresql-common/pgdg
curl -o /usr/share/postgresql-common/pgdg/apt.postgresql.org.asc -fsSL https://www.postgresql.org/media/keys/ACCC4CF8.asc
echo "deb [signed-by=/usr/share/postgresql-common/pgdg/apt.postgresql.org.asc] https://apt.postgresql.org/pub/repos/apt $(. /etc/os-release && echo $VERSION_CODENAME)-pgdg main" \
  > /etc/apt/sources.list.d/pgdg.list
apt update && apt -y install postgresql-17
```

`[B]` 项目 migration 用到 `gen_random_uuid()`（12 处 `[A]`），PG 13+ 内核自带，**不需要 pgcrypto 扩展**。

调参（4G 内存的关键，否则默认配置在大表上会慢）：

```bash
cat >> /etc/postgresql/17/main/postgresql.conf <<'EOF'
listen_addresses = '127.0.0.1'
shared_buffers = 256MB
effective_cache_size = 768MB
work_mem = 8MB
maintenance_work_mem = 64MB
max_connections = 60
wal_compression = on
log_min_duration_statement = 1000
EOF
systemctl restart postgresql
```

> `shared_buffers` 给 256MB 而不是常见的 1GB：这台机还要养 OCR（峰值 ~1.2GB），
> 给 PG 太多会把 OCR 挤进 swap。

#### S1-3 建库建角色

```bash
sudo -u postgres psql <<'SQL'
CREATE DATABASE gk;
-- 三个角色，与 Supabase 同名，让 supabase-js 的 JWT claim 直接可用
```

#### S2-1 生成 JWT secret 与两枚 token

```bash

const crypto = require('crypto')
const secret = process.argv[2]
const b64 = (o) => Buffer.from(JSON.stringify(o)).toString('base64url')
const sign = (payload) => {
  const head = b64({ alg: 'HS256', typ: 'JWT' })
  const body = b64(payload)
  const sig = crypto.createHmac('sha256', secret).update(`${head}.${body}`).digest('base64url')

}

console.log('SERVICE=' + sign({ role: 'service_role', iss: 'growing-kids' }))
```

`[A]` 现状：`.env` 是 `STORAGE_DRIVER=supabase`，`storage.service.ts` 有 4 处真实

| 能力 | local 驱动 | 依据 |
|---|---|---|
| 落盘目录 | `STORAGE_LOCAL_DIR`（默认 `./.local-storage`） | `[A]` 第 59 行 |
| 读取路由 | `GET /api/storage/files/*` | `[A]` `storage.controller.ts` 第 44 行 |

```bash

      "$SUPABASE_URL/storage/v1/object/$bucket/$name" -o "$out" || echo "MISS $name"
```

|---|---|---|
| 1 | 列表加载 | 首页 1–3 秒出列表，骨架消失 |
| 2 | 图片显示 | 头像、题目图片正常（走 `/api/storage/files/*`） |
| 3 | 上传 | 拍照/选图能成功，`uploadFile` 不报域名错 |
| 4 | 导出 | 打印练习卷能下载并打开（走 downloadFile） |
| 5 | 长任务 | 精准 OCR / AI 解题走轮询，不超时（`POST /api/jobs`） |
| 6 | 令牌 | 杀进程重进，登录态正常（`X-Auth-Token` 链路） |

> 第 5 项是 L3 相对 L1 的核心优势：**没有 15s 天花板**。
> `callContainer` 的客户端上限是 15s（`[B]` 云托管 FAQ「timeout 参数最大值不得大于 15 秒，否则无效」），
> 而本项目精准 OCR 实测 **86.8s** `[A]`。改用标准 HTTPS 后，这个约束彻底消失——
> `POST /api/jobs` 的异步化仍然值得保留（防页面卡死），但不再是"生死线"。

### S4 切换与回退（1 小时）

#### S4-1 切换顺序（务必按此顺序，否则会出现"新老都能写"的双写风险）

```
1. 后端切到新库（改 .env → 重启）        ← 此时读新库、写新库
2. 验证 10 分钟（列表/上传/导出各走一遍）
3. 小程序服务器域名切到新域名（若之前有旧域名）
4. 观察 24 小时
5. 旧 Supabase 项目**先降级不删除**（保留只读快照），观察一周后再决定
```

#### S4-2 回退预案（每步都能退）

| 故障 | 回退动作 | 耗时 |
|---|---|---|
| 新库数据不对 | 改回 `SUPABASE_URL` 指向旧 Supabase，重启 | 2 分钟 |
| 文件读不出 | 改回 `STORAGE_DRIVER=supabase`，重启 | 2 分钟 |
| 后端崩 | `systemctl restart gk-api`；看 `journalctl -u gk-api -n 100` | 1 分钟 |
| 证书签不下来 | 先用 IP + 自签证书做**开发调试**（正式版不行） | 10 分钟 |
| 机器被墙/DDoS | 轻量控制台换公网 IP，改 DNS A 记录 | 30 分钟 |
| 备案被驳回 | **S1/S2 全部保留**，改材料重新提交；或临时退回 L2（AnyService） | 视驳回原因 |

> **最后一条是关键**：备案被驳回时，损失只有"等待的时间"，没有沉没的技术投入。
> 这就是为什么 S1/S2 刻意排在备案前面做。

#### S4-3 上线后必须做的三件运维

```bash
# 1) 自动续费（服务器 + 域名），防止备案随资源到期失效
#    控制台操作，无 CLI

# 2) 每日备份（沿用项目已有的备份链，见记忆 §6）
#    关键：备份必须包含 PostgreSQL 数据目录 + /var/lib/gk/storage
#    不能用 pg_dump（记忆：本机无 PG 客户端会"成功但目录为空"）

# 3) 日志轮转（否则 50G 盘会被 access.log 吃满）
cat > /etc/logrotate.d/gk <<'EOF'
/var/log/caddy/*.log /opt/gk/server/logs/*.log {
    daily
    rotate 14
    compress
    delaycompress
    missingok
    notifempty
    copytruncate
}
EOF
```

## 5. 注意事项

### 5.1 备案红线（唯一能让整条路走不通的东西）

**个人主体不能涉及前置审批内容，而教育在列，且个人无法办理前置审批文件。**
（`[B]` 腾讯云「个人备案…不能涉及企业、团体、论坛和前置审批内容」「个人无法办理前置审批文件」；
《互联网信息服务管理办法》第五条含教育）

这不是"审核慢"，是**资格问题**——补不了。

#### 逐项对照表

| 位置 | ❌ 不能出现 | ✅ 建议写法 |
|---|---|---|
| 网站名称 | 教育、培训、课程、辅导、教学、学堂、学童、学院、网校 | 「××的学习记录」「××的笔记」「××杂记」 |
| 服务内容描述 | "教育信息服务""在线教育""课程辅导" | 「用于记录个人学习内容的整理与复习，含题目录入、分类归档与复习提醒，不含互动评论与交易功能」 |
| 首页文案 | "帮助孩子学习""教学辅助" | 「记录自己录入的题目与答案，按学科分类归档」 |
| 域名本身 | `edu-xxx.cn`、`xx-edu.cn`、`xxketang.cn` | 用个人化、中性词 |

> ⚠️ **小程序里叫什么不影响域名备案**。小程序名（"成长学童"）和域名备案是两个独立系统：
> 前者归微信审，后者归管局审。**但域名和网站名称必须按上表避开**。
> 也就是说：小程序可以继续叫成长学童，域名不能叫 `chengzhangxuetong.cn`。

#### 其它高频驳回项（`[C]`）

| 驳回原因 | 规避 |
|---|---|
| 域名实名信息与备案主体不一致（差一个字） | 注册时姓名与身份证**逐字核对** |
| 证件照片模糊/反光/四角不全 | 白天自然光、正上方拍、四角入镜 |

| 一个主体同时只有 1 条备案订单 | 别重复提交 |

### 5.2 技术陷阱（每条都会让人查半天）

| # | 陷阱 | 正确做法 | 依据 |
|---|---|---|---|
| 1 | `SUPABASE_URL=http://localhost:8080` | **必须写 `http://127.0.0.1:8080`** | `[A]` dns-pin 对 IP 字面量短路，对域名不短路 |
| 2 | 直接把 `SUPABASE_URL` 指向 PostgREST 端口 | 必须经 Caddy `handle_path` 剥 `/rest/v1` | `[A]` supabase-js 硬编码拼 `/rest/v1` |
| 3 | 用旧密钥 `sb_secret_…` 当 JWT | 自签 HS256 JWT，role claim 写 `service_role` | `[A]` 现网密钥非 JWT |
| 4 | 忘给 service_role 加 `BYPASSRLS` | `CREATE ROLE service_role … BYPASSRLS` | `[A]` `ocr_results` 启用 RLS 但无 policy，会静默返回 0 行 |
| 5 | OCR 跑 paddle 模式 | 生产用 `OCR_ENGINE_MODE=rapid`，配 `MemoryMax` | `[A]` paddle 常驻 ~1.2GB |
| 6 | Python 输出乱码 | `PYTHONUTF8=1` + `PYTHONIOENCODING=utf-8` | `[A]` 记忆 #117，判据是中文绝不出现 U+FFFD |
| 7 | 只配 request 域名 | request / uploadFile / downloadFile **三类都配** | `[B]` 四类独立校验 |
| 8 | 用自签证书 | 必须受信 CA（Caddy 自动申请即可） | `[B]` 微信不接受自签 |
| 9 | 证书链缺中间证书 | `openssl s_client` 验证，证书数 ≥2 | `[C]` Android 会失败而 iOS 正常 |
| 10 | 事后想扩容磁盘 | SSD **1 元/GB/月**，加 50G = ¥50/月 = ¥600/年 | `[B]` 价格总览。**买时选够** |
| 11 | 忘了 swap | 配 2G swap，`vm.swappiness=10` | OCR 峰值会顶到上限 |
| 12 | 日志不轮转 | logrotate 每日，保留 14 天 | 50G 盘会被 access.log 吃满 |

### 5.3 容量与性能预期

| 项 | 估算 | 依据/口径 |
|---|---|---|
| 内存（空闲） | ~800MB | PG 400 + Node 200 + 其它 200 |
| 内存（OCR 跑 rapid） | ~1.2GB | 加 OCR 400MB |

| 月流量（入门型 600GB） | 60 万次图片下载 | 家庭场景远达不到 |

**响应时间预期**：同机 `127.0.0.1` 访问数据库，`/api/timeline` 应 < 200ms。
对比现网 `[A]` 实测 `/api/timeline/overview` **5777 / 8107 / 6678 ms**——这是本次迁移最直接的收益。

### 5.4 与三条路线的关系（为什么这些投入不作废）

| 工作 | L3 用得上 | L1（云托管）用得上 | L2（AnyService）用得上 |
|---|---|---|---|
| S1 装 PG + PostgREST | ✅ | ⬜（可换 CloudBase PG） | ✅ |
| S1 静态首页 | ✅ | ⬜ | ⬜ |
| S2 迁库（建角色/JWT/migration） | ✅ | ✅（换 URL 即可） | ✅ |
| S2 迁文件到本地 | ✅ | ⬜（云托管无持久盘，要换 COS） | ✅ |
| S2-6 OCR 侧车 | ✅ | ✅（要单独建服务） | ✅ |
| S3 域名 + 证书 | ✅ | ⬜（callContainer 免域名） | ⬜ |

**结论：迁库 + 迁存储 + 后端能跑，这三件事三条路线共用，先做一定不亏。**
