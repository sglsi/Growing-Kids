## 0. 现状基线（实读 GitHub `server/src/storage/database/shared/schema.ts`）

| 表 | 关键列 | 问题 |
|---|---|---|
| `health_check` | id(serial), updated_at | 平台探活，保留即可 |
| `subjects` | id, **name(unique)**, color, sort_order, created_at | **无 user_id**；`name` 全局唯一 → 多用户会冲突 |
| `questions` | id, subject_id(FK), question_content, question_image_keys(jsonb), answer_content, answer_image_keys, solution, wrong_answer, source, status, mastered, mastered_at, recognized_at, created_at, updated_at | **无 user_id**；图片用 jsonb 存 key 数组 |
| `materials` | id, name, type('image'\|'document'), file_key, url, mime_type, size_bytes, subject_id, used, created_at | **无 user_id**；无复习本标记；文档与图片混住 |
| `documents` | id, title, type('docx'\|'pdf'), file_key, url, mime_type, size_bytes, created_at | 无 user_id |

**核心症结**：全库**单租户**（无 `user_id`），不可扩展为多用户；`questions`/`materials` 两张表要靠应用层归并才能"按时间合并展示"。

## B. 待确认清单（每条含建议 + 理由，请逐条拍板）

> 下表是本次设计的**核心**。每条我给出**推荐选项**（★）与备选，请你回复编号即可（例如"B1 选①，B2 选②…"，或直接说"全按建议"）。

### B1. 【关键】是否需要多用户（`user_id`）？

| 选项 | 说明 |
|---|---|
| ★ **① 现在就加 `user_id` + RLS** | 每张业务表带 `user_id`，行级隔离。测试数据可弃，正是零成本重建的窗口期 |
| ② 暂不加，维持单租户 | 与现状一致，改动最小；未来加要迁数据 |

> **建议 ①**。理由：① 本项目定位是**"每个孩子自己的成长伙伴"**，天然多用户；② 现在库是空的，加 `user_id` 成本为零，将来补要改表+洗数据；③ 微信小程序接入后 openid 可直接映射。**风险**：Coze 若用 `service_role` 注入，RLS 会被绕过，需确认（见 B6）。

---

### B2. 【关键】`questions` 与 `materials` 是"合表"还是"分表"？

| 选项 | 说明 | 优点 | 缺点 |
|---|---|---|---|
| ★ **① 合成一张 `timeline_items`**（`kind` 区分 image/question） | 一条时间线，一套分页/一套列表组件 | 彻底消除两表归并的分页边界问题；查询简单 | 题目/图片字段混在一表，部分列稀疏；与现有 NestJS service 改动大 |
| ② 保留两张表 + 后端 `/timeline` 归并 | 沿用现有表结构，只在应用层合并排序 | 改动小、贴近现状 | 分页边界需额外处理（取两表各 page*2 再截断）；代码复杂度在应用层 |
| ③ 保留两表 + 建数据库 `view timeline` 联合 | 用 Postgres 视图 UNION ALL | SQL 层统一，代码简单 | 视图不能建索引、分页性能差、无法写入 |

> **建议 ①**。理由：本项目"最近题目/复习本"本质**就是同一条内容流的两个过滤视图**，合表最贴合语义，且能根除分页边界问题。**代价**是与现有 `questions`/`materials` service 差异较大——但既然"不迁移、重新设计"，正是做这个升级的时机。若你更看重**改动最小**，选 ②。

---

### B3. 标签（`tags`）的存法

| 选项 | 说明 |
|---|---|
| ★ **① `text[]` 数组 + GIN 索引** | 原生数组，`tags @> array['易错']` 即可查；单表搞定，无需标签表 |
| ② `jsonb` | 灵活但数组包含查询不如 `text[]` 直观 |
| ③ 独立 `tags` + `item_tags` 关联表 | 规范但多两张表，v1 过重 |

> **建议 ①**。理由：简单、索引好、查询强，足够支撑"学科之外的搜索/标签"。若将来要"标签重命名/统计"，再升级到 ③。

---

### B4. "最近题目"的排序字段

| 选项 | 说明 |
|---|---|
| ★ **① `created_at`** | 采集入库时间，语义最稳，一定存在 |
| ② `recognized_at` | 识别时间，仅题目有；图片无此字段 |

> **建议 ①**（合表后统一用 `created_at`）。理由：图片没有 `recognized_at`，合表后统一 `created_at` 才能"两表按时间合并"。

---

### B5. 文件存储放哪（库外）

| 选项 | 说明 |
|---|---|
| ★ **① 腾讯云 COS / 阿里云 OSS**（≈0.118 元/GB·月） | 便宜、可生命周期归档、国内 CDN 快 |
| ② Supabase Storage | 与库同平台，省事，但 100GB 后单价高、国内访问慢 |
| ③ 微信云存储 | 若最终迁微信云开发才合适；与当前 Supabase 方案不搭 |

> **建议 ①**，与 `复习本与项目设计.md` §14 结论一致。**库只存 `file_key`**，不存大文件。

### B6. RLS 启用方式（依赖 B1）—— 已确认：**service_role**

> **用户确认：Coze 运行时注入的是 `SERVICE_ROLE_KEY`。**
> 这意味着 **Supabase RLS 会被直接绕过**（service_role 是超级权限，无视 RLS 策略）。

**因此本项目的隔离策略定为**：

| 层 | 做法 |
|---|---|
| **主防线（必须）** | **后端 service 层强制 `where user_id = :currentUserId`** —— 所有查询、更新、删除都必须带该条件；`getCurrentUserId()` 从请求上下文（v1：`users` 单条/预留 `X-User-Id` 头）解析 |
| **写防线** | 新增/插入时 `user_id` 由后端**强制写入**，禁止信任前端传入 |
| **双保险（可选）** | 仍**保留 `enable row level security` + 策略脚本**（注释态）。将来若改用 anon+JWT，取消注释即生效，无需改表 |

> ⚠️ **关键风险提示**：service_role 绕过 RLS → **数据隔离完全依赖后端代码正确性**。漏写一次 `where user_id` 就会越权。**缓解**：① 封装统一的 `userScopedQuery()` 帮助函数，禁止裸查；② 代码评审强制检查；③ 将来接微信登录后，考虑切到 anon+JWT 让 RLS 兜底。

---

### B7. 识别/采集的"中间态"是否入库

| 选项 | 说明 |
|---|---|
| ★ **① 只存最终结果**：识别成功后落一条 `timeline_items(kind='question')`，中间图即用即删 | 库干净、省存储 |
| ② 原图 + 识别结果都留 | 可回溯，但占存储（详见 §11 存储策略） |

> **建议 ①**，配合 §11 策略 5（临时文件清理）。

---

### B8. 软删除 or 硬删除

| 选项 | 说明 |
|---|---|
| ★ **① 软删 `deleted_at`** | 误删可恢复；对象存储可异步按 `deleted_at` 清理 |
| ② 硬删 | 简单；但误删不可逆，且对象存储易残留孤儿文件 |

> **建议 ①**。理由：教育类产品用户可能误操作，且软删能优雅协调"库删了、文件还在"的问题。

---

### B9. `library_docs` 与 `documents` 是否分表

| 选项 | 说明 |
|---|---|
| ★ **① 分两张表** | 资料库=外部文档源；文档页=小程序生成物。职责清晰 |
| ② 合一表 + `origin` 字段区分 | 少一张表，但两页查询都要过滤 |

> **建议 ①**，与决策 5/6（文档页 vs 资料库）一一对应。

---

### B10. 用户与微信账号的绑定时机

| 选项 | 说明 |
|---|---|
| ★ **① 预留 `users` 表 + `open_id` 唯一键，v1 先不接微信登录** | 结构就绪，登录后续接入不返工 |
| ② 现在就接微信静默登录 `wx.login → openid` | 一步到位，但涉及小程序端改动与后端换取 openid |

> **建议 ①**。理由：当前重心是数据结构正确；登录是独立里程碑，先留位不阻塞。

**索引**
```sql
-- 最近题目（全量收件箱）

  where deleted_at is null;
-- 复习本（部分索引，只覆盖已加入的行）
create index timeline_review_idx on timeline_items (user_id, added_to_review_at desc)
  where in_review_book and deleted_at is null;
-- 标签 / 学科
create index timeline_tags_gin on timeline_items using gin (tags);
create index timeline_subject_idx on timeline_items (user_id, subject_id);
```
