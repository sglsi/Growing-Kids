# 去手写 / 自动调正 / 智能高清 —— 实现链路体检报告

> 触发：用户连续五轮反馈「这三个功能点击后还是不能使用」，并明确
> **「它们都不是 AI 功能，是该程序的自有功能」**。
> 本轮要求：系统检查三者的实现途径 → 找出问题 → 修复 → 验证。

## 〇、结论速览

三个功能**都能跑通**，但在真实场景下各有「静默返回原图」的路径 —— 后端认为这是
**安全降级**（宁可不改也不能改坏），前端却一律当成功处理，于是用户看到的永远是
「点了没反应」。这是五轮反馈的真正根因。

| 功能 | 体检结论 | 状态 |
| --- | --- | --- |
| 自动调正 | 唯一检测路径（找纸张外框）在**纸面占满画面**时恒不命中 → 100% 原样返回 | ✅ 已修：新增文本行倾斜估计兜底 |
| 去手写 | 色域阈值只认**彩色**笔迹；黑笔/铅笔与印刷体同为近黑 → 覆盖率 0 → 原样返回 | ✅ 已修：新增深色墨迹检测并取并集 |
| 智能高清 | 本身有效（锐度 +31%），但 OCR 一致性不达标会回退原图且**不告知** | ✅ 已修：回退时弹窗说明 |
| 底层共用 | sharp 单通道 raw 通道陷阱，mask 尺寸不一致时纵向错位 | ✅ 已修：统一 `alignMask` |

## 一、自动调正：为什么「点了没反应」

### 1.1 体检发现

链路：`POST /api/image/process {action:'auto'}` → `ImageService.straighten()`
→ `straightenImage()` → `detectDocumentCorners()` → `detectCornersCV()`。

`detectCornersCV` 的原理是 **Canny 边缘 → 最大轮廓 → approxPolyDP**，它依赖
「画面里存在一条**纸张边界**」。但真实拍摄绝大多数是**纸面占满整个画面**——
根本没有这条边，Canny 抓到的全是文字笔画的细碎边缘，最大轮廓面积远小于
`MIN_AREA_RATIO = 0.25` 护栏。

**实测（OpenCV WASM 正常加载）**：

```
四角自动检测(倾斜图): null
纯自动路径: needManual=true method=none   ← 直接原样返回原图
```

也就是说：**在最常见场景下，自动调正的检测路径 100% 不命中**。
功能没有坏，是它唯一的前提条件在现实里几乎从不成立。

### 1.2 修复：新增文本行倾斜估计（`image-deskew.ts`）

不再找「纸张外框」，改为找「**文字行的走向**」——文档倾斜估计的经典做法
（投影轮廓法），纸上只要有字就能算，与有没有纸张边界无关。

原理：把墨迹沿角度 θ 投影到一条轴上得直方图 hist；文字行越水平，同行墨迹越集中
落在同一 bin，直方图越**尖锐**。取 `Σhist²` 最大的 θ 为倾斜角。扫 ±15°，粗 1°
细化 0.1°，且**不真正旋转图像**（只做坐标变换累加），800px 长边约百毫秒级。

**⚠️ 符号坑（实测校准）**：投影式 `r = y·cosθ − x·sinθ` 取极大时的 θ，数值上
**等于图像当前倾斜角**（真实 +5° → 估计 +4.8°）。要转回正必须施加**反号**的
旋转。早期版本误用 +θ，把 5° 的歪斜转成 9.8°（越调越歪）。

接入后 `straightenImage` 的路径优先级：
`manualCorners` → 自动四角（`auto`）→ **文本行倾斜（`skew`，新增）** → `needManual`。

**实测（同一张倾斜 -4.5°、纸面占满画面的图）**：

```
修复前：needManual=true  method=none            → 原样返回，用户看到"没反应"
修复后：needManual=false method=skew rotate=4.5° 置信 1.00 → 输出 1087x1341
```

## 二、去手写：为什么黑笔/铅笔完全没效果

### 2.1 体检发现

链路：`erase_v2` → `buildHandwritingMask()` → **VLM（外部 Coze）优先**，
失败降级 `maskFromColorThreshold()`（色域阈值）。

色域阈值的判据是「通道极差 `chroma ≥ 22`」，只对**蓝/红等彩色笔**有效。
而中国学生写作业/考试绝大多数用**黑色中性笔或铅笔**，`chroma ≈ 0`，与印刷体
同为近黑 —— 色域法**完全检测不到** → `coverage ≈ 0` → `eraseV2` 走
「未检测到手写，原图返回」。

这与用户「它们是自有功能」的定性也冲突：当前**主路径依赖外部 VLM**。

### 2.2 修复一：新增深色墨迹检测 `maskFromDarkInk`

不用颜色，改用**几何**：印刷体字号统一、成行排列；手写答案通常明显大于正文
印刷字号。判据链：

1. Otsu 二值化 → 墨迹图；
2. **行投影**估计印刷字高 `glyphH`（不用连通块高度——手写一旦与印刷行粘连就会
   并成横跨整页的巨型块，高/宽双双失真，实测合并块宽 620px 被宽护栏整个剔除，
   检出率归零）；
3. 纵向游程 + **邻域最大跨度** ≥ `1.5·glyphH` → 手写「种子」；
4. 种子向邻域生长（半径 ≈ 字高）后**与墨迹取交** —— 既把手写笔画中平缓的段落
   纳入，又绝不把空白纸面或远处印刷体划进来；
5. 保守护栏：候选墨迹 > 全部墨迹 45% → 判定分类失效，整条路径作废。

**实测（同一张试卷，仅改笔色）**：

| 笔迹 | 修复前（色域法） | 修复后（并集） |
| --- | --- | --- |
| 黑色中性笔（大字） | **0.00%** | **2.70%** |
| 铅笔灰（大字） | **0.00%** | **2.58%** |
| 蓝色圆珠笔 | 1.54% | 2.78%（色域 ∪ 深色） |

**反例全部守住了**（宁可漏，不可错擦印刷体）：
纯印刷体 0% / 大号印刷标题 0% / 整页手写 0%。

### 2.3 修复二（底层，既有隐患）：sharp 单通道 raw 的通道陷阱

以 `raw:{channels:1}` 把灰度 mask 喂给 sharp 后，libvips 按 **sRGB 灰阶**处理，
`.resize()` / `.blur()` / `.median()` 之后 `.raw()` 出来的**一律是 3 通道**
（`r=g=b`，长度 `w*h*3`）。老代码直接 `maskBuf[i]` 按单通道索引 → 只读到前 1/3
数据 → **mask 纵向错位、覆盖率失真**。

该分支只在「mask 尺寸 ≠ 图尺寸」时触发，平时掩盖得很好，但一旦触发就是静默错图。
统一收敛到新函数 `alignMask()`：按 stride 取通道 0，保证返回长度严格 `w*h`。

### 2.4 诚实局限（不是 bug，是硬边界）

若黑色笔迹写得**与印刷体同字号**（例如就写在 `______` 上、大小一致），几何与
颜色上都无法与印刷体区分 —— 无模型条件下这是硬边界。此时算法**主动放弃**，
并通过 `debug.notice` 明确告诉用户可以怎么做（换蓝/红笔，或用「编辑裁剪」）。

## 三、智能高清：有效，但「可能被静默回退」

### 3.1 体检发现

`enhanceImage()` 本身是好的。实测（模拟拍照模糊的输入）：

```
输出 1800x2400  锐度：纯放大基准 2.771 → SR 3.637（+31.2%）  改动像素 4.25%
```

真正的问题是 **Phase 3 的 OCR 一致性回退**：处理前后各跑一次 OCR，一致性
< `IMG_OCR_MIN_SCORE`（默认 0.75）就**回退原图** —— 此时连尺寸都没变，用户
看到的就是彻底「没反应」，且**没有任何提示**。

### 3.2 修复

回退时返回 `debug.notice`（含实际得分与阈值），前端弹窗说明并建议改用 x2 快速模式。

> 注：SR 参数本身未调整。实测 sharpen 从 0.9 提到 1.2 只多 3 个百分点增益
> （30.5% → 33.4%），却在 1.33 之后即饱和，收益/风险不划算。

## 四、统一修复：反馈闭环（终结五轮「点了不能用」）

三个功能共有 **4 处**「安全地原样返回原图」的分支。后端新增结构化提示：

```ts
export interface ImageNotice {
  level: 'info' | 'warn'
  title: string
  message: string
}
```

| 分支 | notice |
| --- | --- |
| 去手写未检出手写 | 「未检测到可擦除的手写」+ 支持范围说明 + 两条可操作建议 |
| 自动调正未识别到歪斜 | 「未能自动识别到歪斜」+ 引导改用四角拉框 |
| 智能高清 OCR 回退 | 「高清处理未通过内容校验，已保留原图」+ 实际得分/阈值 + 建议 x2 |

前端 `handleAi` 成功路径不再无条件弹「完成」toast，而是先读
`data.debug?.notice`：有则**弹窗**（用户手动关闭，信息不丢），无则 toast。
