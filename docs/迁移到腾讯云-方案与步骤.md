# 扣子 → 腾讯云 平台迁移方案与详细步骤

> 📌 **归档状态**：本文为历史设计稿，**已并入 `docs/design/GK-QA-16-运维、发布与故障处置手册.md`（GK-QA-16 运维、发布与故障处置手册）**。
> 现行规范与现状以 GK 文档为准；本文仅作决策凭据与演进过程留档，**不再单独维护**。

> 版本：v1.1（2026-10-17）
> 背景：小程序原在扣子（Coze）平台开发并由扣子上线至微信；扣子云平台不稳定（无来由关闭/重启），决定整体迁移至腾讯云。
> 原则：**小程序前端代码不动，迁的是"后端 + 发布通道"**；迁移期间扣子版保持在线作为回滚，域名/体验版切换即完成切换。
> **v1.1 更新**：已实测确认 AI 三件套与对象存储在扣子环境外不可用（PAT 路线死刑，详见 §1.5）——迁移从「可选优化」升级为「功能必需」。

## 0. 一句话结论

| 迁什么 | 去哪 | 工作量 |
|---|---|---|
| 前端 Taro 代码 | **不动**，只换 API 域名 + 发布方式 | 0.5 天 |
| 后端 NestJS | **腾讯云 CloudBase 云托管**（容器，NestJS 原生跑） | 1 天 |
| 数据库 Supabase | **TencentDB for PostgreSQL**（schema 原生兼容，57 处查询改 SQL） | 2-3 天 |
| 对象存储（Coze bucket） | **腾讯云 COS**（S3 兼容，@aws-sdk 已在依赖里） | 0.5 天 |
| AI 能力（豆包 LLM/联网搜题/图生图） | **腾讯混元**（OpenAI 兼容，prompt 结构不变）+ **数据万象 CI** | 2-3 天 |
| 小程序发布 | 扣子 → **微信开发者工具 / miniprogram-ci 直传** | 0.5 天 |
| **ICP 备案** | 腾讯云代提交，**7-20 个工作日，最长链路，必须先启动** |  Passive 等待 |

总计约 **7-10 个工作日**开发量 + 备案等待期。前期云资源成本约 **¥100-300/月**量级（见 §7）。

## 1. 现状盘点：扣子耦合点全清单

迁移前先认清"哪些东西在依赖扣子"。实读代码后共 9 处：

| # | 位置 | 扣子依赖 | 迁移后替代 |
|---|---|---|---|
| 1 | `config/index.ts` L101-105 | `PROJECT_DOMAIN` ← `COZE_PROJECT_DOMAIN_DEFAULT` | 自有域名 `https://api.<你的域名>` |
| 2 | `.cozeproj/` 全目录（14 个脚本） | 扣子工程构建/部署管线（`deploy_build.sh` → `pnpm build`） | 删除，改用标准 `pnpm build` + GitHub Actions |
| 3 | `server/src/storage/storage.service.ts` | `S3Storage`（`COZE_BUCKET_ENDPOINT_URL`/`COZE_BUCKET_NAME`） | 腾讯云 COS SDK（`cos-nodejs-sdk-v5`）或 `@aws-sdk/client-s3` 指向 COS |
| 4 | `server/src/storage/database/supabase-client.ts` | `COZE_SUPABASE_URL/ANON_KEY/SERVICE_ROLE_KEY` + `getReportBuffer`/`createWrappedFetch` + python `coze_workload_identity` 取环境变量 | TencentDB for PostgreSQL 连接串（`pg` + drizzle，二者均已在 `server/package.json`） |
| 5 | `server/src/ocr/ocr.service.ts` | `LLMClient` + 模型 `doubao-seed-2-0-pro-260215`（豆包，做试卷结构化识别） | 混元 `hunyuan-vision` / `hunyuan-turbos`（OpenAI 兼容 messages 格式，改造量极小） |
| 6 | `server/src/search/search.service.ts` | `SearchClient.advancedSearch`（联网搜题） | 混元联网搜索插件，或备选博查/Bing Search API |
| 7 | `server/src/image/image.service.ts` | `ImageGenerationClient` 图生图（自动调正/智能高清/去手写） | 数据万象 CI：透视变换 + 图片高清化 + 图像修复（去手写无 1:1 替代，见 §6 风险） |
| 8 | `server/src/ocr/ocr.service.ts` L51 | `FetchClient` 提取文档文本（PDF/Word） | 本地解析：`pdf-parse` + `mammoth`，不依赖外部服务 |
| 9 | `key/private.appid.key` + `project.config.json` | 目前是 **0 字节空文件**，appid 是占位 `touristappid`（真实值在扣子后台） | 微信公众平台取真实 AppID + 重新生成上传私钥 |

补充事实：
- 后端共 **57 处 `.from(...)` Supabase 查询**，全部要改写为 SQL（最大工作量项）。
- 数据库当前为**测试数据**（v4 设计已拍板"不迁移、重建"）——若上线后已积累真实数据，走 §5-E1 的导出导入路径。
- 无 Dockerfile，需新建。
- 无 `.github`，CI/CD 从零搭。

## 1.5 关键实测结论（2026-10-17，本机直跑，证据确凿）

首次把后端跑到扣子环境之外，逐条实测（curl + 服务端日志 + SDK 隔离探针）：

| 能力 | 实测结果 | 证据 |
|---|---|---|
| 数据库（Supabase） | ✅ **全通** | `/api/subjects` 自动建匿名用户、回传 `X-User-Id`、铺 10 个默认学科；换身份完全隔离；`/api/timeline/overview` 正常 |
| AI 三件套（识图/搜题/图生图） | ❌ **不可用** | 探针直调 `LLMClient.invoke` 报 `code=190000007 no permission; cause=token validation failed: token contains an invalid number of segments` |
| 对象存储（上传/签名 URL） | ❌ **不可用** | `Failed to get x-storage-token: Set COZE_WORKLOAD_IDENTITY_API_KEY` |

**两个 500 的根因是同一个**：SDK 的 AI/存储端点只认**扣子平台运行时注入的 JWT 格式 workload identity 令牌**，用户侧拿不到。2026-10-17 已用控制台申请的 PAT（`pat_` 前缀）实测——在令牌解析阶段即被拒（端点要三段点分的 JWT，PAT 是单段），**PAT 路线死刑，不必再试**。

**这份实测把迁移方案的性质从「可选优化」升级为「功能必需」**：不换混元 + COS，小程序在扣子之外没有任何可用后端。数据库链路已验证可平迁（Supabase 公网可达），最大的未知数已消除。

## 2. 目标架构（腾讯云）

```
微信小程序（Taro 代码不动）
   │  HTTPS（request 合法域名：https://api.你的域名）
   ▼
CloudBase 云托管（NestJS 容器，自动 HTTPS + 自动扩缩容）
   ├─→ TencentDB for PostgreSQL   （主库，跑 migrations/0002_fresh_schema.sql）
   ├─→ 腾讯云 COS                 （图片/文档对象存储，CDN 加速）
   ├─→ 混元大模型 API             （OCR 结构化识别 / 解题 / 图生图）
   │    └─ 联网搜索插件           （联网搜题）
   └─→ 数据万象 CI                （图像高清化 / 透视矫正 / 修复）
```

**为什么选云托管而不是 SCF 云函数**：NestJS 是长驻 Express 应用 + `@nestjs/schedule` 定时任务（匿名数据清理），云托管常驻容器原生支持，零改造；SCF 需要 Web 框架适配且定时任务要拆出去。

**备选：轻量应用服务器（Lighthouse）**——2C2G 约 ¥60-100/月，自己跑 `node + pm2 + nginx + certbot`。控制感最强、最便宜，但要自己管进程/证书/更新。建议：**先用云托管（省事、和小程序生态一体），量大后再迁轻量服务器**。

## 4. 分阶段实施步骤

### 阶段 A：基础设施（Day 1，与备案并行）

**A1. 建 PostgreSQL 实例**
1. 控制台 → TencentDB for PostgreSQL → 新建实例（开发期选最低配，Serverless 版亦可）。
2. 数据库名 `growing_kids`，记录连接串（host/port/user/password）。
3. SQL 窗口执行 `migrations/0002_fresh_schema.sql`（6 表 + users 匿名字段，v4 全新结构）。
4. 旧 `questions`/`materials` 表不存在，无需处理。

**A2. 建 COS 存储桶**
1. 控制台 → 对象存储 → 创建存储桶（地域选与云托管相同，如广州/上海）。
2. 权限：**私有读写**，通过后端签名 URL 访问（与现有 `getPublicUrl` 逻辑对应，有效期保持 24h）。
3. 开启 CDN 加速（可选，图片加载更快）。
4. 创建 API 密钥（SecretId/SecretKey）备用。

**A3. 建 CloudBase 云托管服务**
1. 开通 CloudBase → 云托管 → 新建服务 `gk-server`。
2. 新建 `server/Dockerfile`（见下）。
3. 先手动部署一次验证：`nest build` → `node dist/main`，健康检查 `/api/health`。
4. 绑定自定义域名 `api.你的域名`（云托管自动签 HTTPS 证书）。

```dockerfile
# server/Dockerfile
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm install --omit=dev=false   # 或 COPY pnpm-lock 用 pnpm
COPY . .
RUN npm run build                  # nest build → dist/

FROM node:20-alpine
WORKDIR /app
ENV NODE_ENV=production
COPY --from=builder /app/node_modules ./node_modules
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/package.json ./
EXPOSE 3000
CMD ["node", "dist/main"]
```

**A4. 环境变量配置**（云托管控制台 → 环境变量，或密钥管理 KMS）

| 变量 | 值 | 替换的扣子变量 |
|---|---|---|
| `DATABASE_URL` | `postgres://user:pass@host:5432/growing_kids` | `COZE_SUPABASE_URL` 等 |
| `COS_SECRET_ID` / `COS_SECRET_KEY` | COS API 密钥 | — |
| `COS_BUCKET` / `COS_REGION` | 桶名/地域 | `COZE_BUCKET_NAME` / `COZE_BUCKET_ENDPOINT_URL` |
| `HUNYUAN_API_KEY` | 混元 API Key | — |
| `WX_APPID` / `WX_SECRET` | 微信小程序参数 | — |

### 阶段 B：后端去扣子化改造（Day 2-4）

**B1. 移除 `coze-coding-dev-sdk` 依赖**（改造后 `pnpm remove coze-coding-dev-sdk`）

| 文件 | 改造动作 | 预估 |
|---|---|---|
| `storage/database/supabase-client.ts` | 整体重写为 `pg.Pool` + drizzle（`pg@8` 已在依赖）。删除 python workload identity 取 env 的逻辑，改纯 `process.env` + dotenv | 0.5 天 |
| `storage/storage.service.ts` | `S3Storage` → `cos-nodejs-sdk-v5`（或 `@aws-sdk/client-s3` 指向 COS endpoint，SDK 已在依赖）。`uploadBuffer`/`getPublicUrl` 签名 URL 接口签名不变，上层零改动 | 0.5 天 |
| 各 service 共 **57 处 `.from().select()`** | 改写为 SQL。**红线保持**：每查必带 `WHERE user_id = $1`，禁止裸查（沿用 v4 设计 B6 决策） | 2-3 天 |
| `ocr/ocr.service.ts` | `LLMClient.invoke(messages, {model})` → 混元 OpenAI 兼容接口 `POST https://api.hunyuan.cloud.tencent.com/v1/chat/completions`，**messages 结构完全一致**（含 `image_url` parts），仅换 endpoint + key + model（`hunyuan-vision` 识图 / `hunyuan-turbos` 文本）。`extractJson`/`buildJsonSystem` 原样保留 | 0.5 天 |
| `search/search.service.ts` | `SearchClient.advancedSearch` → 混元请求加 `web_search` 联网插件参数；references 结构映射回 `{title,url,site_name}` | 0.5 天 |
| `image/image.service.ts` | 图生图 → 数据万象 CI 三段：①自动调正=透视变换 ②智能高清=图片高清化（超级分辨率）③去手写=图像修复（见 §6 风险 3，需单独验证） | 1 天 |
| `ocr` 的 `FetchClient` | 删掉，本地 `pdf-parse`（PDF）+ `mammoth`（docx）+ 纯文本直读 | 0.5 天 |

**B2. 定时任务**：`@nestjs/schedule` 的匿名用户清理（每小时）在云托管常驻容器内直接可用，无需改动；若后续迁 SCF 再用定时触发器。

**B3. 本地自测**：`server/.env` 配好上述变量 → `pnpm dev` → 逐条过 `server/MIGRATION.md` §4 校验清单（X-User-Id 回传、多租户隔离、登录迁移等）。

### 阶段 C：前端改造（Day 4-5）

1. **换域名**：`config/index.ts` 的 `PROJECT_DOMAIN` 来源改为 `.env.local` 的 `PROJECT_DOMAIN=https://api.你的域名`（删掉 `COZE_PROJECT_DOMAIN_DEFAULT` 兜底）；`src/network.ts` 无需改。
2. **删扣子工程文件**：`rm -rf .cozeproj`；`package.json` 中 `build:weapp` 等脚本从 `node .cozeproj/scripts/taro-build.cjs` 改回标准 `taro build --type weapp`（其余脚本同理）。
3. **真机参数**：`project.config.json` 填真实 AppID；放入真实 `key/private.appid.key`；`.gitignore` 加 `key/`。
4. **合法域名**：mp.weixin.qq.com → 开发管理 → 服务器域名 → request 合法域名加 `https://api.你的域名`（**须备案通过后才能保存**）。
5. **构建**：`pnpm install && pnpm tsc && pnpm lint:build && pnpm build:weapp` → 产物 `dist/`。
6. **上传**：微信开发者工具打开 `dist/` 上传体验版；或配 `@tarojs/plugin-mini-ci`（已在依赖，配 `TARO_APP_WEAPP_APPID`）走 CI 自动传。

### 阶段 D：CI/CD（Day 5-6）

新建 `.github/workflows/`（当前仓库无 CI）：

```yaml
# ci.yml — PR 门禁
on: pull_request
jobs: { validate: { steps: [checkout, pnpm i, pnpm validate] } }

# deploy-server.yml — main 分支后端自动发布
on: { push: { branches: [main], paths: ['server/**'] } }
steps: checkout → server/ 下构建镜像 → 推腾讯云容器镜像 TCR → 云托管滚动发布

# deploy-weapp.yml — main 分支小程序上传体验版
on: { push: { branches: [main], paths: ['src/**','config/**'] } }
steps: pnpm build:weapp → miniprogram-ci 上传（privateKeyPath: key/private.appid.key）
```

密钥用 GitHub Secrets（COS_SECRET_ID/KEY、HUNYUAN_API_KEY、WX_APPID/SECRET、TCR 凭证）。

### 阶段 E：数据、联调与切换（Day 6+）

**E1. 数据**
- 纯测试数据：无动作，新库即 `0002_fresh_schema.sql`。
- 已有真实数据：Supabase 控制台/pg_dump 导出 → `psql` 导入新 PG（schema 同为 PostgreSQL，注意 `gen_random_uuid()`/`jsonb`/GIN 索引在新库均支持）。

**E2. 联调清单**（双文档合并）
- 后端：`server/MIGRATION.md` §4 全 12 项。
- 前端真机：`MIGRATION-frontend.md` §4 六页全路径 + 登录迁移 + 杀进程重进。
- **新增**：AI 三件套效果对比测试（豆包 vs 混元：同一张卷子各识别 5 次，对比题目切分/答案区分准确率；搜题各测 10 题；图像三操作各测 5 图）。

**E3. 灰度切换**
1. 体验版 → 找 2-3 台真机跑核心路径。
2. 体验版转正式版需备案完成。
3. 切换即回滚：出问题把 `PROJECT_DOMAIN` 指回扣子域名重新发版；数据库以新库为准（旧库不再写）。

## 6. 风险与难点（如实说明）

| # | 风险 | 影响 | 对策 |
|---|---|---|---|
| 1 | **豆包 → 混元效果差异**：OCR 结构化识别（题目切分、红笔批改区分）是核心体验，换模型后 prompt 效果必然有波动 | 高 | 上线前用真实卷子做 A/B 测试；prompt 微调（`buildJsonSystem` 已参数化，好改）；保留 `temperature: 0.1` 低随机 |
| 2 | **联网搜题质量**：混元联网搜索 vs 扣子 SearchClient 检索质量未知 | 中 | 备选博查搜索 API（国内题库覆盖好）/ Bing Search API，接口同为"检索+LLM 整理"结构，可平替 |
| 3 | **去手写无 1:1 替代**：豆包图生图的 inpainting 效果，数据万象"图像修复"需传 mask，手写区域自动分割要自己做（或混元图像编辑能力灰度中） | 中 | 先验证 CI 图像修复+简单 mask（如手写笔迹颜色检测）；不行则降级为"擦除提示词走混生生图"，或该功能标注"迁移后暂不可用"，其余功能先行上线 |
| 4 | **ICP 备案时长**：7-20 工作日不可压缩 | 中（时间） | 第一天提交；期间全部开发用「微信开发者工具不校验域名」模式（`urlCheck: false`）+ H5 本地联调 |
| 5 | **57 处查询改写**工作量大，且 `user_id` 隔离是安全红线 | 中 | 逐模块改 + 每模块跑 MIGRATION §4 隔离测试（换 `X-User-Id` 互不可见） |
| 6 | 云托管冷启动/实例休眠可能导致首请求慢 | 低 | 配置最小常驻实例数 ≥1 |
