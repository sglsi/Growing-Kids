# 密钥管理与安全约定

> 📌 **归档状态**：本文为历史设计稿，**已并入 `docs/design/GK-ADD-07-安全与隐私设计说明书.md`（GK-ADD-07 安全与隐私设计说明书）**。
> 现行规范与现状以 GK 文档为准；本文仅作决策凭据与演进过程留档，**不再单独维护**。

> 2026-10-19 立。背景：思傅问「`.env` 里一堆密码/密钥都是明文，这样安全或合适吗」。
> 结论先行：**本机开发阶段明文放 `.env` 是标准做法，可以继续；但有几条硬红线不能破。**

---

## 一、结论：明文 `.env` 本身没问题

这是 12-Factor App 的标准做法——配置（含密钥）从环境变量注入，代码里不硬编码。
业界默认形态就是「一个 gitignore 掉的 `.env` 文件 + 一个只放占位符的 `.env.example`」。

**本项目当前状态已核实（非推测）**：

| 检查项 | 结果 |
|---|---|
| `server/.env` 是否被 git 跟踪 | ❌ 否。`git log --all -- server/.env` 为空，从未提交过 |
| `.gitignore` 是否覆盖 | ✅ 有 `.env`、`.env.*`，且 `!.env.example` 例外保留 |
| `.env.example` 是否含真值 | ❌ 不含，只有 `<密码>` / `<host>` 这类占位符 |
| 小程序端是否直连 Supabase | ❌ 不直连。前端只调自家 `/api/*`，包里没有 anon key |

所以：**只要 `.env` 不出本机，当前的形态是合规的**。

---

## 二、真正危险的是什么

不是「明文」这个形式，而是**这些密钥一旦外泄的爆炸半径**：

| 密钥 | 权限 | 泄漏后果 | 危险度 |
|---|---|---|---|
| `COZE_SUPABASE_SERVICE_ROLE_KEY` | **绕过 RLS**，整库读写 | 全量数据被读/被删 | 🔴 最高 |
| `DATABASE_URL`（新增） | 整库 DDL + DML | 同上，还能删表 | 🔴 最高 |
| `WX_SECRET` | 微信接口凭据 | 可换 session_key、伪造登录态 | 🔴 高 |
| `COZE_SUPABASE_ANON_KEY` | 受 RLS 约束 | ⚠️ **本项目 RLS 全是注释状态**（`0002` 里 `enable row level security` 被注释），等于裸奔 | 🟠 中高 |
| `WX_APPID` | 公开信息 | 无 | 🟢 低 |

> ⚠️ 关键：**RLS 没开**。Supabase 的 anon key 设计上可以公开（靠 RLS 兜底），
> 但本项目 `migrations/0002_fresh_schema.sql` 里 RLS 语句全是注释，且后端用 service_role 访问。
> 所以 anon key 现在**不能当公开值处理**。

---

## 三、硬红线（必须遵守）

1. **`.env` 永不进版本库。** 提交前用 `git status --short` 扫一眼；
   不确定就跑 `git log --all --oneline -- server/.env`，有输出说明已经泄了，要立刻吊销密钥并清历史。
2. **新增环境变量时同步改 `.env.example`**，只写占位符，**绝不写真值**。
3. **不要把 `.env` 贴进聊天/工单/截图。** 需要帮忙排查时，把值打码（`sed -E 's/(=.{6}).*/\1.../'`）。
4. **生产环境不用文件。** 部署到微信云托管 / 服务器时，走平台的「环境变量配置」面板注入，
   文件不落盘、不进镜像。
5. **密钥轮换**：怀疑泄漏就立即在 Supabase 控制台 `Project Settings → API keys` 点 Rotate，
   换完同步更新 `.env` 和部署环境的变量。

## 四、可选加固（按性价比排序）

| 优先级 | 动作 | 说明 |
|---|---|---|
| P0 | 开 RLS | 把 `0002` 里 4 条 `enable row level security` 打开并配策略。但后端走 service_role 不受影响，主要防 anon key 暴露 —— 由于小程序不直连 Supabase，实际收益有限 |
| P1 | 生产用平台密钥管理 | 微信云托管 / 腾讯云 SSM / GitHub Actions Secrets，别把 `.env` 拷上服务器 |
| P1 | 分离开发与生产密钥 | 生产库不要用开发库的 service_role key；Supabase 免费版只有 2 个项目，至少做到 key 级别隔离 |
| P2 | 本机加密存储 | 用 `git-crypt` / `sops` / 系统钥匙串存 `.env`。收益不大（攻击者拿到 shell 一样能读），**除非多人协作**才值得上 |
| P2 | 加 `.env` 备份到密码管理器 | 防止本机硬盘故障后密钥全丢（Supabase 的 service_role key 可重新查看，DB 密码只能重置） |

---

## 五、一句话回答

> 本机开发阶段**合适**，继续用。唯一不能破的是「别让它进 git、别贴到任何线上渠道」。
> 上生产时把值搬到平台的密钥管理里，`.env` 只留在本机。
