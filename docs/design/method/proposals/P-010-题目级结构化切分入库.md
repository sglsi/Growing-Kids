### ① 判据（L1 / L2 / L3）

**保护性归因：L1 延迟——不新增学习行为，只保护「到期复习时拿到的答案确实是这道题的答案」这一前提。**

与 `P-009` 一样诚实说明：把切分前移到入库阶段，不改善 L1（隔 N 天还能做对）、L2（无提示）、L3（迁移）中的任何一条。它修的是更靠前、也更难修的一环——**错误能不能被定点修复**：

> `P-009` 的「一题一对象」是检索时从全文临时切出来的，对象没有稳定身份、没有来源坐标。家长一旦反馈「答案讲的是另一道题」，唯一手段是改判定算法，而改阈值会误杀一批正例（§8.4 的 40/40 ROC）。合合信息 TextIn 把「解析张冠李戴」列为行业卡点，根因**不在 OCR**，而在「题目 / 答案 / 解析对应关系缺乏工程管控」。

本提案把绑定关系变成**有 ID、有指纹、有版本、可排除**的库内对象：错了改一行，不动算法。宣称同步降级（见 ④）：只说「在资料正文里找到 / 没找到」，不得说成「都能搜到」「精准定位到题」「已证明解析归属」。

> ⚠️ 同 P-005 / P-006 / P-008 / P-009 的写法：若评审认为「保护性归因」不足以支撑 L1，可当作「不涉及判据的检索正确性工程」，直接按 ⑥ 的显式不宣称处理——本提案的证据强度不依赖判据归属成立。

### ② 归因（不变量 / 约束 / 准则）

- **不变量**：无直接不变量。I1 提取 / I2 修正 / I3 间隔均不涉及「入库时怎么切题」——本提案在**数据工程与结果可信度层**，不在学习机制层。
- **约束**：**C-资源**（工作记忆与注意力有限）。家长核对答案时若要自己在几十道连排题里找「这段解析属于哪道题」，是与学习无关的外在负荷；找错了还会把错误讲解带进复习。
- **相关准则**：
  - `GK-SRS-20a M10`：宣称不得超出能力 —— 纯文本无版面坐标时，不得把「结构化绑定」说成「已证明解析归属」；`exact` 必须带可复核的来源位置。
  - `GK-SRS-20a M11`：「找到 / 没找到」是**如实告知**，不是拦截，也不是逼用户去开 AI 开关。
  - `GK-SRS-20a M8`：明确隔离 —— 不碰 `REVIEW_INTERVALS`、不进「到期首次作答正确率」分组。
- **合规约束（外部、不可放宽）**：《双减意见》§15 与 2021-12-13 教育部通知（详见评审 §7.6）⇒ `exact` 才放解析、`topic` 答案必须为 `''`。本提案只有收紧、没有放宽。

**替代证据（工程实测 + 外部技术资料，均非学习效应）**：

3. **外部技术资料**（评审 §7）：作业帮专利 `CN113505786A` 摘要原文「基于空间位置对第一文本数据进行切割拆分，确定待检索的题干内容」；TextIn 把「解析张冠李戴」列为行业卡点且根因在对应关系缺乏工程管控；各家统一「一题一对象 + 多级漏斗 + 置信度闸门」。
4. **本轮本机实测**（M32）：L3 只读取样 4 份整本教辅切出结构化对象后，负例假 `exact` **0/4**、正例 **28/28**、来源定位 **28/28**；六类入库校验逐条可触发；定点排除坏对象后，同文档其它题仍 `exact=true`。

### ④ 算子（T / D / X）

本提案主体是 **D（降维）+ X（明确不做）**。`GK-OPS-22` §3.2 三问决策器（20a §5.1）留痕：

| 问 | 结论 |
|---|---|
| Q1 量级 | 不适用（不是学习干预，不产生新的学习行为） |
| Q2 覆盖 | 不适用（同上） |
| Q3 可测 | **不可测**——「判定精确率 / 可修复性」不在现有结果指标里 ⇒ 按 §3.2 边界情形判 **D（降维）**：只做正确性工程，不做指标、不做宣称 |

| 约束 | 内容 | 理由 |
|---|---|---|
| **① 只做 P1 工程管控层** | `0026` 建对象表、离线构建脚本、判定层消费结构化对象、唯一取数口、M32 验收集 | 评审 §9.0；P2/P3 未批准 |
| **② 一题一对象 + 稳定身份** | `object_fingerprint`（内容+位置+规则版本）、`source_revision`（正文 sha256）、`engine_version`、字符区间、题号 | 对应业界 `question_id` + 父子 ID + 来源坐标；可复算审计 |
| **③ 只收紧不放宽** | `judgeStoredObjects()` 复用 P0 的 `judgeQuestionObject()` 六条硬闸与 `selectUnique()` 唯一性闸门，额外叠加指纹/版本/区间/`link_status` 校验 | 六因子仍是串联否决；改成打分加权就退化回「主题相似」 |
| **④ 唯一切分真相源** | 构建脚本只 `require` 编译后的 `question-match.ts`；产物比源码旧直接退出 | 两套题号规则必然漂移；`question-match.ts` 保持零依赖单文件（M27 tsc 单编后 require） |
| **⑤ 幂等 + 只写目标表** | 唯一键 upsert；只 `insert into question_objects`；不改源表任何列；三条防误删护栏；NUL 清洗 | P-008 踩过 `--full-clean` 误删 65,890 行与 PG text 不接受 U+0000 |
| **⑥ 口径逐字一致** | library 来源按 `.slice(0, 60_000)` 计算 `source_revision`，与 `searchLibraryDocs()` 一致 | 否则对象被永远判「正文已变化，对象过期」；M32 静态断言 |
| **⑦ 无 RLS 必带 user_id** | 取数口唯一，`.eq('user_id', userId)` + 来源收敛；查询失败留痕不静默吞错 | 项目数据红线 + M18 精神 |

| **⑨ 铺量期不倒退** | `QUESTION_OBJECTS_STRICT` 默认 0：无结构化对象时回退 P0；开 1 则无对象即不给 `exact` | 现网尚未铺量，默认开会把 `exact` 全清空；开关为 0 期间 P1 不改善残余风险，文档不得写成已消除 |
| **⑩ 明确不做** | 版面坐标 / 向量库 / Reranker / LLM 兜底 / 改召回 / 建正文索引 / 写生产数据 / 部署 | §8.4 证伪；4 核 4G、`ai_enabled` 默认 false、个人主体 AI 入口收起；P2/P3 未批准 |

**P2 / P3 明确未批准**：`0026` 正文索引与 `text_flat`、`searchLocal()` 双通道召回、`keyHits` 统一打分、`MAX_DEEP_FILES` 3→20~30、删 `coverage<0.2` 闸门、呈现层来源前置 —— **一项都不做**。

### ⑤ falsifier

| # | 触发条件 | 处置 |
|---|---|---|
| 1 | 结构化链路出现任何 1 个 P0 拦得住的假 `exact` | 立即停止，回退 P0；误判零容忍 |
| 2 | 正例召回跌破 90% 或来源定位错对象 | 停下查切分/指纹口径，不得以「更安全」为由做成永远判不出 |
| 3 | 内容指纹不可复算，或正文变更后旧对象仍被复用 | 立即停止；等于版本校验形同虚设 |
| 4 | 定点排除误伤同文档其它题，或 `link_status='rejected'` 仍能 `exact` | 立即停止；这是 P1 存在的唯一理由 |
| 5 | `strict=1` 时无对象仍回退 P0，或 `strict=0` 时无对象却给了 `exact` | 视为开关失守，按 `GK-OPS-22` §3.4 处置 |
| 6 | 构建脚本改了源表、绕过编译产物陈旧检查、或去掉防误删护栏 | 立即停止；P-008 的 65,890 行误删教训 |
| 7 | **把 P1 说成「已证明解析段归属」「已解决张冠李戴」「精准定位到题」** | 按 M10 立即订正；§9.4 与 M32 有实证断言钉着 |
| 8 | 未经单独拍板就在 L3 跑 `--apply`，或未 bump `CACHE_VERSION` | 立即停止并按运维手册回滚；写生产前必须备份 |
| 9 | 因 P1 落地而顺手放宽召回（P2/P3 任一启动） | 立即回退；第二层上线准入仍未全绿 |

**复核时点**：每次 `pnpm verify:ci` 复核 ①②③④⑤⑥⑧（M32 + M27 自动）；⑦⑨ 随每次文档/文案改动与上线评审。

**🔴 已登记且未消除的残余风险**：纯文本没有版面坐标，若原始文本流本身把别人的解析排在这题后面，结构化切分照样会把它们绑成一行。M32 保留一条「重算指纹后的别人解析仍 `exact=true`」的实证断言，防止后人把风险写成已解决。彻底消除需要版面坐标（后续阶段，未批准）；期间 `exact` 必带 `source_location` 供家长回原文复核，这是兜底不是免责。

## 附：为什么 P0 完成就能启动 P1（决策口径澄清）

§8.5 的「P1/P2/P3 一律不启动」针对的是「**召回变宽**会规模化放大残余风险」。P1 做的是「**判定收紧 + 错误可修**」，`judgeStoredObjects()` 只会在 P0 六条硬闸之上再拒绝，不会新增任何 `exact`。两者不是同一类动作，因此启动 P1 不违反「未达标不放行」；真正仍被闸门拦住的是 P2/P3 与 strict 上线。

**决策台账按追加式记录**：`P-009` / `D-012` 里「P1/P2/P3 未批准」是当时拍板范围，作为历史事实保留（M31 有静态断言），本提案不回溯修改它；`D-013` 追加记录 P1 的改判。
