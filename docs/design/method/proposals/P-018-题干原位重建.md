## 4. 关键判断

- 公式位置**不需要**靠 PDF 版式推断——`char_start` 与 docx 文字流同一坐标系，可直接给出插入点。
- 几何图**必须**从 docx 原图抠（png/jpeg 无损），不走 PDF 渲染。
- 公式图像**不能**用 `wmf2svg`（装字体后仍失真，见 §5）。**必须让 LibreOffice 渲染**：docx→PDF 后公式是 `IMAGE` 对象，`get_bounds()` 给出精确 bbox。
- 只用「前后锚点算间隙」不够稳：左锚点常以标点结尾（字框仅 1.6pt），会被误判跨行，且公式字号大于正文时会带进上一行。**正解＝锚点定大致区间 + 在该页 `IMAGE` 对象里按 x 重叠度挑 bbox**。
- `v:shape` 的 `width/height`(pt) 是文档声明的显示尺寸，可作**裁切校验器**（`|bbox_w − shape_w|` 超阈值即拒绝）；本轮先记账，不入准入。

### 5.1 复核修正：字符级错乱的真实根因

> ⚠️ 本节**推翻**本提案上一版及 `8462d41` 的归因。上一版把错乱归为「libwmf 恒等映射 + 替代字体不行」，属**假证伪**：17:31 那批 PNG 是在 L3 **尚未安装 Symbol 字体别名**时渲染的，装完别名后没有重渲就下了结论。

**事实一：恒等映射本身是对的。** 对全部测试 WMF 的 `META_EXTTEXTOUT` 字节与 SVG `<text>` 码位做计数对照：`0xA3`6↔`£`6、`0xB4`10↔`´`10、`0xBC`1↔`¼`1、`0xEF`10↔`ï`10、`0xEC/ED/EE`3↔`ì/í/î`3、`0xD0/CE/D2/F5`↔`Ð/Î/Ò/õ`，每一对完全一致 ⇒ `libwmf 0.2.13` 做的是 `b → U+00B` 的逐字节恒等映射。

**事实二：「Symbol 私有码表 ↔ Latin-1 完全对应」在 Symbol 字体内部成立，且不需要建表。** 极简 SVG 探针（12 个码位 × 4 个字体族 × 2 套 fontconfig）实测：`font-family:Symbol` 下 `U+00A3` 与 `U+F0A3` 都画 `≤`、`U+00B4`/`U+F0B4` 都画 `×`、`U+00BC`/`U+F0BC` 都画 `…`、`U+0044`/`U+F044` 都画 `Δ`；现网别名 `Standard Symbols PS` 与微软原版 `symbol.ttf` 结果一致。字体 cmap 解析印证：原版 `symbol.ttf` 有 Mac Roman 单字节表 + PUA `U+F020..U+F0DD` 表，替代品有 Unicode BMP 表，两者在 U+00A3 处都指向 `≤` 字形。

**事实三：三方最小对照把变量锁死。** 同一个 `<text style="font-family:Symbol">£</text>`：A 无 Symbol 字体 → `£`；B 现网别名 → `≤`；C 原版 symbol.ttf → `≤`。⇒ 17:31 观测到的 `£` 是 **fontconfig 无 Symbol 映射导致 Pango 回退到普通文本字体**，不是编码转换错误。

**为什么仍不走这条路（三条独立阻塞）**：

1. **字体归属错**：真实 SVG 里高位字符挂在 `Symbol` 和 `Times` 两种 family 下；`font-family:Times` 的 `Ð Î Ò õ Ó £ ¼` 共 15 处是 libwmf 把符号字节误标为 Times。把 28 处「Times + 高位字符」的 text 改判为 Symbol 后，`£→≤`、`¼→…` 确实修对，但同时冒出 `S_@J°`、`S_Z∪EOB` 等新错字且右侧被裁 ⇒ 一条规则覆盖不了。
2. **不止一张码表**：WMF 里实测出现 `Times New Roman` / `Symbol` / `Courier New` / `MT Extra` / `Euclid Extra` / `DSMT6/7`；`MT Extra`、`Euclid Extra` 各有独立私有码表，`0xEF/EC/ED/EE` 是括号/根号**拉伸构件**（只有 PUA，无标准 Unicode）。探针显示 `font-family:MT Extra` 时 U+00A3 画 `£`、U+F0A3 才画 `≤`。
3. **度量绑定原字体**：MathType 把每个字符的 x 坐标与 Dx 间距按原版字体字形宽度写死进 WMF；换字体族后字形宽度变化 ⇒ 上下标重叠、分式错位、公式被裁。三路对照里 `S_ÃŶ±` 一组三行都重叠，改 family 的那行更严重。字符映射解决不了这一层。

**结论**：不入库的理由从「字符必错」改为「字体归属与度量不可控 + 时间/CPU 更贵（§5.2）」，**仍走 PDF**。PDF 里 LibreOffice 已完成完整排版，本项目只按 bbox 裁图、不再解释任何字节 ⇒ 从根上绕开上述三条。

### 5.3 PDF 路线会不会「把一个符号识别成另一个」

思傅 2026-11-08 20:40 追问：WMF 路线有字符层错乱，PDF 路线会不会同样把 `≤` 认成 `£`？

**结论：这条链路上不存在「识别」这一步 ⇒ 该错误类别在设计上不成立；但存在另一类静默降质（符号整体消失），已加硬闸门。**

**证据一：公式在 PDF 里是图像，不是字符**（L3 `/tmp/pdf-anatomy.py`，同一份 46 页 PDF）：

| 观测 | 结果 |
|---|---|
| 页面对象分布 | `FORM 46 / PATH 146 / IMAGE 911 / TEXT 4804` |
| 文本层长度 | 16,802 字；正文以 Unicode 输入的 `≠ × ≤ ≥ ±` 全部正确（`≠` 37 次、`±` 7、`≥` 6、`≤` 4、`×` 3） |
| 文本层可疑拉丁乱码 `£ ´ ¼ Ð Î ï Ö Ì Ò` | **0 个** |
| 文本层题干样例 | 「使分式 ␠ 有意义的字母 x 的取值范围」——MathType 公式处**没有任何字符** |
| 公式载体 | `IMAGE` 对象（`FlateDecode` / `DCTDecode` 位图），非 TEXT 对象、无 ToUnicode CMap |

本项目随后只按 `get_bounds()` 取 bbox 裁像素 → WebP，**全程不调用字符解码、OCR 或码表映射**。「`≤` 被识别成 `£`」必须先有「字节 → Unicode 字符」这一步，这条链路没有。这是与 WMF→SVG 路线的**结构性差异**，不是概率高低。

**证据二：真实失效模式是「缺字」而非「换字」**（`/tmp/pdf-symbol-check.py` + `/tmp/pdf-ink-stat.py`）。同一 docx 各转一次 PDF：A 现网（`Symbol`→`Standard Symbols PS`），B 用隔离 fontconfig 排除全部符号字体（`Symbol`→`Liberation Serif`），均用独立 `UserInstallation`：

| 指标 | 结果 |
|---|---|
| 前 12 页 IMAGE 对象 | A/B 各 233 张，公式尺寸各 206 张，尺寸差异 **0** |
| 有像素差异 | 144 张 |
| 墨迹量化 | **91 张 B 明显少于 A**（中位数 **−26.9%**）、**0 张 B 多于 A**、115 张基本持平（抗锯齿/微调） |
| 肉眼对照 | `x ≠ −2` → `x  2`；`2 − x ≠ 0` → `2  x  0`；`x < 2` → `x  2` |
| 是否出现拉丁替换 | **未出现** `£ / ´ / Ð / ï` 之类「一个符号画成另一个」 |

即字体解析失败时符号**整体消失**，不会被画成另一个字符。抽检 A 版 36 张公式图：`x ≠ −2`、`y = 3/(2−x)`、`y = √(x+1)/(x−2)`、`x ≥ −1`、`x + 1 ≥ 0`、`1/(x²−1)`、`5/2` 全部完整正确，无乱码、重叠或切边。⚠️ 这是 **36 张方向性抽检，不是全量符号级验证**。

**风险性质**：别名一旦丢失，soffice 退出码 0、PDF 生成成功、bbox 匹配成功、WebP 正常入库，**全链路不报错**，只有家长看到残题才发现——与「只换 dist 会漏 `ocr-engine/*.py` ⇒ 静默降级」同类。

**护栏**：`netdisk-inline-build.mjs` 的 `assertSymbolFont()` 在 `--apply` 前执行 `fc-match Symbol`，结果不含 `symbol`（大小写不敏感）即 `throw` 拒绝执行；dry-run 不受影响，`INLINE_SKIP_FONT_CHECK=1` 仅供诊断逃生；`M40 B9` 守此契约。L3 实测：正常配置打印「字体闸门通过：StandardSymbolsPS」并正常处理 1 份（7 图 / 4s）；隔离配置下 `exit 1` 且打印修复命令。

**其它错误类别（均非「认错符号」）**：bbox 匹配失败 ⇒ 宁缺不顶替；跨行浮动 ⇒ 跳过；`DCTDecode` 有损压缩 ⇒ 细线略糊（已用 `scale=4` 渲染）；超大 docx ⇒ 480s 超时跳过。这些都有护栏或显式缺口登记。

### 5.4 工具分工核实与「换 Word / WPS」评估（21:20 追加）

#### 5.4.1 先纠正前提：docx 的**文字处理从来不是 LibreOffice**

| 环节 | 实现（真相源） | 是否经 LibreOffice |
|---|---|---|
| 题干 / 解析文字 → `question_objects` | `ocr-engine/pdf_tool.py :: extract_docx()`（L3 部署在 `/opt/gk/ocr-engine/pdf_tool.py`）：`zipfile` 解 `word/document.xml` + 页眉页脚，先保留段落边界再 `re.sub(r'<[^>]+>', '', xml)` 剥标签 | ❌ 零依赖，纯 Python |
| 公式 / 几何图 → WebP | `server/scripts/netdisk-inline-crop.py :: ensure_pdf()` 调 `soffice --headless --convert-to pdf`，再由 `pypdfium2` 取 `IMAGE.get_bounds()` 裁切 | ✅ **仅此一步** |
| P-017 整块原题快照 | `netdisk-figure-crop.py`，同样调 soffice | ✅ |
| 扫描版 PDF | OCR 引擎（PaddleOCR / PPStructureV3） | ❌ |

LibreOffice **不产生任何一个入库文字**，它只产出一份「给人看的像素底图」供裁切。因此 P-017 立项时的根因——`<w:object>` 被正则当标签整块剥掉，题干成「抛物线中，当时，；当时，或3」残串——属于**抽取器口径**，换任何排版引擎都不会改变。

#### 5.4.2 用 Word 自己验证「换工具能否拿到公式字符」

本机 `Microsoft Word 16.0 (Office16/WINWORD.EXE)` COM，只读打开同一份 `468245103369510.docx`（951KB / 18 个 WMF）：

| 观测 | 结果 |
|---|---|
| `Document.InlineShapes.Count` | **208**，类型分布 `1:20`（`wdInlineShapeEmbeddedOLEObject`，正好对应 docx 内 `<w:object>` **20** 个）/ `3:188`（Picture） |
| `Document.Content.Text` | 27,424 字；公式处上下文 `x2＝， 故答案为：x1＝，x2＝． 7．解下列方程：…` |
| Python 剥标签口径 | 27,107 字，**同类残串形态完全一致** |

⇒ 在 Word 眼里公式也是**图形对象而非字符**，Word 自己的文字层同样拿不到公式。这不是 LibreOffice 抽错，也不是「识别」问题，而是 docx 的数据形态。**换 Word / WPS 不会消除「只有文字没有图」**；P-018 的「按字符偏移原位插图」是唯一解法。

#### 5.4.3 换工具能不能消除「转换过程中的错误」：分三层

| 层 | 换 Word / WPS 会不会更好 | 判断 |
|---|---|---|
| 文字层残串 | **完全不会** | 数据形态决定（§5.4.2 实证），与渲染器无关 |
| 公式渲染字形 / 度量 | **理论上会更好** | Word 原生 GDI + 原版 Symbol 字体 + MathType 原始 Dx 间距，最接近作者看到的排版；能降低「字体替代导致符号消失 / 上下标错位」这一类风险。**这是换工具唯一真实收益** |
| 工程链路 | **明显更差，且会打断现有实现** | 见 §5.4.4 四条 |

#### 5.4.4 四条工程阻塞（前三条为实测）

1. **Word 无人值守导出 PDF 在本机挂起**：COM 三次导出全部失败——1.36MB / 515 WMF（36 页）、951KB / 18 WMF（43 页）、346KB / **0 WMF**（36 页）；`Documents.Open` 与 `ComputeStatistics` 均正常，`ExportAsFixedFormat(...,17)` 与 `SaveAs2(...,17)` 都**无产物、CPU 归零、Responding=True、无窗口标题、进程需强杀**。⇒ 与公式数量无关，是 PDF 导出在该环境不可用；批量流水线不能依赖它。
2. **页数 / 页面坐标系不通用**：Word 报大样本 **36 页**、中样本 **43 页**，LibreOffice 版 PDF **均 46 页**。⇒ `figurePage` 不能当原书页码；`question_figures` 29,773 张 + `question_inline_figures` 2,306 张与 `engine_version` 绑定，换引擎必须 bump 版本并**全量重建**。
3. **现用裁图算法只在 IMAGE 对象上工作**：`pick_bbox()` 于 PDF 中筛 `type==3 (IMAGE)` 取 `get_bounds()`，LO 输出已确认公式为 IMAGE（§5.3）；Word 导出通常把 OLE / 公式展成**矢量路径或内嵌字体 TEXT** ⇒ 很可能一张都匹配不到，整条裁图链路要重写，且无证据表明新算法能保住现有 69.5% 定位率。
4. **部署与授权**：L3 为 4C / 3.7G 的 Linux 轻量实例，未装 wine / WPS / OnlyOffice；Word 需 Windows + 授权 + COM。WPS Linux 的 headless 批量转换**无稳定官方契约**（第三方资料称 `wps --headless --convert-to pdf` 可用，另有资料及 WPS 官方社区回复称无官方 headless、需 Xvfb 模拟 GUI，社区帖甚至直接建议改用 soffice）。⚠️ 这条是外部资料的**方向性判断，本项目未实测 WPS**，不作为定论。

**换不掉的错误类别**（与渲染器无关，逐条仍要面对）：bbox 跨行 / 浮动匹配失败（宁缺不顶替）、`DCTDecode` 有损导致细线略糊、超大 docx 480s 超时跳过、字体或组件缺失导致的静默降质、2 worker 的 profile 锁与超时孤儿进程。

#### 5.4.5 PDF 路线的真实优点

| # | 优点 | 证据 / 边界 |
|---|---|---|
| 1 | **结构上不会「把一个符号认成另一个」** | 公式在 PDF 里是 IMAGE 位图，只裁像素、无字符解码 / OCR / 码表映射（§5.3） |
| 2 | 规避 WMF 私有码表、PUA 构件、字体度量三难题 | LibreOffice 已完成排版，公式定型为像素；§5.1 / §5.2 已证伪直接解析 WMF |
| 3 | 快且省 | 同一 515 WMF / 46 页文档：8.1s / ≈8s CPU / 1 次 fork，vs WMF 路线 42.56s / ≈88s CPU / 1030 次 fork |
| 4 | 可批量、可运维 | headless + 独立 `UserInstallation` + `killpg` 超时 + cgroup `MemoryMax` + `ionice -c3 nice -n19` + `assertSymbolFont()` 闸门 |
| 5 | 输出小 | 2,306 张 / 37MB，平均 16.8KB/张；内容寻址 + WebP |
| 6 | 与判定层完全解耦 | 只写 `0029` / `0030` 两张映射表，`question-match.ts` 零改动，图不参与召回与打分 |
| 7 | 小程序可显示 | 复用匿名公开读 `GET /api/storage/files/*`（`<Image>` 不发鉴权头） |
| 8 | 免费、开源、可复现、无授权与合规负担 | LO 24.2.7.2 + 系统字体别名，配置落 `/etc/fonts/conf.d/69-gk-alias.conf` |

#### 5.4.6 PDF 路线的真实缺点（不回避）

| # | 缺点 | 现状 / 护栏 |
|---|---|---|
| 1 | **静默降质**：字体解析失败时符号整体消失，soffice exit 0、PDF / bbox / WebP 全链路不报错 | 已加 `assertSymbolFont()`；但闸门只查 `fc-match Symbol`，**查不出「字体在但字形缺」或 MT Extra 缺失** |
| 2 | **渲染质量依赖本机字体环境** | 不是 Word 原版 Symbol；LO 版本 / 字体集变化会改变输出，结果不可跨环境复现，字体配置必须进部署契约 |
| 3 | **定位率不满**：只认 IMAGE 对象，跨行 / 浮动 / 被合并拆分的公式匹配不到 | 单文档 1,086 个标记仅 755 成功（69.5%），331 个跳过 ⇒ 题干仍可能残；宁缺不顶替 |
| 4 | **页码不是原书页码** | 46 页 vs Word 36 页；`figurePage` 只能当内部索引 |
| 5 | **有损**：部分公式是 `DCTDecode`（JPEG） | 细线 / 上下标略糊，`scale=4` 渲染仅缓解，不能还原 |
| 6 | **每份都要重转换** | 7.1MB 重公式文档单份 480s 超时跳过；全量 7,273 份估计 10–20h（2 worker），峰值内存约 1.6G |
| 7 | **图是像素不是语义** | 不能复制 / 搜索公式、不能无障碍朗读、不能被 LLM 理解；放大看大图受原始裁切分辨率限制 |
| 8 | **只解决「看得懂」，不解决「找得对」** | 图来自库内**相似例题**而非本题答案；`answer` 仍空、`verified` 仍 false；不宣称命中提升，`0021 review_events` 仍 0 行 |
| 9 | **覆盖率极低** | 当前仅 117 / 7,273 份（1.6%），手机上暂时看不到带图 refs |
| 10 | **并发运维固有复杂度** | 单实例 profile 锁、超时孤儿 soffice、cgroup 限额；已修但属于该方案的结构性成本 |

**结论：不换工具，仍走 LibreOffice → PDF → bbox → WebP。** 理由不是「Word 不准」，而是：① 文字层问题与渲染器无关，换工具无收益；② 唯一理论收益（字形 / 度量）可用字体别名 + 闸门覆盖到工程可用水平；③ 换工具会打断已验证的 IMAGE bbox 链路、改变页码坐标系、引入 GUI / 授权 / 无人值守不可用的新风险。若将来确要走 Word，必须**另立提案**，先解决「Word 导出 PDF 里公式以何种对象存在」这一前置问题，再评估重建成本。

## 6. 决策

1. 新增迁移 `0029_question_inline_figures.sql`：只存「图 ↔ 题目对象 ↔ 插入点」映射，**不动任何既有表**。
2. 新增迁移 `0030_question_inline_done.sql`：扫描记账（跑过但没有可入库图的文档也记下，避免反复重试）。
3. 新增离线构建 `netdisk-inline-crop.py`（python 段）+ `netdisk-inline-build.mjs`（node 段）。
4. `ReferenceExample` 增 `inlineFigures[]`（`charOffset / kind / url / width / height`）。
5. 前端用 `RichText` 按 `charOffset` 切段内联渲染：公式图按行高缩放内联，几何图独占一行。
6. `CACHE_VERSION v13 → v14` + 旧断言同步 + 新增 `M40`。
7. `P-017` 的整块快照**保留**作为兜底（不删表、不退库），两套并存。

## 7. 硬约束

- `question-match.ts` **一行不动**（sha256 `84f998ff…` 必须不变）。
- 六条硬闸 / `answer` 空 / `verified=false` / `canAdopt` / `strict=1` 零放宽。
- 内联图**不参与召回与打分**、不改 `note`、不改 `match_level`。
- **定位失败就不入库、不下发**；绝不拿相邻题或相邻行顶替，绝不占位图。
- 公式裁切必须**只含该公式**：裁完白化阈值 242 再 trim，肉眼验收不合格即不入库。
- 几何图必须从 docx 原图抠，不得用 PDF 渲染替代。
- 图不得插到 `reference_disclaimer` 之前。
- 不新开需登录的图片端点（复用 `GET /api/storage/files/*`）。
- 构建与压测在 L3 必须走 cgroup 兜底（`MemoryMax`）+ `ionice -c3 nice -n19` + 单批超时；worker 数由实测确定。

## 8. 保留形式

允许：「公式与图形已按原文位置还原」「原文档第 N 页」。
禁止：§3⑤ falsifier 第 10 条里的全部表述。
