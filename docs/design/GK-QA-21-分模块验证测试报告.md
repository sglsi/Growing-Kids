## 2. 怎么跑

```bash
# 全量（约 6 分钟，后端需正在运行）
cd server && node scripts/verify/run.mjs

# 只跑指定模块
cd server && node scripts/verify/run.mjs M01 M11

# 指定后端（真机 / 远程）
GK_API_BASE=http://192.168.3.242:3001/api node scripts/verify/run.mjs
```

退出码：`0` 全通过，`1` 有失败（可直接接进 CI）。  
报告落盘：`docs/test/verify-summary.md`（人读）与 `docs/test/verify-results.json`（机器比对）。

### 2.1 设计取舍

| 决策                                   | 理由                                                 |
| ------------------------------------ | -------------------------------------------------- |
| **零依赖，只用 Node 内置 fetch/FormData/fs** | 为跑一次验证装半个 npm 宇宙不划算；套件要能拷到任何环境就跑                   |
| **打真实后端，不做 mock**                    | 验的是部署形态下的行为。历史坑（缓存未失效、签名 URL 缺失）都只在真实链路上复现         |
| **自带清理，用独立测试身份**                     | 每个 run 用 `verify-<时间戳>` 作 device id 换匿名身份，不碰真实用户数据 |
| **失败即留证**                            | FAIL 时记录状态码 + 响应体前 300 字符，不用再手工复现一次                |
| **不追求覆盖率数字**                         | 沿用 QA-15「回归优先」：优先把历史事故固化成用例                        |

### 2.3 接进 CI（`.github/workflows/ci.yml`）

按「跑起来需不需要外部依赖」切成两个作业，而不是一股脑全跑：

| 作业 | 触发 | 内容 | 为什么这样切 |
|---|---|---|---|
| **gate** | 任何 push / PR / 手动 | 装依赖 → `build:server` → `build:weapp` → `run.mjs M12 M13` | 不需要数据库、OCR、任何密钥。**代码进主干前连编译都不过**这件事必须无条件拦住 |
| **api-core** | 仅在配了 `GK_SUPABASE_*` 密钥时 | 起 NestJS（local 存储驱动）→ `run.mjs M01–M08 M15` | 需要一套真实的 Supabase 与严格令牌环境。没配就**跳过而不是失败**——个人项目不该因为没给 CI 配库而常年红 |

⚠️ 三个刻意的取舍：

1. **不跑 M09–M11 / M14**：它们要 PaddleOCR 侧车（几百 MB 模型 + Python venv）、大模型 Key、
   本机备份计划任务。在 runner 上复现成本远高于收益，留给"交付前本机跑一次"。
2. **gate 必须先构建再断言**：M13 会检查 `dist/` 与 `server/dist/` 存在——不构建就直接跑，
   等于用一个恒假的断言骗自己。
3. **接口作业的存储用 local 驱动**：跑完即弃，不去动真实 bucket；`AUTH_TOKEN_SECRET` 必须配，
   因为严格令牌模式是整套用例的前提（裸 `X-User-Id` 一律 401）。

本地等价命令：`pnpm verify:ci`（gate 那套）/ `pnpm verify:core`（接口那套）/ `pnpm verify`（全量）。

### 2.4 OCR 识别质量 GT 评测（`server/scripts/ocr-gt/`，独立于本套件）

本套件验的是「接口行为对不对」，验不了「识别得准不准」——后者需要真值。所以单开一条链路：

```bash
cd server
node scripts/ocr-gt/gen.mjs          # 由 cases.json 确定性生成图片
node scripts/ocr-gt/run.mjs          # 评测，出 report.md / report.json
node scripts/ocr-gt/run.mjs --update-baseline
```

- **数据三层**：`clean`（合成印刷体）/ `degraded`（旋转 3°、模糊压对比度）/ `real`（真实照片，
  丢进 `cases/` 配同名 `.txt` 即自动收录，**不需要改代码**）。
- **三个指标**：CER（整体准不准）、行命中率（有没有整行丢——教辅里丢的往往是答案行）、
  数字召回（数错了等于全错）。归一化只做无损变换，**不**把 `×/x`、`O/0` 当同一个字。
- **退出码 0/1/2**：0 达标、1 不达标或相对基线退步、**2 = 环境跑不起来**。把 2 拆出来是因为
  "侧车没起来"被当成"质量变差"会让人去改本来没坏的代码。
- **已知缺陷用 `knownIssue` 标**（xfail）：报告里显形、但不判失败；修好后它会提示"可以移除标记"。

首评结果：7 个案例平均 CER **7.2%**，其中 4 个 clean 案例 0.0%（`arith-clean`/`word-problem`/
`english-lines`），`choice-options` 2.9%，退化案例 0~2.7%（说明摆正链路有效）。
`vertical-sum` 45% 已登记为 `R-算法-07`。

> GT 首跑就抓到两个真问题：一是**选项阅读序错乱**（B 排到 A 前面，CER 25.7% → 修复后 2.9%），
> 二是**竖式符号行丢失**（`+` 与横线整行没了，两个引擎一致，登记未改）。两条都不是"崩了"，
> 接口一直 200、肉眼扫一眼也不刺眼——**只有拿真值比对才看得出来**。

### 2.5 方法论硬门（M16）与度量口径

`GK-OPS-22` 把 `GK-SRS-20a` 接进流程后，其中**三条硬门**落成本套件的第 16 个模块。它们不测接口，测的是「设计与断言有没有走样」：

| 门 | 机器验什么 | 依据 |
|---|---|---|
| **H1 归因门** | `docs/design/method/proposals/*.md` 六栏齐备且非占位；引用的 `GK-SRS-20a M<n>` / `20b 文献 <n>` 真实存在 | OPS-22 §3.1、§4.1 |
| **H2 口径门** | 用户可见面（`src/**`、SRS-03 手册）不含禁用宣称词（`ZPD` / `最近发展区` / `智商` / `提分` …） | 20a M10、20b §5.3 |
| **H3 同步门** | **镜像参数**逐字一致：复习间隔表（20a ↔ 20b ↔ `review.ts` ↔ M15 断言）、导出默认口径（`=== true` ↔ M10 三条用例） | 20a §5.6 落地三关 |

**三个刻意的取舍**：

1. **只验机器能判定的部分。** 「归因是否成立」「边界写得对不对」留给人——把它塞进断言只会逼出假证据，这一点写进了 OPS-22 §4 开头。
2. **门只有三条。** 加到八条的结果是所有人学会绕过；三条刚好能覆盖「缺栏 / 违禁 / 漂移」这三类静默失效。
3. **退出码三态**（0/1/2），`2 = 环境异常`。混进 `1` 会让人去修本来没坏的文档。

**负样本探针（证明门不是摆设）**：故意改坏三处后再跑，门分别报出**具体文件:行**与**不一致的两个值**：

```
✗ H1  ④ 算子 正文为空或仍是占位；引用了不存在的准则 M99；引用了不存在的文献 99（20b 共 58 条）
✗ H2  src/__probe_claim.ts:1 含禁用宣称「ZPD」
✗ H3  间隔表漂移：review.ts = [1,2,5,10,21]，M15 断言 = [1,3,7,14,28]
      间隔表漂移：20a 写的是 [1,3,7,14,28]，代码是 [1,2,5,10,21]
```

**两条度量纪律（不在套件里，只能人守）**：

- **断言覆盖率只报不拦**。20a 附录 A 三向索引里仍有多格是 `——`（M1/M2/M5/M6/M9/M10 尚无对应断言）；把它做成硬门会立刻出现「为了覆盖率写永真断言」，比没有断言更糟。
- **唯一够格的结果指标**是「到期首次作答正确率（按档位分组）」。`timeline_items` 已有 `review_count` / `last_reviewed_at` / `next_review_at`，到期那次作答天然满足 L1（隔了 N 天）+ L2（无提示）。代理指标（复习次数、停留时长）不得当成成功证据。

## 4. 模块契约澄清（第一轮踩到的认知偏差，已固化进用例）

这些不是缺陷，是**接口语义**，写下来是因为它们都让首轮用例"假失败"过一次，  
不写清楚下次还会再踩：

| # | 契约                                              | 说明                                                                        |
| - | ----------------------------------------------- | ------------------------------------------------------------------------- |
| 1 | **上传接口返回 `timeline_id` / `library_id`，不是 `id`** | 命中去重时额外置 `duplicated=true` 并复用原条目 id                                      |
| 2 | **同内容文件会命中业务层去重（#121）**                         | 测试造数据必须每次内容不同，否则第二条复用第一条、名字不更新，按新名查询必然落空                                  |
| 3 | **`documents` 表只装导出产物**                         | 上传的 PDF 走 `library_docs`；`documents` 由 `document/export`、`pdf/combine` 写入 |
| 4 | **记忆详情返回 `{ memory, media }` 两段**               | 不是裸 memory 对象                                                             |
| 5 | **`withUrls` 只在确实有图时才补 URL 字段**                 | 纯文字题目不会带 `question_image_urls`；验证签名 URL 必须先造带图条目                          |
| 6 | **`pdf/combine` 只合成图片素材**                       | 传文字题目 id 会 400「所选素材中没有可合成的图片」                                             |
| 7 | **`search/solve` 参数是 `question_content`**       | 且参数校验先于 AI 闸门：传错参数拿 400 而非 403，这是**正确**的顺序                                |
| 8 | **知识库 `chat/knowledge` 读写均需 admin**             | 「读应该放开」的直觉在这里是错的，已单独立用例固化，避免以后误改                                          |
| 9 | **图像处理回源需公网 URL**                               | 用上传返回的 `url`，不能用本机 `/api/storage/files/<key>` 代理（见 P3-2）                  |

## 6. 发现的问题与修复

### 🔴 P0-1 · `search/solve` 漏装 AI 外发闸门（合规红线）

| 项       | 内容                                                                                                                                     |
| ------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| **现象**  | 用户关闭「AI 与在线检索」开关后，`POST /api/search/solve` 仍返回 **200 + 大模型生成的解答**                                                                      |
| **根因**  | 改造 `users.ai_enabled`（OPS-18 R-合规-02）时，`chat/message` 与 `answer-search` 都补了 `requireAiEnabled()`，**唯独这个端点漏了**。它是全项目唯一会「联网检索 + 调大模型」的入口 |
| **加剧项** | 它连 `requireUserId` 都没有 ⇒ 不带任何身份即可调用，等于对外开了一个**匿名的大模型代理**                                                                               |
| **影响**  | 数据主体是未成年人。开关形同虚设意味着「默认不外发」的合规自证不成立；匿名可调用还有被刷量的风险                                                                                       |
| **修复**  | `search.controller.ts` 注入 `@Req()`，参数校验后调 `requireAiEnabled(req)`；`service` 增加 `userId` 参数仅用于审计日志，**刻意不记录题目正文**（日志长期留存，不落用户内容）         |
| **验证**  | AI 关闭 → 403 `AI_DISABLED`；无身份 → 401；开启后正常返回（M11 用例）                                                                                    |

### 🟠 P1-1 · 图像诊断端点被严格令牌拦截，诊断链断裂

| 项      | 内容                                                                                                                                                 |
| ------ | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| **现象** | `GET /api/image/capabilities` 与 `GET /api/image/ocr-diagnose` 返回 **401 `NEED_AUTH_TOKEN`**                                                         |
| **根因** | 两个端点的设计注释明写「**无需登录也可访问的轻量 GET**」，但 2026-10-27 启用严格令牌化时，`PUBLIC_ROUTES` 白名单没有同步补上这两条                                                                |
| **影响** | 前端在图像功能失败时先查 `capabilities` 来区分「服务未更新」与「本次处理失败」。它自己也要身份 ⇒ 未登录或令牌过期时只能看到 401，正是要根治的「点了不能用但看不到原因」；`ocr-diagnose` 是给部署方自查 OCR 侧车用的，要求登录等于让运维先造个身份才能排查 |
| **修复** | `shared/user-context.ts` 的 `PUBLIC_ROUTES` 补两条，并注释说明信息暴露面（仅版本号/模式/侧车可达性，无用户数据）与公网部署的兜底做法（反向代理单独拦截）                                                 |
| **验证** | 免令牌访问 `capabilities` → 200 且 `version=3`（M09 用例）                                                                                                   |

### 🟡 P2-1 · 账号注销串行 5 轮跨境 DB 往返，耗时 26s

| 项      | 内容                                                                      |
| ------ | ----------------------------------------------------------------------- |
| **现象** | `DELETE /api/account?dry_run=1` 空账号实测 **26s**；真实账号（有题目/图片/记忆）只会更久       |
| **根因** | 收集引用、收集遗留 key、两次表计数、ocr 统计**彼此无数据依赖却串行执行**，5 轮 × Supabase 新加坡单程 1.5~5s  |
| **影响** | 逼近小程序端 60s 超时；注销是用户可感知的同步操作，卡住会被当成「点了没反应」                               |
| **修复** | 前两步合并为 `Promise.all`；两张表的计数/删除并行；`ocr_results` 计数提前发起、最后回收 ⇒ 串行轮次 5 → 2 |
| **验证** | M01 用例新增**性能红线断言**：dry-run 必须 < 60s（实测由 26s 降至约 10s）                    |

### 🟡 P2-2 · LaTeX 矩阵/分段函数输出连续空白碎片

| 项      | 内容                                                                                                    |
| ------ | ----------------------------------------------------------------------------------------------------- |
| **现象** | `\begin{matrix} a & b \\ c & d \end{matrix}` → `" a   b ； c   d "`；`cases` → `" x>0 时 x ； x<0 时 -x "` |
| **根因** | 解析 `&` / `\\` 时会产生空单元格，直接 `join(' ')` 得到连续空格；`cases` 分支未对单元格 trim                                     |
| **影响** | 抄写与读屏时是纯噪音，看着像排版损坏                                                                                    |
| **修复** | `src/utils/latex.ts`：单元格先 `trim()` 再 `filter(Boolean)`，行级同样过滤                                         |
| **验证** | matrix → `"a b；c d"`，cases → `"x>0时x；x<0时-x"`（M12 新增「输出无连续空白碎片」用例）                                    |

### 🔵 P3-1 · `include_answers` 默认口径在两个导出接口间不一致（**已在 2026-10-28 统一并落地**）

- 原状：`pdf/combine` 是 `include_answers === true` 才含答案（默认纯题卷），`document/export` 是
  `!== false` 就含答案（**不传 = 含答案**）⇒ 同一产品两套默认，漏传参数就打不出空白练习卷。
- 裁定（产品口径，不是技术取舍）：**本产品主用途是打给孩子做练习**，答案属于「对答案 / 讲解」的
  第二用途，必须显式索取。
- 落地：`withAnswers = params.include_answers === true`；副标题直接印版本
  （「练习卷（不含答案）」/「答疑解惑（含答案与解析）」）；前端汇总页拆成**两颗按钮**——
  「打印练习卷」与「答疑解惑（含答案）」，详情页与复习本合成的文案同步。
- **怎么验**：只看 HTTP 200 验不出带没带答案——返回的是 .docx（zip）。为此套件加了
  **零依赖 ZIP 读取器**（`lib/zip.mjs`：解析中央目录 → inflate `word/document.xml` → 抽 `<w:t>`），
  M10 直接断言正文里有没有「正确答案」「解析文本」。这正是它在首轮躲过验证的原因。
- 顺带修掉一个**静默回归**：导出的「复习进度」一行原本读 `content.review_count`，而 C4 迁移后
  档位已上列 ⇒ 该行会永久消失。现改为读列、`content` 兜底。
- 状态：OPS-18 `R-技术-13` **已关闭**。

### 🔵 P3-2 · 本地存储驱动下，图像处理回源自己会被自己 401（**登记**）

`ImageService.download()` 只对 `SAFE_FORWARD_HOSTS`（coze/volcengine 等外部白名单）转发请求头。  
若用 `STORAGE_DRIVER=local`，图片 URL 指向本服务的 `/api/storage/files/<key>`，而该路由要身份  
⇒ 回源 401 ⇒ 图像处理全线 500。

生产用 supabase 驱动（公网签名 URL）**不受影响**；真机开发虽连 `192.168.3.242` 后端，但对象存储  
仍是 supabase，同样不受影响。故登记观察：仅在「本地盘自建存储」部署形态下需要处理（可让  
`ImageService` 识别自家 `/api/storage/files/<key>` 后直连 `storageService.readObject()`，顺带省一次 HTTP 往返）。

## 7. 回归与门禁建议

| 场景        | 建议                                                          |
| --------- | ----------------------------------------------------------- |
| **日常开发**  | 改动业务接口后跑 `node scripts/verify/run.mjs M0X`（按改动模块选），秒级反馈     |
| **提交前**   | 全量跑一遍；`run.mjs` 退出码可直接当门禁                                   |
| **发布前**   | 全量 + `check:isolation` + 真机 UAT 清单（GK-QA-15 §真机）            |
| **新增模块**  | 在 `modules/` 下新增一个 `NN-name.mjs` 即可被 `run.mjs` 自动发现，无需改注册代码 |
| **新增历史坑** | 补进对应模块的用例，标题带 🔴，注释写清事故来源（与 QA-15「回归优先」一致）                  |
| **改学习行为（L1+）** | 附提案单 + 跑 `pnpm method:check`（= M16）；CI 的 `gate` 作业同样会跑它                    |

**已知限制**：

1. 套件验证的是「接口契约 + 隔离 + 不崩」，**不评估图像算法质量**（那是 `dynamic-tests/probe-*.ts` 的职责）。
2. OCR 真实识别质量未覆盖（需 GT 数据集 + 人工判分），本套件只保证端点守门与错误可解释。
3. 备份/恢复演练（`db-backup.mjs` 全链路 + 网盘往返 + `gk_rehearsal` 库比对）**未纳入**自动套件——  
   它会真实上传网盘、建临时库，耗时长且有副作用，仍按 GK-OPS-18 的周演练计划人工执行。
4. 前端 UI 交互（渲染、滚动、隐私授权弹窗）只能真机手测，本套件只覆盖纯函数层。
5. **M16 只守「结构 / 词表 / 镜像」**，不判断归因是否成立、边界写得对不对——那两条只有人能判（OPS-22 §4 的取舍）。
