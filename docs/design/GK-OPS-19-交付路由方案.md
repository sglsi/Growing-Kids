# GK-OPS-19 交付路由方案（后端托管与上线路径）

> 编号：GK-OPS-19 ｜ 版本：v1.1 ｜ 日期：2026-10-29 ｜ 状态：**已定方案，尚未实施 · ⛔ B2（云托管公网域名 + wx.request）已于 2026-10-29 被官方文档否决，仅剩 B1 / C 二选一**
> 上游：`docs/后端托管与小程序发布-调研纪要.md`（实证与资费底稿）、GK-QA-16 第 4/7 章（发布清单）
> 定位：回答「这套东西怎么从我的电脑上，变成一个别人能用的小程序」。

---

## 0. 一句话结论

**工作在云端（NestJS + Python OCR + Supabase）与「别人能用」之间，唯一真实障碍是「域名」。**
本项目所有 request 都指向**单一后端地址**（`PROJECT_DOMAIN` 编译期注入），没有 CDN、
没有多个外部域名——这是巨大优势：**只要解决那一个域名或改用不依赖域名的通道，全盘皆通。**

当前状态只能跑**开发版 + 局域网 IP**；一旦要出「体验版 / 正式版」，必须走下面三条路之一。

⚠️ **2026-10-29 校正**：「不依赖域名的通道」在本项目语境下**只有 `wx.cloud.callContainer` 一个**。
云托管的默认公网域名不能当正式后端的调用地址（官方：「小程序后台也无法配置使用默认公网域名」），
绑自定义域名又要求域名已备案 ⇒ 「免备案 + 零改造」的组合不存在，见 §3.1。

## 1. 为什么现在跑不起来的事实基础（实证，非推测）

| 事实 | 依据 |
|---|---|
| `app.workbuddy.host` 不能当小程序后端 | 边缘网关拦截 UA 含 `MicroMessenger` 的请求（403 且返回"请在浏览器中打开"HTML）；且平台子域无 ICP 备案，进不了 request 合法域名白名单 |
| Supabase 只能存数据、不能跑 API | Edge Functions 是 Deno 短函数，无长驻进程；本项目后端 159 个 ts / 28 模块，含定时任务、multer 上传、pdf-lib/docx 生成 |
| WorkBuddy cloud-service 迁移 = 重写后端 | BaaS（DB/Auth/Storage/LLM），无容器与长驻运行时；且文档型库要重设计 schema |
| 开发版一直在吃「豁免」 | `urlCheck:false` 下微信不校验合法域名；这条豁免**仅存在于开发阶段** |

## 2. 三条路线

| | A · 保持局域网 | **B · 微信云托管** | C · 腾讯云 VPS |
|---|---|---|---|
| 能否出体验版/正式版 | ❌ 只能自己本机 | ✅ | ✅ |
| 备案 | 免 | **免**（走 `callContainer` 时） | ❌ 必须（个人 7-20 工作日） |
| 首月/首年成本 | ¥0 | ¥0（3 个月免费额度）→ ~¥35/月 | ¥109/年 首年 + 域名 ~¥55/年 |
| 三年合计 | ¥0 但不可用 | ≈ ¥1,155 | ≈ ¥1,130 |
| 后端代码改造 | 无 | 约 90% 原样 | 原样跑（有 root，Compose 可用） |
| 运维负担 | 本机自管 | 平台托管 | 全自管（Node/Python/OCR/证书/备份） |
| 适合谁 | 开发期、自用 | **要给别人用时的首选** | 追求长期完全自主 |

**C 不建议现在做**：三年成本与 B 几乎持平，却要多付「7-20 工作日备案 + 全部运维」。
**A 保留**作为日常开发形态。生产目标锁定 **B**。

## 3. 路线 B 的两条子路径（差异巨大，必须二选一）

| 子路径 | 原理 | 前端改造 | 后端改造 |
|---|---|---|---|
| **B1 `wx.cloud.callContainer`** | 官方私有链路，明确"无需域名、无需配服务器域名、无需备案" | **大**：请求体 ≤100 KiB、超时 15s ⇒ **拍照/相册 OCR、文档导入等核心图片链路必须改走 `wx.cloud.uploadFile` 换 fileID** | 无 |
| **B2 云托管公网域名 + `wx.request`** | 云托管提供的公网域名，在控制台关联小程序后登记进 request 合法域名白名单 | **几乎为零**：只需把 `PROJECT_DOMAIN` 换成云托管域名 | 无 |

### 3.1 ⛔ B2 已被官方否决（2026-10-29 校正，不必再验）

原本文写着"先花 10 分钟验证 B2：关联小程序后，云托管公网域名是否会自动进 request 白名单"。
2026-10-29 复核官方文档，**这个验证不必做了，结论是"不行"**：

> 微信云托管《开发常识》原文：「默认公网域名性能有限制，**仅能支持接口测试使用**，请勿用于正式生产环境。
> **小程序后台也无法配置使用默认公网域名。**」

同一页也给了唯一的豁免，措辞是"CallContainer"而非"公网域名"：

> 「小程序/公众号可使用 CallContainer，**无需域名，因此不需要在 mp 管理后台配置服务器域名，
> 从而一开始就无需申请域名，也无需备案**。」

另外，"云托管绑自定义域名"这条退路同样要备案——官方要求「自定义域名**仅支持已备案的域名**进行绑定」。

⇒ **B2 从方案池里划掉。** 云托管能免的只有 `callContainer` 这一条通道，而它要求前端改造（见 3.2 之外的图片链路问题）。

**于是实际只剩两条路，取舍写在 `docs/后端托管与小程序发布-调研纪要.md` §8.3：**

| | B1 `callContainer` | C 自有服务器 + 已备案域名 |
|---|---|---|
| 免备案 | ✅ | ❌ 7-20 工作日 |
| 代码改动 | 大（图片链路 + 15s/100KB 约束 + 同镜像） | 几乎为零 |
| 风险落点 | 代码 | 运维 |

**一句话**：不再有"免备案且零改造"的选项，必须在这两者之间选一个，且等待时间同量级（3-5 天改代码 vs 7-20 天等备案）。

### 3.2 上到云托管时的三个已知硬约束（提前知道，别踩）

1. **不支持 Compose** ⇒ NestJS 与 Python OCR 侧车必须**打进同一个镜像**（约 1.5–2 GB）。
2. **容器无持久化磁盘** ⇒ 文件必须走对象存储。**本项目已用 Supabase Storage，天然吻合**，无需改动。
3. **OCR 是 CPU 密集 + 首次加载模型慢** ⇒ 实例规格别低于 1 核 2G，否则首次识别会长时间白屏。
4. **免费额度账要算清**：720 核·小时 ÷（24h×90 天）≈ **只够 0.33 核常驻**。
   0.5 核常驻三个月约超支 ¥19.8；且**仅首个环境赠送**，开生产/预发第二个环境即按刊例计价。
