## 1. 登记规则

### 1.1 登记格式

每一条风险在**所属章节的总表**中占一行，字段固定为九列：

| 编号 | 类别 | 描述 | 影响 | 概率 | 处置决策 | 状态 | 责任人 | 复核周期 |
|---|---|---|---|---|---|---|---|---|

- **影响**：对用户/交付的后果严重度，`高`（阻断发布或数据错误）/ `中`（功能降级、体验受损）/ `低`（维护成本）；
- **概率**：`高`（已发生或必然发生）/ `中`（特定条件下发生）/ `低`（小概率）；
- **描述**：一句话说清"是什么"，**不写解决方案**（方案写进同章的「判据与缓解」小节，按编号对应）；
- 需要展开的条目在同章「判据与缓解手段（按编号）」里给：现象 → 判据命令 → 缓解手段 → **为什么不彻底解决**。

### 1.2 编号规则

`R-<类别>-<两位序号>`，类别五选一：

| 类别码 | 含义 | 典型内容 |
|---|---|---|
| `技术` | 技术风险 | 外部依赖不可用、架构假设失效、安全边界 |
| `算法` | 算法已知缺口 | 指标不达标但已决策接受、能力未实现 |
| `工程` | 工程债 | 结构性问题、垃圾未清、规范未落地 |
| `合规` | 合规风险 | 密钥、隐私、内容安全、第三方传输 |
| `已关闭` | 已解决的历史风险 | 复发防护（**只增不改**，用于防复发） |

⚠️ **编号一旦分配永不重排、永不复用**。删除条目时把状态改为「已关闭」并**保留原编号**；若关闭事项值得作为复发防护教材，在 `R-已关闭-` 序列里再登记一条（两处互引）。

### 1.3 状态机

```
待评估 ──► 接受（不修）
   │            │
   └──► 缓解中 ─┴──► 已关闭
```

| 状态 | 含义 | 硬要求 |
|---|---|---|
| `待评估` | 已发现、未决策 | **必须给出评估截止日期**，否则不算登记完成 |
| `接受` | **决定不修** | 必须写三件事：① 理由 ② 代价（会坏成什么样）③ **触发重新评估的量化条件** |
| `缓解中` | 有手段但未消除 | 必须写清"缓解到什么程度"与"剩下的尾巴是什么" |
| `已关闭` | 已消除 / 已不再适用 | 必须写清关闭凭据（提交号、实测结果、或决策变更） |

### 1.4 维护纪律

1. **「接受」也是一种决策**——不修不是"忘了"，而是明确取舍。不写理由的「接受」等于没决策，评审时直接打回。
2. **触发条件必须可观测**：写"用户量过千再评估"合格，写"以后再看"不合格（无法判断何时触发）。
3. **复核周期**：`缓解中` / `待评估` 条目每月首个工作日过一遍；`接受` 条目按各自触发条件复核（不排定期）。
4. **状态变更必须同时更新**：① 本条状态 ② 复核日期 ③ 本文末尾变更记录表。三处不同步视为文档缺陷。
5. **与 ADD-04 第 12 章「演进路线与遗留问题」互为索引**：架构级遗留问题在 ADD-04 提出，在本册登记处置决策；两处描述冲突时以本册为准（本册是决策记录）。
6. **算法类缺口与 DD-10 第 11 章互为索引**；合规类与 ADD-07 第 8 章「发布前安全清单」互为索引。

### 判据与缓解手段（按编号）

**`R-技术-01` Supabase IP 间歇封锁**

- 现象：查询突然全部 `fetch failed` / 全站 500，几秒后自愈；同一 key 换机器可能不复现。
- 根因：Supabase 域名走 Cloudflare，直连 IP 被 CF 层判定异常后封锁（与项目代码无关）。
- 判据：`node server/scripts/health-probe.mjs` 连续报 DB 失败而 CPU/内存平稳；日志出现 `supabase-dns-pin` 重探记录。
- 缓解：`server/src/storage/database/supabase-dns-pin.ts` —— 维护 **33 个候选 IP**，启动时逐个 TLS 探测优选，**5 分钟**周期自愈重探；命中失败自动切换。
- ⚠️ **静态 IP 池方案已证伪，勿回退**（理由见 ADD-04 第 8 章被否决方案）。彻底方案=自建 Postgres / 专用连接串，未排期。

**`R-技术-02` RLS 未启用（已决策接受）**

- 现状：全部表 `RLS` 关闭，后端用 `service_role`（绕过 RLS），隔离 100% 靠代码 `.eq('user_id', userId)`。**单点疏漏 = 越权读**。
- 2026-10-24 重新评估结论：**不予启用**。四条理由——① service_role 绕过，开了也不生效；② 登录体系无 Supabase JWT，`auth.uid()` 取不到值，策略写不出来；③ 现有查询已全覆盖，RLS 不增加覆盖面；④ 与"多用户共享"预留模型冲突（见 ADD-07 第 3 章）。
- 替代：静态门禁 `server/scripts/check-isolation.mjs`（`pnpm --filter server check:isolation`）。**2026-10-27 实测：扫描 113 处 `.from()` 调用点，零缺口**（票据落库后由 108 增至 113；`login_tickets` 入白名单，理由是"按 token 主键寻址，`user_id` 只在授权成功后写入、不是隔离维度"）。
- 残余风险已转移 → `R-技术-09`（身份头伪造）与 `R-技术-11`（门禁漏报）。
- **触发重新评估的条件**（任一即重评）：① 引入 Supabase Auth / 第三方 JWT 登录；② 出现第二个服务端写库进程（不止本 NestJS）；③ 数据共享（家长/孩子/朋友）进入实施。

**`R-技术-03` ima 日配额 220021**

- 现象：某天搜题突然全部返回"资料获取次数已达上限"，次日自动恢复；**零命中也扣次**，无法靠"少返回结果"省配额。
- 判据：日志 `220021`（`answer-search.service.ts:306`、`ima-provider.ts:70`）。
- 缓解：① **探针式检索**，先探后取，把每次搜题的 ima 调用从"6 库并行"压到**最坏 4 次**（`IMA_PROBE_MAX=2` + `IMA_FALLBACK_KB_MAX=2`，见 DD-11 第 4 章）；② 撞配额即**整体停检**（重试无意义），专属文案单独提示、不混进泛化失败；③ 叠加 `answer_cache` 持久缓存（同题不重复消耗）。
- 不可消除：配额在服务端按日重置，客户端无退避空间。

**`R-技术-04` LLM 供应商可用性**

- 现象：扣子（Coze）SDK 只在平台运行时可拿到 JWT，**部署包外不可用** —— 曾导致线上对话全挂。
- 缓解：改走 OpenAPI；三 provider 降级链 **coze → deepseek → hunyuan**，任一失败自动下移，全失败返回明确文案而非空响应（见 DD-11 第 5 章）。
- 残余：三家全挂时对话不可用（接受，属外部依赖固有风险）。

**`R-技术-05` 无 CI/CD 与自动化门禁（已决策接受：不接）**

> **大白话版**（先说人话，术语在后面）

**这是什么？**
现在这个项目没有"自动质检员"。改完代码，全靠人记得自己跑一遍检查：类型对不对、小程序语法有没有踩坑、有没有漏掉权限过滤、包有没有重新打。**没人替你把关，你自己既是运动员又是裁判。**

**不管会怎样？**
最坏的不是"程序报错"——报错反而是好事，当场就发现了。最坏的是**什么都没发生**：

- 你改了前端代码，但忘了重新打包 → 手机上跑的还是**上一个版本**。你以为在测新功能，其实在测旧功能，测半天"怎么没效果"，最后发现根本没发出去。
- 你加了个新功能，忘了跑权限隔离检查 → 代码本身不报错，但**可能让 A 家长看到 B 家长孩子的错题**。这类问题不会在测试时暴露，只会在真实用户那里爆。
- 你改了个小地方，以为不会影响别的 → 结果把三个月前修好的一个 bug 又改回来了（"回归"）。

**一句话**：这类问题的共同点是**安静**——不弹窗、不报错、不崩溃，只是悄悄变坏，等发现时已经上线了。

**能不能装个自动质检员？**
能，但**这个项目装了不划算**，理由很具体：

- 自动化质检员（CI）跑在云上的 Linux 机器里。而这个项目一半的核心能力（OCR 识别、图像去手写）依赖**本机 Windows 侧的 Python 环境和 2-3GB 的模型**。云上那台机器跑不了，等于质检员只能检查"前半截"（纯前端 + 纯 TypeScript），后半截（最重的图像/OCR）照样靠人。
- 装了之后会出现更糟的情况：CI 绿灯，人就以为"没问题了"，**反而放松了后半截的人工检查**。绿灯给人虚假的安全感，比没有绿灯更危险。

**所以决定怎么做？**
不接 CI，改成**把检查压成一条命令**：发布前敲一次，全部门禁跑完，看退出码。人工还在，但把"记得跑 7 步"降到"记得跑 1 条命令"，把最容易漏的环节做成不可跳过的收尾动作。

**触发重新评估的条件**：① 团队出现第二个人提交代码（"你自己既是运动员又是裁判"就不再成立，必须有第三方把关）；② 图像/OCR 链路被拆成独立服务、能在 Linux 上跑起来（CI 才有能力覆盖全链路）；③ 出现一次"因为漏跑检查而上线的线上事故"。

---

- 现状（术语口径）：无 Github Actions、无 pre-commit hook；回归靠人工按 QA-15 第 7 章 7 步走。
- 风险点：**"忘了跑"型回归**——`pnpm build:weapp` 忘跑、`check:isolation` 忘跑，两者都不会报错只会静默发旧货（见 `R-已关闭-01`）。
- 缓解（当前）：QA-15 第 7 章门禁清单**逐条手工勾**；`R-已关闭-01` 的"grep dist 特征串"作为强制收尾动作。
- 决策：**不接 CI**（理由见上）。代价=门禁强度完全依赖执行人的纪律，没有第三方兜底。

**`R-技术-06` 无定期备份（已关闭：自建备份 + 异地副本 + 每周恢复演练）**

- **查证结论（2026-10-27，Supabase 官方定价页与文档）—— 当前免费套餐没有可用备份**：

| 能力 | Free（当前） | Pro（$25/月） | 说明 |
|---|---|---|---|
| 自动每日备份 | ❌ **无** | ✅ 保留 **7 天** | Free 仅在项目**被暂停**时留一份快照，不是定期备份 |
| PITR（时间点恢复） | ❌ 无 | ❌ 需**付费附加项** | 还需 Small 及以上计算规格 |
| 手动导出 | ✅ 允许 | ✅ | **唯一现在能用的路径** |

  ⇒ 平台侧不兜底。且 Free 项目**闲置约 1 周会被自动暂停**，暂停期间数据虽在、但期间发生的损坏无从回滚。

- 风险原貌：误删/误改**无回滚手段**；`migrations/` 只能重建结构，**不能恢复数据**。`purgeUserData()`（账号注销）是真删，误触发即不可逆——这条风险的现实重量由此上升。

**① 落地实现（三个脚本 + 两个计划任务）**

| 件 | 路径 | 职责 |

**② 四个关键取舍（写下来是为了防止后人"优化"回去）**

| 决策 | 选择 | 理由 |
|---|---|---|
| 用什么导 | **纯 Node + 项目已有的 `pg`**，不用 `pg_dump` | 本机没装 PostgreSQL 客户端。计划任务里"找不到命令"是典型**静默失败**：任务显示已执行、备份目录空空如也，等要恢复才发现三个月没备份 |
| 导什么 | **只导数据，不导结构** | `migrations/` 是 schema 唯一真相源（`R-工程-09`）。恢复 = 空库跑迁移 + 灌数据，顺带每次都验证迁移链本身可用。另存一份结构只会与 migrations 漂移 |
| 加不加密 | **AES-256-GCM 加密后才上传** | 导出包含**全体用户**数据（未成年人错题与学习轨迹）。落到个人网盘账号上，明文一份泄露 = 全体泄露。GCM 带完整性认证：改一个字节解密即失败——备份最怕的不是打不开，是**能打开但内容是错的** |
| 放哪 | **百度网盘 `/apps/GrowingKids/GrowingKids备份/`** | 该账号实测 **总 13.3 TB / 已用 9.73 TB / 剩余 3.58 TB**，且 OAuth 通道早已在用于资料库归档（不新增依赖、不新增供应商）。数据库导出仅约 64 KB，容量完全不是约束；真正的价值是**异地**（与 Supabase 不同供应商、不同账号） |

> 关于「上 T 的存储方案」：`docs/策略3-生命周期分层-配置清单.md` 里那套 COS 冷热分层（年增量 ≈ 2.2 TB）解决的是**对象存储（图片）**的成本，不是数据库备份。两者不冲突：库备份走网盘（小、要快、要异地），将来若要备份用户图片，才轮到 COS 归档层。已登记在下方"残余风险"。

**④ 恢复演练怎么做到不碰生产数据**

用 postgres 超级用户（有 `CREATEDB`，`migrator` 没有）建一个固定名的空库 `gk_rehearsal`，在里面原样跑 `migrations/`、灌数据、比对，结束后**清空 schema**（不是删库）。

> ⚠️ 为什么是"清 schema"而不是"删库重建"：Supabase 走 pooler，客户端 end() 之后服务端会话还会滞留几十秒，`drop database` 会稳定报 `is being accessed by other users`（实测连试 10 次 50 秒仍失败）。我们本来就是该库的客户端，`drop schema` 不撞这个限制。附带好处：演练结束数据被擦掉，实例上**不残留第二份用户数据**。

**⑤ 残余风险（不因为"已关闭"就当作没有）**

1. **网盘是消费级存储**：不承诺可用性 SLA，也存在风控删除/限速的可能。缓解=**本地保留 14 份**，网盘只是异地那一份；两者同时丢才会真丢。
2. **口令托管**：`BACKUP_PASSPHRASE` 在 `server/.env.secrets`，另有一份 `server/backups/KEY-ESCROW.txt`。**磁盘全损时口令与备份会一起丢** ⇒ 必须抄进密码管理器（首次生成时脚本会醒目标注）。
3. **只备份数据库，不备份对象存储图片**：图片在 Supabase Storage，随 Supabase 账号存在。Free 项目暂停不删数据，但**账号级事故无法靠本方案恢复**。触发条件见下。
4. **备份含全体用户数据**：已加密，且只存在本机 + 私人网盘账号；不进仓库（`.gitignore` 已加 `/server/backups/`）。隐私政策已同步声明"数据库备份"这一处理活动（见 `R-合规-03`）。

**⑥ 触发重新评估的条件**：① 存储量或图片资产需要单独备份 ⇒ 引入 COS 归档层（见 `docs/策略3-生命周期分层-配置清单.md`）；② 恢复演练连续两次失败 ⇒ 备份方案本身要重做；③ 迁移到自建 PG ⇒ 可改回 `pg_dump -Fc` 并用 PITR。

**`R-技术-09` 身份头可伪造（已关闭：裸头通道已关）**

| 路由类别 | 匹配范围 | 允许的身份来源 | 为什么 |
|---|---|---|---|
| **公开路由** | `/api/health*`、`/api/auth/login`、`/api/auth/anonymous`、`/api/auth/logout`、`/api/auth/qr-login*` | 完全匿名 | **健康拨测不带令牌**，若也要求令牌会 401 ⇒ 巡检误判后端已挂 ⇒ 触发无意义重启。这是首版一刀切踩过的真实坑 |

**`R-技术-10` 单机假设（已关闭：三项一起解除）**

- 原三处硬绑定单机：① `mem-cache` 是**进程内**缓存；② H5 扫码票据存在**进程内存**（`login_tickets` 建了但写入方未启用）；③ OCR 侧车是**本机子进程**（`:9301`），无法共享。
- **为什么必须三项一起做**：只做一项会得到更糟的半吊子状态——比如只把缓存换 Redis、票据还在内存里，扩容后登录会随机失败，而缓存又是一致的，**排查方向会完全错**。所以本轮按"一起解除"执行。

| # | 项 | 落地 | 关闭凭据 |
|---|---|---|---|
| 1 | 缓存换后端 | `server/src/shared/cache-store.ts`：`CacheStore` 接口 + `MemoryCacheStore`（默认）/ `RedisCacheStore`。配 `REDIS_URL` 且装了 `ioredis` 即切 Redis；Redis 失效**自动回落内存并告警**，不炸服务 | **槽位已接完**。`memGet/memSet` 全部改名 `cacheGet/cacheSet` 并 async 化（25 处调用点加 `await`）——改名是刻意的：async 化后沿用旧名，漏 `await` 会拿到一个永远真值的 Promise 而不报错，是**最难查的一类 bug** |
| 2 | 票据落库 | `qr-login.service.ts` 重写：`QR_TICKET_STORE=auto\|db\|memory`。`auto` 下 db 不可用降级内存并**只告警一次**；`db` 强制模式**不降级**。`authorize` 用 `.eq('status','pending')` 条件更新做互斥，避免并发重复授权 | 实测 `login_tickets` 写入 1 行 `pending`；`/api/health/runtime` 报 `ticketStore=auto(db 优先)` |
| 3 | 侧车外置 | 早已具备，本轮仅核验：`PPSV3_SUPERVISE=0` 关托管 + `PPSV3_URL` 指向远端；`=1` 强制托管且 spawn 失败显式报错；`192.168.3.242:9301` 即外置形态 | `ppsv3.client.ts:285-310`、`ocr.service.ts:1301-1313`；不可达时抛"OCR 侧车不可达（`PPSV3_URL /healthz` 无响应）"而非静默 |

- **现状诚实说明**：能力齐了，**默认仍跑单机**（没配 `REDIS_URL`，`cache.backend=memory`）。区别在于——以前扩容**要改代码**，现在扩容**只改环境变量**。这是本条真正解决的问题。

**`R-技术-11` 隔离门禁是启发式（已决策接受）**

- 机制：向后看 **12 行**内找 `.eq('user_id'`，配合常量表名还原、insert/upsert 链豁免、白名单。
- 必然的漏报形态：① 查询链超过 12 行（跨多段 `.select(...)` 拼接）；② 表名由变量间接给出且不是文件内 `const NAME = 'table'` 形式；③ 把 `.eq` 提到链外变量再传入。

**`R-算法-01` T7 手写压印刷不可分（已决策接受）**

- 关闭凭据：提交 `4ec593b`。实现方式是**中间件重写路径**，不是把 70 个 handler 重挂一遍：

| 要点 | 做法 | 为什么 |
|---|---|---|
| 重写而非重挂 | `/api/v2/xxx` → 内部改写为 `/api/xxx` | 70+ 个 handler 不用动，**不可能因为"忘了挂某个 v2"而漏掉接口** |
| 同步改两个字段 | `req.url` **与** `req.originalUrl` 都改 | 只改 `req.url` 时，日志与 Nest 路由匹配会各自看到不同路径，排障时会被误导 |
| 旧前缀保留 | `/api` 继续可用 | 兼容期必须能双跑，否则等于强制所有客户端同时升级 |
| 可观测 | 响应头 `X-Api-Version` | 实测 `/api/v2/health/runtime` 返回 `X-Api-Version: v2`，排查时一眼看出走的是哪条 |

- ⚠️ **这不是完整的版本治理**：当前 v2 只是"别名 + 打标"，**没有任何 v1/v2 行为分叉的机制**。真要做破坏性变更时，仍需在 handler 内按版本分支或分模块挂载。本条关闭的是"没有版本入口"，不是"版本治理已完成"。

|---|---|---|

| 数据 | `users.ai_enabled boolean not null default false` | 默认 `false` ⇒ **新增账号天然是仅本地**（fail-closed） |
| 后端闸门 | `shared/user-context.ts` 的 `requireAiEnabled()` | 未开启即 **403**，`msg` 明确写出"当前为仅本地模式"与开启入口 |
| 拦哪些 | `/api/chat/message`（智能客服）、`/api/chat`（通用对话）、`/api/answer-search/:id`（search / kb / ai **三条通道全部**） | 三条通道都是外发：联网检索也算外发，所以一刀切 |
| 不拦哪些 | OCR、图像处理、题库读写、导出、资料库 | 全部在本机/本项目内完成 |
| 读写接口 | `GET /api/settings`、`PUT /api/settings/ai` | 改完**立刻失效缓存**（否则最多 60s 才生效，会被当成"开关没作用"） |
| 前端 | `services/ai-settings.ts`（单飞 + 缓存 + fail-closed）、`pages/profile` 开关卡片 | 打开方向**二次确认**（等于监护人同意外发），关闭方向不确认——收紧权限不需要征求同意 |

**② 为什么默认关，而不是默认开**

数据主体是未成年人。缺省"默认外发"需要在监管与家长两头都自证合规；缺省"默认不外发"只需要一句话说明白。**后者的合规成本低一个数量级**，代价只是用户要多点一次开关。

**③ 实测（2026-10-27，反向也验了）**

**④ 仍然保留的约束（不因有了开关就放宽）**

- 隐私说明中**明确告知**接收方类型与用途（已写入政策第三方清单）。
- **数据最小化**：只传当前题目，不传整本资料、不传与作答无关的元信息。
- search / kb / ai **三模式互不兜底**，不要为了"效果更好"偷偷跨模式降级（DD-11 第 2 章红线）。

**触发重新评估的条件**：① 产品决定"默认开启"；② 引入新的第三方 AI 供应商；③ 出现按用户计费/配额，需要按开关区别限流。

**③ 注销即删，且覆盖缓存层（含"不删别人共同体"约束）**

- 新增 `DELETE /api/account`（`server/src/maintenance/account.controller.ts`），`?dry_run=1` 先算代价再确认；前端 profile 页点注销先跑 dry-run 把"会删几条、会留几条"摆给用户看。
- `purgeUserData()` 的删/留边界：

| 对象 | 处理 | 为什么 |
|---|---|---|
| `documents` / `questions` / `memories` / `timeline_*` / `chat_sessions` 等 | 删（`on delete cascade`） | 有 `user_id`、只属于本人 |
| `chat_messages` / `user_quota` | **显式删** | 无级联约束，漏删会留孤儿行 |
| `blob_objects` + 存储对象 | `blobService.release()` 归还 `ref_count`，**归零才真删** | **若同一份文件仍被其他账号条目引用，保留**——按 key 直删会毁掉别人的数据 |
| **`ocr_results`** | **一律不动** | 按 sha256 **内容寻址、跨用户共享**。同一道题（同一张图）多个家长都传过，删一个账号的识别缓存会连带毁掉其他人的。这是"非重复要求"的直接体现 |
| `blob_objects`（无引用） | 真删 | `ref_count` 归零即无任何条目引用 |

- 回执字段即"我删了什么、留了什么、为什么"：`{blobsTotal, blobsReleased, blobsKeptForOtherUsers, rowsDeleted, ocrResultsKept, note}`。**`blobsKeptForOtherUsers` 与 `ocrResultsKept` 不为零是正常且正确的**，不是 bug。
- ⚠️ 顺序纪律：**先收集 hash 再删行**。反过来的话，行删完了就查不到该释放哪些 blob，文件会永久占据存储。
- ⚠️ 与 `R-技术-06` 的联动：这个端点是**真删不可逆**，备份没落地之前，误触发就没有任何回滚手段。这是两条风险唯一交叉的地方，发布前须一起确认。

**④ 数据保留期限**（原"待确认"第 3 点）

- 现行策略：账号数据**存续至用户注销**，无自动过期；`answer_cache` / `ocr_results` 为**跨用户共享缓存**，按"内容是否存在引用"决定去留，不随单个账号过期。
- 已写入政策「保存多久」一节：**账号注销即删；共享缓存层因内容寻址与多用户复用，保留至无人引用**。这句必须留着——它是"注销即删"与"不删别人共同体"两者之间唯一自洽的表述方式。

**`R-合规-04` 存储桶为 public（已决策接受，留作后续规划）**

- 现状：`SUPABASE_STORAGE_PUBLIC` 默认 `'true'`（`storage.service.ts:41`）⇒ 走 `getPublicUrl`，**URL 永久有效、无签名、无过期**。
- 实际防线：key 形如 `blobs/xx/<64位sha256>/...`，**不可枚举、不可猜**；手机端另走 `/api/storage/files/{key}` 代理（可加鉴权/审计）。
- **决策（2026-10-27）**：**本期不改私有桶**，登记为后续规划。
- 决策依据（不是"没空"）：① 改私有桶要全链路换签名 URL——小程序 `<Image>`、PDF 合成、Word 导出、网盘归档、`withUrls` 回填，一处漏改就是"图片某处打不开"这类散点故障；② 当前"不可猜 key + 代理"已覆盖主要威胁（猜不出、枚举不到）；③ **在没上生产、没外部用户之前，改与不改的风险差别为零**——现在动它属于把成本花在风险最低的时间点。
- **残余风险照实写**：URL 一旦被截图/转发/日志记录，**永久有效且无法撤销**（只能换 key 重传）；第三方拿到 URL 即可访问该文件，不经过任何鉴权。这与"未成年人照片"叠加时，是**中危而非低危**。
- **触发重新评估的条件（任一）**：① 出现 key 或 URL 泄露事件；② 合规审计要求"文件不得匿名可访问"；③ 接入任何形式的分享/导出给第三方；④ **正式版发布前**（QA-16 回退清单里会再问一次）。

**`R-合规-05` 隐私保护指引未上报（代码已就绪，剩人工一步）**

- 事实：微信要求在小程序后台「**用户隐私保护指引**」里**逐项声明实际使用的隐私接口**（入口有两个，走哪个见 ⓪）。
- 后果链（为什么是发布阻断项）：不勾 ⇒ `getPrivacySetting` **恒返回 `needAuthorization=false`** ⇒ 用户点了同意也**不生效** ⇒ 审核驳回；即便绕过去，实际也在**无授权采集**。
- 代码侧已就绪（无需再改）：`app.config.ts` 开 `__usePrivacyCheck__`；`utils/privacy.ts` 全局注册 `onNeedPrivacyAuthorization`（一处注册全站生效）；同意键必须是**原生 `button` + `openType="agreePrivacyAuthorization"`**——基础库会校验 buttonId 的真实点击，**用 `View` 伪造无效**。

**❌ 三个最容易做错的地方**

1. **只改这个指引，不改小程序内的《隐私政策》**——两者是两份东西（平台声明 vs 应用内文本），内容必须一致。政策改了要同时改 `PRIVACY_POLICY_VERSION`（版本号变了才会重新征求监护人同意）。
2. **以为开发版测过就行**——`urlCheck:false` + 开发版豁免让隐私校验在开发阶段**不生效**，这就是 `R-已关闭-11` 描述的那个坑。必须用真机（体验版/正式版）验。
3. **审核通过就以为完事**——`errno 112` 是在**运行时**报的，不在审核阶段报。第 7 步的验证不能省。

**① 本项目实际用到的隐私接口（按代码实测，不是按猜测）**

| 官方清单项 | 代码依据 | 是否必勾 |
|---|---|---|
| **相册（选中的照片或视频信息）** | `Taro.chooseMedia({ sourceType: ['camera','album'] })`、`Taro.chooseImage({ sourceType: ['album','camera'] })` | ✅ 必勾 |
| **摄像头** | 同上 `sourceType` 含 `camera` | ✅ 必勾 |
| **选中的文件** | `Taro.chooseMessageFile()`（从微信聊天选 PDF/图片导入资料库，`library` 与 `answer-editor` 各一处） | ✅ 必勾 |
| **剪切板** | `Taro.setClipboardData()`（复制图片链接、复制代码块、复制 OCR 文本）。⚠️ **只写不读，但依然必须勾** | ✅ **必勾**（见下方说明） |
| 位置 / 录音 / 通讯录 / 微信运动 / 手机号 / 日历 | 代码**零调用**（`grep getLocation / startRecord / chooseAddress` 均无命中） | ❌ 不要勾 |

> ⚠️ **剪切板为什么"只写也必须勾"（2026-10-27 查证官方口径，比原先的推论更硬）**：
> 微信官方隐私接口清单里 `wx.setClipboardData` **与** `wx.getClipboardData` **同列在「剪切板」一项下**，声明与否看的是"有没有调用这个接口"，不是"读还是写"。
> 不声明的实际后果不是"审核可能挑刺"，而是**运行时直接失败**：
> `setClipboardData:fail api scope is not declared in the privacy agreement`（`errno 112`）。
> ⇒ 表现是**用户点「复制」没反应**，而开发阶段（未上传、`urlCheck:false`）往往测不出来。这与 `R-已关闭-11` 属同一类"只在真机/体验版爆发"的坑。
>
> **验证方法**：真机点一次「复制链接」，若 toast 报错或无声失败，就是没声明或声明还没下发（官方说明**声明后约 5 分钟生效**）。

| 百度网盘（用户文档） | 用户主动保存的文档文件 | 用户主动开启的云端归档副本 | 否（用户自己的资料副本） |
| 百度网盘（运维备份） | **数据库全量导出（已 AES-256-GCM 加密）** | 运维灾备，防止数据丢失 | 否（加密存储，运营方不读取内容） |

> ⚠️ 最后一行是 **2026-10-27 新增的处理活动**（`R-技术-06` 落地带来）：备份文件包含全体用户数据，因此**必须在隐私政策与平台指引里都声明**，不能因为"加密了"就不写。声明口径：接收方=百度网盘（个人账号），内容=加密后的数据库备份，用途=灾备恢复，且明确"运营方不以可读形式访问备份内容"。

**⑤ 验证方法（做完必须验，不能只看后台显示"已保存"）**

1. mp 后台保存后，**等 5-10 分钟**（配置有下发延迟）；
2. 开发者工具「清缓存 → 全部清除」→ 重新编译；
3. 首次触发 `chooseMedia` 时**应弹出隐私授权弹窗**——**不弹就是没生效**；
4. 代码侧校验：`Taro.getPrivacySetting()` 返回 `needAuthorization: true`（首次、未同意时）。若恒为 `false`，说明后台没勾上或还没下发。

- ⚠️ **这一步无法由代码解决**，只能人工在 mp 后台操作。已作为发布前 14 项清单的阻断项（ADD-07 第 8 章）。
- 关联经验：`R-已关闭-11`（开发版豁免 ≠ 体验版豁免）。

| 方案 | 做法 | 代价 | 适合 |
|---|---|---|---|
| **A. 本期发一版体验版→正式版** | 走入口2，随本次提审 + 发布一起生效 | 等于提前启动 `R-技术-07` 那 9 项前提（备案域名、`urlCheck:true`、密钥轮换…），工作量不小 | 本来就打算近期上线 |

**`R-合规-06` 匿名用户跳过内容安全（已决策接受）**

> 用户问的是"这件事到底意味着什么"，所以这一条写到能拿去做风险判断的颗粒度。

**① 机制上发生了什么**

- 微信 `msgSecCheck v2` **强制要求传 `openid`**（`openid` 是小程序内用户的唯一标识）。不传或传错 → 返回 **`40003 invalid openid`**，等于调用失败。
- 拿到 `openid` 的唯一途径是**用户用微信登录**（`wx.login` → `code2session`）。
- 而本项目的设计允许**不登录先用**：首次打开时后端自动建一个**匿名账号**（`open_id IS NULL`，靠 `X-Device-Id` 标识，**30 天滑动过期**）。
- ⇒ **匿名用户根本没有 `openid` 可传**，`msgSecCheck` 从原理上就调不了。这不是"忘了做"，是**接口前提不满足**。

**② 当前的实际行为（代码事实）**

| 场景 | 行为 |
|---|---|
| 已登录用户（`open_id` 非空） | 按 `userId → users.open_id` 换 openid（**缓存 5 分钟**，避免每条消息查库），正常检测 |
| 匿名用户（`open_id` 为 NULL） | **跳过检测**，只 `console.warn` **一次**（不是每条都刷日志） |
| 检测接口本身故障 | 按既定的 best-effort 策略记 `console.error` 打全错，不阻断用户操作 |

- 注意"只告警一次"的设计意图：匿名是**正常且常见**的状态（新用户第一次打开就是匿名），如果每条都 warn，日志会被秒刷满，真故障反而看不见。**告警一次是"提示存在该状态"，不是"每次跳过都报"。**

**③ 实际风险有多大（要按场景分开看，不能笼统说"高风险"）**

| 写入位置 | 匿名是否可写 | 风险实质 |
|---|---|---|
| AI 对话内容 | 可写 | **只回给自己看**，不进入任何共享视图，也不进 system prompt ⇒ 影响面=自己的会话 |
| 题目文本（识别结果） | 可写 | 只存自己账号下，不外露 |
| `knowledge_articles`（全局表，进 system prompt） | **不可写** | 走 `requireAdmin()`，匿名必 403（`R-技术-08` 已关闭） |
| 公开发布 / 分享 | **不存在该功能** | 本项目是单人单库，无 UGC 公开展示位 |

⇒ **结论：匿名的未检测内容在当前产品形态下不会扩散到其他用户**。这是"接受"这个决策真正的支撑——不是因为"改起来麻烦"，而是**没有扩散路径**。风险等级从中降为低的依据就在这里。

**④ 残余风险（诚实列出，不淡化）**

1. **监管视角不等于产品视角**：备案/巡查时，若被抽查发现"存在未经过内容安全检测的写入路径"，即便内容不扩散，也可能被要求整改。这是本条风险的**主要来源**，且与用户量无关。
2. **匿名账号可无限重建**：清掉本地存储即得一个新匿名号。匿名身份是 **30 天滑动过期**（`ANONYMOUS_TTL_MS = 30 * 24 * 3600 * 1000`，每次请求续期），这个时长对"防滥用"约束很弱——对故意滥用者，30 天的门槛约等于无。
3. **一旦开放任何公开能力，风险立即从中跳到高**：比如"错题分享给朋友""班级排行榜""公开题库"——那时匿名未检测内容就有了扩散路径。

**⑤ 决定与触发条件**

- 决策：**接受现状**（`R-技术-08` 关闭后，匿名已无写全局表的路径，扩散面被堵死）。
- **触发重新评估的条件**（任一）：
  1. 开放任何**公开发布 / 分享 / 排行榜**类能力 → 立即改为"匿名必须先登录才能写文本"；
  2. 平台明确要求**全量**内容检测（含匿名）→ 同上；
  3. 出现一次真实的内容违规投诉（不论是否扩散）→ 同上，并按 `R-技术-11` 触发条件①同步升级隔离手段。
- 彻底方案（未排期）：**匿名账号也强制先 `wx.login` 换 openid**，只把"登录"与"建账号"解耦——用户仍无感（不弹授权框），但拿到 openid 后内容安全就能全覆盖。代价是首次打开多一次 `wx.login` 往返（约 100-300ms）。

⇒ **影响**：三个代码断层的可复发路径已经封死（结构性问题，不是补丁）。真正剩下的不是"技术债"，而是**一项必须由人完成的外部动作**：mp 后台「用户隐私保护指引」勾选相册/摄像头（`R-合规-05` ⓪）。这一项不做，②的代码再正确也不起作用——**它只会在真正点「上传」的那一刻暴露**，这也是本条至今仍被标为"发布前必须走一遍"的原因。
- **`R-已关闭-03` / `-10`** —— 这两条是同一类错误的两次实例：**"两份状态"**（列表两份、答案两份）。归纳出的纪律比条目本身有用：**同一个可编辑/可展示的东西，只能有一个数据源**。

**与其它章节的交叉（复发性最强的地方）**

| 交叉点 | 说明 |
|---|---|
| `-01` ↔ `R-技术-05` | 不接 CI 的代价，全部由 `-01` 承担。**只要这条还开着，`-01` 就永远活跃** |
| `-11` ↔ `R-合规-05` | 同一类"只在真上传时爆发"的坑。`-11` 的三个代码断层已全部可验证（①`packOptions` ②`__usePrivacyCheck__` ③`rotate-wx-secret.mjs`）；`R-合规-05` 剩 mp 后台勾选这一**外部人工步骤**——两者叠加才是完整的发布前检查 |
| `-09` ↔ `R-技术-11` | 门禁**误报**（已关闭）与门禁**漏报**（已接受）是两件事，别混为一谈 |
| `-02` ↔ `R-技术-01` | 数据库连不上时，后端症状与"代码没生效"几乎一样，先看日志里的 DB 错误再怀疑代码 |

**一句话行动结论**：新加代码时，只需要记住三条——① 交付前必须重建 dist 并验特征串；② 任何 python 子进程必须走 `pythonEnv()`；③ 任何"可编辑的东西"不许有第二份副本。这三条覆盖了 12 条里 7 条的可复发路径。

## 7. 项目备案（不处置，但必须查得到）

**这一章解决什么问题**：有些东西已经明确「不修／不删／不改」，但它不能就此从视野里消失——否则半年后有人翻到它，会重新纠结一遍"这玩意儿是不是垃圾"，或者更糟：以为没人管，顺手删掉。

**备案 ≠ 风险条目**。风险条目问的是"要不要处置"，备案问的是"这是什么东西、为什么留着、什么时候该再看一眼"。所以备案项**不参与 1.3.1 的状态统计**。
