## 1. 登记规则

### 1.1 登记格式

每一条风险在**所属章节的总表**中占一行，字段固定为九列：

| 编号 | 类别 | 描述 | 影响 | 概率 | 处置决策 | 状态 | 责任人 | 复核周期 |
|---|---|---|---|---|---|---|---|---|

- **影响**：对用户/交付的后果严重度，`高`（阻断发布或数据错误）/ `中`（功能降级、体验受损）/ `低`（维护成本）；
- **概率**：`高`（已发生或必然发生）/ `中`（特定条件下发生）/ `低`（小概率）；
- **描述**：一句话说清"是什么"，**不写解决方案**（方案写进同章的「判据与缓解」小节，按编号对应）；
- 需要展开的条目在同章「判据与缓解手段（按编号）」里给：现象 → 判据命令 → 缓解手段 → **为什么不彻底解决**。

### 1.2 编号规则

`R-<类别>-<两位序号>`，类别五选一：

| 类别码 | 含义 | 典型内容 |
|---|---|---|
| `技术` | 技术风险 | 外部依赖不可用、架构假设失效、安全边界 |
| `算法` | 算法已知缺口 | 指标不达标但已决策接受、能力未实现 |
| `工程` | 工程债 | 结构性问题、垃圾未清、规范未落地 |
| `合规` | 合规风险 | 密钥、隐私、内容安全、第三方传输 |
| `已关闭` | 已解决的历史风险 | 复发防护（**只增不改**，用于防复发） |

⚠️ **编号一旦分配永不重排、永不复用**。删除条目时把状态改为「已关闭」并**保留原编号**；若关闭事项值得作为复发防护教材，在 `R-已关闭-` 序列里再登记一条（两处互引）。

### 1.3 状态机

```
待评估 ──► 接受（不修）
   │            │
   └──► 缓解中 ─┴──► 已关闭
```

| 状态 | 含义 | 硬要求 |
|---|---|---|
| `待评估` | 已发现、未决策 | **必须给出评估截止日期**，否则不算登记完成 |
| `接受` | **决定不修** | 必须写三件事：① 理由 ② 代价（会坏成什么样）③ **触发重新评估的量化条件** |
| `缓解中` | 有手段但未消除 | 必须写清"缓解到什么程度"与"剩下的尾巴是什么" |
| `已关闭` | 已消除 / 已不再适用 | 必须写清关闭凭据（提交号、实测结果、或决策变更） |

### 1.4 维护纪律

1. **「接受」也是一种决策**——不修不是"忘了"，而是明确取舍。不写理由的「接受」等于没决策，评审时直接打回。
2. **触发条件必须可观测**：写"用户量过千再评估"合格，写"以后再看"不合格（无法判断何时触发）。
3. **复核周期**：`缓解中` / `待评估` 条目每月首个工作日过一遍；`接受` 条目按各自触发条件复核（不排定期）。
4. **状态变更必须同时更新**：① 本条状态 ② 复核日期 ③ 本文末尾变更记录表。三处不同步视为文档缺陷。
5. **与 ADD-04 第 12 章「演进路线与遗留问题」互为索引**：架构级遗留问题在 ADD-04 提出，在本册登记处置决策；两处描述冲突时以本册为准（本册是决策记录）。
6. **算法类缺口与 DD-10 第 11 章互为索引**；合规类与 ADD-07 第 8 章「发布前安全清单」互为索引。

### 判据与缓解手段（按编号）

**`R-技术-01` Supabase IP 间歇封锁**

- 现象：查询突然全部 `fetch failed` / 全站 500，几秒后自愈；同一 key 换机器可能不复现。
- 根因：Supabase 域名走 Cloudflare，直连 IP 被 CF 层判定异常后封锁（与项目代码无关）。
- 判据：`node server/scripts/health-probe.mjs` 连续报 DB 失败而 CPU/内存平稳；日志出现 `supabase-dns-pin` 重探记录。
- 缓解：`server/src/storage/database/supabase-dns-pin.ts` —— 维护 **33 个候选 IP**，启动时逐个 TLS 探测优选，**5 分钟**周期自愈重探；命中失败自动切换。
- ⚠️ **静态 IP 池方案已证伪，勿回退**（理由见 ADD-04 第 8 章被否决方案）。彻底方案=自建 Postgres / 专用连接串，未排期。

**`R-技术-02` RLS 未启用（已决策接受）**

- 现状：全部表 `RLS` 关闭，后端用 `service_role`（绕过 RLS），隔离 100% 靠代码 `.eq('user_id', userId)`。**单点疏漏 = 越权读**。
- 2026-10-24 重新评估结论：**不予启用**。四条理由——① service_role 绕过，开了也不生效；② 登录体系无 Supabase JWT，`auth.uid()` 取不到值，策略写不出来；③ 现有查询已全覆盖，RLS 不增加覆盖面；④ 与"多用户共享"预留模型冲突（见 ADD-07 第 3 章）。
- 替代：静态门禁 `server/scripts/check-isolation.mjs`（`pnpm --filter server check:isolation`）。**2026-10-27 实测：扫描 108 处 `.from()` 调用点，零缺口**。
- 残余风险已转移 → `R-技术-09`（身份头伪造）与 `R-技术-11`（门禁漏报）。
- **触发重新评估的条件**（任一即重评）：① 引入 Supabase Auth / 第三方 JWT 登录；② 出现第二个服务端写库进程（不止本 NestJS）；③ 数据共享（家长/孩子/朋友）进入实施。

**`R-技术-03` ima 日配额 220021**

- 现象：某天搜题突然全部返回"资料获取次数已达上限"，次日自动恢复；**零命中也扣次**，无法靠"少返回结果"省配额。
- 判据：日志 `220021`（`answer-search.service.ts:306`、`ima-provider.ts:70`）。
- 缓解：① **探针式检索**，先探后取，把每次搜题的 ima 调用从"6 库并行"压到**最坏 4 次**（`IMA_PROBE_MAX=2` + `IMA_FALLBACK_KB_MAX=2`，见 DD-11 第 4 章）；② 撞配额即**整体停检**（重试无意义），专属文案单独提示、不混进泛化失败；③ 叠加 `answer_cache` 持久缓存（同题不重复消耗）。
- 不可消除：配额在服务端按日重置，客户端无退避空间。

**`R-技术-04` LLM 供应商可用性**

- 现象：扣子（Coze）SDK 只在平台运行时可拿到 JWT，**部署包外不可用** —— 曾导致线上对话全挂。
- 缓解：改走 OpenAPI；三 provider 降级链 **coze → deepseek → hunyuan**，任一失败自动下移，全失败返回明确文案而非空响应（见 DD-11 第 5 章）。
- 残余：三家全挂时对话不可用（接受，属外部依赖固有风险）。

**`R-技术-05` 无 CI/CD 与自动化门禁**

- 现状：无 Github Actions、无 pre-commit hook；回归靠人工按 QA-15 第 7 章 7 步走。
- 风险点：**"忘了跑"型回归**——`pnpm build:weapp` 忘跑、`check:isolation` 忘跑，两者都不会报错只会静默发旧货（见 `R-已关闭-01`）。
- 缓解（当前）：QA-15 第 7 章门禁清单**逐条手工勾**；`R-已关闭-01` 的"grep dist 特征串"作为强制收尾动作。
- 待决策：是否接 CI（成本主要在"构建依赖 Windows 侧 OCR 环境"，CI 只能覆盖纯前端/纯 TS 部分）。

**`R-技术-06` 无定期备份**

- 现状：依赖 Supabase 平台侧能力，**本仓库无备份脚本、无恢复演练记录**。
- 风险：误删/误改无回滚手段；`migrations/` 只能重建结构，不能恢复数据。
- 待办：① 确认当前 Supabase 套餐的备份保留窗口与 PITR 是否可用；② 若不可用，自建 `pg_dump` 定时导出到对象存储；③ **至少做一次恢复演练**（没有演练的备份等于没有备份）。
- 状态说明：`待评估` —— 需思傅确认套餐档位后才能定方案。

**`R-技术-07` 生产环境尚未落地**

- 现状：仅本地联调（`PROJECT_DOMAIN=http://192.168.3.242:3001`）+ 微信**开发版/体验版**，无公网生产后端。
- 关键约束：`*.app.workbuddy.host` **不能当生产后端**（临时隧道，不保证可用性与域名白名单）；正式版需备案域名 + HTTPS。
- 改造点与两硬约束见 QA-16 第 7 章（云托管）；域名白名单/备案/隐私声明的连锁阻断见 QA-16 第 4 章与 `R-合规-05`。

**`R-技术-08` 全局表零鉴权（已加固，未彻底）**

- 对象：`knowledge_articles` —— 全局表（无 `user_id`），**内容直接拼进 system prompt**，被污染即等于给 AI 下指令。
- 已落地：`requireAdmin()` + `CHAT_ADMIN_IDS` 白名单（逗号分隔 user id，放 `.env.secrets`）。实测非白名单账号写 → **403**。
- ⚠️ **未配 `CHAT_ADMIN_IDS` 时门禁降级为"放行 + warn"**（`user-context.ts:179`）——这是有意的兼容设计，但意味着**部署时漏配 = 门禁失效**。发布前检查项已写入 ADD-07 第 8 章。
- 彻底方案：`users` 加 `role` 列做正式管理员体系（可扩展到多管理员、可审计），**待思傅决策**，未排期。

**`R-技术-09` 身份头可伪造（已实施令牌，剩收尾）**

- 现象：`X-User-Id` 是裸字符串，无签名 ⇒ 改 header 即可读写他人数据（在 `R-技术-02` 前提下无第二道防线）。
- 已落地：`server/src/shared/auth-token.ts` —— **HMAC-SHA256** 票据、TTL **30 天**、**滑动续签**（每响应回写新令牌）、比对用 `timingSafeEqual`。中间件优先级：**令牌 > 裸 `X-User-Id`（兼容期，命中即 warn）> `X-Open-Id` > `X-Device-Id` > 匿名建号**。
- **剩余收尾**：前端全量改为只发令牌后，**关掉裸 id 通道**（当前为兼容期）。
- 更彻底方案（Supabase Auth JWT）与 `R-技术-02` 合并评估，见其触发条件①。

**`R-技术-10` 进程内状态与单机假设（已决策接受）**

- 三处硬绑定单机：① `mem-cache` 是**进程内**缓存（timeline 30s / 用户 60s / 答案 24h，DD-13 第 4 章）；② H5 扫码登录票据**存在进程内存**（`login_tickets` 表建了但写入方未启用，见 `R-工程-08`）；③ OCR 侧车是**本机子进程/本地服务**（`9300` 端口），无法共享。
- 后果：一旦起两个副本，会出现"同一用户在两副本看到不同数据"、扫码票据查不到、侧车重复拉起吃内存 2-3GB/实例。
- **决策：明确不做横向扩容**，单机 + `wake-server` 保活（QA-16 第 5 章）。代价=单点，重启期间不可用（约 10-30s，前端 `wake.ts` 自动唤醒重放）。
- **触发重新评估的条件**（任一）：① 日活 > 500 或并发 > 20；② 需要 7×24 可用性承诺；③ 要在多台机器上跑 OCR。届时需先把 mem-cache 换 Redis、票据落库、侧车改独立服务——**三项必须一起做**，只做一项会得到更糟的半吊子状态。

**`R-技术-11` 隔离门禁是启发式（已决策接受）**

- 机制：向后看 **12 行**内找 `.eq('user_id'`，配合常量表名还原、insert/upsert 链豁免、白名单。
- 必然的漏报形态：① 查询链超过 12 行（跨多段 `.select(...)` 拼接）；② 表名由变量间接给出且不是文件内 `const NAME = 'table'` 形式；③ 把 `.eq` 提到链外变量再传入。
- **决策：接受，用 code review 兜底**。理由=把窗口从 12 行放到 30 行会带来大量误报，误报多了就会被"习惯性忽略"，比漏报更危险。
- 触发条件：① 出现真实越权事故（无论是否被门禁捕获）→ 立刻升级为"运行时断言 + 集成测试"双轨；② 门禁季度误报率 > 30%（说明启发式已失配）。

### 判据与缓解手段（按编号）

**`R-算法-01` T7 手写压印刷不可分（已决策接受）**

- 现象：场景 ②（黑笔手写**压在**印刷字上）擦除后仍留 **38.27%** 残余，构成为 **2784px 手写紧邻（间距 ≤10px，G16 口径既定豁免）+ 2722px 纯连坐（手写直接压印刷 → 并成同一连通域，同色同笔画宽不可分）**。
- ⚠️ **指标方向别记反**：38.27% 是"该擦的没擦净"（残留），不是"把印刷擦了"（误擦）。误擦口径见 `R-算法-02`。
- 根因实证：T7 根因报告 4 组实验证伪——粗细闸门、print 占比、`protectPrintGeneric` 像素级保护（反而使 G15 擦净 33/44 → 13/44）。
- 产品决策：**保持现状**（疑罪从无，宁可少擦）。人工补救=`manual_regions` 手动画区补擦。
- **触发重新评估的条件**（任一）：① 出现更高优先级的用户反馈（"手写没擦掉"被明确列为不可接受）；② 出现新的可分离特征（如不同笔压/不同色相/更高分辨率下笔画宽分离）；③ 换用支持语义分割的擦除模型。
- 附带说明：残余 77.4% 的部分**不是缺陷**——小手写答案自成行成为行内自身参考（自一致），共识门不过即保留，属"疑罪从无"的既定取舍。

**`R-算法-02` G16 指标看护**

- 口径：**G16 `M ≤ 2.0%`**（框外印刷误擦率）。常量即 `G16_TAU` / `G16_NH`（见 DD-10 第 6 章参数表）。

- 缺口：无 CI 自动执行（受 `R-技术-05` 制约），当前靠人工；GT 图像不在仓库（`R-算法-05`），需回原工作区复跑。
- 回归规模参考：`docs/reports/issue-three-image-features.md:174-190` 的 **38 + 212 条断言**。

**`R-算法-03` OCR 侧车冷启动**

- 参数：`DEFAULT_IDLE_MS = 15min`（**900s**，`sidecar.supervisor.ts:58`）/ `OCR_TIGHT_IDLE_MS = 2min`（`sidecar.supervisor.ts:59`）。PPSV3 3.x 管线驻留 **~2-3GB**，空闲必须回收，否则本机内存被吃死。

- 决策：接受。precise 本身是"愿意等"的场景；fast 模式走常驻 RapidOCR 不受影响。

**`R-算法-04` 公式渲染为近似实现**

- 现状：`src/utils/latex.ts` 自研，vlist 布局 + 根号近似（`√` + `border-top` 拼合）；`cases` / `aligned` 等环境只做近似。
- 后果：复杂公式与专业排版有肉眼可见差距；**编辑态绝不显示 LaTeX 源码**（红线）。
- 降级策略：不支持的结构**整行回退为源码文本**（可接受降级，不炸版）。
- 决策：接受。触发条件：出现"公式看不清导致做题错误"的反馈 → 评估接 KaTeX 的 WebView 渲染或开源渲染方案。

**`R-算法-05` GT 数据集不在仓库内**

- 现状：`/workspace/worksheet-test/annotated` 等 GT 图像不在本仓库，**G13 / G15 / G16 无法在原地复跑**。

- 决策：接受（数据集体积与版权原因不入库）。**诚实记录**：无法复跑就写"无法复跑"，不许拿方向性推断冒充实测数据。
- **触发条件**：① 要做发布前算法验收；② 要接 CI 自动回归。届时需把 GT 数据集放到独立私有存储，并在 QA-15 登记获取方式。

**`R-算法-06` 占位能力未实现**

- 决策：保持占位 + 在 DD-10 明确标注（已完成）。改进项：配置非法值时启动期 warn 一次（避免静默）。

**`R-合规-02` 第三方数据传输**

- 要求：① 隐私说明中**明确告知**接收方类型与用途；② **数据最小化**——只传当前题目，不传整本资料、不传与作答无关的元信息；③ 用户可选模式（search/kb/ai 三模式互不兜底）本身就是一种"少传"的手段，不要为了"效果更好"偷偷跨模式兜底（DD-11 第 2 章红线）。

**`R-合规-03` 儿童隐私**

- 特殊点：用户是**家长**，但**数据主体是未成年人**（错题、成绩、学习轨迹）⇒ 适用更严口径。
- 待确认：① 是否需要正式《隐私政策》文本（微信平台通常要求，且要能从小程序内打开）；② 是否需要监护人同意流程；③ 数据保留期限（当前 `answer_cache` 永久、`ocr_results` 永久，需明确"按用户删除"是否覆盖缓存层）。
- 现状：`docs/` 下有《安全与隐私设计方案》，但**没有面向用户的隐私政策文本**。

**`R-合规-04` 存储桶为 public**

- 现状：`SUPABASE_STORAGE_PUBLIC` 默认 `'true'`（`storage.service.ts:41`）⇒ 走 `getPublicUrl`，**URL 永久有效、无签名、无过期**。

- 决策依据：改私有桶需要全链路改签名 URL（含小程序 `<Image>`、PDF 合成、Word 导出、网盘归档），成本高；当前"不可猜 key + 代理"已够用。
- **触发重新评估的条件**：① 出现 key 泄露事件；② 有合规审计要求"文件不得匿名可访问"；③ 接入第三方分享功能。

**`R-合规-05` 隐私保护指引未上报（发布阻断项）**

- 事实：微信要求在小程序后台「设置 → 服务内容声明 → 用户隐私保护指引」**勾选实际使用的权限**（本项目需：相册、摄像头）。
- 后果链：不勾 ⇒ `getPrivacySetting` **恒返回 `needAuthorization=false`** ⇒ 用户点了同意也**不生效** ⇒ 审核驳回；即使绕过，实际仍在无授权采集。
- 现状：代码侧已就绪——`app.config.ts` 开 `__usePrivacyCheck__`，`utils/privacy.ts` 全局注册 `onNeedPrivacyAuthorization`，同意键为**原生 button + `openType=agreePrivacyAuthorization`**（基础库校验真实点击，View 伪造无效）。
- ⚠️ **这一条无法由代码解决**，必须人工在 mp 后台勾选。已作为发布前 14 项清单的阻断项（ADD-07 第 8 章）。
- 关联经验：`R-已关闭-11`（开发版豁免 ≠ 体验版豁免）。

**`R-合规-06` 匿名用户跳过内容安全（已决策接受）**

- 现状：`msgSecCheck v2` **强制要求 openid**，不带返回 `40003 invalid openid`；匿名用户 `open_id` 为 NULL ⇒ **只能跳过检测**，当前仅打一次告警。

- **触发条件**：① 开放匿名用户的公开发布/分享能力；② 平台要求全量检测。届时改为"匿名必须先登录才能写文本"。
