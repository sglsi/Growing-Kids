| # | 发现 | 证据 |
|---|---|---|
| **F1** | **照四步做完会得到假的 `exact`**：拿 1 道真实几何题在 10,454 份正文里跑现网 `judge()`，判出 3 份 `exact=true`，**逐条核对 3 份全是别的题的解析** ⇒ 单例精确率 **0/3** | 见 §3.3，误判机制定位到 `question-match.ts:229` |

## 1. 当前试题检索比对的核心思想（代码事实）

### 1.1 主线：检索词与判定锚点**分离**

这是 `P-006`/`D-009` 定下的骨架，也是整个设计最值得保留的部分（`server/src/shared/question-match.ts` 头注释）：

- **召回（找资料）**：`extractKeys()` 用学科主题词表 `TOPIC_WORDS`（浮力、平行四边形、勾股定理…）+ 4 字滑窗，解决「哪本教辅讲这个专题」；再补 3 个 `extractDistinctive().keys`。合并后最多 9 个 key（`netdisk-search.service.ts:213-214`）。
- **判定（认原题）**：`extractDistinctive()` 把题干 `normalizeForMatch()`（只留汉字/字母/数字）后按 **6 字滑窗、步长 3** 取长锚点，再用 `isSameQuestion()` / `judge()` 要求 **≥3 个长锚点共现且命中率 ≥40%**，并定位【答案】/【解析】段。
- **硬闸**：`match_level = exact | topic | none`。只有 `exact` 才允许把 `solutionExcerpt` 放进 `answer`；`topic` 必须 `answer:''` + `verified:false`。**无数据源豁免**——网盘、`library_docs`、自有题库、ima 全要过闸（`answer-search.service.ts:295-446`）。

> 设计取向：**宁可判不出（topic），也不冒充（exact）**。这条是 D-009 的底线，本评审的所有建议都以不破坏它为前提。

### 1.2 检索链路（现状）

```
mode=kb（answer-search.service.ts:295）
  ① 自有题库同题答案  ── isSameQuestion()
  ② library_docs 正文  ── name/text_content.ilike + judge()      ← 已有一份「正文召回」实现
  ③ 网盘 netdiskFiles ── NetdiskSearchService.search()
       L0  searchLocal()  : name/path ilike OR，limit 500，**无 ORDER BY**
       L1  内存排序       : keyHits → bigram coverage → 名字长度，取 top 20
       L2  深挖           : 只取前 3 份 → ensureText()（缓存优先）→ coverage<0.2 丢弃 → judge()
  ④ ima 知识库        ── isSameQuestion()
  ⑤ 兜底              ── 只列同主题资料，answer 恒为空
```

**覆盖事实**：`netdisk_files` 78,430 行中 `text_status='ok'` 仅 **10,454 行（13.3%）**。其余 67,244 行（大 PDF、扫描版、`.doc`）本轮方案 A 明确不覆盖。所以「正文召回」的适用面是这 13.3%，报告里不能说成「资料都能搜」。

### 1.3 已有的一份「正文召回」实现，正好是反面教材

`answer-search.service.ts:537-569` 的 `searchLibraryDocs()` **已经**在做正文召回：

```ts
const clean = extractDistinctive(question).keys ...   // 归一化后的 6 字锚点
const ors = clean.flatMap(k => [`name.ilike.%${k}%`, `text_content.ilike.%${k}%`])
```

它把**归一化锚点**直接打在**未归一化正文**上，且 `.limit(30)` 无排序。这与本次实测的 F2 完全同源 ⇒ 这条路径现在大概率也只在靠文件名召回。**四步方案若照抄这个写法，等于把已知缺陷从 `library_docs` 复制到 10,454 份规模的 `netdisk_files`。**

## 2. 四步逐条比对

| 步 | 原设想 | 必要性 | 核查结论 | 判定 |
|---|---|---|---|---|
| **1** | `0026` 建 `text_content` trigram 索引 | **必要** | 内容不够：只有索引，没有解决「归一化错配」；且 §17「有索引=毫秒级」是**未验证推断**。0024 实测 18 个 `ilike` OR 已退化到 **615ms**，长文本 GIN 还要做 **lossy recheck**（每行 200k 字），收益可能远低于预期 | ⚠️ **需重定义 + 先做样本实验** |
| **2** | `searchLocal()` 加 `text_content` 召回 | **必要** | **最危险的一步**：直接塞进现有 `or` 链会同时触发 ① 归一化锚点 0 命中 ② 10~12 个正文 `ilike` ⇒ 20~30s/次 ③ `.limit(500)` 无排序截断（实测 9 个普通词就命中 **15,123** 行）④ `keyHits` 只按 name/path 算 ⇒ 正文命中行恒为 0 分、永远排不进 top20 | 🔴 **不可照原样实施** |
| **3** | `keyHits` 计入正文 + 排序加权 | **必要** | **不是独立第 3 步，是第 2 步的生效条件**：不一起改，第 2 步等于白做。且「命中几个检索词」这个指标本身要换成「**归一化锚点共现数**」——它才是与 `judge()` 同口径的信号 | 🔴 **合并进第 2 步，且换指标** |
| **4** | 深挖走缓存（不占 `MAX_DEEP_FILES`） | **伪需求** | `ensureText():487` 对 `text_status='ok' && text_content` 直接返回，离线抽取已经喂饱它 ⇒ **已生效**。真需求是另三条：禁在线下载、`MAX_DEEP_FILES` 3→20~30、删 `coverage<0.2` 闸门 | ✅ 已生效 / ⚠️ 真需求被漏掉 |

### 2.1 第 2 步为什么比想象中危险

`searchLocal()` 现在的形状（`netdisk-search.service.ts:375-427`）：

```ts
const ors = clean.flatMap(k => [`name.ilike.%${k}%`, `path.ilike.%${k}%`]).join(',')
.from(TABLE).select('fs_id, name, path, size_bytes')
  .eq('user_id', userId).eq('is_dir', false).or(ors).limit(500)
const keyHits = clean.filter(k => name.includes(k) || path.includes(k)).length
```

四个叠加缺陷：

1. **归一化错配**：key 是 `ACABD点`（`AC>AB，D点` 去标点后拼成），正文里是 `AC＞AB，D点`。`ilike` 不做归一化 ⇒ 结构性漏召回。
2. **or 链膨胀**：现有 9 个 key × 2 字段 = 18 个条件已经 615ms；再加正文就是 10~20 个 **200k 字长文本** `ilike`，单次检索直接撞微信 60s 上限。
3. **无排序截断**：`.limit(500)` 没有 `.order()`，PostgREST 返回的是物理顺序前 500 行。实测 9 个常见词命中 **15,123** 行 ⇒ **96.7% 的候选被任意丢掉**，真正那道题大概率不在里面。
4. **keyHits 口径**：只按 name/path 算 ⇒ 纯正文命中的行 `keyHits=0`，排序垫底，进不了 `l1` top20，更进不了 `MAX_DEEP_FILES=3` 的深挖 ⇒ **加完召回依然看不到它们**。

### 2.2 第 1 步：§17 的「毫秒级」需要打折

`pg_trgm` 实测粒度（L3）：6 字中文 → **8 个 trigram**，4 字 → 5 个，2 字 → 3 个。GIN 能按 trigram 筛掉不含的行，但**留下的行仍需 recheck**——对 200k 字的正文逐行做 `ilike`，成本远高于对几十字的文件名做同样的事（`name_trgm_idx` 单 key 1.97ms 是短文本口径）。

另有两项未量化的成本：94MB 正文归一化后约 **72.8MB**（抽样 500 份实测 77.1%），GIN 索引体积可能达数百 MB；L3 是 4C4G，构建耗时与内存峰值都未知。

⇒ **`0026` 必须是「先拿 1,000 份做样本索引实验，量出耗时/体积/单查延迟，再决定全量」**，不能一把梭。这也是报告 §17 自己列的「尚未验证」三项。

### 2.3 第 4 步：真需求被漏掉的三条

- `MAX_DEEP_FILES=3`（`:43`）：`l1` 有 20 份，只深挖 3 份。正文已缓存后，每份深挖只剩「读 200k 字 + `judge()` 4~11ms」，完全可以提到 20~30 份。
- `if (score < 0.2) continue`（`:312`）：用 **bigram 覆盖率**当 `judge()` 的前置闸门，而 P-006 明确否决了 bigram 作为「是不是这道题」的判据。`AB=6` 这类符号题覆盖率天然极低 ⇒ 精确匹配被闸门挡在门外。
- `ensureText()` 对 `pending`/`none` 行仍会**在线下载 + 抽正文**（`:491-528`），单次检索可能卡 60s。离线索引的架构是「索引在前、网盘在后」，在线检索就不该再碰网盘。

## 3. 决定性实测：照原方案落地会发生什么

**实验环境**：L3 生产库（只读 SQL），本地用**现网编译产物** `server/dist/shared/question-match.js` 跑 `judge()`，与线上判定逻辑逐字一致。
**真实题目**（取自 `timeline_items`，随机抽样）：

> `16、如图，在△ABC中AC>AB,D点在AC上，AB=CD,E，F分别是BC，AD的中点，连接EF并延长，与BA的延长线交于点G，连结GD，若∠EFC=60°，DG=√3，AC=5，则△ABC的面积为多少`

其 `extractDistinctive().keys` 前 3 个是 `16如图在A` / `图在ABC中` / `BC中ACA`，`longAnchors` 共 16 个。

### 3.1 现状：这道题在 name/path 上 **0 命中**

12 个归一化锚点打 `name ilike / path ilike`，返回 **0 行**（907ms）。⇒ 现有链路对这道题完全找不到；**当前是安全的（不误判），但无效**。

### 3.2 归一化错配：原文 `ilike` 几乎打不中

| 锚点 | `text_content ilike` 命中 | 说明 |
|---|---|---|
| `ACABD点` | **0** | 正文是 `AC＞AB，D点` |
| `中点连接EF` | **0** | 正文里有标点/换行 |
| `AD的中点连` | **0** | 同上 |
| `F分别是BC` | 49 | 少数抽取结果丢了标点才撞上 |
| `平行四边形`（对照，纯中文） | 1,102 | 无标点词不受影响 |

5 个词合计 **12.7s**（≈2.5s/词，与 §17 的 2.8s 一致）。⇒ **「把 `text_content ilike` 塞进 `or` 链」对区分性锚点基本不召回，只会把主题词噪声放大。**

### 3.3 归一化后能找到题，但判定全错

把正文做 `regexp_replace(text_content,'[^一-龥A-Za-z0-9]','','g')` 后用同一批 12 个锚点打分，10,454 份的共现分布：

| 命中锚点数 | 份数 |
|---|---|
| **10** | **2** |
| 4 | 5 |
| 3 | 17 |
| 2 | 85 |
| 1 | 574 |
| 0 | 9,771 |

拿到命中 ≥3 的 8 份正文，逐份跑现网 `judge()`：

| 文档 | SQL 命中 | `judge()` | 全文锚点 | 解析段内锚点 | 实际解析内容 |
|---|---|---|---|---|---|
| 四边形（下）.pdf ×2 | **10/12** | `exact=false` | 13/16 | 无解析段 | **正文里确有这道题的原型**（见下），但是讲义题目、没有答案 |
| 专题13 平行四边形…（解析版）.docx | 4/12 | 🔴 **`exact=true`** | 7/16 | 4 | 矩形 ABCD、AD=2AB、正方形 ABEF —— **另一道题** |
| 考点22 菱形及其综合（解析版）.docx | 4/12 | 🔴 **`exact=true`** | 7/16 | 3 | 菱形 ABCD、∠ADC=60°、等边三角形 —— **另一道题** |
| 考点14 三角形与全等三角形（解析版）.docx | 4/12 | 🔴 **`exact=true`** | 8/16 | 3 | △ABC≌△DEB、BE=BC=5、∠B=40° —— **另一道题** |
| 其余 4 份 | 3~4 | `exact=false` | — | — | 原卷版无解析 / 未过门槛 |

**3 个 `exact` 全是误判。** 若按原四步上线，`answer-search.service.ts:351-361` 会直接把其中一份 `solutionExcerpt` 塞进 `answer` 并标 `verified:true` ⇒ **D-009 修掉的病，原样复发，而且因为「正文命中」看起来更有证据，更难被用户察觉。**

> 样本量说明：这是 **1 道题 / 8 份候选**的单例，不是全库精确率统计。但误判机制是代码层面的确定性逻辑（下节），不是偶发抖动，所以风险是系统性的。

### 3.4 误判机制：两条判据的口径不一致

`question-match.ts`：

- `countAnchorHits()`（`:126-137`）在 **整篇正文** 上统计锚点共现。一本 3 万字教辅里连排几十道几何题，「E、F 分别是 BC、AD 的中点」「∠=60°」「AC=5」「ABCD」这些片段散落各处，凑够 7~8 个锚点、过 40% 门槛毫不费力。
- `locateSolution()`（`:165-202`）在众多【解析】段里挑「锚点共现最多」的一段，但 **对 `anchorsHit` 没有下限**；即使所有段都与本题无关，它照样返回一个 `best`。
- `judge():229` 的第三条前提是 `!!sec` —— **只要文档里任意位置出现过【解析】字样就算数**，完全不要求该段与本题相关。

⇒ `exact = 全文锚点达标 AND 文中有任意解析段`。这两条在「整本教辅」上同时成立太容易了。实测中 3 份误判文档的**段内锚点也有 3~4 个**（都是几何题常见表述），说明**单纯加「段内 ≥3」也拦不住**。

**还有一个更隐蔽的边界**：那 2 份命中 10/12 的讲义，正文里是

> `问题二：如图，在 ∆ABC 中， AC AB = ，D 点在 AC 上，AB＝CD，E、F 分别是 BC、AD 的中点，连结 EF 并延长…若∠EFC＝ 60°，连结 GD，判断 ∆AGD 的形状并证明。`

与用户题目**题干条件完全相同，但设问不同**（讲义问「判断 △AGD 的形状」，用户问「△ABC 的面积为多少」）。`isSameQuestion()` 只看条件、不看设问 ⇒ 即便这份讲义有解析，直接采纳也是**答非所问**。教辅里同题干改编/多问极常见，这不是个例。

### 3.5 性能实测汇总

| 场景 | 实测 | 判定 |
|---|---|---|
| 单 key 正文 `ilike`（对照 §17） | 2.8s | ❌ 不可用 |
| 5 key 原文 `ilike` | **12.7s** | ❌ |
| 全量 10,454 份**运行时归一化** + 12 锚点打分 | **3 分 06 秒** | ❌ 归一化必须预计算 |
| 先用 `中点/ABC` 粗筛再归一化 | **41s** | ❌ 粗筛也救不了 |
| `name/path` 18 个 `ilike` OR（有 0024 索引） | **615ms** / 命中 15,123 行 | ⚠️ 索引退化 + `.limit(500)` 任意截断 |
| `name` 单 key（有 0024 索引） | 1.97ms | ✅ 短文本基准 |
| 归一化体积（抽样 500 份） | 3,087,967 → 2,380,099 字 = **77.1%** | 全量约 **7,285 万字 / 72.8MB** |

⇒ **§17「没有索引 = 28 秒/次，有索引 = 毫秒级，中间没有第三种可能」这个二选一过于乐观**：索引只解决「扫哪些行」，不解决「长文本 recheck」和「无排序 limit 截断」。必须先做样本索引实验。

## 4. 最优方案：重排后的实施序列

原四步是一条「数据 → 索引 → 召回 → 排序 → 缓存」的工程链。**缺的是最前面的正确性前提，以及中间的「文档结构」这一层。** 建议改为四个阶段，P0 不通过就不准进 P1。

### P0 · 正确性前置（**新增，最高优先，全部未批准**）

| 项 | 内容 | 验收 |
|---|---|---|
| **P0-1 真题验收集** | 从 `timeline_items` 抽 **20~30 道**真实题干（覆盖数学/物理/语文、含符号题），人工标注每道在库里「有无原题 / 有无解析 / 在哪份文件」 | 标注集入库或落 `docs/reports/` 附件，**可重跑** |
| **P0-2 判定口径修复** | ① `judge()` 的 exact 从「全文锚点共现」改为「**题干窗口内连续共现 + 紧随其后的解析段**」；② `locateSolution()` 增加 `anchorsHit` 下限与「与题干窗口距离」约束；③ 新增**设问一致性**检查（提取「求…/…为多少/判断…/证明…」与解析段结论类型比对）；④ 保留数学符号（`= > < ∠ √ ° ⊥ ∥ △`）而不是一律删掉——`AC>AB` 压成 `ACAB` 后反而成了最常见的噪声串 | 拿 P0-1 集跑：现状 3/3 误判 ⇒ **误判必须归零** |
| **P0-3 准入闸门** | 指标：**误判数 = 0**（D-009 硬约束：宁可 `topic` 不可冒充）、`exact` 精确率 ≥0.9、端到端 P95 < 3s | 三条全绿才准进 P1；任何一条不达标就停在「召回变宽但一律 `topic`」 |

> P0-2 的 ④ 值得单独说明：`normalizeForMatch()` 去标点对语文/文字题合理，对理科题把**最有区分度的符号和数值关系**抹平了（实测 `ACAB`/`ABCD` 反而命中一堆无关几何题）。建议改为「两套锚点」：文字锚点仍归一化，理科符号/数值锚点单独保留并加权。

### P1 · 数据结构与索引（**重定义 `0026`，未批准**）

原「只建 trigram 索引」改为四件事，且**先用 1,000 份样本做实验**：

1. **归一化列** `text_flat`（`regexp_replace` 口径与 `normalizeForMatch()` 逐字对齐），离线回填 10,454 行；**不需要重新下载任何文件**（正文已在库里，纯 CPU）。实测归一化后约 7,285 万字 / 72.8MB。
2. **题目级切分**（本次评审的核心建议）：按 `【例 N】` / `N．` / `问题N` / `【答案】` 等标记，把整本教辅切成 **chunk**（题或题+解析为一段），落 `netdisk_chunks` 表或 `text_chunks jsonb` 列。实测样本里这些标记清晰可切（`四边形（下）.pdf` 有 `【例 4/5/6】`、解析版 docx 有【答案】/【解析】）。
   - 这一层同时解决三件事：**锚点共现不再跨题拼凑**（F1 的根因）、trigram 索引在短文本上 recheck 便宜、解析段可以直接从「题干 chunk 的相邻 chunk」取。
3. **索引**：在 `text_flat` / chunk 上建 GIN `gin_trgm_ops`，partial `where text_status='ok'`；**先量构建耗时、索引体积、单查/多查延迟**，达标才全量。
4. **查询约束**：正文召回只用 **3~4 个最长且最稀有的锚点**，≥4 字，显式排除 2~3 字短 key；不塞进 `name/path` 的 `or` 链。

> 「切分」是四步方案里完全没有的一层，但它是「正确甚至精确匹配」的结构性前提：**把整本 3 万字教辅当成一个文档，就不可能可靠地指出「哪道题的解析」。**

### P2 · 召回与排序（**重定义第 2、3 步，未批准**）

- **双通道**：`name/path` 通道保持现状（走 0024 索引）；正文通道独立查询，两条结果合并去重。
- **统一打分口径**：用「**归一化锚点共现数**」替代 `keyHits` + bigram `coverage` 两套并存的分数；它与 `judge()` 同源，排序与判定不再各说各话。
- **SQL 层 top-N**：按共现数排序后再取 top，废掉无 `.order()` 的 `.limit(500)` 任意截断。
- **删除 `coverage(qSet, text) < 0.2` 闸门**（`:312`），交给 `judge()` 判定。
- **保留 `.eq('user_id', userId)`**（无 RLS 红线）、`text_status='ok'` 过滤、`%,()` 转义。

### P3 · 深挖、呈现与回归（**重定义第 4 步，未批准**）

- `MAX_DEEP_FILES` 3 → 20~30；`DEEP_BUDGET_MS` 保持 18s 兜底。
- **禁止在线下载/抽取**：`text_status` 非 `ok` 的候选直接跳过深挖（在线检索不再碰网盘）。
- `exact` 结果附「题干窗口 + 解析段」双证据，前端展示时标出来源 chunk，便于家长核对。
- 🔴 **`CACHE_VERSION` v4 → v5**（`answer-search.service.ts:46`）：改了 `note` / 结果结构必须 bump，否则 `answer_cache` 会继续吐旧文案。
- **回归扩展**：`M27`（硬闸）加「长文档不得误判」用例；`M30` 加归一化列/切分/缓存版本断言；新增验收模块跑 P0-1 标注集。
- **前后端同步发货**（`D-009` 教训）：只换后端时旧前端会把 `answer:''` 也采纳。


## 7. 业界做法对照（2026-11-06 外部调研，只读）

> 缘起：思傅问「猿辅导、夸克等当前做得比较好的机构是如何实现题目比对的」。本节只做公开资料比对，**不改任何代码、不写任何库**；来源强度在 §7.6 逐条标注，二手信息不当事实用。

### 7.1 一句话结论

**业界没有一家是「拿题干去比整篇文档正文」。** 共同范式是：先把资料结构化成「**一道题一个对象**」，再用多级漏斗做同题判定，最后用**置信度闸门**决定给不给答案。我们那四步缺的正是最前面这一层，这从外部侧再次印证了 §0 的 F1 与 §4 的 P1。

### 7.2 共同范式（五级漏斗）

| 级 | 做什么 | 典型手段 |
|---|---|---|
| ① **输入结构化** | OCR + 版面分析 → **题目级切分**，题号/题干/选项/答案/解析绑定为同一对象，带 `question_id`、父子 ID、来源页码/坐标、版本号 | 版面分析模型、题号正则、结构化 JSON |
| ② **离线建库** | 建索引，不在请求时算全文 | 倒排（BM25/关键词）+ 正排 + 向量索引（FAISS/HNSW）+ 热题缓存 |
| ③ **多级召回** | 由便宜到贵逐层收窄 | 归一化字面快筛（SimHash/MinHash 海明距离）→ 语义向量 ANN Top-K → 倒排补充，多路融合 |
| ④ **精排 + 终判** | 候选集几十条内做精确比对 | Cross-Encoder / Reranker 重排 → 阈值分层 → 必要时 LLM 判「是否语义等价」输出概率 |
| ⑤ **置信度闸门** | 决定**给不给答案**，而不是只决定排序 | 高置信给标准答案；中置信只给知识点/思路引导；低置信回退检索结果或标注「AI 生成需甄别」，并附可追溯来源 |

作业帮 2020 年公开演讲把检索系统直接拆成「**策略层、正排系统、倒排系统、离线建库**」四部分（腾讯新闻，★）；这个分法和我们 `searchLocal()` 里「一次 `ilike` 打全表」不在一个抽象层级上。

### 7.4 对本报告结论的验证

| 本报告判断 | 外部证据 | 判定 |
|---|---|---|
| **F1**：整本 3 万字教辅当一份文档 ⇒ `exact` 全是别的题的解析（实测 0/3） | TextIn 明说「解析张冠李戴」是行业已知卡点、根因是对应关系；作业帮专利先「切割拆分确定题干」才检索；所有机构都是一题一对象 | ✅ **强印证** |
| **P1**：必须新增「题目级切分」层 | 作业帮专利 + 品玩 5 步含切分 + TextIn 版面拆题 + RAG 切块实践提示「别把一道题及其解析从中间截断」 | ✅ **强印证** |
| **P0**：真题验收集 + 误判归零才准入 | 阿里云「上线后抽样人工核对按误杀/漏判回调」；查重专利「人工复核库动态调阈最大化 F1」；作业帮 12 轮审核；TextIn「关系校验 + 分层抽检 + 未达标不进下一步」 | ✅ **强印证**（P0 不是我们发明的额外负担，是行业标配） |
| `exact / topic / none`「宁可判不出也不冒充」 | 小猿四级检索的置信度分层、夸克「检索刹车」低置信回退/打标签 —— 取向一致 | ✅ **印证** |
| §17「有索引=毫秒级」被证伪 | 业界从不靠单条 `ilike`：多级漏斗 + 正排/倒排/向量分层 + 离线建库 + 缓存。我们 18 个 OR 实测 615ms 属正常量级 | ✅ **印证** |
| 「深挖走缓存」是伪需求 | 离线建库/预计算是所有家的标配（作业帮「离线建库」、向量预生成、Redis 热题缓存）；我们已靠离线抽取把正文落进 `text_content` 等效达成 | ✅ **印证** |

**一句话**：我们评审的方向和业界一致，差别是**我们还停在「整份文件」这一层**，而产业界从第一天起就是「一题一对象」。

### 7.5 哪些别搬（比「学谁」更重要）

| 别搬 | 理由（本项目约束） |
|---|---|
| ⛔ 向量库 + Reranker + LLM 终判 | L3 是 4 核 4G、正文 94MB / 10,454 份；`users.ai_enabled` 默认 false、个人主体 `AI_PUBLIC_ENTRY=false`、AI 入口整体收起。引入 embedding/重排要新增模型服务与内存，与「家长主用、可用性优先」不匹配。更要紧的是：**我们的题干是用户自己录入的原题，不是拍照 OCR**，没有「改个数字 / 换个情境」的语义变式需求 ⇒ 字面锚点共现已经够用 |
| ⛔ LLM 生成/兜底答案 | 这正是 `D-009` 硬闸要防的；F1 已实测证明「文中有解析段 ≠ 本题解析」。业界用 LLM 是**题库没命中时**的兜底，我们连结构化题库都没有，兜底只会放大假答案 |
| ⛔ 亿级公共题库 | 语料是用户自己网盘里的教辅（78,430 行 / 11,184 份可抽），定位是**私有资料检索**，不是公共题库 |

**可以搬的三条（成本低、直接对应 P0/P1）**：
1. **一题一对象 + 父子 ID + 来源位置**：chunk 表带 `file_id`、起止偏移、题目/解析段类型，判定时只用 chunk 内文本；
2. **多因子校验**：锚点共现 + **设问一致性** + 相邻解析段（对应 F1 里「条件全同、设问不同」那例），替代单一「全文共现」；
3. **「未达标不放行」的准入闸门**：验收集驱动阈值，误判不归零不得进 P2 —— 这正是 TextIn 的流程闭环和查重专利的 F1 自适应。

## 8. 「未达标不放行」：主要思想与评判标准（P-009 / D-012）

> 缘起：思傅问「『未达标不放行』的主要思想是什么，评判标准又是什么」。本节是这个问题的正式回答，也是 `P-009` 判定层的验收口径。全部数字来自本机对 L3 只读取样语料的复现实验，**未写任何生产数据**。

### 8.1 主要思想：举证责任倒置，而不是「调高阈值」

一句话：**系统必须先证明「这是这道题、而且解析来自它」，才允许给答案；证明不了就只给资料，不给答案。**

这句话听起来像常识，但和检索系统的默认习惯正好相反：

| | 默认习惯（排序思维） | 未达标不放行（准入思维） |
|---|---|---|
| 起点 | 候选里挑「最像的」 | 每个候选先独立举证 |
| 输出 | Top-1 一定返回点什么 | 举证失败 ⇒ `topic`，`answer:''` |
| 责任 | 「像不像」由用户自己判断 | 「是不是」由系统举证，用户只做复核 |
| 出错成本 | 答错一题，用户下次不搜了 | ⚠️ 见 8.2 |
| 阈值的作用 | 排序分数，调低就多给结果 | **准入条件，逐条布尔，不能互相补偿** |

三个要点：

1. **举证责任倒置**。不是「没证据说明它不是本题，所以先给答案」，而是「没有完整证据链，就不给」。`exact` 是一个需要被**证明**的结论，不是相似度排名的第一名。
2. **成本不对称**。漏判的代价是用户看到一串同主题资料、自己翻一下；误判的代价是把**另一道题的解析**写进本题答案（P-006 的生产事故本体），家长按它讲给孩子，错了还不知道。更硬的约束是 §7.6 的双减合规：`exact` 才放解析、`topic` 答案必须为空，**既是正确性红线也是合规红线**，不能用「提高召回率」去换。所以两者不等价，最优化目标不是 F1，而是**误判归零约束下尽量提高召回**。
3. **闸门是准入，不是排序**。多个因子是**串联的否决项**，不是加权求和：锚点命中再多，设问冲突也直接否决；解析段再长，题干提不出 3 个长锚点也直接否决。这一点是本轮实现最容易被人「优化」掉的地方——一旦有人把六条改成打分加权求和，整套硬闸就退化回旧的「主题相似」打分，F1 会原地复活。

> 业界对应：TextIn 的流程是「资料入棚 → 图像质检 → 结构化解析 → **关系校验** → 分层抽检 → 入库上架，**未达标不进下一步**」；查重专利 `CN121031565` 用人工复核库动态调阈并把目标函数锁在最大化 F1；作业帮题目最多 12 轮人工审核。**闸门管的是「能不能进下一步」，不是「排第几」**——这一层在我们原四步方案里完全缺失。

### 8.2 常见误解（这三条都不是「未达标不放行」）

| 误解 | 为什么不对 |
|---|---|
| 「把相似度阈值从 0.4 调到 0.9」 | 阈值是**排序**参数；长文档里错的那道题一样能拿高分（实测讲义那份锚点命中 **13/16 = 81%**，光调阈值必然放行） |
| 「置信度低就加一句『请核对』」 | 这属于**呈现层补救**，答案已经给出去了；合规上「查完再补引导」无效，门槛必须在结果展示**之前** |
| 「先给答案，用户可以不采纳」 | 采纳按钮只防「写进题库」，防不住「已经看到并用错了」；而且本项目是把解析直接呈现在结果页 |

### 8.3 评判标准：两层闸门，各自有独立判据

#### 第一层 · 单次请求硬闸（代码级，逐条布尔，任一不过即降级）

`server/src/shared/question-match.ts` 的 `judgeQuestionObject()` 是唯一判据集中处，`rejectReason` 逐条留痕。当前实现六条：

| # | 达标条件 | 常量 / 依据 | 不达标时的动作 |
|---|---|---|---|
| 1 | 题干能抽出 **≥3 个长锚点** | `MATCH_MIN_LONG_ANCHORS = 3` | 判不出，`topic` |
| 2 | 题目对象切分成功（题干 ≤ 6000 字） | `MATCH_MAX_OBJECT_CHARS` | 长文档切不动 ⇒ 宁可判不出 |
| 3 | **设问一致**：不冲突 | `compareAsk()` → `same / conflict / unknown`；`conflict` 硬否决 | 条件相同但问的不是一回事（讲义「判断 △AGD 形状」vs 用户「求 △ABC 面积」）⇒ 否决 |
| 4 | **锚点共现限定在该对象的题干内**，命中 ≥3 且命中率达标 | `MATCH_MIN_LONG_RATIO = 0.4`；设问 `unknown` 时收紧到 `MATCH_STRICT_ANCHOR_RATIO = 0.55` | 全文拼凑锚点不再算数 |
| 5 | **相邻解析段**有效：紧随该题干、去空白 ≥8 字、且**不混入下一题题号** | `MATCH_MIN_SOLUTION_CHARS`、`SOLUTION_BOUNDARY_RE` | 边界串题 ⇒ 该对象不可信 |
| 6 | **来源位置可追溯且唯一定位** | `SourceLocation`（source / objectIndex / label / charStart-End）；多对象并列达标 ⇒ 否决 | 不知道答案来自哪一道题，就不给 |

放行后的硬约束：`exact` 必带 `source_location`、`solution` 取自**该对象**的解析段；`topic / none` 一律 `answer:''`、`verified:false`、**不带** `source_location`（M27 有断言）。

> 「设问 `unknown` 时把锚点门槛从 0.4 提到 0.55」是这条思想的典型体现：**证据少一项，就要求其余证据更强**，而不是把缺失的证据当成 0 分继续加权。

#### 第二层 · 上线准入闸门（验收级，决定「能不能进 P1」）

这层管的是**方案本身**，不是单次请求。对应 §4 的 P0-3，并补上来源定位：

| 指标 | 达标线 | 为什么 |
|---|---|---|
| **误判归零** | 验收集全部负例 `exact === 0` | D-009 硬约束，一票否决；不是「≤1%」 |
| **正例召回下限** | 真实题目自匹配 `exact` 率 ≥ 90% | 防止用「一律降级 topic」刷零误判 |
| **来源定位准确率** | `source_location.objectIndex` 落在正确题目对象 = **100%** | 定位错了，解析照样张冠李戴 |
| **精确率 / 延迟** | `exact` 精确率 ≥ 0.9、端到端 P95 < 3s | §4 P0-3 原口径 |
| **验收集可重跑** | fixture 固化 + 自动模块，不靠一次性手工结论 | 否则后人改了阈值没人发现 |

**验收集必须同时含三类样本**，缺一类就没有证明力：① 真原题 vs 长文档（负例，测跨题拼凑）；② 真实题目自匹配（正例，测切分与召回）；③ 条件相同设问不同（负例，测设问因子）。`server/scripts/verify/fixtures/question-object-cases.json` 是 L3 `netdisk_files.text_content` 的只读取样（4 份整本教辅，保留原始题号 /【答案】/【解析】/ OCR 噪音）。

### 8.4 实测：哪几条已经达标，哪一条**没有**

本机复现（`tsc` 单编 `question-match.ts` 后跑 fixture，2026-11-06）：

| 验收项 | 实测 | 判定 |
|---|---|---|
| 1 道真实几何题 vs 4 份整本教辅（**8 / 10 / 10 / 12** 个题目对象） | 假 `exact` = **0/4** | ✅ 误判归零（跨题拼凑这一类） |
| 跨题拼凑复现：把一道题的条件拆进 3 个题目对象 | 旧全文判据 `isSameQuestion()` = **true**，新 `judgeObjects()` = **false** | ✅ 直接证明第 4 节的 F1 已被切分层修掉 |
| **A/B 对照**：同一份正文逐字不变，只把用户设问从「判断形状」改成「求面积」 | `exact` **true → false**，原因「设问冲突 area vs shape」，且该负例锚点命中率仍 ≥0.4 | ✅ 证明多因子不是摆设：单看锚点必放行 |
| 其中 `四边形（下）.pdf` 最相似对象 | 对象内锚点 **13/16（0.81）**，按判据顺序首先被「设问冲突 area vs ratio」否决（该讲义无【答案】/【解析】标记，另有第二重否决） | ✅ 长文档里「高分对象」确实存在，靠硬闸拦下 |
| 六条硬闸逐条隔离触发 | 6/6 各自给出对应 `rejectReason`，对照组正常放行 | ✅ 不是加权求和，也不是「一律不放行」 |
| 真实题目自匹配（含解析、题干 ≥30 字的对象） | **28/28 exact**、漏判 **0** | ✅ 正例召回 100% |
| 来源定位 | **28/28** 落在正确 `objectIndex` | ✅ 定位准确率 100% |
| 单题片段老行为（M27） | 21/21 通过 | ✅ P-006 契约未回退 |
| **合成「题干 A + 别人的解析段」** | **仍会放行** | ❌ **未达标，见下** |

**必须如实写下的残余风险**：前一轮对 40 正例 / 40 负例做过关系信号的 ROC 实测，想用「解析段与题干共享的符号指纹 / 答案提示词」证明「这段解析属于本题」：

```
link.score>=1     正例放行 31/40 (78%)   负例放行 16/40 (40%)
link.score>=2     正例放行 30/40 (75%)   负例放行 13/40 (33%)
cue               正例放行 38/40 (95%)   负例放行 37/40 (93%)
link>=1 OR cue    正例放行 40/40 (100%)  负例放行 38/40 (95%)
link>=2 AND cue   正例放行 28/40 (70%)   负例放行 13/40 (33%)
```

**没有任何一条规则能做到「误判归零 + 正例召回够高」**：能拦住「张冠李戴」的阈值同时会误杀三成正例，能保住正例的规则几乎不拦负例。答案是提示词（`故选 / 所以 / 解得 / 的面积为`）在同一章任何一道题的解析里都会出现，符号指纹（`ABCD`、`60`）也会撞。最小复现已固化进 M31：`solutionLink(题干, 本题解析).score` 与 `solutionLink(题干, 别人的解析).score` **都等于 1**，连排序都分不开，更不用说当硬闸。

⇒ **纯文本在没有版面坐标和父子 ID 的情况下，无法证明「紧邻的解析段就是本题的解析」**。当前 `adjacentSolution` 只能证明三件事：解析段紧邻题目对象、足够长、边界没串到下一题；**不能证明内容归属**。因此 `solutionLink()` 在实现里被明确定位为**软置信度**（只影响 `confidence` 与呈现层「请核对」提示，不参与放行），而不是硬闸——硬凑一个阈值只会把「看起来达标」写进文档，实际仍在放错答案。

### 8.5 结论：把闸门用在方案自己身上

「未达标不放行」如果对别人严格、对自己宽松，就只是话术。按 8.3 的第二层判据逐条对照本轮：

- ✅ 跨题拼凑类误判归零、正例召回、来源定位三项达标；
- ❌ **解析段归属这一类误判未归零**，且已证明纯文本做不到；
- ⇒ **上线准入闸门未全绿**。据此，P-009 的落地范围**只允许到 P0 判定层**，且必须同时满足：
  1. **P1 / P2 / P3 一律不启动**：不建 `0026` 索引、不改 `searchLocal()` 双通道召回、不放宽 `MAX_DEEP_FILES`、不写生产数据、不部署。召回一旦变宽，8.4 的残余风险会被**规模化放大**，正是评审 §0 要防的局面。
  2. **消除该风险的唯一可靠路径**是 §7.5 可搬的第 1 条真正落地：**入库时把题目预切分为带稳定 ID / 来源坐标 / 内容指纹的对象**（题干与解析在切分阶段就绑定成同一 `question_id`），而不是运行时从全文临时猜关系。这属于 P1 的**前置条件**，不是优化项；在它完成前不做「解析内容归属」的任何宣称。
  3. `exact` 结果必须带 `source_location`，呈现层（P3）加「来源可追溯 + 请核对」，让家长能按题号回原文复核——这是残余风险期间**唯一诚实的兜底**，不是把风险洗掉。
  4. `CACHE_VERSION` 已 bump 到 `v5`，避免旧缓存继续吐全文级假 `exact`。

> 一句话回答思傅：**思想是「举证责任在系统、误判零容忍、因子串联否决」；评判标准是「单次请求六条硬闸逐条布尔 + 上线前验收集误判归零／正例召回 ≥90%／来源定位 100%」两层。当前实现过了第一层，第二层卡在「解析段归属」，所以按同一条规矩，检索侧的后续阶段也不放行。**

## 9. P1 结构化切分入库（P-010 / D-013，2026-11-06 后续拍板）

### 9.0 与 §8.5 的关系：决策台账是追加式的

§8.5 写「P1 / P2 / P3 一律不启动」，是 **D-012 当时**的拍板范围，作为历史事实保留，不回溯涂改。本节记录的是**后续一次新拍板**：思傅在确认 P0 完成后指示「再进行 P1 的结构化切分入库」，据此由 `D-013` 把 **P1 从「未批准」改判为「已批准（仅工程管控层）」**。

这不违反「未达标不放行」，因为两者的对象不同：

| | §8.5 拦的是什么 | 本次放行的是什么 |
|---|---|---|
| 动作 | **放宽召回**：建正文索引、双通道检索、扩大深挖份数 | **收紧判定**：入库时把题干与解析预先绑定，加指纹/版本/定点排除校验 |
| 对 `exact` 数量的影响 | 变多 ⇒ 残余风险被规模化放大 | 只减不增（`judgeStoredObjects()` 只会拒绝，不会放宽） |
| 结论 | ❌ 继续锁 | ✅ 允许落代码 + 本地/开发库验证 |

### 9.3 P1 真正带来的三项能力（P0 做不到）

1. **可复算审计**：篡改 `solution_text` 而不重算指纹 ⇒ 该对象立即被拒；改 `engine_version` / 正文 ⇒ 全部对象过期。**实测**：M32 六类校验逐条可触发，`store.rejected` 留痕。
2. **正文变更自动失效**：`source_revision = sha256(正文)` 与运行时读到的正文比对，不重跑重建就不会拿旧解析当新题答案。
3. **误判定点排除**（最关键）：家长反馈「答案讲的是另一道题」时，按 `object_fingerprint` 把**那一个对象**标 `link_status='rejected'` ⇒ 它永不 `exact`，**同文档其它题照常命中**（M32 实测 `false` / `true`）。P0 时代只能改判定算法，一改就误杀一片。

这正是业界（TextIn）所说「题目/答案/解析对应关系缺乏**工程管控**」的解法：不是靠算法证明归属，而是让绑定关系有稳定身份、可追溯、可修正。

### 9.4 🔴 P1 未消除什么（不得写成已解决）

**纯文本没有版面坐标。若原始文本流本身把别人的解析排在这道题后面，结构化切分照样会把它们绑成一行。**

M32 有一条故意保留的断言：把某个对象的 `solution_text` 换成别人的解析、**并重新计算指纹**（模拟「入库时就已经串了」），`judgeStoredObjects()` **仍返回 `exact=true`**。这与 §8.4 的 40/40 ROC 结论一致，不是回归。

因此：
- **P1 未证明解析段归属**，只是把「运行时猜关系」变成「入库时一次决定 + 可复算 + 可定点修」；
- 彻底消除需要**版面坐标 / 父子 ID**（PDF 页号、区块 bbox、题干与解析的版面邻接），属后续阶段，未批准；
- 期间 `exact` 必带 `source_location`（文件名 + 题号 + 字符区间）供家长回原文复核；这是兜底，不是免责；
- `QUESTION_OBJECTS_STRICT=0` 期间，未铺量的来源仍回退 P0，**P1 不改善它们的残余风险**。
