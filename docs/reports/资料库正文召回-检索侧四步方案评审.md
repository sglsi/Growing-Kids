## 0. 结论先行

| # | 发现 | 证据 |
|---|---|---|
| **F1** | **照四步做完会得到假的 `exact`**：拿 1 道真实几何题在 10,454 份正文里跑现网 `judge()`，判出 3 份 `exact=true`，**逐条核对 3 份全是别的题的解析** ⇒ 单例精确率 **0/3** | 见 §3.3，误判机制定位到 `question-match.ts:229` |

## 1. 当前试题检索比对的核心思想（代码事实）

### 1.1 主线：检索词与判定锚点**分离**

这是 `P-006`/`D-009` 定下的骨架，也是整个设计最值得保留的部分（`server/src/shared/question-match.ts` 头注释）：

- **召回（找资料）**：`extractKeys()` 用学科主题词表 `TOPIC_WORDS`（浮力、平行四边形、勾股定理…）+ 4 字滑窗，解决「哪本教辅讲这个专题」；再补 3 个 `extractDistinctive().keys`。合并后最多 9 个 key（`netdisk-search.service.ts:213-214`）。
- **判定（认原题）**：`extractDistinctive()` 把题干 `normalizeForMatch()`（只留汉字/字母/数字）后按 **6 字滑窗、步长 3** 取长锚点，再用 `isSameQuestion()` / `judge()` 要求 **≥3 个长锚点共现且命中率 ≥40%**，并定位【答案】/【解析】段。
- **硬闸**：`match_level = exact | topic | none`。只有 `exact` 才允许把 `solutionExcerpt` 放进 `answer`；`topic` 必须 `answer:''` + `verified:false`。**无数据源豁免**——网盘、`library_docs`、自有题库、ima 全要过闸（`answer-search.service.ts:295-446`）。

> 设计取向：**宁可判不出（topic），也不冒充（exact）**。这条是 D-009 的底线，本评审的所有建议都以不破坏它为前提。

### 1.2 检索链路（现状）

```
mode=kb（answer-search.service.ts:295）
  ① 自有题库同题答案  ── isSameQuestion()
  ② library_docs 正文  ── name/text_content.ilike + judge()      ← 已有一份「正文召回」实现
  ③ 网盘 netdiskFiles ── NetdiskSearchService.search()
       L0  searchLocal()  : name/path ilike OR，limit 500，**无 ORDER BY**
       L1  内存排序       : keyHits → bigram coverage → 名字长度，取 top 20
       L2  深挖           : 只取前 3 份 → ensureText()（缓存优先）→ coverage<0.2 丢弃 → judge()
  ④ ima 知识库        ── isSameQuestion()
  ⑤ 兜底              ── 只列同主题资料，answer 恒为空
```

**覆盖事实**：`netdisk_files` 78,430 行中 `text_status='ok'` 仅 **10,454 行（13.3%）**。其余 67,244 行（大 PDF、扫描版、`.doc`）本轮方案 A 明确不覆盖。所以「正文召回」的适用面是这 13.3%，报告里不能说成「资料都能搜」。

### 1.3 已有的一份「正文召回」实现，正好是反面教材

`answer-search.service.ts:537-569` 的 `searchLibraryDocs()` **已经**在做正文召回：

```ts
const clean = extractDistinctive(question).keys ...   // 归一化后的 6 字锚点
const ors = clean.flatMap(k => [`name.ilike.%${k}%`, `text_content.ilike.%${k}%`])
```

它把**归一化锚点**直接打在**未归一化正文**上，且 `.limit(30)` 无排序。这与本次实测的 F2 完全同源 ⇒ 这条路径现在大概率也只在靠文件名召回。**四步方案若照抄这个写法，等于把已知缺陷从 `library_docs` 复制到 10,454 份规模的 `netdisk_files`。**

## 2. 四步逐条比对

| 步 | 原设想 | 必要性 | 核查结论 | 判定 |
|---|---|---|---|---|
| **1** | `0026` 建 `text_content` trigram 索引 | **必要** | 内容不够：只有索引，没有解决「归一化错配」；且 §17「有索引=毫秒级」是**未验证推断**。0024 实测 18 个 `ilike` OR 已退化到 **615ms**，长文本 GIN 还要做 **lossy recheck**（每行 200k 字），收益可能远低于预期 | ⚠️ **需重定义 + 先做样本实验** |
| **2** | `searchLocal()` 加 `text_content` 召回 | **必要** | **最危险的一步**：直接塞进现有 `or` 链会同时触发 ① 归一化锚点 0 命中 ② 10~12 个正文 `ilike` ⇒ 20~30s/次 ③ `.limit(500)` 无排序截断（实测 9 个普通词就命中 **15,123** 行）④ `keyHits` 只按 name/path 算 ⇒ 正文命中行恒为 0 分、永远排不进 top20 | 🔴 **不可照原样实施** |
| **3** | `keyHits` 计入正文 + 排序加权 | **必要** | **不是独立第 3 步，是第 2 步的生效条件**：不一起改，第 2 步等于白做。且「命中几个检索词」这个指标本身要换成「**归一化锚点共现数**」——它才是与 `judge()` 同口径的信号 | 🔴 **合并进第 2 步，且换指标** |
| **4** | 深挖走缓存（不占 `MAX_DEEP_FILES`） | **伪需求** | `ensureText():487` 对 `text_status='ok' && text_content` 直接返回，离线抽取已经喂饱它 ⇒ **已生效**。真需求是另三条：禁在线下载、`MAX_DEEP_FILES` 3→20~30、删 `coverage<0.2` 闸门 | ✅ 已生效 / ⚠️ 真需求被漏掉 |

### 2.1 第 2 步为什么比想象中危险

`searchLocal()` 现在的形状（`netdisk-search.service.ts:375-427`）：

```ts
const ors = clean.flatMap(k => [`name.ilike.%${k}%`, `path.ilike.%${k}%`]).join(',')
.from(TABLE).select('fs_id, name, path, size_bytes')
  .eq('user_id', userId).eq('is_dir', false).or(ors).limit(500)
const keyHits = clean.filter(k => name.includes(k) || path.includes(k)).length
```

四个叠加缺陷：

1. **归一化错配**：key 是 `ACABD点`（`AC>AB，D点` 去标点后拼成），正文里是 `AC＞AB，D点`。`ilike` 不做归一化 ⇒ 结构性漏召回。
2. **or 链膨胀**：现有 9 个 key × 2 字段 = 18 个条件已经 615ms；再加正文就是 10~20 个 **200k 字长文本** `ilike`，单次检索直接撞微信 60s 上限。
3. **无排序截断**：`.limit(500)` 没有 `.order()`，PostgREST 返回的是物理顺序前 500 行。实测 9 个常见词命中 **15,123** 行 ⇒ **96.7% 的候选被任意丢掉**，真正那道题大概率不在里面。
4. **keyHits 口径**：只按 name/path 算 ⇒ 纯正文命中的行 `keyHits=0`，排序垫底，进不了 `l1` top20，更进不了 `MAX_DEEP_FILES=3` 的深挖 ⇒ **加完召回依然看不到它们**。

### 2.2 第 1 步：§17 的「毫秒级」需要打折

`pg_trgm` 实测粒度（L3）：6 字中文 → **8 个 trigram**，4 字 → 5 个，2 字 → 3 个。GIN 能按 trigram 筛掉不含的行，但**留下的行仍需 recheck**——对 200k 字的正文逐行做 `ilike`，成本远高于对几十字的文件名做同样的事（`name_trgm_idx` 单 key 1.97ms 是短文本口径）。

另有两项未量化的成本：94MB 正文归一化后约 **72.8MB**（抽样 500 份实测 77.1%），GIN 索引体积可能达数百 MB；L3 是 4C4G，构建耗时与内存峰值都未知。

⇒ **`0026` 必须是「先拿 1,000 份做样本索引实验，量出耗时/体积/单查延迟，再决定全量」**，不能一把梭。这也是报告 §17 自己列的「尚未验证」三项。

### 2.3 第 4 步：真需求被漏掉的三条

- `MAX_DEEP_FILES=3`（`:43`）：`l1` 有 20 份，只深挖 3 份。正文已缓存后，每份深挖只剩「读 200k 字 + `judge()` 4~11ms」，完全可以提到 20~30 份。
- `if (score < 0.2) continue`（`:312`）：用 **bigram 覆盖率**当 `judge()` 的前置闸门，而 P-006 明确否决了 bigram 作为「是不是这道题」的判据。`AB=6` 这类符号题覆盖率天然极低 ⇒ 精确匹配被闸门挡在门外。
- `ensureText()` 对 `pending`/`none` 行仍会**在线下载 + 抽正文**（`:491-528`），单次检索可能卡 60s。离线索引的架构是「索引在前、网盘在后」，在线检索就不该再碰网盘。

## 3. 决定性实测：照原方案落地会发生什么

**实验环境**：L3 生产库（只读 SQL），本地用**现网编译产物** `server/dist/shared/question-match.js` 跑 `judge()`，与线上判定逻辑逐字一致。
**真实题目**（取自 `timeline_items`，随机抽样）：

> `16、如图，在△ABC中AC>AB,D点在AC上，AB=CD,E，F分别是BC，AD的中点，连接EF并延长，与BA的延长线交于点G，连结GD，若∠EFC=60°，DG=√3，AC=5，则△ABC的面积为多少`

其 `extractDistinctive().keys` 前 3 个是 `16如图在A` / `图在ABC中` / `BC中ACA`，`longAnchors` 共 16 个。

### 3.1 现状：这道题在 name/path 上 **0 命中**

12 个归一化锚点打 `name ilike / path ilike`，返回 **0 行**（907ms）。⇒ 现有链路对这道题完全找不到；**当前是安全的（不误判），但无效**。

### 3.2 归一化错配：原文 `ilike` 几乎打不中

| 锚点 | `text_content ilike` 命中 | 说明 |
|---|---|---|
| `ACABD点` | **0** | 正文是 `AC＞AB，D点` |
| `中点连接EF` | **0** | 正文里有标点/换行 |
| `AD的中点连` | **0** | 同上 |
| `F分别是BC` | 49 | 少数抽取结果丢了标点才撞上 |
| `平行四边形`（对照，纯中文） | 1,102 | 无标点词不受影响 |

5 个词合计 **12.7s**（≈2.5s/词，与 §17 的 2.8s 一致）。⇒ **「把 `text_content ilike` 塞进 `or` 链」对区分性锚点基本不召回，只会把主题词噪声放大。**

### 3.3 归一化后能找到题，但判定全错

把正文做 `regexp_replace(text_content,'[^一-龥A-Za-z0-9]','','g')` 后用同一批 12 个锚点打分，10,454 份的共现分布：

| 命中锚点数 | 份数 |
|---|---|
| **10** | **2** |
| 4 | 5 |
| 3 | 17 |
| 2 | 85 |
| 1 | 574 |
| 0 | 9,771 |

拿到命中 ≥3 的 8 份正文，逐份跑现网 `judge()`：

| 文档 | SQL 命中 | `judge()` | 全文锚点 | 解析段内锚点 | 实际解析内容 |
|---|---|---|---|---|---|
| 四边形（下）.pdf ×2 | **10/12** | `exact=false` | 13/16 | 无解析段 | **正文里确有这道题的原型**（见下），但是讲义题目、没有答案 |
| 专题13 平行四边形…（解析版）.docx | 4/12 | 🔴 **`exact=true`** | 7/16 | 4 | 矩形 ABCD、AD=2AB、正方形 ABEF —— **另一道题** |
| 考点22 菱形及其综合（解析版）.docx | 4/12 | 🔴 **`exact=true`** | 7/16 | 3 | 菱形 ABCD、∠ADC=60°、等边三角形 —— **另一道题** |
| 考点14 三角形与全等三角形（解析版）.docx | 4/12 | 🔴 **`exact=true`** | 8/16 | 3 | △ABC≌△DEB、BE=BC=5、∠B=40° —— **另一道题** |
| 其余 4 份 | 3~4 | `exact=false` | — | — | 原卷版无解析 / 未过门槛 |

**3 个 `exact` 全是误判。** 若按原四步上线，`answer-search.service.ts:351-361` 会直接把其中一份 `solutionExcerpt` 塞进 `answer` 并标 `verified:true` ⇒ **D-009 修掉的病，原样复发，而且因为「正文命中」看起来更有证据，更难被用户察觉。**

> 样本量说明：这是 **1 道题 / 8 份候选**的单例，不是全库精确率统计。但误判机制是代码层面的确定性逻辑（下节），不是偶发抖动，所以风险是系统性的。

### 3.4 误判机制：两条判据的口径不一致

`question-match.ts`：

- `countAnchorHits()`（`:126-137`）在 **整篇正文** 上统计锚点共现。一本 3 万字教辅里连排几十道几何题，「E、F 分别是 BC、AD 的中点」「∠=60°」「AC=5」「ABCD」这些片段散落各处，凑够 7~8 个锚点、过 40% 门槛毫不费力。
- `locateSolution()`（`:165-202`）在众多【解析】段里挑「锚点共现最多」的一段，但 **对 `anchorsHit` 没有下限**；即使所有段都与本题无关，它照样返回一个 `best`。
- `judge():229` 的第三条前提是 `!!sec` —— **只要文档里任意位置出现过【解析】字样就算数**，完全不要求该段与本题相关。

⇒ `exact = 全文锚点达标 AND 文中有任意解析段`。这两条在「整本教辅」上同时成立太容易了。实测中 3 份误判文档的**段内锚点也有 3~4 个**（都是几何题常见表述），说明**单纯加「段内 ≥3」也拦不住**。

**还有一个更隐蔽的边界**：那 2 份命中 10/12 的讲义，正文里是

> `问题二：如图，在 ∆ABC 中， AC AB = ，D 点在 AC 上，AB＝CD，E、F 分别是 BC、AD 的中点，连结 EF 并延长…若∠EFC＝ 60°，连结 GD，判断 ∆AGD 的形状并证明。`

与用户题目**题干条件完全相同，但设问不同**（讲义问「判断 △AGD 的形状」，用户问「△ABC 的面积为多少」）。`isSameQuestion()` 只看条件、不看设问 ⇒ 即便这份讲义有解析，直接采纳也是**答非所问**。教辅里同题干改编/多问极常见，这不是个例。

### 3.5 性能实测汇总

| 场景 | 实测 | 判定 |
|---|---|---|
| 单 key 正文 `ilike`（对照 §17） | 2.8s | ❌ 不可用 |
| 5 key 原文 `ilike` | **12.7s** | ❌ |
| 全量 10,454 份**运行时归一化** + 12 锚点打分 | **3 分 06 秒** | ❌ 归一化必须预计算 |
| 先用 `中点/ABC` 粗筛再归一化 | **41s** | ❌ 粗筛也救不了 |
| `name/path` 18 个 `ilike` OR（有 0024 索引） | **615ms** / 命中 15,123 行 | ⚠️ 索引退化 + `.limit(500)` 任意截断 |
| `name` 单 key（有 0024 索引） | 1.97ms | ✅ 短文本基准 |
| 归一化体积（抽样 500 份） | 3,087,967 → 2,380,099 字 = **77.1%** | 全量约 **7,285 万字 / 72.8MB** |

⇒ **§17「没有索引 = 28 秒/次，有索引 = 毫秒级，中间没有第三种可能」这个二选一过于乐观**：索引只解决「扫哪些行」，不解决「长文本 recheck」和「无排序 limit 截断」。必须先做样本索引实验。

## 4. 最优方案：重排后的实施序列

原四步是一条「数据 → 索引 → 召回 → 排序 → 缓存」的工程链。**缺的是最前面的正确性前提，以及中间的「文档结构」这一层。** 建议改为四个阶段，P0 不通过就不准进 P1。

### P0 · 正确性前置（**新增，最高优先，全部未批准**）

| 项 | 内容 | 验收 |
|---|---|---|
| **P0-1 真题验收集** | 从 `timeline_items` 抽 **20~30 道**真实题干（覆盖数学/物理/语文、含符号题），人工标注每道在库里「有无原题 / 有无解析 / 在哪份文件」 | 标注集入库或落 `docs/reports/` 附件，**可重跑** |
| **P0-2 判定口径修复** | ① `judge()` 的 exact 从「全文锚点共现」改为「**题干窗口内连续共现 + 紧随其后的解析段**」；② `locateSolution()` 增加 `anchorsHit` 下限与「与题干窗口距离」约束；③ 新增**设问一致性**检查（提取「求…/…为多少/判断…/证明…」与解析段结论类型比对）；④ 保留数学符号（`= > < ∠ √ ° ⊥ ∥ △`）而不是一律删掉——`AC>AB` 压成 `ACAB` 后反而成了最常见的噪声串 | 拿 P0-1 集跑：现状 3/3 误判 ⇒ **误判必须归零** |
| **P0-3 准入闸门** | 指标：**误判数 = 0**（D-009 硬约束：宁可 `topic` 不可冒充）、`exact` 精确率 ≥0.9、端到端 P95 < 3s | 三条全绿才准进 P1；任何一条不达标就停在「召回变宽但一律 `topic`」 |

> P0-2 的 ④ 值得单独说明：`normalizeForMatch()` 去标点对语文/文字题合理，对理科题把**最有区分度的符号和数值关系**抹平了（实测 `ACAB`/`ABCD` 反而命中一堆无关几何题）。建议改为「两套锚点」：文字锚点仍归一化，理科符号/数值锚点单独保留并加权。

### P1 · 数据结构与索引（**重定义 `0026`，未批准**）

原「只建 trigram 索引」改为四件事，且**先用 1,000 份样本做实验**：

1. **归一化列** `text_flat`（`regexp_replace` 口径与 `normalizeForMatch()` 逐字对齐），离线回填 10,454 行；**不需要重新下载任何文件**（正文已在库里，纯 CPU）。实测归一化后约 7,285 万字 / 72.8MB。
2. **题目级切分**（本次评审的核心建议）：按 `【例 N】` / `N．` / `问题N` / `【答案】` 等标记，把整本教辅切成 **chunk**（题或题+解析为一段），落 `netdisk_chunks` 表或 `text_chunks jsonb` 列。实测样本里这些标记清晰可切（`四边形（下）.pdf` 有 `【例 4/5/6】`、解析版 docx 有【答案】/【解析】）。
   - 这一层同时解决三件事：**锚点共现不再跨题拼凑**（F1 的根因）、trigram 索引在短文本上 recheck 便宜、解析段可以直接从「题干 chunk 的相邻 chunk」取。
3. **索引**：在 `text_flat` / chunk 上建 GIN `gin_trgm_ops`，partial `where text_status='ok'`；**先量构建耗时、索引体积、单查/多查延迟**，达标才全量。
4. **查询约束**：正文召回只用 **3~4 个最长且最稀有的锚点**，≥4 字，显式排除 2~3 字短 key；不塞进 `name/path` 的 `or` 链。

> 「切分」是四步方案里完全没有的一层，但它是「正确甚至精确匹配」的结构性前提：**把整本 3 万字教辅当成一个文档，就不可能可靠地指出「哪道题的解析」。**

### P2 · 召回与排序（**重定义第 2、3 步，未批准**）

- **双通道**：`name/path` 通道保持现状（走 0024 索引）；正文通道独立查询，两条结果合并去重。
- **统一打分口径**：用「**归一化锚点共现数**」替代 `keyHits` + bigram `coverage` 两套并存的分数；它与 `judge()` 同源，排序与判定不再各说各话。
- **SQL 层 top-N**：按共现数排序后再取 top，废掉无 `.order()` 的 `.limit(500)` 任意截断。
- **删除 `coverage(qSet, text) < 0.2` 闸门**（`:312`），交给 `judge()` 判定。
- **保留 `.eq('user_id', userId)`**（无 RLS 红线）、`text_status='ok'` 过滤、`%,()` 转义。

### P3 · 深挖、呈现与回归（**重定义第 4 步，未批准**）

- `MAX_DEEP_FILES` 3 → 20~30；`DEEP_BUDGET_MS` 保持 18s 兜底。
- **禁止在线下载/抽取**：`text_status` 非 `ok` 的候选直接跳过深挖（在线检索不再碰网盘）。
- `exact` 结果附「题干窗口 + 解析段」双证据，前端展示时标出来源 chunk，便于家长核对。
- 🔴 **`CACHE_VERSION` v4 → v5**（`answer-search.service.ts:46`）：改了 `note` / 结果结构必须 bump，否则 `answer_cache` 会继续吐旧文案。
- **回归扩展**：`M27`（硬闸）加「长文档不得误判」用例；`M30` 加归一化列/切分/缓存版本断言；新增验收模块跑 P0-1 标注集。
- **前后端同步发货**（`D-009` 教训）：只换后端时旧前端会把 `answer:''` 也采纳。
