# P-020 「看得懂」目标：主流设计方法调研与 F5 语义闸设计

> 日期：2026-11-10 ｜ 关联：`P-020`、`P-022`、`docs/reports/P-020-阶段3-二次评审报告.md`、D-031
> 触发：思傅「首先完成『看得懂』相关目标的实现，可检索当前的主流设计思想和设计方法」
> 🔴 本报告只做**方法比对 + 只读设计**，不写生产库、不产图、不改判定层、不下发图。

## 1. 要解决的到底是什么问题

二次评审的实证不是「坐标算错了」，而是「**坐标算对了，但插在孩子看不懂的地方**」：16 处 `offset_zero` 里可见的 7 处有 6 处，插入点落在老式 Word（VML / OLE shape）尺寸数字残串上，如 `1088390010947400`、`98107568580`、`-37147512763528`、`30861007861303.`。这些数字被 `extract_docx` 当正文读了出来。

所以「看得懂」是一个**落点语义正确性**问题，不是检索/召回问题，也不是学习干预问题（不进 `0021` 分组）。

## 2. 检索到的主流设计思想（2026-11-10 实检）

| # | 主流做法 | 核心规则 | 来源 |
|---|---|---|---|
| 1 | **Span grounding / 落点回验** | 每个预测结果必须能在原文里取到真实子串，取不到就丢：「If a prediction has no honest span in the page, it is gone」 | Digital Relics, *Best Practices to Avoid entity extraction pitfalls* |
| 2 | **保留原始字面（keep original surface form）** | 只做便宜的确定性修复，不要「现代化」重写原文；过度清洗会破坏下游依赖原始字形的匹配 | 同上；araclean *Offset-preserving normalization* |
| 3 | **Offset-preserving normalization** | 若必须清洗文本，必须维护 original ↔ normalized 双向 `OffsetMap`（`to_original` / `to_normalized`），否则坐标不可回溯 | araclean；HuggingFace `NormalizedString` alignment tracking |
| 4 | **让流水线自己暴露失败** | 不要只报聚合指标；逐条记录判定理由、上下文、失败类别，按来源/类型分层拆解 | Digital Relics；TrueSight *工业级零干预数据管道* |
| 5 | **Fail-closed + 置信度降级** | 定位漂移 / 置信度不足时转人工或直接丢弃，不强行输出结构化结果 | TrueSight（Confidence < 0.85 转人工）；项目不变量 B |
| 6 | **分层抽样人工复核量级** | 可辩护的复核需 200–300 条分层随机样本，逐条对照原页面 adjudicate；30 条「一眼看」不够 | Digital Relics |
| 7 | **可复现元数据** | 记录模型/脚本版本、清洗步骤、语料 hash、gold sample，使每个结论可回溯 | Digital Relics |
| 8 | **图是「文字层里的一个字符」** | Word `InlineShape` 位于 text layer，被当作字符定位 ⇒ 用字符偏移锚定图是格式本身的语义，不是 hack | Microsoft Learn, *InlineShape Object* |
| 9 | **偏移单位必须显式约定** | code point / UTF-16 / UTF-8 byte / grapheme 四种计数互不等价，跨端必须转换 | Token360 *Character Offsets in AI Citations*；项目 `cpToUtf16()` |
| 10 | **老格式解析要按 piece/CLX 索引** | `.doc` 正文分布在多个 piece，须按「字符位置 ↔ 文件偏移」映射读取 | word-extractor OLE 解析架构；P-019 重转链路 |

## 3. 采纳 / 不采纳矩阵（与本项目红线逐条比对）

| 做法 | 处置 | 理由 |
|---|---|---|
| ① 落点回验 / fail-closed | ✅ **采纳** → F5 | 与 `P-020` 不变量 B「定位不到不入库不下发」逐字一致 |
| ② 保留原始字面 | ✅ **采纳，且更保守** | `text_content` / `text_sha256` / `char_start` 一行不动；F0 同源铁律钉的是入库文字流，清洗会让 10,147 份正文与 656,898 个题目对象坐标全部失效 |
| ③ OffsetMap | ✅ **采纳其结论，走更保守分支** | 因为**根本不改原文**，就不需要重映射；F5 只决定「发不发」，不产生新坐标系 |
| ④ 逐条暴露失败 | ✅ **采纳** | `candidate_details` 从「每份最多 3 条 samples（14.5%）」改为**全量逐条**输出 `semantic` / `drop_reason` / 上下文证据 |
| ⑤ 置信度过滤 | ✅ **采纳其「丢」分支** | 项目是 fail-closed，不做「低于阈值仍自动放行」 |
| ⑥ 200–300 条分层复核 | ✅ **采纳并加码** | 全量 1,838 候选逐条机器判定 + ≥30 条逐条上下文证据清单；🔴 **机器判定不冒充人工签核** |
| ⑦ 可复现元数据 | ✅ **采纳** | seed、脚本 sha、F5 配置、真相源 sha、gold sample 全部写入 summary |
| ⑧ InlineShape 字符语义 | ✅ **印证既有设计** | `char_start` 锚定不是 hack，不需要换方案 |
| ⑨ 偏移单位约定 | ✅ **印证既有红线** | 前端 `cpToUtf16()` 不动；F5 在 Python 码点域判定，不跨端传新坐标 |
| ⑩ piece/CLX 原生解析 | ❌ **不采纳** | 换解析引擎 ⇒ 必 bump 版本 + 全量重跑 10,147 份，风险不可控；现有重转 + F0 同源已足够 |
| 深度学习版面分割 / VLM 语义定位 | ❌ **不采纳** | 项目红线 ⛔ 不上向量库 / Reranker / LLM 兜底；且 L3 仅 4C/3.7G，跑不动推理 |
| OCR 图像预处理管线 | ❌ **不采纳** | 本项目公式走 PDF 位图渲染、不做识别，不是 OCR 质量问题 |
| 第三方闭源解析器（Spire.Doc 等）替换真相源 | ❌ **不采纳** | 同上换引擎问题；且免费版有页数限制 |
| 全局清洗长数字 | ❌ **不采纳** | 题干里的准考证号 / 年份 / 数据也可能是长数字；只在**插入点邻域**判定，且真实长数字距离插点远时放行（自测 `far_long_number`） |

## 4. F5 语义闸设计

**位置**：`server/scripts/doc-inline-shadow.py` → `semantic_gate(stem, off)`，纯函数、零依赖、只读。

**判据**（任一命中 ⇒ 该图一律丢弃，记 `drop_reason`）：

| 判据 | 对应实证 / 依据 |
|---|---|
| `off <= 0` | 16 处 `offset_zero`；插在题干最前 ⇒ 语义未证明（P-022 §3 第 3 条） |
| `off > len(stem)` | 越界保护 |
| 插入点前 8 字内出现 ≥7 位长数字残串（可带 `-` / 尾 `.`） | 6/7 可见残串实证 + 32 条抽查 |
| 插入点后 8 字内出现同类残串 | 同上 |
| 邻域出现 `U+FFFD` | 142 份乱码文档，F0 拦不住 |
| `len(stem) > 3000` | 二次评审 2 处超长 stem（693/3347、10986/12024）；第 3 份「12不定方程」1853 字只切 1 个题对象、记账 274 个图标记，风险集中 |

**不做的事**（比「改得更干净」更重要）：不清洗 `stem`、不重算 `char_offset`、不改 `clean` / `a` / `text_content`、不碰 `text_sha256`、不碰 `question-match.ts`、不 bump `CACHE_VERSION`。

**为什么「一律丢图」而不是「清洗后插到正确位置」**：清洗会改变字符坐标，必须引入 OffsetMap 并把 656,898 个题目对象的 `char_start` 全部重算；而项目铁律是「定位不到不入库不下发，绝不拿相邻题顶替」。在举证责任倒置下，**少给一张图**远好于**给一张插错地方的图**。

**可回放证据**：每条候选输出 `semantic`（pass/drop）、`drop_reason`、`semantic_evidence`（off、stem_len、前后各 16 字窗口、命中的噪声串），全量写进 summary 的 `candidate_details`。
