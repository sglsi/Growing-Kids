## 0. 现状与目标（一页速览）

| 维度 | 现状（Coze 期） | 目标（迁云后） |
|---|---|---|
| 数据库 | Supabase(Postgres)，凭据由 Coze workload identity 注入 | 腾讯云 PostgreSQL（主栈），经 `DbProvider` 抽象切换 |
| 对象存储 | 见 `存储空间优化` 文档（图片裁剪块 `cropKey`） | 腾讯云 COS；必要时跨云 OSS 互拷 |
| OCR 侧车 | `ocr-engine/` FastAPI + PaddleOCR/RapidOCR | 同左，受管部署（容器 / SCF 常驻） |
| 语义切分 / 兜底 | 豆包 Seed 2.0 Pro（Coze `LLMClient`） | 腾讯混元；跨云兜底接通义千问 Qwen3-VL |
| 告警 | `ConsoleAlertSink`（日志）/ 通用 webhook | 企业微信机器人 / 飞书（§6） |

**核心原则**：迁移是"换房东"，不是"破门搬"。AppID 不变 → `openid` 稳定 → 用户无感知；数据靠双写 + 对账保证无损。

## 1. 迁入腾讯：平台对比与建议

### 1.1 四维对比（云 / 存储 / 工具 / 大模型）

| 维度 | 腾讯云（推荐主栈） | 阿里云（跨云兜底） |
|---|---|---|
| **微信原生整合** | 天然：TCB 微信免鉴权、云调用、云支付一体 | 弱，需自建 OAuth/中转 |
| 云函数 / 运行时 | SCF（云函数）+ TCB（含 DB/存储/鉴权一体化） | FC（函数计算）+ 自建鉴权 |
| 对象存储 | COS（与小程序、CDN、SCF 同生态） | OSS |
| 关系库 | 云数据库 PostgreSQL / TDSQL-C | RDS PostgreSQL / PolarDB |
| 大模型 | 混元（文本/多模态，微信域内低延迟） | 通义千问 Qwen3 / Qwen3-VL |
| 向量 / 检索 | 向量数据库 / PostgreSQL `pgvector` 扩展 | 相同（PG 自带） |
| 成本 | 微信小程序的流量/调用有套餐优势 | 通用云，价格随量 |
| 生态契合 | **高**（小程序原生） | 中（偏中后台/电商） |

### 1.2 建议结论

> **主栈 = 腾讯云（TCB + COS + SCF + 混元）**，理由：本项目是**微信小程序**，腾讯云在鉴权、调用、存储、模型延迟上都有原生优势，迁移摩擦最小。
>
> **跨云兜底 = 通义千问 Qwen3-VL**：仅作为「语义切分 / 多模态兜底」的第二供应商，用 `LLMClient` 抽象（见 `local-vlm.client.ts`）以 `provider` 切换，避免单云单模型故障导致出题中断。**不要把主库/存储也双云化**——那会引入一致性地狱，得不偿失。

### 1.3 关键决策理由

1. **AppID 不变是迁移零痛点的前提**：微信 `openid` 由 AppID + 微信 unionid 派生。只要 AppID 不动，老用户 `openid` 不变，数据按 `openid` 关联即可无缝承接。
2. **存储抽象已就位**：`DbProvider`（§7.6）把"换数据库"降维成"换一个 Provider 实现 + 开一个开关"，业务代码零改。
3. **OCR 侧车与云无关**：侧车是独立 Python 进程，部署到哪朵云的容器/函数都行，本体不动。
4. **大模型最该留后路**：模型能力波动大、配额易变，用 Provider 抽象做"主混元 + 兜底 Qwen"即可，无需动存储架构。

## 2. 迁移四层设计与注意事项

> 落地骨架见 `错题提取-技术文档.md` §7.6。此处给出**设计方法论 + 注意事项清单**，供执行时逐项核对。

### 2.1 四层设计

| 层 | 目标 | 已落地情况 |
|---|---|---|
| **① 架构抽象** | 数据访问层与厂商解耦 | ✅ `DbProvider` 接口 + Supabase/TencentPg 双实现 + 工厂模式 |
| **② 数据可移植** | openid 稳定、引用键不变 | ✅ 数据以 `openid`/`cropKey` 关联，迁移不改语义 |
| **③ 双写灰度对账回滚** | 增量切换、可回退 | ⚠️ 骨架（dual 模式 + `mirrorInsert/Update/Delete`）已就绪，待迁移窗口内把 27 处写路径补齐 |
| **④ 用户无感** | 切换不登录、不丢数据 | ✅ 由 AppID 不变 + 双写对账保证 |

### 2.2 执行四步法（迁移窗口内）

1. **双写（dual）**：`DB_PROVIDER=dual`，按 §7.6.4 把全部写路径接 `mirrorInsert/mirrorUpdate/mirrorDelete` 镜像到腾讯云 PG。
2. **灰度**：入口层按 `userId` 分流，先 5% 用户走新链路，观察双写成功率。
3. **对账**：`pg_dump` 主库 + 新库，按 `openid` 比记录数 / 关键字段，确认无丢无错。
4. **回滚窗口**：稳定后旧库**只读保留 30 天**再下线；图片裁剪块按 `cropKey` 原样 `COS↔OSS` 拷贝，DB 引用继续有效。

### 2.3 注意事项清单（坑点）

> 以下任一项疏漏都会造成「用户困难」或「数据不一致」，迁移前逐条核对。

| # | 风险点 | 说明与对策 |
|---|---|---|
| N1 | **AppID 改动** | 切忌中途换 AppID，否则 `openid` 全部失效、用户"被清空"。如需换主体，走微信「账号迁移」流程保 unionid。 |
| N2 | **cropKey 语义漂移** | 图片块以 `cropKey` 入库引用。迁移时只拷贝对象、不改 key，DB 引用才继续有效；**切勿重新生成 key**。 |
| N3 | **双写不对称** | 仅主库成功、次库失败要用 best-effort 吞错并告警（`dual-write.ts` 已做），但**对账必须覆盖全部写路径**——漏接的写路径不会报错，只会静默丢数据。 |
| N4 | **迁移期读旧写新** | 双写期内读仍走主库；切到 `tencent-pg` 主库前，务必确认读路径也已切到 `getDbProvider()`，否则读到旧库、写入新库。 |
| N5 | **凭据三重 fallback** | Coze 期凭据经 env→.env→workload identity 注入；腾讯云期用**密钥管理（如 SSM/密钥对）**，禁止硬编码进仓库。 |
| N6 | **存量字段免迁移** | `timeline_items.content` 等是 jsonb，新增字段免 DDL；但新增**独立表**仍要走 migration（见 `migrations/`）。 |
| N7 | **配额口径** | 配额服务（`quota.service.ts`）按用户统计用量，迁移后需确认计数源一致，避免"迁移后配额清零/翻倍"。 |
| N8 | **下游/缓存失效** | 60s 配额缓存、对象存储 CDN 缓存需在切换后主动失效一次，避免读到旧值。 |
| N9 | **回滚演练** | 上线前用影子流量跑一遍"次库→主库"回滚，确认 `DB_PROVIDER` 改回即恢复，不依赖人工数据搬运。 |
| N10 | **端侧缓存版本** | 小程序本地缓存若存了用户数据快照，迁移后要能识别"缓存来自旧库"并刷新，防止旧数据覆盖新库。 |

## 3. 本地存储策略

本地存储分两层：**端侧（小程序本地）** 与 **云对象存储（COS/OSS）**。两者职责不同、不可混淆。

### 3.1 端侧本地存储（离线可读、弱网可用）

| 用途 | 机制（小程序） | 注意 |
|---|---|---|
| 用户草稿 / 未同步错题 | `wx.setStorageSync` / `StorageManager` | 仅缓存、非真相源；联网后以上行同步为准 |
| OCR 结果临时态 | 内存 + 本地缓存 | 侧车不可用时前端可编辑的纯文字态，落库前临时持有 |
| 配额/配置快照 | 本地缓存 60s（见 `quota.service.ts`） | 切换后主动失效（N8） |
| 离线题库（可选） | 本地分包 / `wx.getFileSystemManager` | 大文件走分包加载，不占主包 |

**原则**：端侧只做"加速 + 离线兜底"，**唯一真相源永远是云库**。迁移时端侧缓存按 N10 处理。

### 3.2 云对象存储（COS 为主）

- 图片以**裁剪块**存储，键为 `cropKey`（`question_images/answer_images` 存 key 数组，DB 不存二进制）。
- 腾讯云期用 **COS**；跨云兜底可落到 **OSS**，迁移窗口内 `cropKey` 跨云原样拷贝（§2.2 第 4 步）。
- 访问走**带签名的临时 URL** 或 CDN，避免暴露存储桶直链。

### 3.3 缓存层

- 配额/统计类读多写少数据有 60s 内存缓存（`quota.service.ts`）——**未失效前读到旧值**，这是有意设计（见 `存储空间优化` 文档验收项八）。
- 对象存储之上可叠 CDN；切换后用 purge 一次。

## 4. SBERT / 知识图谱 / IRT（智能化增强路径）

> 当前状态：v5 起已落地「本地优先」实现 + 可选升级钩子（默认关闭）。详见 `错题提取-技术文档.md` §4.1、§5(P2)、§7.6。
> 设计立场：**尽量不依赖大模型/外部服务**，SBERT/知识图谱/IRT 只留接口与策略开关，模型/题库到位后再"填肉"。

### 4.1 现状一览（已落地）

| 能力 | 当前实现 | 可选升级钩子 |
|---|---|---|
| **错因分析** | 本地规则引擎 `ocr-error.ts` `classifyError`（未作答/符号错/计算错/概念混/审题偏/步骤错） | `sbertPolicy()` 默认 off、`sbertErrorScore` 接口就位，启用后算语义分填 `sbert` |
| **相似题/变式题** | 历史错题文本相似（Dice）+ 知识点标签重叠（`ocr-similar.ts`→ `POST /api/timeline/:id/similar`） | 标签即轻量"知识图谱"节点；`review_count`/`mastered` 作难度代理 |
| **复习曲线** | 艾宾浩斯（P2 已落地） | — |

### 4.2 SBERT 语义差异

- **钩子位置**：`sbertPolicy()` / `sbertErrorScore`，由 `SBERT_MODE=off`（默认）控制。
- **启用前置**：需自托管 embedding 端点（如 `bge-small-zh` / `multilingual-e5` 经 ONNX 或推理服务）。
- **私有网段强校验 + fail-open**：端点不可达时自动降级回规则引擎，不影响主链路（与 `localVlmPolicy` 同思路）。
- **用途**：细化错因分类、提升相似题召回（语义近义题也能命中）。

### 4.3 知识图谱

- **现状（轻量）**：以"知识点标签"为节点、错题为边，做标签重叠检索——不引入图数据库也能跑。
- **升级路径**：
  - 用 `pgvector` 存题目 embedding，做语义近邻（替代/补充标签重叠）；
  - 或引入轻量图存储（如 Neo4j / 腾讯云图数据库）做"知识点→题型→错因"路径推理；
  - **前置条件**：结构化知识点体系（教材章节→知识点映射表），需人工/半自动标注。

### 4.4 IRT 难度自适应

- **现状（代理）**：以 `review_count`（复习次数）/`mastered`（是否掌握）作难度与掌握度代理，驱动复习优先级。
- **升级路径（真实 IRT）**：
  - 需**作答记录题库 + 难度标定**：用 2PL/3PL 模型估题目区分度/难度、估用户能力 θ；
  - 数据来源：用户长期作答日志（错题+对题+复习命中/遗漏）；
  - 收益：从"按次数排队"升级为"按掌握度精排复习序列"，显著提效。
- **前置条件**：足量标注难度的高质量题库 + 用户级作答轨迹采集（当前仅落错题，对题/练习轨迹需在采集层补埋点）。

### 4.5 升级优先级建议

1. **先 IRT 代理升级**（成本最低）：补"对题/练习轨迹"埋点 → 用现有代理指标做精排，无需模型。
2. **再 SBERT 语义增强**（收益高、依赖可控）：自托管 embedding 端点，开 `SBERT_MODE`，低风险 fail-open。
3. **知识图谱最后**（依赖最重）：先 `pgvector` 语义近邻跑通，再视需要上图数据库。

## 5. 接真实告警渠道（企业微信机器人 / 飞书）

> 落地代码：`server/src/ocr/ocr-health.ts` 的 `WebhookAlertSink` + 工厂 `getOcrAlertSink()`。
> 关联：`OCR-架构说明.md` §6.2（健康探针 + 告警埋点）。

### 5.1 工作原理

- 告警由 `OcrAlertSink` 抽象，`WebhookAlertSink` 把事件 POST 到配置的 webhook。
- 每次告警**先同步打印 `ConsoleAlertSink`**（`[ocr-alert]` 前缀），再异步 POST webhook；webhook 失败**不阻断**主链路。
- 告警事件：`sidecar-unreachable` / `sidecar-recovered` / `sidecar-unhealthy` / `sidecar-startup-failed`（含义见 §6.2 表）。

### 5.2 环境变量

| 变量 | 默认 | 说明 |
|---|---|---|
| `OCR_ALERT_WEBHOOK_URL` | 空 | 配置后告警走 webhook；为空则仅 console |
| `OCR_ALERT_WEBHOOK_TYPE` | `generic` | `generic`=纯 JSON / `wecom`=企业微信 / `feishu`=飞书 |

### 5.3 企业微信机器人接入

1. 企业微信 → 群 → **添加群机器人** → 复制 Webhook 地址（`https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=XXXX`）。
2. 配置：
   ```bash
   export OCR_ALERT_WEBHOOK_URL="https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=XXXX"
   export OCR_ALERT_WEBHOOK_TYPE="wecom"
   ```
3. 消息体（`WebhookAlertSink` 自动组装，无需手写）：
   ```json
   { "msgtype": "markdown", "markdown": { "content": "**OCR 告警**\n> sidecar-unreachable\n{\"consecutive\":3}" } }
   ```
4. 可选加签：企业微信机器人支持「签名校验」，在群机器人安全设置里开启后，需在 URL 之外带 `timestamp`+`sign`。当前 `WebhookAlertSink` 走无签基础形态；**如需加签**，在 `buildBody` 前由 URL 携带密钥并补足签名参数即可（属小增量，按安全需求再补）。

### 5.4 飞书自定义机器人接入

1. 飞书群 → **设置 → 群机器人 → 添加自定义机器人** → 复制 Webhook（`https://open.feishu.cn/open-apis/bot/v2/hook/XXXX`）。
2. 配置：
   ```bash
   export OCR_ALERT_WEBHOOK_URL="https://open.feishu.cn/open-apis/bot/v2/hook/XXXX"
   export OCR_ALERT_WEBHOOK_TYPE="feishu"
   ```
3. 消息体（自动组装）：
   ```json
   { "msg_type": "text", "content": { "text": "[OCR告警] sidecar-unreachable\n{\"consecutive\":3}" } }
   ```
4. 可选加签：飞书机器人开启「签名校验」后需在 body 带 `timestamp`+`sign`。当前发 `text` 基础形态即可接收；**如需加签**同上，按飞书文档补齐签名字段。

### 5.5 验证要点

- 不配 `URL` → 仅 `[ocr-alert]` 日志，零外部依赖（默认安全）。
- 配 `URL`+`wecom` → 企业微信收到 markdown 卡片。
- 配 `URL`+`feishu` → 飞书收到 text 消息。
- webhook 不可达 → 仅 console 打印，主链路不抛错（与探针、双写同一 fail-open 哲学）。

### 5.6 部署建议

- 独立容器部署侧车时 `OCR_SUPERVISE=0`，但**保留 `OCR_AUTO_PROBE=true`**——探针与告警不依赖 supervisor，跨部署形态持续监控。
- 告警 webhook **走密钥管理**，勿硬编码；群机器人 key 等同"可发消息的令牌"，泄露即滥发。
- **「可用率跌到阈值自动告警」已落地**（2026-10-10）：`OcrHealthProbe` 在每次探活时顺带读取埋点滑动窗口 `successRate()`，低于 `OCR_AVAIL_WARN_THRESHOLD`（默认 0.8）、且窗口样本 ≥ `OCR_AVAIL_MIN_SAMPLES`（默认 5）时，连续 `OCR_AVAIL_FAILS`（默认 3）次触发 `sidecar-low-availability`；恢复后触发 `sidecar-availability-recovered`。窗口无样本（空闲期）不评估，避免误报。详见 `OCR-架构说明.md` §6.2。
