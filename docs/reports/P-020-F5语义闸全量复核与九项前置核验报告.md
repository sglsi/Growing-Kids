## 4. 本轮新发现的两类残余风险（如实登记，不隐藏）

**① 宽窗口扫描发现 4 条放行候选邻域仍有短数字串**（1,354 条中 4 条，0.3%）：
```
off=14  before="6.读“长江三角洲”图完成。"     after="\n043815\n\n1983740"
off=127 before="不含点）上任取一点（，，），记，" after="的内心分别为，，\n0240030"
off=69  before="点,连结交圆于点,连结并延长与边"   after="交于点,证明:\n\n1714500"
off=34  before="化合反应的是(B)(导学号 58"      after="504170)\nA．2Na＋2H"
```
前 3 条是 6–7 位残串，因距离 >8 字或不足 7 位未被 F5 拦；**第 4 条疑似题目「导学号 58504170」被换行拆开，是正常内容**。⇒ 不能简单放宽阈值（`_`/短数字会误伤），按 fail-closed 列为**待人工签核边界**，不擅自加规则。

**② 更根本：老 `.doc` 的题干文字本身不完整**。40 条分层清单里肉眼可见「在锐角中，是边上不同的两点」「上任取一点（，，），记，的内心」——`△ABC`、坐标、点名等字母/公式对象在 `extract_docx` 剥标签时被整块丢掉。窄正则下界统计：**1,354 条放行候选里 15 条（1.1%）有明显字符丢失痕迹**，且这是保守下界。

⇒ **F5 解决的是「图插在哪」，解决不了「题干有没有字」**。这直接回答「公式图表能否完全正确显示」：老 `.doc` 侧即使图放对了，题干仍可能读不懂。根因指向 `m:oMath` / `w:object` 未定性（236 个），属独立提案，不在本轮 F5 范围内。

### 还有一条工程事实：`--apply` 链路根本不存在

- `doc-inline-shadow.mjs` 是影子脚本，**硬拒 `--apply`（exit 3）**，按设计不含产图/写库代码；
- `netdisk-inline-build.mjs` 下载的是 **`.docx` 原件**并直接跑 `crop.py`，`pendingSources()` 写死 `nf.ext='docx'`；
- `.doc` 重转产物是**临时转换、用完即删**（`fs.rm`），不持久化。

⇒ 要让 Q5 写 `.doc` 内联图，必须**新建一条产图链路**：下载 `.doc` → 独立 profile 重转 docx → F0 同源 → `parse_docx` 取图标记 → F2/F5 判定 → `crop.py` 产图 → 写 `question_inline_figures` / `question_inline_done` / webp 落盘 → 一键下线。这是**新的生产真相源脚本**，不是改一行候选 SQL。
