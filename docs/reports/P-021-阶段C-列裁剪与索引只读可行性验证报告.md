## 3. 方向 ④ 索引：前提被证伪

### 3.1 生产索引清单（只读 `pg_indexes`）

| 索引 | 定义要点 |
|---|---|
| `netdisk_files_name_trgm_idx` | `USING gin (name gin_trgm_ops) WHERE (is_dir = false)` |
| `netdisk_files_path_trgm_idx` | `USING gin (path gin_trgm_ops) WHERE (is_dir = false)` |
| `netdisk_files_text_flat_trgm_idx` | `USING gin (text_flat gin_trgm_ops) WHERE (is_dir=false AND text_status='ok' AND text_flat IS NOT NULL)` |
| 其余 7 个 | pkey、`user_dir` / `user_fs` / `user_name` / `user_seen` / `user_text` / `text_flat_todo` 等 |

⇒ 阶段 C §2④ 依据 D-029 的 `EXPLAIN` 推断「只有 `text_flat` 有 trigram 索引」是**抽样视角误判**：当时那条语句只涉及 `text_flat`，不涉 `name/path`，不代表后两者无索引。历史行保留不涂改，本条以只读直查给出更保守的修正。

## 4. 方向 ③ 列裁剪：条件可行，但口径是硬前置

### 4.1 为什么必须验

`netdisk-search.service.ts:830–857`：通道 B 的 SQL 用 `text_flat.ilike.%k%` 粗筛后，把 `text_flat` 大字段拉回 JS，`flatText()` 归一化后用 `String.includes` **复算共现数**（注释明写「避免 PostgREST 的 ilike 与 JS 的 String.includes 口径漂移」）。列裁剪＝不拉大字段、把共现计数下推到 SQL ⇒ 必须证明两侧逐题逐字相等，否则主排序键漂移，触碰 P-008 老根因与 P0 六闸的举证责任倒置。

`flatText()`（`public-library.ts:52`）＝ `normalizeForMatch(s.replace(NUL,''))`，`normalizeForMatch`（`question-match.ts:51`）＝ 只留汉字 / 字母 / 数字。`text_flat` 入库时已是归一化流 ⇒ JS 侧二次归一化是幂等的，漂移只可能来自 SQL 的 `ILIKE` 语义。

### 4.2 只读比对结果（2,000 行样本）

| key | `ILIKE` 命中 | 字面 `strpos` 命中 | **drift** | 判定 |
|---|---:|---:|---:|---|
| `平行四边形` | 206 | 206 | **0** | 纯汉字长锚点，一致 |
| `面积最大值` | 16 | 16 | **0** | 一致 |
| `2026` | 32 | 32 | **0** | 纯数字，一致 |
| `已知 抛物线` | 0 | 0 | **0** | 含空格，两侧一致失败 |
| `ABC` | 1,172 | 1,099 | **73** | `ILIKE` 大小写不敏感 |
| `abc` | 1,172 | 275 | **897** | 同上，差异更大 |
| `a_b` | 1,129 | 0 | **1,129** | `_` 是 LIKE 单字符通配符 ⇒ SQL 假阳性 |
| `A_B` | 1,129 | 0 | **1,129** | 同上 |

**双 key 共现计数下推模拟**（`CASE WHEN … ILIKE` 之和 vs `CASE WHEN strpos>0` 之和）：`cohit_mismatch_rows = 0 / 2000`。

⇒ 在**纯汉字 / 数字长锚点**口径下，SQL 侧共现计数与 JS `flatText` 计数逐题一致，**列裁剪在口径上条件可行**；收益上界仍按阶段 C 的 ≈0.3–0.8 s（传输 / 序列化），**不是收益预测**。

### 4.3 实施前必过的口径条件

1. 🔴 `textClean`（`netdisk-search.service.ts:825`）只剔 `[%,()]`，**未剔 `_`、未统一大小写**。若 `textAnchors` 含英文或 `_`，`ILIKE` 粗筛会放进 JS 侧计数为 0 的行（或反之），共现数漂移。
2. SQL 侧计数必须改用 **`strpos` / 大小写敏感字面匹配**，并与 WHERE 粗筛同口径；直接用 `ILIKE` 下推会固化漂移。
3. 归一化口径必须与 `question-match.ts::normalizeForMatch()` 逐字一致（`flatText` 唯一真相源），不得在 SQL 里另写正则（PG 正则的 `\u4e00-\u9fa5` 与 JS Unicode 范围不等价）。
4. 改 `netdisk-search.service.ts` 查询结构 ⇒ **独立提案 + 前后对照 + M 门同步**（`P-021` §4 阶段 D 明令本提案不预授权）。本轮**不改代码**。

按阶段 C §2③「不相等即放弃」：本轮结论是**条件可行**，不是「可以实施」。
