## 1. 结论先行

**能，而且这套「双轨」架构项目里已经预埋好了，不是要从零新建。**

- **比对层**本来就是纯文字：`shared/question-match.ts` 只读 `question_objects.stem_text`，六道 P0 硬闸、举证责任倒置、`verified` 口径全部不碰图片。
- **展示层**本来就有整题图：`shared/question-reference.ts` 的 `ReferenceExample.figureUrl` 是 **P-017 整题块级快照**（`question_figures`，migration `0028`），生成链路 `netdisk-figure-build.mjs` + `netdisk-figure-crop.py`（docx → PDF → `pypdfium2` 按题区间裁切 → WebP），前端 `answer-editor.tsx` 已渲染并可全屏放大。
- 契约里已经明写边界：`figureUrl` 是「整题块级快照（兜底）」，`inlineFigures` 才是「原位插图」；`netdisk-search.service.ts` 的注释和 `0028` 建表说明都强调**只替换呈现、不替换判定依据**，且「查不到就是没有图，绝不拿相邻题顶替」。

所以思傅这个提法**不需要改判定层、不需要改前后端契约、不需要 bump `CACHE_VERSION` v14** —— 只要给 `.doc` 把整题快照补出来即可。

🔴 但要落地，有 **三个必须先解决的缺口**（§4），以及一条必须说清的边界：**双轨只解决「显对」，不改善「给对」**（§5）。

## 4. 三个必须先解决的缺口

### 缺口 ①  `.doc` 侧整题快照 0 张，且没有现成产图链路

- `netdisk-figure-build.mjs::pendingSources()` 写死 `nf.ext = 'docx'`，并且**下载的是 docx 原件**。
- `.doc` 在 `netdisk_files` 里是老式 OLE 二进制，必须先经 P-019 重转成 docx 才能转 PDF；而 D-032 已确认**重转产物用完即删**，`doc_convert_done` 只留 `text_sha256` 等元数据。
- D-033 新建的 `doc-inline-figure-build.mjs` / `doc-inline-figure-crop.py` 已经有「下载 `.doc` → 独立 LO profile 重转 → F0 同源 → 产图」骨架，但**它产的是内联插图，不是整题 band 快照**。`--apply` 双硬锁仍在。

⇒ 需要在该骨架上新增「整题快照」输出模式（复用 `netdisk-figure-crop.py::locate()` / `band_of()` 的定位与裁切口径），**不改 `netdisk-inline-build.mjs`**，保持 docx 零回归。

### 缺口 ②  定位靠文字锚点，而 `.doc` 文字恰好是残缺的 —— 有「给出整题错图」的风险

`locate()` 的三级策略：

1. `char_start/正文总长` 折算预期页，±3 页里找 `stem[:28→20→14→10]`；
2. 找不到 ⇒ **③ 全篇兜底**：把整本 PDF 文本拼起来 `blob.find(a)`，退化到「全篇任意位置」。

老 `.doc` 题干的字母/公式/坐标是**静默丢失**（不是 `U+FFFD`，对象级仅 174 个），于是：

- 短锚点可能碰巧命中**另一道相似题**；
- 更危险的是第 ③ 重兜底在缺字题上会被频繁触发；
- 结果是**整张题图给错** —— 比 D-034 里「插错一张小图」严重得多，因为这次错的是**整道题**。

⇒ 生产前必须补两道新硬闸（属新增设计，需随路线立项、先补门再动代码）：

- **图文同源复核闸**：裁出的 band 内取 PDF 文本层，与 `stem` 做长锚点共现校验（可复用 `countAnchorHits()` 口径），不达标**丢图**，不得下发；
- **收紧兜底**：`.doc` 来源禁用或收紧「全篇任意位置」，`ANCHOR_MIN` 与页窗按 `.doc` 单独标定，且必须在**独立盲测样本**上验，禁止用 D-034 的 40 条调阈值又用同一批验收（§4 教训）。

### 缺口 ③  覆盖率诚实边界与资源

- 整题快照目前只铺了 **620/3,705 份 docx（16.7%）**；若要把「展示用整题」做成统一形态，docx 剩余 **3,085 份**也要补跑。
- P-017 的运行纪律写在脚本头部：`FIGURE_BATCH` 默认 2、最多 1 worker、`ionice -c3 nice -n19`、`MemAvailable <700MB` 等待、单批 8min 上限 —— 当年 2 worker × batch 8 把 L3 压到 sshd 都 fork 不出来。`.doc` 还多一层重转，**必须先做 PDF 渲染/裁切/产图/写库资源压测**（此项在 D-034 仍锁清单里）。
- `.doc` 42,619 个 stem≥10 字只是 `ANCHOR_MIN` 上界；fail-closed 下必然有大量题「没图」，前端必须明说「原文含图，暂不支持显示」，**不能静默留白**。

## 5. 必须说清的边界：双轨只解决「显对」，不改善「给对」

这一条最容易被方案的光鲜面遮住：

- **比对层用的正是那份残缺的 `stem_text`**。老 `.doc` 题干缺字母/公式 ⇒ 锚点不足 ⇒ 召回不到或召回偏，`exact` 六闸更难通过。
- 把展示换成整题快照，能一次性绕开「缺字、公式丢失、图错位、水印误判、WPS/网盘渲染差异」，解决的是**「显对」**。
- 但**「给对」完全不受益**：判定层一行未动、`0021 review_events` 仍 **0 行**、第二层准入未全绿、P95 仍 3.4s 量级。

按项目既定目标（思傅 11-08 重锚＝「检索到正确解答思路和解答过程」，**不追 exact**；参考例题层本来就是同源配对 + 事先声明 + `verified:false`），这个短板是**已知且已声明**的，不算新引入回归；但**不能把双轨说成「检索变准了」**。

另外三条既有红线继续适用：

- **读得懂 ≠ 题目可解**（D-034：22 条通过里有 3 条「缺图做不了题」）⇒ 整题快照的验收要单独统计「题目是否可解」；
- **错图比没图更糟** ⇒ fail-closed 优先于覆盖率；
- 整题 band 若把**答案/解析区**也裁进去，会与「请先自己想一想」的事先声明、以及「`exact` 才放解析」口径冲突 ⇒ 裁切边界需单独定义并人工抽检。
