## 0. 文档目的与范围

本文档定「错题提取」功能的方向、已落地实现与后续路线。核心澄清：**"提取错题"的本意是切出错题区域并对该区域做 OCR 得到文本，而非整图关联后存储/展示整图。**

- **v1 曾偏离本意**（整图关联），**P0 已纠正**（切块 + 逐块识别 + 落区域文本）。详见 §1.2。
- 所有代码结论基于 `push-ready/` 实际源码核查，`文件:行号` 已标注（行号对应 v3 更新时的代码状态），便于直接定位落地。

## 1. 核心定义

### 1.1 原始意图（权威定义）

> 能够自动从图片/文档中**提取其中的错题**；如果题目和答题卡是不同的图片/文档，能够将两者进行**正确的关联**。

"提取错题" = **切取出错题区域（切块）+ 对该区域进行 OCR 识别得到文本**：

- **提取单位是"区域"，不是"整张图"**：每张错题在库里应体现为"切出的题块图 + 该块 OCR 文本"。
- **题 + 答跨图关联是附属要求**：题目图与答题卡图是不同图片/文档时，按题号把"题面块"与"答案"正确配对。

### 1.2 V1 历史偏差（**已由 P0 纠正**）

v1 主链路（`recognize/index.tsx` → `recognize-pair`）走的是**整图关联 → 保存 → 展示**：每道题存的是**整张**题面图/答案图，未切单题块、未存区域级 OCR 文本。两处根因：

1. `OcrService.recognizePair` 的 `finalize`：每题 `question_image_keys = 整张题目图 keys`；
2. 无 VLM 时对"题+答合并文本"做 `structureLocalItems`，答案页文本会被误切进题目 items。

> ✅ **P0 已纠正**：主链路切换为 `POST /api/image/extract-wrong`，先本地切块、再逐块 OCR，落库的是"题块图 + 区域文本"（见 §2）。`recognize-pair` 已不再是错题提取主链路（代码保留但无调用方）。

### 1.3 目标流程

用户已确认：**转向"切块 → 逐块识别 → 知识点/错因/推荐闭环"**。

```
图片/文档输入（题面图 / 答题卡图 可分开）
  │
  ├─[切块]  wrongq 切块引擎（本地优先：红笔锚定 + 版面分析 + decideLocal）
  │           └─ 无 VLM 即可切出单题块（block + box），VLM 仅可选升级且 fail-open
  │
  ├─[逐块识别]  每块 → 本地 OCR 侧车（PaddleOCR / RapidOCR）→ 区域文本
  │           └─ 仅当本地置信不足 → VLM 升级层（自托管本地 VLM，见 §6）
  │
  ├─[题答跨图关联]  题面块.题号 ↔ 答案图.题号（多题）
  │
  ├─[落库]  POST /api/timeline/batch
  │           └─ question_images = 题面块裁图 / question = 区域 OCR 文本
  │              answer_images  = 答案图 key   / answer  = 匹配的答案文本
  │
  ├─[展示]  detail 按 题面块 / 答案图 分组
  │
  └─[闭环增值 · P1/P2]  知识点聚合 / 错因诊断 / 相似题推荐 / 复习曲线
```

> ⚠️ 目标流程中的**本地层级规则（大题/小题合并）在 P0 未覆盖**，当前每个切块独立成题（`level=1`），列为 P1 遗留（见 §2.7）。

### 2.3 接口契约：`POST /api/image/extract-wrong`

定义位置：`image.controller.ts:117-123`（路由）· `ExtractWrongDto`（`image.types.ts:7`）· `ImageService.extractWrong`（`image.service.ts:565`）

**请求**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `image_url` | `string` | ✅ | 题面图公网 URL（应为**带红笔批改**的图，切块以红笔为锚点） |
| `answer_image_keys` | `string[]` | ❌ | 答案图 storage key；提供则按题号关联答案文本 |

**响应**（`data`）

| 字段 | 类型 | 说明 |
|---|---|---|
| `items` | `RecognizedItem[]` | 每个元素 = 一个切出的错题区域 |
| `unmatched_questions` | `string[]` | 有答案图但未按题号匹配上的题面块（题号，或 `#blockId`） |
| `answer_image_keys` | `string[]` | 原样回传的答案图 key |
| `quality` | `{ sharpness, sharp, hint, sample_size }` | P1⑥ 清晰度门禁结果；`hint` 为提示语（不通过时非空） |
| `block_source` | `'red' \| 'layout' \| 'none'` | P1④ 本次切块依据：红笔锚定 / 纯版面兜底 / 无 |
| `deduped` | `number` | P1⑬ 被批内近重复合并掉的题数 |
| `debug` | `object` | 诊断信息（vlm 策略、块数、层级推断数等） |

**`items[]` 字段语义（切块级）**

| 字段 | 取值 | 说明 |
|---|---|---|
| `question_image_keys` | `[切块裁图 key]` | ⭐ 存的是**切块**，不是整图 |
| `question_content` | 区域 OCR 文本 | ⭐ 该切块区域的 OCR 全文（题干+作答+批改痕迹），不丢信息 |
| `stem` | 印刷题干 | P1①⑦ 经语义分离出的干净印刷题干；未分离时回退为全文 |
| `wrong_answer` | 学生作答文本 | P1①⑦ 分离出的手写/学生作答（无则空串） |
| `solution` | 教师红笔订正文本 | P1①⑦ 分离出的红笔批改/订正（无则空串） |
| `answer_content` | 匹配的答案文本 | 按题号从答案图命中；未命中为空串 |
| `answer_image_keys` | 答案图 key 数组 | P1⑪ 命中题号时挂「对应答案块裁图」，否则整张答案图 key |
| `tags` | `string[]` | P1⑬ 知识点关键词候选（学科词表命中，非分类器结论，用户可改） |
| `error_analysis` | `ErrorAnalysis` | P2⑯ 错因分析结论（本地规则引擎产出；`type`/`label`/`reason`/`suggestion`，可选 `sbert` 分） |
| `status` | `'answered' \| 'pending'` | 命中答案则 answered，否则 pending（提示可联网搜题） |
| `level` / `parent_index` | `1`/`2` · `null`/下标 | P1② 大题=1/顶层，小题=2/指向父题下标 |

## 3. 切块引擎的大模型依赖现状

用户对切块引擎的要求是"**尽量不要依赖大模型**"。核查 `wrongq.ts` 与 `wrongq-vlm.ts` 后确认：**已具备本地优先基础，且 P0 已固化为硬约束**。

### 3.1 抓取事实

`extractWrongQuestions(buf, opts, prebuiltCtx)` 流水线：

```ts
// wrongq.ts:23-37  —— 本地流水线永远先跑
const ctx = buildLayoutContext(buf)        // 版面上下文（三栏 + 栏内行）
const red = detectRedMarks(ctx.flatBuf, …) // 红笔标记
const blocks = buildBlocks(red.marks, ctx) // 题块构建
decideLocal(blocks, red.marks)             // 本地判定（wrong/correct/blank）

// VLM 仅是可选升级层，且仅在显式开启时
if (opts.allowVlm && opts.imageUrl) {
  const r = await vlmQuestionBlocks(opts.imageUrl, blocks.length)
  if (r.used && r.items.length) fuseVlm(blocks, r.items, ctx.w, ctx.h)
}
```

- **本地切块不依赖任何大模型**：红笔锚定 + 版面分析 + `decideLocal` 全本地计算。
- **VLM 仅可选升级**（`wrongq-vlm.ts`）：用于密排难例出粗框，且 `vlmQuestionBlocks` 设计为 **fail-open**——凭证缺失时返回 `used=false`，本地层独立产出，绝不阻塞。
- 本环境 `COZE_API_TOKEN` 未配置，VLM 判定实际 `used=false`。

### 3.2 硬约束（已写入 P0 实现）

> ✅ **"切块引擎尽量不依赖大模型"已成立**：`extractWrong` 调用时硬编码 `allowVlm: false` 且不传 `imageUrl`，VLM 分支**根本不会进入**。逐块 OCR 走本地侧车，与切块同源本地优先。

1. 切块主路径 = 本地（红笔锚定 + 版面 + `decideLocal`），**VLM 默认关闭**。
2. 若后续启用 VLM 升级，模型应指向**自托管本地多模态 VLM**（PaddleOCR-VL / Qwen2.5-VL），不走外部付费 API。
3. 逐块识别主路径 = 本地 OCR 侧车（PaddleOCR / RapidOCR）。

## 4. 主流错题提取方案（2025 调研 · 供对标）

### 4.1 范式迁移：从 OCR 到多模态 VLM

传统 OCR（Tesseract / Textract / PaddleOCR）正被**多模态 VLM 直接出结构化结果**取代——VLM 自动处理旋转、表格、多栏、手写批注。2025.10 开源本地 VLM OCR 集中爆发：PaddleOCR-VL-0.9B、Qwen2.5-VL、DeepSeek-OCR-3B、OlmOCR-2-7B 等，可自托管、隐私合规、成本极低。

| 维度 | 传统 OCR | 多模态 VLM |
|---|---|---|
| 机制 | 字符识别（点线分析） | Transformer 视觉 token 语义理解 |
| 阅读顺序 | 简单自上而下 / 左到右启发式 | 多栏、复杂版面感知 |
| 表格 | 需单独检测模型 | 原生保留表格结构 |
| 手写批注 | 准确率低、需专用模型 | 近人类水平，可提取为独立字段 |
| 输出 | 带框文本块 | 结构化 Markdown / JSON / HTML |
| 成本（1K 页） | $1–5 | $1–20（Gemini Flash 等更省） |

### 4.2 主流错题本 App 的能力闭环

```
拍照/截图 → 图像预处理(去噪CLAHE / 边缘定纸张 / 透视纠偏 / 质量评分)
        → OCR/VLM 结构化 → 单题切分(题号 / 版面区块 / 红笔锚定)
        → 知识点分类(BERT+知识图谱) → 错因分析(规则引擎 + SBERT 语义差异)
        → 相似题/变式题推荐(协同过滤 + 知识图谱 + IRT 难度)
        → 艾宾浩斯复习曲线 → 导出 Word / 打印
```

### 4.3 关键技术指标（行业通行做法）

- **手写 OCR**：CRNN+Attention（中文 92% / 公式 85%，公式经 Mathpix → LaTeX）
- **题目查重**：SimHash + 余弦相似度（查全率 > 95%）
- **知识点标注**：BERT + 教育词库（F1 ≈ 0.88）
- **错因诊断**：规则引擎 + Sentence-BERT 语义差异
- **推荐**：知识图谱路径推理 + 协同过滤 + IRT 难度自适应
- **混合解析路由**：按置信度把"简单数字文档"走快 OCR、"扫描/拍照/手写"走 VLM（与本项目 `vlmPolicy()` 思路一致）

### 4.4 与本项目对照（P0 落地后的位置）

主流闭环为："拍照 → 预处理 → **OCR/VLM 结构化 → 单题切分** → 知识点/错因/推荐 → 复习 → 导出"。

本项目当前已落地到 **"单题切分 + 本地 OCR 结构化 + 落库"**（P0）；缺失的是最前面的**预处理**、中间的**语义分离（错答/批改）**与后半程的**增值闭环**（P1/P2）。

## 6. 关键设计张力与调和：VLM 依赖 vs "本地优先"

### 6.1 问题

部分建议提到"让 VLM 真正看图"，而用户原则要求"**本地优先、尽量不依赖大模型**"。是否冲突？

**字面读有冲突**：本地 OCR 侧车只输出文本，无法"看图"。但二者正交——混淆的是"VLM 做什么"与"VLM 何时用 / 在哪跑"。

### 6.2 调和方案（三层约束）

1. **VLM 是"升级层"不是"默认层"**：默认热路径 = wrongq 切块（本地）+ 本地 OCR 侧车 + 本地层级规则（零 VLM）。仅本地置信不足才升级。
2. **被升级调用的 VLM 应是自托管本地多模态模型**：PaddleOCR-VL / Qwen2.5-VL，替代外部 Coze API，**外部依赖为 0**。
3. **修正分支语义**：默认升级路径走 `vlmDirectImages`（真看图），可指向自托管端点；"只喂文本"作为低成本通道保留。

### 6.3 推荐路由（结合现有 `vlmPolicy()`）

```
输入: 题面图 + 答题卡图
  │
  ├─[默认·本地] wrongq 切块(allowVlm=false) → 本地 OCR 侧车 → 逐块文本 + 题号关联
  │         └─ 置信度达标? ── 是 ──▶ 返回 items（零 VLM）  ← P0 已落地到此
  │
  └─[升级·可选] 本地置信度不足?
            └─ 是 ──▶ 自托管本地多模态 VLM (PaddleOCR-VL / Qwen2.5-VL)
                      └─ 返回 items + unmatched_questions      ← P1（#14）

开关: OCR_VLM_MODE=auto(默认)/never/always · OCR_USE_VLM · OCR_LOCAL_MIN_AVG_LEN
```

> 修正后的核心表述：**切块与逐块识别一律本地优先（零大模型）；VLM 仅作为"本地置信不足时的可选升级"，且被调模型为自托管本地多模态 VLM。与"尽量不依赖大模型"无任何冲突。**

| `supabase-db.provider.ts` | `SupabaseDbProvider`：包装现有 `getSupabaseClient()`，insert/update/remove 走 builder，`raw()` 暴露原生客户端兜底 |
| `tencent-pg.provider.ts` | `TencentPgDbProvider`：用 `pg` 连腾讯云 PostgreSQL，参数化 SQL（标识符 `quote()` 防注入），未配置 `TENCENT_PG_URL` 时 `health()=false` 且写操作安全跳过 |
| `db-provider.factory.ts` | `getDbProvider()`（主库）/ `getSecondaryProvider()`（次库）+ `DB_PROVIDER` 模式解析 |
| `dual-write.ts` | `isDualWriteEnabled()` + `mirrorInsert/mirrorUpdate/mirrorDelete`：双写镜像，**best-effort 不抛错**（主库权威） |
| `pg-shim.d.ts` | 本地最小 `pg` 类型声明（项目未装 `@types/pg`，避免联网装依赖） |

### 7.6.3 模式切换

环境变量 `DB_PROVIDER`：

| 值 | 行为 |
|---|---|
| `supabase`（默认） | 主库 = Supabase，现有 28 处 `getSupabaseClient()` 调用零改动、零回归 |
| `tencent-pg` | 主库 = 腾讯云 PG（**为未来整切预留**；需逐步把调用点改走 `getDbProvider()`，属迁移窗口内的增量工作） |
| `dual` | 主库 = Supabase，且开启**双写**，把写操作镜像到腾讯云 PG（迁移期用） |

次库连接：`TENCENT_PG_URL`（腾讯云 PG 实例地址）、`TENCENT_PG_SSL`（默认 true）、`TENCENT_PG_POOL_MAX`（默认 5）。

### 7.6.4 已接入的代表写路径

`timeline.service.ts`：
- `create` / `createBatch`：主库 insert 成功后 `await mirrorInsert(TABLE, payload)`；
- `update`：主库 update 命中后 `await mirrorUpdate(TABLE, payload, { user_id, id })`。

模式为 supabase 时这些调用**直接 return、零开销**；模式为 dual 且次库不可用/报错时仅告警、绝不阻断主库——保证迁移零风险。其余 27 处写路径按相同一行模式在迁移窗口内增量接入即可。

### 7.6.5 验证（纯函数，12/12 通过）

环境无 DB（沙箱缺 Coze 凭据与腾讯云实例），沿用编译产物独立验证法：
- 模式解析：`supabase`/`tencent-pg`/`dual` 透传、非法值回退 supabase；
- `isDualWriteEnabled` 仅 dual 为真；
- `TencentPgDbProvider` 无 `TENCENT_PG_URL` 时 `health()=false`、`getSecondaryProvider()=null`（不连网、不拖主库）；
- 双写扇出：dual 下 `mirrorInsert/mirrorUpdate` 正确调用注入的次库且参数/where 正确；supabase 下不调次库；
- 次库抛错被吞掉（主库权威）。

### 7.6.6 迁移期执行要点（配合对话中的四步法）

1. **双写**：`DB_PROVIDER=dual`，按 §7.6.4 把全部写路径接镜像；
2. **灰度**：先 5% 用户走新链路（入口层按 userId 分流）；
3. **对账**：`pg_dump` 主库 + 新库按 openid 比记录数/关键字段，确认无丢无错；
4. **回滚窗口**：稳定后旧库只读保留 30 天再下线，AppID 全程不变（openid 稳定 → 用户无感知）。
5. 图片裁图按 `cropKey` 原样拷贝 COS↔OSS，DB 引用全部继续有效。

### 8.2 接口烟测

```bash
# 需先拿到题面图公网 URL 与答案图 key
curl -X POST http://<host>/api/image/extract-wrong \
  -H 'Content-Type: application/json' \
  -H 'X-User-Id: <uid>' \
  -d '{"image_url":"<题目图URL>","answer_image_keys":["<答案图key>"]}'
```

关注点：
- `items[].question_image_keys` 应为**单个切块 key**（长度 1），而非整图；
- `items[].question_content` 为该区域 OCR 文本，非空；
- 提供了答案图时，`answer_content` 命中的项应填入答案文本，未命中进入 `unmatched_questions`。

### 8.3 端到端手测路径

首页 → **错题提取** → 分别选「题目图」（须带红笔批改）与「答案图」→ **识别并关联**：

1. 应切出多道题（每道题对应图上被标记的一块），而非只有 1 题；
2. 若存在未匹配到答案的题，顶部应出现「N 道题目未匹配到答案」横幅；
3. 「保存到最近题目」后进入详情页：
   - **「题面图」区显示的应是切出的小块图**（每题各不同），不是同一张整图 —— 这是 P0 纠正是否生效的**最直观判据**；
   - 「答题卡图」区显示答案图；
   - 「正确答案」框应已填入按题号匹配的答案文本。

> 若详情页仍显示同一张整图，说明走的是旧链路（可能为前端未加载最新包 / 后端未部署新接口）。

### 8.4 回归注意

- 题面图若无红笔批改痕迹，`wrongq` 切不出块（局限 ④），属预期行为，需先补前置项。

## 9. 去手写 · 印刷保护：当前方案与备用方案（印盾外科）

> 本章节记录去手写（擦除手写、保留印刷）的**当前生产方案**与**备用方案**。
> 备用方案（代号"印盾外科"）当前为孤立实验件，**仅作文档化留存**；只有当当前方案在生产实测中效果不达标时，才按 §9.4 启动对照实测，不预先接入。

### 9.1 当前生产方案（已落地，v21.5 · 疑罪从无）

- **入口**：`image.service.eraseV2 → erase-mask-policy.buildEraseMask`（`server/src/image/erase-mask-policy.ts`）。
- **核心原则**：词级判别器给每个词打三态（`0=印刷 / 1=手写 / 2=疑虑`），**只有 `state===1`（确信手写）进最终 mask**，`0/2` 一律丢弃——"疑罪从无"。
- **两种策略**（`ErasePolicy`）：
  - `word`（默认）：最终 mask = 词通道确信手写。框外损伤最低。
  - `union_generic`（备选）：hybrid 经 `protectPrintGeneric`（颜色无关印刷保护）后 ∪ 词通道确信手写。召回更高。
- **印刷保护机制**：`handwriting-mask.protectPrintGeneric`——连通域 + 域内印刷像素占比 ≥ 0.6 判定为印刷字，则清零该域擦除像素。**不依赖 OCR 侧车、自包含，更稳健**。
- **端到端实测**（4 卷 / 44 手写框 / 16 插图框）：

  | 策略 | 擦净手写 | 插图受损 | 框外改动 |
  |---|---|---|---|
  | `word`（默认） | 34/44（77%） | 6/16 | 90,881 px |
  | `union_generic` | 37/44（84%） | 7/16 | 95,783 px |

### 9.2 备用方案：印盾外科（OCR 框先验保护盾 + surgical 模式）

- **出处**：`server/src/image/ocr-prior.ts`（文件头自陈"去手写集成实验"）。
- **思想**：用 OCR 检测到的文字框在**区域级**标出"哪里有字"，把"像素级手写 vs 印刷无法区分"的死结（代码注释称 T7）转成区域级约束，从而外科手术式地只擦手写、护印刷。
- **三件套**：
  - `buildOcrShieldMask`（**印盾** = 印刷体保护盾）：把文字框设为禁擦区（shield=255 → 擦除 mask 在该区置 0），机制上杜绝擦到印刷/文字。
  - `buildOcrPriorMask`（**先验**）：把"框内深墨"作为去手写候选，收敛判别器候选集。
  - `loadOcrBoxes`（**框来源**）：优先读 `OCR_BOXES_JSON`，否则调侧车 `/recognize` 拿框。
- **两种形态**：
  - `surgical=false`（默认）：整框 + dilate 禁擦（最强保证）。
  - `surgical=true`（**外科**）：仅"框内深墨"禁擦（ROI ∩ 深墨），空背景不被无谓保护，更精准。
  - `printOnly=true`：只护**高置信印刷框**（`score ≥ OCR_PRINT_MIN_SCORE=0.95`），疑似手写框不护、照常擦——压低整框盾牺牲的手写擦除率。阈值的依据：纯印刷框 score 中位 0.983、手写框中位 0.725；0.95 的误护手写率仅 3.7%（0.90 为 18.5%）。
- **唯一合理的生效组合**：`buildOcrShieldMask({ printOnly: true, surgical: true })`——既护印刷又不误护框内手写。
- **当前状态（重要）**：`buildOcrShieldMask / buildOcrPriorMask / loadOcrBoxes / OCR_PRINT_MIN_SCORE` 在 `ocr-prior.ts` **之外零调用方**（仅 `server/run-single-erase.ts` 手动脚本与 `dist` 编译产物引用），**未接入 `eraseV2` 生产链路 → 运行效果为零**。它是孤立实验件，生产实际跑的是 §9.1 的 `protectPrintGeneric`。
- **与当前方案的优劣对照**：

  | 维度 | 当前方案（protectPrintGeneric） | 备用（印盾外科） |
  |---|---|---|
  | 机制 | 连通域 + 印刷像素占比 | OCR 框区域先验 + 深墨交集 |
  | 侧车依赖 | 无（自包含） | 强（框来自侧车/JSON） |
  | 稳健性 | 高 | 侧车挂则失效（降级走原链路） |
  | 思路优雅度 | 中 | 高（化解 T7 区域级约束） |
  | 实证指标 | 有（4 卷 44 框实测） | 无（仅 score 阈值有实测支撑） |

### 9.3 触发条件（何时启用备用方案）

当 §9.1 当前方案在生产实测中**任一**出现时，启动 §9.4 对照实测：
- 印刷 / 插图损伤率超阈值（如插图受损持续 > 7/16，或用户集中反馈"擦到字"）；
- 手写擦净率不足（如 `word` 策略下 < 70%，且 `union_generic` 仍不达预期）；
- VLM / 侧车降级场景下擦除质量断崖，需要区域先验兜底。

### 9.4 对照实测方案（A/B，暂不执行）

> 仅当 §9.3 触发时执行；当前仅作文档留存。

1. **接入方式**：在 `buildEraseMask` 中将 `buildOcrShieldMask({ printOnly: true, surgical: true })` 作为**额外 AND 保护层**（与 `protectPrintGeneric` 叠加，而非替换），输出取交集。
2. **对照对象**：`union_generic`（当前最强策略）作为基线 A；A + 印盾外科作为实验组 B。
3. **对照指标**：擦净手写率、插图/印刷受损数、框外改动像素、VLM/侧车降级时表现。
4. **数据集**：沿用 4 卷 / 44 手写框 / 16 插图框 基准，并额外记录侧车不可用时的降级路径。
5. **晋级判定**：若 B 在"损伤不升、擦净不降"前提下任一指标显著改善（尤其插图受损下降），则印盾外科由实验态晋级为主路径之一；否则保持备用、不并入生产。
