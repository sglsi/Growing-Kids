# 问题 2（裁剪范围误差 + 四边选不中）修复说明 — 逐个击破 · 第 2/5 个

## 6 步流程回顾
1. **归类领域**：微信小程序 `Canvas 2D` 裁剪编辑器（坐标映射 / 分辨率）。
2. **查标准范式**：`canvasToTempFilePath` 的 `x/y/width/destWidth` 单位为**缓冲像素**；成熟方案（we-cropper）全程保持**单一确定单位**。
3. **确认 API 边界**：`Canvas 2D` 缓冲有**硬上限**（iOS 4096、安卓设备相关，超限即报 `set width out of range 11000>8192`）；该接口坐标在微信 8.0.26/8.0.27 等版本对 dpr 解释不一致。
4. **看成熟项目做法**：we-cropper 把图片坐标与裁剪框坐标**同比**映射到同一画布坐标系，杜绝两套单位漂移。
5. **结合本项目取舍**：本项目导出画布是离屏的（只用于生成图片），dpr 对清晰度毫无增益，却会撑爆缓冲上限并引入跨版本歧义 → **直接弃用 dpr**。
6. **落地验证**：类型检查 + 真实 H5 构建 + 动态测试 41/41（含零偏移、缓冲≤4096 用例）。

## 根因（真机"框选≠导出"的真正来源）
- 旧代码 `node.width = naturalW * dpr`：一张 4000px 原图 × dpr 3 = **12000px 缓冲 → 撞上限 → 报 `11000>8192`**（这同时是问题 4 的成因）。
- `canvasToTempFilePath` 的 `x/y/width` 旧代码乘了 dpr；该接口在不同微信版本对 dpr 的解释不一致，**裁剪坐标随之漂移**，表现为"框选范围 ≠ 导出范围"。

## 改动（仅 `demo/src/components/image-editor.tsx`）
- `exportEdited`：导出缓冲改为 **原图逻辑尺寸 × fit**（`fit = min(1, 4096/maxSide)`），**不再乘 dpr**；输出分辨率 = 原图裁剪分辨率（手机原图已 3000–4000px，足够高清）。
- 抽出纯函数 `cropToBufferRect(r, canvasW, canvasH)`：归一化裁剪框 → 缓冲像素，**预览框与导出共用同一组归一化坐标 → 零偏移**。
- 旋转烘焙：同样走 `cropToBufferRect`，90°/270° 宽高互换、整图铺满无裁边。
- 四边选不中：触摸层加 `id="cropTouchLayer"`，每次触摸前测**触摸层自身**坐标（含 -24 外扩），用其坐标系算点，消除父级 inset / 布局漂移；`HANDLE_HIT=32` 命中半径保留。
