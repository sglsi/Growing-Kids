# 问题 4 / 问题 5 修复说明

> 承接"逐个击破"节奏：本轮处理 **问题 4（首页"使用此图"报 `set width out of range 11000>8192`）** 与 **问题 5（多次操作后裁剪不可用，报"操作失败，请重试"）**。
> 二者根因同源——都在首页编辑器的 **导出 Canvas** 这条链路上，故合并为一轮。
> 严格遵循 6 步流程：归类领域 → 查标准范式 → 确认 API 能力边界 → 看成熟项目做法 → 结合本项目取舍 → 落地验证。

---

## 问题 4：导出缓冲超上限

### 1 归类
图像处理 / 平台 API 约束类问题（微信 Canvas 2D 缓冲硬上限），不是业务逻辑错。

### 2 查标准范式 + 3 确认 API 边界
微信官方文档明确：**Canvas 2D 的画布缓冲有硬上限**（iOS 约 4096，安卓设备相关），超出即报
`set width out of range 11000>8192`。
旧代码 `node.width = 原图宽 × dpr`：一张 4000px 原图 × dpr 3 = **12000px 缓冲 → 直接撞上限**。

### 4 看成熟项目做法
成熟裁剪库（we-cropper 等）导出时**不做无谓的超采样**：手机原图（3000~4000px）本身已足够高清，再乘 dpr 只是徒增溢出风险。

### 5 结合本项目取舍
**导出缓冲 = 原图逻辑尺寸，不乘 dpr；并以 `MAX_CANVAS_SIDE=4096` 封顶。**
输出分辨率 = 原图裁剪分辨率（≥ 屏幕显示所需），既高清又永不超限。

### 6 落地
`image-editor.tsx`：
- 新增模块级常量 `MAX_CANVAS_SIDE = 4096`；
- `drawAndExport` 内 `fit = min(1, 4096 / max(naturalW, naturalH))`，缓冲 `bufW/bufH = 原图 × fit`；
- 离屏 `<Canvas>` 的 CSS 尺寸同样 `min(naturalW, 4096)` 封顶。

## 问题 5：多次操作后裁剪不可用

### 1 归类
资源生命周期 / 平台对象管理类问题（微信离屏 Canvas 节点的引用失效），**不是裁剪算法错**。

### 2 查标准范式 + 3 确认 API 边界
微信 `type="2d"` 的 Canvas 节点是**有生命周期的对象**，通过 `createSelectorQuery().fields({node:true})` 获取；
它不是稳定单例，跨多次操作复用存在**引用被回收 / 脱离视图（detached）** 的风险。

### 4 看成熟项目做法
成熟做法：**要用时重新 `select` 查询当前活跃节点**，而不是启动时拿一个存着用到底。

### 5 结合本项目取舍
旧 `getCanvasNode()` 把节点**永久缓存**在 `canvasNodeRef.current`——首次拿到就再不重查。
多次操作（裁剪→AI→再裁剪→旋转）后旧节点失效 → 所有 `canvasToTempFilePath({canvas:旧节点})` 永久失败
→ 被 catch 吞成笼统的"操作失败，请重试"，用户表现为"用几次之后裁剪就用不了"。

修复：
1. `exportEdited` **每次导出前 `canvasNodeRef.current = null`**，重新查询当前活跃节点；
2. 抽出 `drawAndExport(node, rot, fullFrame)` 负责绘制+导出，外层 `exportEdited` 负责"取节点 + 失败重试"；
3. **首轮失败清缓存重试一次**，覆盖瞬时失效。

### 6 落地
`image-editor.tsx`：`exportEdited` 重写为上面的"重查 + 重试"结构；新增 `drawAndExport`。
