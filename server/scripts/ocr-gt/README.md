# OCR 识别质量 GT 数据集（小型）

一句话：**给「识别得准不准」一个可复现的判据**，而不是靠"看着还行"。

```
server/scripts/ocr-gt/
├── cases.json      案例定义（源真相：渲染参数 + 期望文本 + 阈值）
├── cases/          生成的图 + 可选的真实照片（同名 .txt 为真值）
├── gen.mjs         由 cases.json 确定性生成 PNG
├── run.mjs         跑真后端 + 真引擎，算 CER / 行命中 / 数字召回
├── lib/metrics.mjs 指标实现（零依赖）
├── baseline.json   基线（当前引擎的真实水平）
└── report.md       最近一次评测报告（自动生成）
```

## 怎么跑

```bash
cd server
node scripts/ocr-gt/gen.mjs              # 首次/改了 cases.json 后：生成图
node scripts/ocr-gt/run.mjs              # 评测（fast 模式，约 1 分钟）
node scripts/ocr-gt/run.mjs --mode precise
node scripts/ocr-gt/run.mjs --update-baseline   # 确认当前水平后更新基线
node scripts/ocr-gt/run.mjs --case arith-clean
```

前置：后端在跑（`node dist/main -p 3001`）、OCR 侧车可用
（`curl http://127.0.0.1:3001/api/image/ocr-diagnose` 返回 `sidecar.disabled=false`）。

退出码：**0** 达标　**1** 不达标或相对基线退步　**2** 环境跑不起来（后端/侧车缺席）。
2 与 1 分开，是为了不把"环境没起来"误读成"质量变差"——那会让人去改本来没坏的代码。

## 为什么图是"生成"的

真实照片更接近生产，但**不可复现**：换角度、换光线，CER 就变了，于是"这轮涨了"
到底是代码退步还是照片不一样，永远说不清。

合成图把变量摁死：图与期望文本同出 `cases.json` 一份文件，任何指标变化都只能
归因到识别链路本身。这是回归测试要的性质。

## 三层数据

| 层 | 来源 | 作用 | 容差 |
|---|---|---|---|
| `clean` | 合成，清晰印刷体 | 基准能力：数字、中文、英文、括号、分数 | 严（CER ≤ 8%~12%） |
| `degraded` | 由 clean 旋转 3° / 模糊 + 压对比度 | 拍照链路（摆正、去噪）是否有效 | 宽（CER ≤ 18%） |
| `real` | 你自己的照片 | 真实分布 | 最宽，且**主要看与自己基线的对比** |

**加真实照片不需要改代码**：把图丢进 `cases/`，同目录放同名 `.txt`（真值按行写），
`run.mjs` 自动收录（例：`cases/homework-01.jpg` + `cases/homework-01.txt`）。

## 指标

| 指标 | 定义 | 为什么需要 |
|---|---|---|
| **CER** | 字符编辑距离 ÷ 参考长度 | 整体抄得准不准 |
| **行命中率** | 参考文本每行在结果里能否找到（最佳窗口 CER ≤ 0.25） | **整行丢失**比个别字错严重得多——丢的往往是答案行 |
| **数字召回** | 参考里的数字串有多少原样出现 | 教辅里数错了等于全错 |

归一化只做**无损**变换（去空白、全角转半角、常见中文标点归一）。
刻意**不**把 `×/x`、`O/0`、`l/1` 当同一个字——那恰恰是要测的错误。

## 这套 GT 第一次跑就抓到的问题

1. **阅读序缺陷（已修）**：`A. 0.6  B. 2/3  C. 0.58  D. 3/5` 识别成 `B → A → C → D`。
   根因是行级排序用 `y0 升序 → x0 升序`，而同一视觉行各框的 `y0` 有 1~2px 抖动，
   B 的上沿恰好高 1px 就排到了 A 前面。选项顺序一乱，**答案就对错位**。
   改为"按行中心聚视觉行、行内按 x"（`ocr-segment.ts` `sortLinesByReadingOrder`），
   CER 25.7% → 2.9%，行命中 50% → 100%。
2. **竖式结构丢失（未修，登记 `R-算法-07`）**：独立成行的 `+` 与横线 `-----` 在
   fast 与 precise 两个引擎里都被丢掉，`3 7 / + 1 5 / ----- / 5 2` 退化成 `37 / 15 / 52`。
   数字没识别错，但"谁加谁、横线在哪"全没了——对打印出来的竖式题，这等于题干失真。
   `cases.json` 里标了 `knownIssue`，报告里显形但不判失败；修好后会显示
   「已不再复现（请移除 knownIssue）」。

> 这两条正好说明 GT 的价值：它们都不是"崩了"，接口一直 200、肉眼扫一眼也不刺眼，
> 只有拿真值去比对才看得出来。
